## Return

As your **last action** after final-tree verification — after the tip-landed gate, on both scratch arms — assemble one compact JSON object carrying exactly the fields below and write it with the **Write** tool to `<run-scratch>/finalization-handoff-$ISSUE_NUMBER.json`. When a file already exists at that path (a re-dispatch), Read it first so the Write tool's overwrite guard permits the write. Leaving it unwritten, or writing it before the clean-tree backstop, fails the parent's validation or the `NOT_IGNORED` clean-tree gate. Include every actionable warning, unresolved obligation and required coverage disposition once, with its workpad/artifact reference; no transcript, tool-output dump, child report, procedure text or reasoning history. Check it once with the parent's reader — `.prflow/vendor/prflow/scripts/validate-review-fix-handoff.py --schema finalization --handoff-file <path> --checkout-root <REPO_ROOT> --dispatch-id <DISPATCH_ID> --issue-number <ISSUE_NUMBER>`, on not-found/rc-127 the same flags on `SKILL_DIR/../../scripts/validate-review-fix-handoff.py`. Exit 0 is a pass. On exit 2 or 3, correct what it names (a `usage:` error means fix your command, not the handoff), rewrite, and re-run once; any other result, including a refused reader (no output and no exit status), leaves the check to the parent. Then make your whole hand-back — your final message and any runner-provided hand-back tool message alike — exactly the three-line envelope `outcome`, `handoff_path`, `dispatch_id`, with nothing added.

Fields (a JSON bool is rejected where an int is required):

- Identity, non-null on **every** outcome: `schema_version` `1`; `issue_number`, `pr_number` ints; `dispatch_id`, `repo_root` (realpath must equal the checkout root), `pr_url`, `run_id`, `run_attempt`, `entry_head`, `workpad_id` strings.
- Routing: `outcome` one of `proceed`/`blocked`/`needs-recovery`/`needs-repair`/`error`; `reason` a non-empty string on every non-`proceed` outcome; `warnings`, `unresolved_obligations` arrays or `null`; `extension` `null` or an object closed to `parent_state`/`worker_state` (each `observed-content`/`observed-empty`/`unestablished` or `null`), `parent_digest`/`worker_digest` (each the loader's `sha256=<64 hex> bytes=<int>` string or `null`), `trusted_root` (string or `null`) and `pending_notes` (array of strings or `null`); `worker_state: observed-content` requires a non-null `worker_digest`. There is no `question` field.
- Evidence, non-null on `proceed`, else nullable: `branch` string; `final_head` 40-char lowercase-hex sha; `checkpoint4`, `review_coverage` (exactly `{"waived_by": "<REVIEW_WAIVER_SOURCE>"}` when that operand is dispatched), `tip_landed` objects; `verification` object with a 40-hex `candidate_sha` (both also non-null on `needs-repair`); `steps` object carrying `§4.0`, `§4.0.5`, `§4.0.6`, `§4.1`, `§4.2`, `§4.3`, each with a non-empty string `disposition`.

Use `outcome: proceed` only after all owned steps have their established dispositions and the final gates permit continuation. A missing observation is null on a stop record, never a guessed value; the identity fields are dispatch literals you echo, never null. Distinguish `proceed`, `blocked`, `needs-recovery`, `needs-repair` and `error`. Your result does not claim the PR was published or the implementation run completed.
