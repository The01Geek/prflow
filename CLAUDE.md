# PRFlow — project memory

PRFlow is a single [Claude Code](https://code.claude.com) plugin published at the repo root; the repo is also its own marketplace. It turns a GitHub issue into a reviewed, documented, merged PR, and a weekly retrospective loop improves the automation. Full system reference: [`docs/internal/DEVFLOW_SYSTEM_OVERVIEW.md`](docs/internal/DEVFLOW_SYSTEM_OVERVIEW.md). Internal-docs entry map: [`docs/internal/index.md`](docs/internal/index.md) — start there to find the page that owns a topic. Contributor guide: [`CONTRIBUTING.md`](CONTRIBUTING.md).

## Commands

```bash
bash lib/preflight.sh      # verify git/gh/jq/python3.11+ on PATH (PyYAML is advisory here — reported but not gated; the suite below still requires it)
bash lib/test/run.sh       # full suite, serially: jq filters + shell helpers + python; gh-stubbed, no network/auth
lib/test/run-parallel.sh   # the same suite, CI's tested shard partition run concurrently in this checkout (issue #1086); the cloud implement tier's gate, the local tier's diagnostic instrument
git ls-files '*.sh' | grep -v '^lib/test/' | xargs -r shellcheck --severity=warning -e SC1091
shellcheck --severity=warning -e SC1091 --extended-analysis=false lib/test/run.sh
git ls-files '*.py' | xargs -r ruff check
```

**The `lib/test/run.sh` lint needs ShellCheck ≥ 0.10.0 and the `--extended-analysis=false` flag — both, or the dataflow pass OOMs on a file this size (issue #745).** The flag (and the equivalent `# shellcheck extended-analysis=false` directive) landed in **0.10.0**, so on the 0.9.x that `ubuntu-latest`/Ubuntu 24.04 ships the flag errors and the directive is silently ignored (SC1107) — which is why CI installs a pinned ≥ 0.10.0 binary rather than using the runner image's, and why you check `shellcheck --version` at the desk before concluding the lint is broken. The remaining `lib/test/**/*.sh` files are linted by the explicit list in `.github/workflows/ci.yml`, and `lib/test/lint-carveout-guard.py` (driven from `lib/test/run.sh`) turns the suite RED if a tracked `lib/test` script is neither in that CI-linted set nor under `lib/test/fixtures/`.

CI (`.github/workflows/ci.yml`) runs the same suite + lint on every PR. The **required** status check is the job name **`lib + python tests`** (not "CI", which is the workflow name and never resolves). CI checks out full history (`fetch-depth: 0`) so `origin/main` resolves and the `#434` stale-prose self-scan runs live there rather than self-skipping (issue #456).

**The suite reports three tallies — passed, failed, and *skipped* — and `0 failed` does NOT mean "everything ran" (issue #456).** A check can **self-skip**: it neither passed nor failed, because the host could not run it or express its condition. A run with skips reads `N passed, M failed, K skipped` followed by one line per skipped check (name, kind, reason), and the exit code is unchanged (`[ "$FAIL" -eq 0 ]` — a skip never fails the suite). Each skip carries a **kind** — `blocking-gate` (a real gate that should have run here but could not — the `#434` self-scan arms) and `host-capability` (the host cannot express the condition — `#423 T6b`). Every self-skip routes through the single `skip <name> <kind> <reason>` helper in `lib/test/run.sh`, whose `printf '  NOTE ` emit is the only sanctioned one; a meta-assertion turns the suite RED for such an emit outside that helper. **A skipped check is never a clean pass:** when reading a suite run as verification (issue #405), a non-empty skip population must be surfaced, not laundered into `result: pass` — `/devflow:review-and-fix` records skips in `verification_evidence.skipped_checks` (distinct from `result: skipped`, which means the whole suite run was skipped) and a run whose `skipped_checks` is non-empty is not reported as a clean pass.

**Which signal discharges a whole-suite completion gate — the tier decides, and the two tiers differ for a mechanical reason (issue #1607).** The commands above are the *local* form. Work the tiers in order:

1. **Local/interactive tier — in THIS repository any local run's whole-suite completion gate is a CI reading for the commit it pushed, not an in-environment suite pass (issue #1607).** Do not launch the full suite locally to discharge a gate; run a focused module to iterate, then push and read CI. A local run can push, wait and resume while a headless cloud run cannot, which is the mechanical reason the two rungs differ; the derivation — non-reproducibility under this repository's worktree concurrency, disagreement with the merge-gating signal in both directions, runtime, and the measured Actions concurrency cap — is in [`docs/internal/claude-md-tiered-suite-rationale.md`](docs/internal/claude-md-tiered-suite-rationale.md).

   - **Scope — three boundaries, each load-bearing.** It is a PRFlow-repository policy, so it is never carried into a `skills/**` or `agents/**` body, which ship verbatim and rightly keep telling a consumer to run *their* suite with CI as a denial-only fallback. It binds **every** local run's completion gate — implement, maintenance and ad-hoc work alike — except the standalone fix loop and reception passes, which stay governed by `.prflow/prompt-extensions/{review-and-fix,receiving-code-review}.md`, which still forbid a loop to cite CI for its own progress. And where a rule elsewhere is anchored to "the completion-gate whole-suite pass" — the `--with-floors` artifact-regeneration row among them — that anchor resolves **here** to the commit you are about to push and read CI for.
   - **The procedure: check the tree clean, commit, push, then read CI for the head this run leaves.** Only the **last** pushed head's reading binds, because a later push cancels the in-flight run for an earlier one.
   - **Establish that a run exists for the pushed SHA before reading any result, with `gh run list --commit <full-40-char-sha>`.** A push here has produced *no run at all*, and an absent run is not a pass; never abbreviate the SHA, since `gh run list` matches nothing and still exits 0 when handed an abbreviated one.
   - **Read the verdict with `gh pr checks <pr>` and find each required check — `lib + python tests` and `lint (shellcheck + actionlint + ruff)`, the `# prflow:required-check`-marked `ci.yml` jobs the completion-evidence record must cover (issue #1898) — in the rollup by name, not `--required`,** which here prints `no required checks reported on the '<branch>' branch` and exits **1**, an empty read whose non-zero status is easily misread as a failing check. Requiring those names is also what stops a head carrying green `DevFlow` runs while `ci.yml` never ran from reading as a pass. (`lib + python tests` alone remains the GitHub branch-protection required status check that gates the human merge; the completion-evidence set is the broader `# prflow:required-check` set the local-tier gate below reads.)
   - **`gh pr checks` has no commit selector and always reads the PR's *current* head, so confirm `gh pr view <pr> --json headRefOid` still equals the SHA you pushed, before *and* after the reading.** A push by anyone else in between silently moves what you are reading, and if it moved the reading does not bind — re-establish against the new head.
   - **Where no PR is open yet, `gh pr checks` has nothing to address** — open the draft PR first, or read the run's own conclusion for the SHA. Expect to wait several minutes, since the state immediately after a push is normally `queued` or `in_progress`.
   - **The pass condition is that every `# prflow:required-check` job (`lib + python tests` and `lint (shellcheck + actionlint + ruff)`) is itself present and passing** — issue #1898 made the completion-evidence record cover the whole required-check set, so a green `lib + python tests` beside a red or absent `lint` is not a pass. While the run is queued its checks have not registered, so `gh pr checks` lists only unrelated checks (a `skipping` Mintlify row) and reads as nothing-failed; a required check that is absent, `skipped`, `neutral` or `cancelled`, an unavailable query, a head with no run, and a run still in progress are each **unestablished**, never a pass — a run that cannot establish a CI result for its own pushed commit must not report completion.
   - **A run maintaining a workpad records this CI reading as completion evidence through `workpad.py update <issue> --record-completion-evidence-ci <head-sha> <tier> <run-url> --completion-ci-check <name> <conclusion> …` (issue #1611; the tier operand and check set landed in #1898), and `workpad.py`'s `_terminal_complete_gate` accepts that CI-derived marker family — distinct from the in-env verification-flight family — on that basis.** The record is validated offline (no network, no `gh`): its `<tier>` must be `local` (a `cloud` tier is refused — a cloud run owes an in-environment result), the recorded SHA must be a full 40-lowercase-hex head equal to `git rev-parse HEAD` over a clean tree, its `--completion-ci-check` pairs must cover the required-check set declared in `.github/workflows/ci.yml`, and every recorded conclusion must be a success. So a run that established a green required check for the commit it pushed writes `--status Complete` without either running a suite the tier ladder does not gate on or misdescribing what it verified, while a run that established no CI result records nothing and is refused exactly as before. Exactly one completion-evidence marker (counted across both families together) is required — a run recording the CI marker must not also record a verification-flight marker. The full mechanism is disclosed in [`docs/internal/implement-skill.md`](docs/internal/implement-skill.md).
   - **Batch into one consolidated push per iteration.** Verifying by push spends Actions capacity against an account-wide concurrency cap, each push costs several runs, and concurrent runs hold their slots for their whole duration.
   - **This changes only what discharges the whole-suite *gate*** — focused runs, the local suite's richer failure detail, and the invocation forms below are all unchanged.

   **Invocation form, whenever you do run a suite command here:** the scripts carry the executable bit and a `#!/usr/bin/env bash` shebang, so answer a classifier denial of the `bash <path>` wrapper (see the *LEADING token* gotcha and the classifier-fallback Convention below) by invoking the path **directly as the leading token** — `lib/test/run.sh`, `lib/preflight.sh`, `lib/test/run-module.sh <module-id>` (never `bash lib/test/run.sh`) — through the documented `DEVFLOW_BASH` selection boundary.

   **There is no known-flake set — every FAIL is a real failure to diagnose.** A red assertion that reproduces only under pool saturation is a defect in that assertion's slack budget: fix the assertion, do not re-run the suite hoping for green. A local red that CI does not reproduce is **uncharacterised**, not explained — attributing it to an existing issue that does not in fact cover it is worse than leaving it open.
2. **Cloud `/devflow:implement` tier — in-env verification is the gate during the run; CI is the post-PR merge gate, not an in-run verification channel (issue #405).** This repo grants the suite/lint direct forms — `Bash(lib/test/run.sh:*)`, `Bash(lib/test/run-parallel.sh:*)`, `Bash(lib/test/run-module.sh:*)`, `Bash(lib/test/run-shard.sh:*)`, `Bash(lib/test/shard-tally.py:*)`, `Bash(lib/preflight.sh:*)`, `Bash(shellcheck:*)` — in **both** `prflow_implement.allowed_tools` and `prflow.allowed_tools`, so a cloud implement run **runs the suite in its own environment** (the direct leading-token form; the `bash <path>` wrapper stays deny-floored) and verifies every verification-command AC and the inline review pass's test evidence there. The scope rule below governs this tier unchanged: a focused module is the *intermediate iteration* default and never discharges a completion gate, and when the tier's per-command execution ceiling (set in `devflow-implement.yml` via the Claude step's `settings` input — `BASH_MAX_TIMEOUT_MS`, the largest timeout a command may request (raised by issue #1179), and `BASH_DEFAULT_TIMEOUT_MS`, the wall a command that requests none gets — both durations owned by `devflow-implement.yml` and referred to here by setting name so that file stays their single source) terminates the coordinator, decompose the partition through the shard dispatcher and recombine it rather than downgrading the evidence to a focused run. The run **never waits on, polls, re-checks, or cites CI for its own progress** — a verification command that is *not* granted goes **Blocked** naming `prflow_implement.allowed_tools` as the remedy, never a silent stall. CI (`lib + python tests`) remains the **required post-PR check that gates the human merge**; the run does not tick anything on it. The consumer-facing form of this rule is canonical in [`docs/internal/implement-skill.md`](docs/internal/implement-skill.md). The read-only `review` tier (`devflow-runner.yml`) is out of scope here: its wait-for-CI-then-review posture is the correct post-PR sequence. <!-- canonical: docs/internal/implement-skill.md -->
3. **The auditable skip is a cloud-tier rule (issue #1607)** — the local tier has no in-env pass to skip, so no skip record is owed there for not running the suite. Only a *permission/sandbox denial* of the direct form (e.g. the runner's `mktemp` writes are blocked) — **never** a suite that *runs and fails* — excuses a missing in-env whole-suite result, and the skip must be recorded in the workpad so it is an auditable decision. A reflection saying "could not run the suite" without having tried the direct-leading-token form first, on a tier where it is available, does not qualify. **A command the tier terminated at its per-command execution ceiling is not one of these skips either (issue #1132)** — it neither ran to a verdict nor was denied, so it routes to the shard decomposition above, and only an unobservable *recombined* run terminates the work, as the `execution-ceiling` Blocked terminal rather than as an auditable skip. **The local tier has its own unestablished-result terminal and it is not this one:** a local run that cannot establish a CI result for its pushed commit stops at `Blocked` naming that, rather than recording a skip and claiming completion.

### Choosing the iteration test (issues #707, #789)

This subsection and the two below are the **single home** of the suite-running policy for every tier and every command. They are scoped by tier, not by command, so no prompt extension restates them — an extension carries only the binding its own command adds.

- **Select the test explicitly and record the selection.** Read `lib/test/modules/coverage-map.json` for a candidate — `owner` names the covering shell module, and `focused_test` the covering Python test for a `lib/`/`scripts/` unit no shell module owns — then confirm the id in `scripts/workflow-flight-recorder-registry.json` before running it. Never infer or automate changed-file-to-module routing: the caller supplies the touched-surface set and nothing here derives it.
- **Tier 1 — iterate on the covering focused test.** Run a registered shell surface as `lib/test/run-module.sh <module-id>` and a Python unit as its `focused_test` file — one of the four parts `test_python_scripts.py` was split into for the `python-pool` shard (issue #2007): `lib/test/test_python_scripts.py`, `lib/test/test_python_scripts_part2.py`, `_part3.py`, and `_part4.py`. Each part is a flat linear script with no argv handling — it accepts no test selector, so passing one narrows nothing and silently runs that whole part — so the `focused_test` entry in `coverage-map.json` names the specific part that owns a unit's assertions and selecting a Python run means running that part. Invoke each as a **direct leading token** and never `python3 <path>` — the interpreter-head shape the cloud matcher denies (#401).
- **Tier 2 — coalescing extraction.** A surface with no covering focused test (a `lib/test/run.sh`-resident shell block) takes the full suite for its **first** mid-iteration cycle, and a **second** cycle on that same surface extracts a durable module instead — dispatched as an Agent-tool subagent, written RED-first, and registered.
- **The full-suite fallback is a closed set:** (a) a surface whose checks need `run.sh`'s full-suite global setup; (b) a check that legitimately self-skips, which a module may not (`run-module.sh` makes `skip()` fatal); (c) a surface whose tier-2 extraction cannot be completed; (d) the first mid-iteration cycle on a `run.sh`-resident surface, cloud tier only — the local tier's gate is the CI reading. A run that takes any of them records a `## Devflow Reflection` bullet naming **which** case applied, so a missing-module signal reaches the retrospective instead of vanishing.
- **Focused-first is a precondition on the mid-iteration full-suite launch, not routing advice.** Before launching the complete suite mid-iteration, every touched surface with a covering focused test invocable on this tier must already have been run this cycle; a surface is **exempt** on any of four total grounds — no coverage-map entry at all (the majority case, since the map covers only `lib/` and `scripts/`), a declared exempt subtree, an `unmodularized` entry with no `focused_test`, or a covering test this tier cannot invoke. A covering test that **ran and failed** also discharges the precondition, for the sole purpose of launching the full suite to diagnose it.
- **An unestablished record is not a satisfied precondition.** A run that cannot establish which covering tests it already ran this cycle re-runs them, and one that lost the touched-surface record itself degrades to the full-suite default rather than blocking on an unsatisfiable precondition.
- **The selection record has a named sink — never free prose in a general-purpose field.** Write it through `scripts/focused_selection.py` (`build_record` → a machine-parseable dict; `encode_marker` → the `<!-- prflow:focused-selection … -->` marker; `decode_markers` reads it back), naming per touched surface either the coverage-map entry consulted and the target selected or which exemption ground applied, plus whether the single flight was consulted (`single_flight_consulted`).
- **A mid-iteration `#434` stale-prose `blocking-gate` skip on a dirty tree is expected.** Commit the tree and continue rather than re-running the full suite to clear it — committing is the action the skip calls for.

### The whole-suite gate

- **Only a whole-suite result discharges a completion gate, and which result counts is tier-scoped (issue #1607).** A focused result discharges intermediate iteration alone, on every tier. On the **local/interactive** tier the whole-suite result is the CI reading for the commit the run pushed, per rung 1 of the tier ladder above. On the **cloud implement** tier it is a result the coordinator produced in a single run, or one recombined from the complete shard partition — nothing else.
- **Read every bullet below by whether it states a *gate* rule or describes an in-environment *launch*: a launch bullet binds a tier only while that tier is actually running the suite.** The local tier runs it to iterate and to diagnose, so the launch bullets apply then and not when it discharges the gate by reading CI; the cloud tier launches to discharge its gate, so they always apply there. A bullet marked **(gate rule)** binds every tier however the result was obtained. Classify by that question rather than by position, so a bullet added later has a scope without this one being edited.
- **The whole-suite command is the parallel coordinator `lib/test/run-parallel.sh` (issue #1086).** It runs the tested partition CI shards — the population comes from `lib/test/run-shard.sh --list-shards` — concurrently in this checkout, recombines through `lib/test/shard-tally.py`, retains every launched shard's complete log under an ignored run root, and prints one compact aggregate. On the **cloud** tier invoke it as a bare granted leading token with nothing around it, because the matcher refuses caller-side assignments, redirects and background processes (#401/#455) — and there give the Bash tool an explicit `timeout` of `1200000`, since the coordinator exceeds the tier's default per-command wall (`BASH_DEFAULT_TIMEOUT_MS`, set in `devflow-implement.yml`) and is otherwise killed with no output.
- **Read the result before making a claim (gate rule).** A nonzero failure tally, a nonempty skip tally, a **non-zero exit status** (which the coordinator returns for a shard that did not complete even when its tally reads clean), or a run that never started is not a completion — report the failure detail and iterate. This binds whichever result the tier's gate uses, so on the local tier it is the CI reading that must be read and satisfied: the push that triggered it is what gets read, never what stands in for reading it.
- **Batch every owed fix into one whole-suite pass (gate rule; issue #1252).** Before launching one — mid-iteration or at the gate — apply every failure the previous pass's `Failure recap` named, every edit already identified, and the batched artifact-regeneration pass. On the local tier "one pass" is the one commit you push and read CI for, so the fixes are batched into that push.
- **An unestablished owed-fix set is never an empty one, and the two launches resolve it differently (gate rule).** Mid-iteration, apply what you can establish, launch, and record the remainder through `scripts/workpad.py` with the `deferred` reflection kind; **at a completion gate it blocks instead** — establish the set, apply it, then launch, and a gate run that still cannot establish it stops at `Blocked` naming that set rather than claiming completion. A limb with nothing to read is established-and-empty; only a limb the run tried to read and could not is unestablished.
- **Consult `scripts/verification-flight.py`'s single flight before any suite execution — whole-suite, shard, or focused, not only a full-suite relaunch (#528, #1923) — and record that you did.** Read its durable status handle first and reuse a clean result it already holds for the current tree; diagnose a failure from the run's own `Failure recap` and the retained log the runner named — every runner (`run-parallel.sh`, `run-shard.sh`, `run-module.sh`) names the log it kept — instead of re-executing. The flight correctly does **not** suppress a post-edit relaunch, because the checkout has drifted. The exact consult forms are `verification-flight.py claim --input-file <declaration.json>` and `verification-flight.py status --flight <key> --current-checkout-file <fingerprint.json>`; direct every further interface question to `--help`, which now states the claim declaration's required keys, a complete copyable example declaration and the constraints the validator enforces (`schema_version` is the integer 1, `external_services` the string `none`, the four `checkout` object-id fields lowercase hex from `checkout-fingerprint.py`, and the optional `candidate_identity` from `reception-record.py`), and each exit code's meaning — and `checkout-fingerprint.py --help` describes its five fields and their ledger relationship — rather than grepping the source.
- **When the tier terminates the coordinator at its per-command execution ceiling, decompose — do not downgrade (issue #1132).** Run `lib/test/run-parallel.sh --preflight` once (read-only, sub-second, same verdict contract as the coordinator's own pre-launch check — apply the remedy the refusal itself names: regenerate and commit a drifted artifact, trim a file the reference-size ceiling names, or classify a brand-sweep occurrence), enumerate with `lib/test/run-shard.sh --list-shards`, run **every** shard as `lib/test/run-shard.sh <shard>`, then recombine with `lib/test/shard-tally.py combine` over this run's tally paths passing `--require-shards "$(lib/test/run-shard.sh --list-shards)"`. That reconciles the recombination against the true partition by name, so an omitted shard fails closed naming it (issue #1289) instead of printing a whole-suite-shaped green summary.
- **A same-tree failed-shard-only relaunch discharges the gate after a RED pass whose fix changed no repository file, but only when the tree is proven byte-identical (issue #2008).** Each launch records its checkout fingerprint — `scripts/checkout-fingerprint.py`'s five fields (`checkout_id`, `head`, `index_digest`, `tracked_digest`, `untracked_digest`) — as `fingerprint.json` in its retained run root (`lib/test/run-parallel.sh`) or tally dir (`lib/test/run-shard.sh`), written *unestablished* (never omitted) when it cannot be produced. To reuse the RED run's clean shards, produce a fresh fingerprint and run `lib/test/shard-tally.py same-tree-eligible --recorded <RED-run-root>/fingerprint.json --fresh <fresh>/fingerprint.json`; only its exit-0 `ELIGIBLE` (all five fields equal) permits relaunching just the failed shards with `lib/test/run-shard.sh <shard>` and recombining them with the RED run's retained clean-shard tallies through `lib/test/shard-tally.py combine … --require-shards "$(lib/test/run-shard.sh --list-shards)"`. On any field mismatch — and on any unestablished fingerprint on either side, which is never a match — the full `lib/test/run-parallel.sh` relaunch stays mandatory. Read the RED run root by its recorded path, never by globbing for the newest root.
- **Silence does not distinguish a clean preflight from a matcher denial.** A clean run is silent by design and a denied one emits nothing either, so treat an unreadable no-output result as the denial and fall back to running the recombined partition.
- **A `run.sh`-resident surface may run the `monolith` shard mid-iteration where a shard is the real saving (issue #1253).** `lib/test/run.sh`-resident assertions are the `monolith` shard's population, so such a surface runs `lib/test/run-shard.sh monolith` in place of a whole-suite pass on a tier where the coordinator meaningfully exceeds one shard (the coordinator ran ~15m40s on 2026-08-19 in Actions run 32289799442, up from ~10m16s on 2026-08-03 in run 30857543531, against ~3.9 min for the single `monolith` shard measured 2026-08-04 per issue #1253's AC1). The substitution is cloud-tier-only: it replaces the coordinator, and the local tier never launches one.
- **Four limits, or that instrument becomes a downgrade.** `monolith` is a cheaper **whole-file** run and not a focused module; it covers **one surface only**, so every other touched surface still takes its own covering test; it **never discharges a completion gate**; and under `DEVFLOW_SKIP_SUITE_MODULES=1` / `DEVFLOW_SKIP_PYTHON_POOL=1` the two selectors no-op their own call sites in `run.sh`, so an edit to those lines is `run.sh`-resident yet unexercised by the shard.
- **Record a mid-iteration shard run in the focused-selection sink as that surface's exemption entry**, naming the shard in the reason clause; no field is added to `scripts/focused_selection.py`'s schema.
- **On the cloud tier read `run-shard.sh`'s terminal `Failure recap` through `| tail -<n>`** rather than taking its whole echoed log into context — a permitted shape, since `tail` is granted. That tail is the *first* read, not the only one: `run-shard.sh` names the absolute path of the log it retained (issue #1923), so every later slice of that same run's output is re-read from that log (`sed -n`, `grep`, a wider `tail`), never obtained by re-executing the shard — re-running a suite solely to obtain output a prior run already retained is forbidden.
- **Do not read the coordinator's wall-clock as CI's.** CI isolates each shard on its own runner while the coordinator's shards share one host's CPU, memory, checkout and process namespace, so its `real` time is the slowest shard *under contention*.
- **Launch a backgrounded suite through `python3 lib/test/launch-detached.py <suite command>` (issue #1216).** It restores SIGHUP/SIGINT/SIGQUIT/SIGTERM to their default disposition in the child, places it in a new session, and reports the child's real exit status — without it a backgrounded launch hands the suite an ignored SIGINT its signal-trap assertions cannot handle.
- **Stop a suite process by recorded PID, never by pattern.** Sibling worktrees under `.claude/worktrees/` run their own suites under the same command names, so a `pgrep -f`/`pkill -f` sweep matches other branches' live runs and nothing in the output attributes a PID to a checkout. The coordinator's run root encodes its own PID (`.prflow/tmp/parallel-suite/run-<pid>-<n>`); confirm with `ps -o ppid=,lstart=,etime= -p <pid>` that a candidate is orphaned, childless and old enough before `kill <pid>`, and leave it alone if the cross-check does not resolve.

### Recording a whole-suite launch (issues #719, #1249)

- **On the local/interactive tier the recorded event is the CI reading, not a launch (issue #1607).** That tier's `Verification evidence:` marker carries the full 40-character SHA read, the required check's name and its conclusion, and the URL of the run the conclusion was read from — the run URL standing in for the retained-log root a launch would name. Everything else below applies unchanged, including the `note` reflection kind.
- **Every tier that maintains a workpad records one `Verification evidence:` marker per whole-suite launch**, through `scripts/workpad.py` with the **`note`** reflection kind — the only kind `lib/cheap-gate.jq` does not treat as friction, so any other kind would fire the retrospective gate on exactly the runs that complied. A run that launched twice ends with two records.
- **Each record carries** the command invoked, the outcome as the coordinator itself reported it (its `aggregate CLEAN` / `aggregate FAILED` line), the pass/fail/skip tallies when reported, the coordinator's retained-log root, the coordinator's reported elapsed wall-clock time (its `run-parallel: elapsed <N>s` line), and the launch's **own start time**. The records are told apart by that per-launch run root, so there is no launch counter or ordinal to maintain.
- **Four paths produce no run root, and each names what to record instead:** a tier-**denied** launch (no output at all — record the refusal, with no root), a launch **terminated at the execution ceiling** (record the termination, then route to the shard decomposition), the **shard-decomposition** path itself (record the recombination and the shard tally), and the **CI reading** that discharges the local/interactive gate (issue #1607), which launches nothing at all — record the full 40-character SHA read, the required check's name and conclusion, and the run URL, per this subsection's local-tier bullet above.
- **A gate discharged by the same-tree failed-shard-only recombination (issue #2008) records its `Verification evidence:` marker naming BOTH run roots** — the RED run's retained root (source of the reused clean-shard tallies) and the fresh failed-shard relaunch's root — so a later reader can retrace which tallies the whole-suite result was assembled from.
- **The CI-reading path does not consult the single flight, and owes no record of having done so.** `scripts/verification-flight.py` is a **reuse coordinator**, and the obligation to consult it is scoped to a full-suite *relaunch* — which this path does not perform. Nor could it: a CI reading is bound to one pushed commit on an external service and is therefore non-reusable by construction — the same non-reusable disposition the ledger records for an `external_services` declaration that truthfully names a live service (issue #2080), which is recorded and never served as a clean prior result rather than refused at claim time. There is nothing for the flight to suppress, so consulting it would be a no-op with a misleading record, and declaring such a reading hermetic to obtain a flight would be false.
- **Fallback channel:** a run with no workpad records the marker in the PR description, and a run with neither a workpad nor a PR names that terminal and reports the evidence **unrecordable** rather than stalling.
- **`lib/cheap-gate.jq` is not wired to the marker**, so per-launch completeness is legible to a later reader and never machine-prevented.

## Architecture

- `skills/` — one `SKILL.md` per command (`/devflow:implement`, `/devflow:review`, `/devflow:review-and-fix`, the `/devflow:docs` family, `/devflow:create-issue`, `/devflow:retrospective-weekly`, …), plus the two skills vendored from the `superpowers` plugin (`requesting-code-review`, the review engine's final-pass reviewer dispatched as a `general-purpose` Task; `receiving-code-review`, the fix-loop principles) under their upstream MIT license — see `LICENSES/superpowers-LICENSE`. Both are *runtime-dispatched* by PRFlow's engine; the `superpowers:writing-skills` authoring discipline is **not** vendored — it is a development-time tool, referenced as the external skill in the Conventions below.
- **Both vendored skills are installed into third-party consumer repos, so their SKILL.md bodies must be repo-agnostic:** no `lib/test/run.sh`, no `lib + python tests`, no PRFlow-internal step numbers, and **no citation of PRFlow's own `CLAUDE.md`** — the vendor slice never copies it, so the pointer resolves against the consumer's own, unrelated project-memory file. Use generic language ("the project's test suite", "the fix step") instead. `lib/test/lint-shipped-pruned-path.py` enforces the `CLAUDE.md` half.
- **The shipped prompt surface is mechanically checked (issue #1072).** `lib/test/lint-shipped-pruned-path.py` audits every `skills/**` and `agents/**` file for a reference to a path the vendor slice prunes, deriving that forbidden set from `vendor-slice.sh` itself rather than a hardcoded literal, and fails the suite on any such reference carrying no explicit `<!-- pruned-path-ok: <reason> -->` declaration. The audited population is `skills/**` and `agents/**` only — the copied `scripts/`/`lib/` surface stays a separate concern, so state the coverage claim as that population and never as "the whole shipped surface". **A prune target that is also a documented `docs.*` config default is exempt (issue #1309):** `docs/external` and `docs/internal` are simultaneously the defaults of `.docs.external` / `.docs.internal`, so the lint derives an exemption set from the path-shaped `docs.*` defaults in `.prflow/config.schema.json` (by trailing-slash-normalized equality, never prefix) and subtracts it before scanning — a shipped sentence naming a documented `docs.*` default needs no marker. **A `.github/workflows/` member the installer never ships is another forbidden class (issue #1402):** `devflow_copy_slice()` copies no `.github/` at all, so no workflow is a prune target and the derivation above is blind to the family, while a consumer *does* have `.github/workflows/` — making a blanket `.github/` ban wrong. The lint therefore derives a never-shipped set at run time by word-list membership over the parsed `install.sh` workflow copy loop's literal operand list — the one declaration that puts a workflow in a consumer's checkout — subtracts it from the `.github/workflows/*.yml` basenames present, and reports an unmarked `<basename>.yml` reference in either the fully-qualified or the bare spelling; an unestablished declaration refuses non-zero naming `install.sh` rather than auditing against an empty set. **`DEVFLOW_WITHHELD_TIER` is NOT read by the lint (issue #1423)** — its members reach no fresh install, so counting them as shipped told a fresh consumer that a file they lack resolves, and they are now forbidden like any other never-shipped name; a withheld name that also left the tree (`devflow-review`) needs no carve-out, because the derivation intersects with what is **tracked**. The residuals — an extensionless stem, a `.yaml` suffix, a workflow no longer in the tree, and a consumer's own same-named workflow — are enumerated in the lint's own docstring. **A PRFlow-internal development-harness identifier is a further forbidden class (issue #2114):** unlike the derived sets above, the denylist (`structural-pin-ok`, `CEILING_TRIPWIRE_FRACTION`, `run-parallel` at minimum) is a hardcoded module constant guarded non-empty at import — there is no producer file to derive it from — and a shipped body naming one, unmarked, instructs a consumer's agent about a pin-corpus marker or suite tool their tree does not carry.
- **Every first-party `skills/**` body ships verbatim into a consumer repo, so since issue #1190 that population carries ZERO references to any PRFlow-internal file under the exempted doc roots `docs/external/` and `docs/internal/`** — not only a `docs/*.md` page but any PRFlow-owned file beneath them (e.g. `docs/external/docs.json`, `docs/external/index.mdx`), none of which resolves in a consumer's checkout. Do not reintroduce one, nor a re-spelled `docs/internal/…` form: restate the claim's backing inline, or point at an artifact the consumer actually has. Since issue #1309 those two roots are exempt from `lint-shipped-pruned-path.py` (they are also documented `docs.*` defaults), so nothing mechanically catches a PRFlow-owned file named beneath them — the review pass is the sole control.
- `agents/` — first-party subagents: the review-engine trio `checklist-generator`, `checklist-deduper`, `checklist-verifier`, plus `code-explorer` and `code-architect` (the `/devflow:implement` discovery/planning agents, vendored from Anthropic's feature-dev plugin under Apache-2.0) and the five `pr-review-toolkit` review agents `code-reviewer`, `comment-analyzer`, `pr-test-analyzer`, `silent-failure-hunter`, `type-design-analyzer` (vendored under Apache-2.0). See the matching files under `LICENSES/`.
- `scripts/` — Python + shell CLIs (`workpad.py`, `config-get.sh`, `match-deferrals.py`, `file-deferrals.py`, `parse-acs.py`, `resolve-*-trigger.sh`, …).
- `lib/` — retrospective-loop helpers (`*.sh`, `*.jq`), `preflight.sh`, `test/`.
- `.github/` — optional cloud tier: workflows + composite actions (incl. `vendor-plugin`). **The automatic pull-request-triggered review tier is WITHHELD from this release (issue #936):** `devflow-review.yml` is no longer in the tree and `install.sh` ships none of that tier's files (the `installer-wiring` module asserts they stay uninstalled). The always-available review path is a collaborator commenting `/devflow:review`, gated by `devflow.yml`'s `authorize-actor.sh`, so a fork contributor cannot self-trigger one; a consumer can additionally opt into an automatic CI-green review request via the copy-pasteable snippet in [`docs/internal/workflow-triggers.md`](docs/internal/workflow-triggers.md), which is the canonical statement this bullet summarizes. <!-- canonical: docs/internal/workflow-triggers.md -->
- **Everything downstream of the withheld tier STAYS in the tree — a "sole-caller is unreachable, delete it" sweep is wrong here.** Deleting a helper breaks an existing consumer that upgrades, because `install.sh` re-stamps `prflow_version` and re-running the installer keeps that repo's already-installed `devflow-review.yml` while vendoring a plugin missing the helper it calls. Reachability from this tree is not the criterion; resolvability from an installed consumer copy is.
- `.prflow/` — `config.example.json` + `config.schema.json` (+ tracked `learnings/`, `logs/`). The live `config.json` is **tracked** here too, force-added past the `/.prflow/*` ignore rule (`git add -f`) so the cloud tier reads it from the committed tree.
## Gotchas (load-bearing — easy to get wrong)

- **Skills locate bundled helpers via the portable single-statement anchor `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../<dir>/…`, NEVER `${CLAUDE_PLUGIN_ROOT}`** (not substituted inside `SKILL.md` bodies). Resolve the anchor **inline in the statement that uses it** at every call site: `${CLAUDE_SKILL_DIR}` is *empty* (not merely unset) on non-Claude-Code runners, and Copilot CLI's inline `bash -c` marshaling strips a variable assigned in one statement and read in a later one, so the assign-then-reuse recipe is banned. The cloud-tier **workflows** are the one exception: they use the literal vendored path `.prflow/vendor/prflow/scripts/…`. **Where a skill consumes the anchor's *value* directly to resolve `<skill-dir>` (the resolve-once step in `/prflow:implement` and `/prflow:review`), resolve it from the runner-reported base directory FIRST — the `echo "${CLAUDE_SKILL_DIR:-…}"` command is a refusable fallback** (a runner may deny the `${VAR:-default}` argument expansion, so a run keyed only on its output stalls at its first command), classified into three outcome shapes: a tool-level refusal leaves the `$CLAUDE_SKILL_DIR` channel *unestablished* (distinct from a run that printed empty or the placeholder unsubstituted). `lib/test/lint-reported-base-dir-arm.py` pins that the reported-base-directory-first arm precedes the value-consuming expansion at each enrolled call site.
- **A cloud-reachable *skill* call site uses the conditional form, NOT the bare anchor (#1256/#1124).** The cloud matcher denies the unexpanded anchor both as a **leading token** and in **argument position** under a granted head, so emit the granted vendored literal `.prflow/vendor/prflow/scripts/<helper>` as the leading token first and, on a `command not found` / `No such file` / rc-127 reading, re-invoke the same helper with the `.prflow/vendor/prflow/` prefix removed — the bare anchor line stays as the **fallback arm**, which preserves portability on runners where neither repo-relative path exists. This is **not** a blanket replacement of the anchor: `lib/test/lint-anchor-fallback-arm.py` fails only for an **enrolled** call site emitting the anchor leading token with no vendored fallback arm, and every other anchor invocation under `skills/` stays the sanctioned single-source form until it becomes cloud-reachable and is enrolled.
- **Windows-form runner-reported paths are normalized at prompt time**, by one standalone `wslpath -u`/`cygpath -u` probe or `lib/normalize-path.sh`'s textual rules; the skills carry **no** shell normalization mirrors (#275). Relatedly, `workpad.py` reads `.prflow.workpad_marker` from `.prflow/config.json` directly in Python rather than by exec-ing `config-get.sh`, which Windows cannot exec ([WinError 193]).
- **The `.prflow/` config and prompt-extension readers resolve their *default* path anchored to the git repo root (#295), not the cwd.** `config-get.sh`, `workpad.py`'s marker read, `load-prompt-extension.sh`, `match-deferrals.py`, `match-lint-adjudications.py` and `render-audit-prompt.py` use `git rev-parse --show-toplevel` (falling back to `pwd`/`Path.cwd()`), so a skill run from a **subdirectory** still loads the consumer's root config instead of silently missing it. A **non-empty** explicit `CONFIG_FILE`/`--config` arg is still honored verbatim; a no-git-root-**and**-no-`.prflow/` tree emits a stderr breadcrumb instead of a silent default; the Python readers resolve the root via a native `git` subprocess, never a `.sh` exec. That list is not closed — later readers self-declare by the `SHARED REPO-ROOT CONFIG CONTRACT` phrase, so grep the phrase. **Known limitation:** `--show-toplevel` returns the *nearest* git root, so a nested submodule or a monorepo whose `.prflow/` is not at the git root is not covered.
- **`load-prompt-extension.sh` anchors on the repo root only on its FALLBACK branch (#874).** When `DEVFLOW_PROMPT_EXTENSION_ROOT` is set and non-empty it composes `<root>/<skill>.md` from that value directly and never calls `git rev-parse`. Both cloud tiers that run the review engine set it, because the loader's bytes become the reviewing agent's appended prompt, and the enumerations naming this reader in `.prflow/config.schema.json` and `scripts/emit-git-env.sh` are a coupled pair recording the fallback-only scope.
- **The `SKILL.md` `` !`cmd` `` injection is refused DETERMINISTICALLY and SILENTLY on the cloud headless tier, and no grant can fix it (2026-08-08).** The cause is a **phase mismatch**, not pattern matching: `allowed-tools`/`--allowed-tools` grants authorize the model's tool calls *after* the skill loads, while `` !`cmd` `` runs *during* loading as a preprocessor (`anthropics/claude-code#39048`; the headless silent-success envelope — `subtype: success`, `is_error: false`, `num_turns: 0` — is `#80223`). `lib/capability-profiles.json` already grants **both** `Bash(*/render-prompt-extension.sh:*)` and the exact vendored literal and the refusal still fires, so do not spend a probe run adding grants; the only reported-working options (bare `Bash`, `--dangerously-skip-permissions`) are barred here because the review profile is a security boundary. **The refusal aborts the ENTIRE `Skill`-tool load, and is invisible to the run's own denial telemetry (forensic audit of run `31287654057`).** The load returns an `is_error` result whose whole content is a permission-refusal string and no skill body at all, so the run loses the skill rather than merely its extension; and because that surfaces as a `Skill` tool result rather than a `permission_denied` event, it does not increment `permission_denials_count`, so the no-verdict denial-count check cannot see the failure class. **Historical record — no `skills/**` body carries a placeholder any more** (PRs #1471 and #1473 retired the channel, and `lib/test/modules/prompt-extension-reader.sh` pins its absence per site), so that hazard is no longer live in this tree; while placeholders existed, nothing rendered, no `PROMPT-EXTENSION-STATUS:` line appeared, and every extension-only rule — prompt-surface edit routing, the `Writing-skills evidence:` producer contract, the Phase 3 review gate — was absent for a whole run that still reported `Complete` (run 31236010867 / issue #1416 / PR #1433).
- **A prompt extension is FETCHED THROUGH THE `load-prompt-extension.sh` LADDER, never by reading its file directly — and that ladder is the SOLE delivery channel (issue #1462; PRs #1471, #1473).** The ladder is the single place the extension root is resolved, and on the review tiers that resolution is a security control: `devflow.yml` materializes a trusted base-ref closure precisely so the reviewing agent's own prompt is not read from the PR head, and a direct file read bypasses it. All five call sites — `skills/implement/SKILL.md`, `skills/review/SKILL.md`, `skills/review-and-fix/SKILL.md` (its own extension and `receiving-code-review`), `skills/pr-description/SKILL.md` — therefore invoke the ladder **unconditionally**, and **every extension-state failure arm fires unconditionally too** — nothing else delivers consumer policy into those bodies, so a failure left unreported drops that policy from the run silently. **The ladder result is a `Bash` tool output with no re-attachment on context compaction (issue #1574), so a surface that re-enters itself re-invokes its ladder at each existing re-entry boundary in addition to the run-start load** — `implement` at every phase (re-)entry and mid-phase re-anchor, `review` at every phase and shadow entry, and the fix loop once per iteration for the `review-and-fix` and `receiving-code-review` ladders alike — treating the returned text as a refresh of already-loaded policy rather than a fresh directive; `pr-description` is single-pass and re-invokes nowhere. This re-load timing does not weaken the sole-delivery-channel rule: the ladder stays the only channel that delivers consumer policy into these bodies. The **anchor-resolution** arm (a missing helper path on *every* rung) is reported regardless of extension state, because it breaks every other bundled-helper call site in the run rather than merely losing an extension. **On an implement run** each surface's outcome is recorded on the workpad as a nested `prompt extension resolved: …` `## Progress` row, whose text and tick substring are single-sourced in `scripts/workpad.py`'s `_EXTENSION_ROWS` and whose tick is issued only from an implement phase file — the standalone `/prflow:review`, `/prflow:review-and-fix` and `/prflow:pr-description` paths have no workpad and record nothing. The row's existence is deterministic, its tick is the run's own report.
- **Read a prompt extension WHOLE-FILE — never `| head -<n>`.** That same run loaded the 325-line `review-and-fix` extension as `… | head -60`, truncating away the Phase 3 gate at ~line 225, so the in-run backstop for the failure above was lost on the same surface twice over.
- **A boundary-gated reference or a skill root over 61,750 bytes turns the suite RED (issue #1595), and the remedy is to trim the file — never to exempt it.** `lib/test/lint-reference-size.py` audits every tracked `.md` file whose first and last **non-blank** lines are a matching boundary-marker pair — the `<!-- prflow:<command>-ref … start/end -->` family and `review-and-fix`'s `# Reference: …` / `<!-- END <name>.md -->` family alike — plus every skill root (`skills/<name>/SKILL.md` at any depth), deriving that population by reading each file rather than from a path list, so a new skill and a newly-gated reference are covered with no second edit. The ceiling is 95% of the Read tool's 25,000-token cap converted at the **floor** of the measured bytes-per-token densities (2.60, never their mean — a denser file truncates at a smaller byte size), because a file over it cannot be returned in one read. Each gated surface's boundary contract pages such a file whole before its marker checks run, so an over-budget-but-intact reference loads instead of misreading as damage — but the extra reads still cost, and a smaller reader budget may not complete the paging, so the remedy stays trim-the-file. The files already over it carry **expiring** exemptions in `lib/test/reference-size-exemptions.json`: each names exactly one file, one naming a file outside the record's frozen `recorded_set` is refused, and an exemption goes RED once its file drops to or under the ceiling — so a landed trim is finished by deleting that file's rows. Several implement and review-and-fix phase files sit within tens of bytes of the line, so ordinary prose added to one of them should expect to hit this — run the check rather than guessing which: `lib/test/lint-reference-size.py` as a direct leading token locally, and `lib/test/run-shard.sh monolith` on the cloud implement tier, where the lint's own path is granted in no profile.
- **The consumer-facing `devflow` -> `prflow` rename is Tier 1 of issue #1002, and `lib/rename-map.json` is its SINGLE SOURCE.** Renamed: the state directory `.devflow/` -> `.prflow/`, the vendored plugin path, and the seven top-level config keys. **FROZEN and NOT renamed** — do not "helpfully" sweep them: `devflow-marketplace`, every `.github/workflows/` **filename**, the `DEVFLOW_*` env vars, `devflow_module_pin_*`, the internal `devflow_*` shell function names, the subagent-override namespace `devflow:<agent>` and the transitional `/devflow:<command>` spellings (permanently accepted aliases, not renames), and the **byte contents** of `.prflow/learnings/*.jsonl` + `.prflow/logs/*.tsv`. Renaming a frozen env var does not move a setting — it deletes it, usually silently.
- **Tiers 2, 3 and 4 have SHIPPED, and each moved specific names out of the frozen list — read `lib/rename-map.json`, not this summary, for which.** Tier 2 (#1003) unfroze the provenance label, the telemetry branch and the comment-marker namespace into the map's `identifiers` block, which `lib/test/pin-corpus-lint.py`'s `_build_rename_substitution` reads — without it every respelled pinned literal reaches the `#810` gate as new pin authorship. The two `workflows.*` config sub-keys Tier 4 (#1041) unfroze migrate only behind `scaffold-config.sh`'s fail-closed freshness gate and the backfill's anti-graft guard, because a naive rename takes a consumer *silently offline*.
- **A revision-side read is the trap a tree-wide rename sweep gets wrong.** A `git show <pre-rename-ref>:<path>` argument, a frozen census snapshot's recorded path, or a merge-base `ls-tree` pathspec must keep the OLD spelling or resolve nothing — as must the escaped/regex-quoted path forms (`\.prflow\/vendor\/prflow\/…`), which a literal-path sweep misses entirely.
- **`/prflow:init` migrates a consumer as ONE atomic unit — `scripts/migrate-consumer-tier1.sh`, all four members or none (issue #1002).** The members are enumerated in `lib/rename-map.json`'s `atomic_unit` and never transcribed. It is **fail-closed where the rest of the repo is best-effort**: it plans, validates every precondition, stages every byte, then commits behind a rollback journal, so one unsatisfiable member refuses the whole set and leaves the tree byte-identical. Do not "fix" that into log-and-continue — the shipped workflows invoke bundled helpers at the vendored path as leading tokens and the cloud grants are per-literal-path, so a half-moved tree is silently **denied**, not merely broken. Coupled sites, edited together: `lib/rename-map.json` <-> `lib/resolve-state-dir.sh` <-> `lib/state_dir.py`.
- **The state DIRECTORY has a loud transitional read-through; the config KEYS deliberately do not.** Readers resolve `.prflow/` first and fall back to `.devflow/` **only** when the canonical path is absent and the superseded one is present, breadcrumbing `/prflow:init` every time — without it a plugin auto-update ahead of any migration run resolves an absent config and silently reverts every `// default` read. The end criterion is confirmation-gated, not a timer, and lives in `lib/rename-map.json`. For the keys, migration is **detected** rather than read through (#988) — by `config-get.sh`'s superseded-key probe and a per-family `::error::` guard in the two shipped workflows' `config` jobs — because a silent key fallback makes the migration unobservable and therefore permanent.
- **That per-family gate is a set-DIFFERENCE, so it fires only on an ABSENT canonical family (issue #1083).** Those `config` jobs therefore also carry an advisory stray-family `::warning::` for a superseded family sitting *beside* a present canonical one: it reads presence from the config's key set so a valid-falsy stray survives, matches by the `^devflow(_|$)` **shape** rather than any literal — spelling one would mark a shipped workflow stale under the freshness gate — and sits outside the enable gate so a disabled repo mid-migration is still told. Those blocks are a byte-identical coupled mirror driven by `lib/test/modules/tier1-rename-migration.sh`.
- **Config is `.prflow/config.json` (JSON), read via python3 by a single resolver** (`config-get.sh` / `config-source.sh`) — `node` is NOT required anywhere in the config-read path (issue #220). PyYAML is required only because `match-deferrals.py` and `consolidate-changesets.py` lazily import it. Renaming a config key? grep `.py`, `.sh`, `.yml`, and jq lines — silent-fail consumers exist.
- **`/devflow:create-issue` is a thin root plus MARKER-gated references, and its entry gate degrades — it does NOT fail closed (#614).** A reference is loaded with the runner's **file-read tool** (never a shell invocation) and accepted only when its literal first line is its `start` boundary marker and its last line the matching `end` marker, each naming that file's own path. A failed load **degrades best-effort** (breadcrumb plus the routing row's named degraded behavior), and no routing row's failure arm may terminate the run — nothing blocks issue *creation*. Do not "unify" it onto the review engine's fail-closed contract.
- **create-issue's coupled sites are edited together:** the routing table — relocated off the always-read root into `skills/create-issue/references/degradation-routing.md` (issue #1644) — has a marker-contract column that must byte-match each file's marker id, and the `#614` block in `lib/test/modules/create-issue-contract.sh` reconciles that table (read from `degradation-routing.md`) against the on-disk `references/*.md` set each way round — exempting exactly `audit-prompt-template.md`, whose consumer is a Python renderer (`scripts/render-audit-prompt.py`) rather than a gated runtime read; `issue-template.md` is itself a routed reference under marker id `issue-template` (it stays out of `$CI_BUNDLE`, which tracks where content-survival pins point, not routing).
- **The create-issue Step 3.6 audit LIFECYCLE is owned by `scripts/issue-audit-state.py`, not by prose.** Transition legality, round numbering and kind, arm routing, budgets, digest and sentinel comparison, offer triggers, override records and the audit-summary field set are all its answers, which the skill obeys rather than re-deriving.
- **create-issue pin routing is decided per pin, never by default:** a pin asserting content survives *somewhere* in the shipped skill targets the concatenated `$CI_BUNDLE`; a pin whose guarantee is **location-sensitive** keeps a specific-file target. **Pointer purity is non-negotiable** — no routing row or restatement may quote a literal the module pins uniquely, and a collision is resolved by rewording the pointer, never by weakening the pin.
- **The review engine is shared, and it is a BUNDLE — a thin root plus gated phase references (#529).** `/devflow:review` Phases 0–4.3 are executed *verbatim* by `/devflow:review-and-fix`, which adds the fix loop and shadow pass and skips Phase 4.4; edit `skills/review/SKILL.md` and never paraphrase the engine into the fix-loop skill. Each phase's authoritative procedure lives in `skills/review/phases/*.md`, reached through the root's entry gate — re-derive bundle identity, `Read` the reference, clear its boundary contract — on every entry, including a Step 2.6 shadow entry. Three references are gated *out* of the default path by their own predicates (the Phase 0.3.6 blocker recheck, the Phase 0.6 stale-prose lint under `prflow_review.stale_prose.enabled`, and the Phase 4.1.7 stale adjudication), and `phase-4-4-github-post.md` is standalone-only.
- **The reviewed surface is every source, not the root.** `extract-command-heads.py`/`extract-command-shapes.py` take the whole bundle in one call and `lib/test/run.sh` asserts engine-content pins against a concatenated `$REVIEW_BUNDLE`, so a sentence may move between references without breaking its pin; `$REVIEW_ROOT` is reserved for pins genuinely about the root.
- **Cloud allowlists & command shapes — a head or shape the runner doesn't grant is SILENTLY denied, and a run can end with NO verdict (issues #363, #401, #484).** A command the active profile omits is refused *before it runs*: it burns budget and produces no output, not a loud failure. **Heads are not enough — the matcher also denies composite *shapes* whose every head is granted:** a leading `VAR=`/`cd`, a `/tmp` redirect, a heredoc write, an interpreter head, the unexpanded anchor as the leading token, or **a `$VAR`/`${VAR}` expansion anywhere in the command** (`Contains simple_expansion`/`Contains expansion`) — the dominant cause, so substitute the literal value; per-occurrence adjudications are canonical in [`docs/internal/cloud-allowlist.md`](docs/internal/cloud-allowlist.md). Use a permitted shape (a Write into `.prflow/tmp/**`, `… | tee`, a repo-relative vendored-literal helper path) and on two denials of a shape *switch* to a permitted alternative rather than iterating variants. <!-- canonical: docs/internal/cloud-allowlist.md -->
- **Grants are per-HEAD across the whole pipeline (#455):** one ungranted head in a tail refuses the entire statement, and `paste` is granted nowhere — use `tr`/`sed`/`grep`. `lib/test/extract-command-heads.py` + `extract-command-shapes.py` turn an ungranted head or denied-shape fence RED at the desk, and `.github/workflows/matcher-probe.yml` is the re-runnable evidence source — re-run it after a `claude-code-action` upgrade before changing shape rules or grants.

A PR touching the engine surface adds a uniquely-named `.changeset/*.md` file and does **NOT** edit `.claude-plugin/plugin.json` or `CHANGELOG.md` directly, because editing those shared hot spots conflicts on every concurrent PR. On merge to `main` the `version-consolidate` workflow bumps by the **highest** pending bump, prepends one dated CHANGELOG entry, deletes the consumed changesets, and commits with the load-bearing `chore: bump version` subject.
- **Editing a `.github/workflows/` file is ordinary work, not maintainer-only.** It needs a `workflows`-scoped push and the App HAS that scope, so an autonomous run edits a workflow file like any other file. Whoever changes one must still ensure `main` branch protection permits the job's `contents: write` bump commit.
- **A review verdict's IDENTITY is a producer-emitted marker, never the shape of agent prose (issue #1030).** `post-review-verdict.sh` stamps `<!-- prflow:review-verdict head=<40-hex> verdict=<APPROVE|REJECT> -->` as line 1 of the review body and as the line after the run key in the progress comment; the reviewing agent composes it nowhere. Readers scan a body's **first two lines only**, so a marker a finding quotes deeper in the body is prose. Only the `prflow:` spelling is accepted. The canonical statement and its consumers' transitional prose arms — retired only on a confirmation-gated sweep, never a timer — live in [`docs/internal/DEVFLOW_SYSTEM_OVERVIEW.md`](docs/internal/DEVFLOW_SYSTEM_OVERVIEW.md) §8; this bullet is the non-authoritative summary. <!-- canonical: docs/internal/DEVFLOW_SYSTEM_OVERVIEW.md -->
- **`post-review-verdict.sh` is the only granted *marking* post path, not the only granted post path.** `Bash(gh api:*)` is granted in all three profiles and `POST …/pulls/N/reviews` through it creates a real, unmarked, merge-blocking review. A prefix grant cannot separate that write from the engine's reads of the same endpoint, so per issue #1250 the control is downstream: the Phase 4.4 reach record classifies the head's reviews via `scripts/classify-head-reviews.sh` and reports an unmarked one truthfully.
- **Review-outcome analysis sources verdicts from the IMMUTABLE bot PR reviews, never the progress comments.** The run-keyed progress comment is edited in place so superseded REJECTs vanish, while the bot-posted review is the durable record — but its body is a stub, so findings and severities live in the progress comment, joined via `review.commit_id` = the comment's "Reviewed HEAD:" line. **That join key is mutable** — GitHub can change a review's `commit_id` after submission (#1247) — so where the reviewed *tree* must be identified, read the verdict marker's `head=`; this join is a measurement convenience, not a reviewed-tree authority.
- **`agent_overrides` model/effort values reach the standalone `/devflow:review` — the merge-gating judge — not just the fix loop.** The engine is shared, so "cheapen a reviewer agent" changes what reviews every PR before merge. During any measurement or experiment window treat the judge's roster economics as frozen — dispatch-scoping keys are judge-neutral, model repricing is not.
## Conventions

- **Portability:** no GNU-only flags. Use `python3` for date math (not `date -d`) and ERE / `sed -E` (not `grep -P`); helpers must work on macOS/BSD without GNU coreutils. **`\b` (word boundary) is a GNU extension, and its failure mode is silent:** BSD `sed` and BSD `grep -E` accept a pattern containing `\b` without error and simply match nothing, so a guard built on it *passes while checking nothing* on exactly the platform this convention targets. Use the portable `(^|[^a-zA-Z_])` instead.
- **Consumer runners are not `ubuntu-latest` — account for custom GitHub runners, including Windows (Git Bash) hosts, in every workflow, composite-action, or runner-provisioning change.** The shipped workflows resolve `runs-on` from the consumer's `DEVFLOW_RUNNER` repo variable, so they reach self-hosted Linux/macOS/Windows and arm64 runners with **no workflow edit** — a step that assumes image-preinstalled tools (`unzip`, `sudo`, GNU coreutils), Linux-only paths, or full control of the platform matrix silently breaks those consumers. On a platform the change does not cover, degrade gracefully (warn-and-continue, or reuse a version-verified pre-provisioned tool from the runner image) rather than failing closed; reserve fail-closed for integrity checks (digest/version mismatches), where it stays mandatory.
- **A shell snippet in a skill file must survive a non-bash interactive shell — and the unmatched glob is the trap.** Fenced blocks under `skills/` are prose an agent runs verbatim in whatever shell its harness supplies, commonly **zsh**; zsh's default `nomatch` makes an unmatched filename pattern a refusal of *that one command*, which it skips before carrying on. The harm is a **silently empty enumeration** — the step meant to list something emits nothing, and no surrounding prose distinguishes "there is nothing here" from "the shell declined to look". Put one line beside the glob, inside the same block: `[ -n "${ZSH_VERSION:-}" ] && setopt nonomatch || :` (a no-op on every other shell), and better still report the empty case explicitly (`… 2>/dev/null || echo "(none)"`). The mechanical backstop is `lib/test/lint-skills-glob-guard.py`, discharged by that guard line or a `# glob-ok: <reason>` marker; it claims no completeness, and its recognised shape and disclosed residuals live in its own docstring. The sibling rule from the same class: no bash-only builtin (`compgen`) in a `skills/` prose block.
- **No secrets, owner-specific IDs, or product names in committed files.**
- New `.py`/`.sh` files carry the SPDX header (`SPDX-FileCopyrightText: 2026 Daniel Radman` / `SPDX-License-Identifier: MIT`).
- Docs reference bare source paths (`scripts/workpad.py`), never `path:line` — line numbers rot.
- **Prefer generated evidence over exact checked-in numbers — EXCEPT where an exact literal is itself the enforcement (issue #656).** A figure a reader treats as *current* rots silently the moment the measured thing changes and the copy does not, so render it live and assert it positionally rather than hand-transcribing it. A literal stays checked-in only when it *is* the enforcement — a **past-time snapshot** (unre-derivable history), an **enforcement constant** (a ceiling or threshold the check compares against; prefer *pinning* it), or a **future target** (a pin would trap the change that moves it). Register each exempt literal with a one-line rationale, and never machine-render a frozen figure, which would overwrite the snapshot and falsify the record.
- **A suite assertion or lint helper that enumerates the repository tree sources its population from an index-reading `git ls-files` — with no `--others` — never a repository-root-anchored recursive walk (issue #711).** A root-anchored walk descends into every sibling git worktree under `.claude/worktrees/`, so the check counts those checkouts' copies and goes red locally with a number that varies between runs on the same commit, while CI stays green. A **working-tree** enumeration (`--others`, even with `--exclude-standard`) is **not automatically** worktree-immune: when its pathspec can reach sibling worktrees its protection comes from an untracked `.git/info/exclude` line no clone inherits, so a helper that needs one carries its own `.claude/worktrees/` exclusion. A closed, non-recursive leaf pathspec that cannot reach that subtree is the narrow exception. The enforcing mechanism is `lib/test/lint-tree-enumeration.py`, which turns the suite RED for an **undeclared** recursive walk in a tracked `lib/test/` `.py`/`.sh` file carrying no `# tree-walk-ok: <reason>` marker — a member of the declaration-marker family (`# structural-pin-ok:`, `# raw-guard-ok:`, `# tree-walk-ok:`, `# argjson-ok:`, `# pruned-path-ok:`, `# glob-ok:`). It is deliberately not exhaustive; its module docstring closes the candidate-token set and the accepted residuals.
- **Comment discipline — a comment survives inline only if it names a wrong change it prevents.** The canonical statement is the authoring rule in `skills/implement/phases/phase-2-sweeps-contract.md` §2.3, and this bullet is its non-authoritative summary. The rule binds exactly four populations and nothing else — inline comments in library and script source, test files, module docstrings and contract headers, and workflow and YAML files — so skill and agent prose bodies are outside it and governed as before. Within those populations, a comment the change adds or modifies survives inline only when a competent agent would otherwise make a specific, nameable wrong change at that line or at a coupled site the clause names by file or symbol; it is written as the prohibition and its consequence, capped at three physical source lines, and everything else — derivation, worked example, provenance, design narrative — moves to the project's internal documentation or is deleted. Three carve-outs are absolute: a comment a tool, licence, or policy requires present (a machine-read declaration or suppression marker, or a licence/SPDX/vendored-attribution header — the declaration-marker family enumerated in the issue-#711 bullet above among them); a contract-header docstring's specification statement, which stays while the derivation and provenance around it move; and any comment whose load-bearing status the author cannot decide, which stays. This governs prose comments only. Distinct from it, the same §2.3.4a sweep enforces the mirror-fact rule (a comment must not restate a fact the code beside it already carries) and the restatement rule (a fact in one added or changed comment is not restated in another).
- **Updating `CLAUDE.md`? Use `/claude-md-management:revise-claude-md` (targeted additions) or `/claude-md-management:claude-md-improver` (full audit) — never hand-edit without running at least one.**
- **Autonomous `/devflow:implement` runs make a *required* `CLAUDE.md` edit directly — carve-out to the rule above (issue #366).** Any `CLAUDE.md` edit an autonomous PRFlow run is *required* to make — whether by a Phase-3 review finding **or by the issue's own acceptance criteria** — is made **directly by the orchestrator**, citing this carve-out and recording it in the workpad, **never** by invoking `revise-claude-md`/`claude-md-improver` mid-run, because a nested interactive skill runs as a tail call and stalls the run. Interactive and human sessions still use those skills per the bullet above, and other interactive skills a run is required to invoke are dispatched into an **Agent-tool subagent** instead (issue #362). This bullet is the `CLAUDE.md` half of a coupled pair — its mirror is the `CLAUDE.md` edit carve-out in `skills/implement/SKILL.md`; edit both together.
- **Placement rule — the runtime test decides the surface, and it runs FIRST (single source; issue #1352).** A rule that governs **how a PRFlow command behaves when it runs** lives in that command's shipped `skills/**` body, whichever tier or command it binds and whether or not it is command-specific. `CLAUDE.md` and `.prflow/prompt-extensions/**` are both repo-local and are installed into no consumer checkout, so a runtime rule placed in either binds this repository's own runs and silently exempts every installed copy — the failure is invisible, because the rule still reads as satisfied here. Only once a rule has failed that test — it governs how this repository is *developed*, not how a command runs — does the `CLAUDE.md`-vs-extension split below apply. A rule that is **not command-specific** — including any rule scoped by *tier* (local/interactive, cloud-implement, cloud-review) rather than by command — lives in `CLAUDE.md` in one copy and appears in no extension. A rule that applies **only to one command's runs** lives in that command's extension and not in `CLAUDE.md`. Nothing appears in both. **Arm one means *not command-specific*, not *universally applicable*:** a rule need not apply to every command to belong in `CLAUDE.md` — it need only not be tied to a single one; the consequence is that tier-scoped and cross-command content concentrates in `CLAUDE.md`, the reliably-loaded one of the two repo-local surfaces, and `CLAUDE.md` is the canonical copy when the two surfaces disagree. Permitted exceptions — a coupled mirror a test pins identical, a non-authoritative `CLAUDE.md` summary paired with a canonical page, a command-specific *application* of a general rule, or a vendored consumer-shipped body — stay under the coupled-invariant discipline above rather than being duplications to remove.
- **Retiring duplicate-prose pins:** an existence-only pin whose census row reads `counted_occurrences >= 2` is removed only together with at least one copy; one reading `< 2` **and** adjudicated into a prose bucket may be removed on its own (issue #876) — every other case, and an absent row, retains. See `CONTRIBUTING.md` under **Retiring existence-only pins** for the canonical ordered arms, and for whether the prose-bucketed arm currently selects — a prose-bucketed population exists only between a re-adjudication and the sweep it authorizes, so a copy of that state here would rot on the next sweep.
- **Editing any skill file (`SKILL.md`)? ALWAYS invoke the `writing-skills` skill first** (`superpowers:writing-skills`) and follow its RED/GREEN discipline — never hand-edit a `SKILL.md` body directly. The skill enforces the verify-before-deploy loop that keeps a skill's triggering and behavior intact. **Autonomous `/devflow:implement` runs satisfy this mandate differently:** they never invoke it through the Skill tool mid-phase, since that tail call would stall the run, so the implement prompt extension's "Prompt-surface edit routing" rule routes each prompt-surface edit through a context-isolated Agent-tool subagent and records a `Writing-skills evidence:` marker in the workpad per returning subagent. Interactive and human sessions keep invoking the skill directly **and record a `Writing-skills evidence:` line in the PR description**, the review gate's discharge surface for human PRs.
- **The writing-skills marker has a stated shape (issue #1171):** it carries a disposition slot for each of the skill's named steps — `skill-loaded`, `guidance-applied`, `pressure-scenario`, `micro-tests` — each written `=yes` or `=no` with a one-clause reason, so a step that was not performed is *recorded* rather than inferred from silence. **`no` is a permitted, fully discharging value on every slot:** the gate asks for a stated disposition, never a particular one, and never demands the subagent pressure-scenario cycle. A slot whose disposition is missing is **undischarged**, not compliant (*unknown is not zero*, applied to attestation), and the remedy is to restate the marker rather than perform the step. Canonical statement of the slots: the implement extension's evidence contract (producer) and the two review extensions' byte-identical gate (consumer) — this summary is non-authoritative, and this bullet and that routing rule are a coupled pair edited together.
- **A dispatched Agent-tool subagent works in the orchestrator's own checkout, so confirm the tree is clean, commit what is not, and only then dispatch (issue #1254)** — on every tier, and from every command that dispatches into its checkout, the docs pass, the fix loop and the create-issue audit alike. Unless the runner hands the subagent a working copy of its own it reads and writes the same files the orchestrator has open, and a version-control command it runs inside its own RED/GREEN cycle is scoped to a path rather than to that subagent's edit, so it discards whatever the orchestrator left uncommitted. A runner-provided separate working copy is a stronger way to meet the same obligation, never the obligation itself: when such isolation is unavailable — and equally when whether the runner provides it is unestablished — commit first, then dispatch, and the routing still runs. When the tree state **cannot be established**, establish it (`git status --porcelain`) before dispatching at all. When the run holds work it must deliberately *not* commit — a Phase 2.1.5 proof edit, which `scripts/phase2-durability-checkpoint.sh` keeps out of history by ordering — park that work under a handle you record and restore it after the helper returns, or dispatch into a working copy of the helper's own; with neither available, **do not dispatch** and record `Blocked` naming the uncommittable work.
- **Helper cutover deletes the superseded prose — same change.** When an executable helper becomes the sole tested owner of a workflow decision on every path that previously consumed the prose, that same change removes the superseded mandatory prose, the duplicated branch/enum mirrors, and the obsolete prose pins, re-anchoring each removed pin's guarded regression to a helper-behavior test. Policy, human decision points, invocation contracts and essential stop conditions stay in the skill; rare-path explanation moves to progressively loaded references, and operative decision logic never does. Removing decision-owning mandatory prose whose decision has no sole tested owner is unauthorized.
- **Instruction-plus-consequence prose rule (skill and phase files, `CLAUDE.md`, and `.prflow/prompt-extensions/**`).** In any of those files, each instruction carries the instruction, at most one sentence naming what breaks if it is skipped, and a pointer only to an artifact that ships with the plugin. Prose that pre-empts a reviewer's misreading, and maintainer notes directing no agent action, belong in the issue and in git history — not in the file an agent executes.
- **Marketing/positioning copy** (`README.md`, `docs/internal/DEVFLOW_SYSTEM_OVERVIEW.md`) leads with the wedge — *out-of-the-box agentic coding works on pet projects but can't complete a real ticket in a large production codebase; PRFlow makes it ship*. Honor the honest-claims guardrails (review-ready, **not** auto-merged; shadow review **narrows, never closes** the gap). §21 is the messaging source of truth.
- Don't push to `main` from an agent; the classifier blocks `git push origin main`. Inside `/devflow:implement` & `/devflow:review-and-fix` there is standing permission to auto-commit+push to the *feature* branch.
- **A local-tier classifier denial refuses a command *form*, never the work — fix the form, and never downgrade the conclusion.** The classifier routinely denies `bash <path>`, `shellcheck`, `ruff`, and helpers invoked by path; it is a **structural harness boundary**, since an agent is barred from writing `.claude/` to widen its own allowlist, so the run cannot self-grant and the remedy is operator-side. Work a denial in order rather than skipping to the last rung: retry through the documented authorized form — a helper via `python3 <path>` (a local-tier fallback only; the cloud matcher denies that interpreter head, #789), the workpad via the invocation ladder in `skills/implement/SKILL.md` rather than a hand-written comment, and **the suite as a direct leading token (`lib/test/run.sh`), which is never one of these fallbacks** — a wrapper denial is a reason to fix the invocation form for the focused runs you still want, never what authorizes reading CI, whose rung-1 role as this tier's whole-suite completion gate (issue #1607) is unchanged by any denial — *evidence before assertion*.
- **Widening the allowlist is a human action.** A human adds the rules at user scope (`~/.claude/settings.json`) or runs the consent-gated `scripts/provision-auto-mode.sh`; never commit a `permissions.allow` block to this repo's `.claude/settings.json` from an agent, which the classifier denies and the cloud tier discards anyway. `scripts/provision-local-settings.sh` is **not** a way to widen it and is **not** consent-gated: it writes only `extraKnownMarketplaces` and `enabledPlugins`, immediately and ungated, when `/prflow:init` invokes it.
