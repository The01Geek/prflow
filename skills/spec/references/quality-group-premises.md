## Quality group — verified claims and external premises

Each obligation appears once, as its checklist row plus the rule text it carries.

- [ ] **Every relied-on third-party behavior went through the WebFetch → WebSearch → ask-the-user ladder with its source recorded, or became a Blocked question / flagged assumption.** The premise class is **relied-on third-party behavior** — every behavior of an external platform, API, or service the issue **relies on** (load-bearing for the Desired Behavior, an acceptance criterion, **or** the Implementation Notes Approach — not only an AC's mechanism): webhook / event delivery, trigger syntax, token scopes, endpoint behavior, response shapes, rate limits, and the like. Never assume it. Verify it with this **decided fallback ladder**, stopping at the first rung that resolves it: **(1)** the vendor's **official documentation via `WebFetch`** (not memory); **(2)** when the docs are not reachable, **`WebSearch`**; **(3)** when search is unavailable or fails, **ask the user to provide the documentation**. Record the fact and its source URL in `Technical Context` before you write the claim. **Ladder terminal arm — decided two ways.** When the ladder yields **no documentation** and **no working example in this codebase already proves** the behavior, the item becomes a `## 🚫 Blocked` entry phrased as a **direct question** — the exact vendor fact plus one line on why it blocks the work. When a **working in-codebase example does prove** the behavior but documentation is still unavailable, write the claim inline as an explicitly flagged `— assumption, confirm before implementing` line **citing that example**, not a Blocked entry. Treat an empty or inconclusive ladder result as **unverified**, never as silent confirmation. Verification covers **load-bearing** premises only, so an **incidental third-party mention** stays light and triggers none, and drafting is never blocked in a data-less authoring context.
- [ ] **Every "Verified:" bullet carries a self-contained re-derivation handle — the repository path in backticks plus the sentence quoted verbatim from it.** Write a bolded `**Verified:**` label, the repository path in backticks, and a double-quoted sentence of at least eight characters copied verbatim from that file (the recognized quotation used by the handle-repair steps). The run bootstrap's canonical write runs `scripts/check-verified-premises.py` over the assembled draft; inspect its `handle=` and `ungraded_claim=` report to check the handles and catch verification claims in ungraded shapes. An implementing run re-checks the filed issue with the same helper. Two forms the helper cannot grade stay prose, never `Verified:` bullets: an **externally verified fact** uses `Per <URL>, checked <YYYY-MM-DD>: <fact>` (the helper makes no network call); a **documentation-absence claim** names the search performed and its empty result (the helper has no negation). A `Verified:` premise asserts a **present-tense fact about the current tree**; a claim about the world *after* the change is written as an acceptance criterion, not a premise.
- [ ] **A premise verified as "the code does X" was read with its enclosing gates/conditionals and their defaults on the path to X, and any claim holding only under a non-default configuration states that precondition inside the claim.** Confirming that the code doing X exists and does X is not complete until you have read the **enclosing gates, conditionals, and their defaults** on the path that reaches X. When X is one clause of a multi-clause rule or one step of an ordered procedure, also read each other clause of that rule and the steps whose order the claim depends on; the `Verified:` bullet quotes the clause that makes the claim true and names each other clause or step it read; a sibling read that is denied, empty, partial or inconclusive leaves the premise unverified and out of the `Verified:` bullets. This discipline runs **twice**: at drafting time, and again in Step 3.5's self-steelman, which re-applies it to the *assembled* draft (under Step 3.5's definition of verified) before the user sees it.
- [ ] **A "Verified:" premise asserting what a data value *means* — whether it is an on/off pair, the wider set of states it can hold, which values an enumeration admits, whether it can be null, or what units it carries — is grounded in a code site that reads the value and branches on it, and is written only after searching for a wider domain than the claim admits.** A definition site alone — a schema column, a field declaration, a form binding — is consistent with such a claim without establishing it; the site that establishes a value's meaning is the code that reads the value and acts on its states, so ground the bullet there rather than at a definition site. Before writing the claim, read the sites that consume the value and confirm none distinguishes more states than the claim admits — observing a narrow value at one site does not verify a narrow domain, and a consuming site that establishes a wider domain withholds the claim.
