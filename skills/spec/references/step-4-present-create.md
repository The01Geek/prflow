### Step 4: Review with the user, then create

Sub-steps: 1 present the draft (saved-file path by default; body in chat on request) · 2 write the draft file · 3 render the audit summary line and disclosures · 3a the combined decision question · 4 iterate on feedback · 5 create (5a label, 5b dependencies, 5c investigation record) · 6 the single post-creation pause (assignment + gated implement offer).

Every pre-creation question this step asks is 3a's one combined decision question — one question per presentation, re-asked whole only where 3a says so. Nothing is asked before the draft has been presented (its saved-file path at sub-step 3, or the body on a forced-render arm), and nothing that gates creation is asked after `record-creation-epoch` binds it; sub-step 6's post-creation pause gates nothing.

**The issue is never created until the user has seen the draft as presented — its saved-file path, or the body printed on request — and explicitly approved it.** This gate is **unconditional** — no matter how thoroughly Step 2 resolved every decision, and no matter what the user said earlier. A rough user story is not approval of the assembled ticket.

**Presentation gate (before the draft is shown).** Clear these four in order. Each blocks presentation only; none blocks creation.

- **Consume the clean Steelman projection.** Re-read the latest Steelman pass and `.prflow/tmp/spec/<slug>/steelman-projection-<slug>.json`, require matching pass numbers, then run `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/run-jq.sh -e -f "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../lib/projection-gate.jq ".prflow/tmp/spec/<slug>/steelman-projection-<slug>.json"`. It restates `references/step-3-5-steelman.md`'s entry-confirmation contract (item 9) deliberately: a Step 4 entry need not hold that reference. Missing, stale, wrong-typed, inconsistent, or unmatched state stops presentation and returns to Step 3.5's revise-and-re-gate path, **at most once per presentation attempt**: a second failure is reported in chat and presentation proceeds with the projection state named unestablished. The read-only degraded arm is eligible only when its current-turn inline state is `represented` with an empty unmatched array. Nonempty ACs or a clean Step 3.6 verdict never substitute for this check.
- **Confirm the run bootstrap ran.** This run holds a minted nonce and a bound draft root (`query-draft-binding` answers a real absolute root). If neither exists, stop and run the bootstrap now before presenting. This gate re-enters the run bootstrap and never an audit round; the Step 4 working-file listing no longer names the audit artifact — confirming it is this gate's own job below, not the listing's.
- **Read what the bootstrap's two Step 3.5 gates left, rather than asserting they ran.** The verified-premise check and the acceptance-criteria parseability gate execute at the bootstrap canonical write (`references/step-3-6-audit-dispatch.md`), and what this run carries from them is the only evidence available here: an established `acceptance_criteria` array, or the in-chat breadcrumb naming the failure kind. Carrying neither, the count marker renders its unavailable token (sub-step 3) — never a claim that the gates ran.
- **Confirm the audit artifact only when a round was opened.** A run that has elected no audit round has no audit artifact, and the gate admits it — it never re-enters Step 3.6 to dispatch a round the user has not been asked about. Only when this run has elected and opened a round is `.prflow/tmp/spec/<slug>/issue-audit-<slug>.md` expected — then confirm it is present and holds this run's audit (the Step 3.6 write deletes any same-slug leftover first). If any `.prflow/tmp/` write or delete was refused earlier in this run, the on-disk artifact can only be a stale leftover: distrust it and rely solely on the visible inline-in-chat audit block re-posted this turn, per `references/fallback-read-only-sandbox.md` — the run-state condition, not a local write failure, is what selects that fallback here.

**The provenance signature is already in the body — do not append it again here.** The run bootstrap (`references/step-3-6-audit-shared.md`) appended the shared `/prflow:spec` provenance line as the body's last line before its first canonical draft write, so it is already inside the bytes shown and written here and posted as the created issue. On a sub-step 4 revision, keep it as the body's last line — re-appending it only if the regenerated body no longer carries it — so exactly one copy survives every re-presentation.

1. **Present the draft — saved-file path by default, body in chat only on request.** The saved draft file (sub-step 2) is the default presentation and its path is shown at sub-step 3; the full body is printed in chat only when the user chooses *print the full draft in chat* at 3a, or on a forced-render arm — a write-failed run, a `bound=none` run, or a non-interactive run — each of which prints the body before 3a's question and offers no print answer. **When you do print it** (on request or on a forced-render arm), show the complete rendered issue in chat: post the exact title and the full body — every section, verbatim, as Markdown — directly in your message. Do not summarize, abridge, or describe it. Do not use the runner's user-question tool (`AskUserQuestion` or its equivalent) to stand in for showing the body — such tools truncate.
2. Also write the draft to a file for easy review — at the MAIN repo root. Reuse the run's kebab-case `<slug>`: Step 1 binds it, and this is the only site that derives one instead. Read it from turn-one context, else resolve it through the run-directory-registry slug-resolve fence stated once in the skill root's *Runner setup* section, following that section's adopt / ambiguous-candidate (`--adopt-slug`) / derive-from-title handling.

   Create the run's scratch directory under the main working-tree root with the bundled cleanup helper — it resolves the main root itself and creates `<root>/.prflow/tmp/spec/<slug>/`, printing the roots so no fence captures a command's output:
   ```bash
   "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/cleanup-spec-run.sh --ensure-run-dir --slug <slug> --resolve main-root
   ```
   Read the printed `main_root=<absolute path>` and `run_dir=<absolute path>` lines from the tool result and transcribe those literal paths into the write below — never a captured shell variable. A `run_dir=none reason=<word>` line (a read-only sandbox or an uncreatable directory) takes the write-failed forced-render arm (sub-step 1) exactly as a failed `mkdir -p` did.

   Write the rendered title + body to the absolute path `<run_dir>/issue-draft-<slug>.md` (the `run_dir=` value printed above), with the title as a top `# ` heading. Perform this write through the *Staged canonical-draft write* shared procedure in `references/step-3-6-audit-shared.md` — load that file per the *Reference routing* rules when this entry does not already hold it (a failed load takes that reference's own degraded behavior, per those rules). The procedure records no revision, so it runs the stage → apply → verify steps, and its landed re-check compares the canonical file against this write's own in-turn `--expect-digest`. Use the main root, not the cwd.

   Bind the draft root once, then reuse it — bind if not already bound. The binding is recorded by the first landed canonical-draft write of the run, normally Step 3.6's pre-dispatch write. Do not assume what that site did — detect the case here: read `query-draft-binding "<slug>" --nonce "<nonce>"` and branch as Step 3.6's binding procedure specifies — already-bound (skip, take the `bound=` root); `bound=none` with no `reason=` (run Step 3.6's `record-draft-binding … --tier main-root` fence here; it is query-first and idempotent, so `binding-already-recorded` is the benign expected outcome); `reason=foreign-nonce` (the foreign-nonce arm of `references/fallback-draft-write-recovery.md`, loaded per `references/degradation-routing.md` — surface the drift, never the quiet unbound arm, and never compose a path); and a query that returns no answer at all (state owner unavailable, or the invocation refused) — attempt no bind, and treat the run as legitimately unbound. An unbound run is legal and must stay safe: `none` is a decided token, not a path, so never compose a path from it — fall back to the `run_dir=`/`main_root=` values the `--ensure-run-dir` line printed above for this write and follow the `bound=none` display arm in sub-step 3.

   Every later write site (a Step 3.6 re-dispatch write, the sub-step 4 overwrite, and the sub-step 5c record write) runs in a later turn, so it takes the bound root from `query-draft-binding "<slug>" --nonce "<nonce>"`'s `bound=` field — never context recall, never a second `--ensure-run-dir` main-root resolution while a binding exists; `<bound-root>` in the sub-step 3 display note is that same root. The presentation write above is the exception: same turn, root already in hand. **When the binding read reported a bare `bound=none` (no `reason=`), the run is legitimately unbound: re-run the sub-step 2 `--ensure-run-dir --slug <slug> --resolve main-root` line for *this* turn and write under the `run_dir=`/`main_root=` it prints** — never compose a relative `none/…` path from the token, and never reach for a root printed in an earlier turn. Take the `bound=none` display arm in sub-step 3 alongside it. On the file arm, forward the exact absolute canonical path to `record-dispatch --write-path <that path>`, which the state owner refuses with `write-path-mismatch` on divergence.

   Keep this one `<slug>` throughout, reusing that exact absolute path from then on. On an embed/inline-arm epoch this saved file is not the source the issue is created from; on a file-arm epoch it *is* the posting source — but only through the gated `emit-body` emitter (sub-step 5), never by passing the path to `--body-file <path>` directly. If the write fails (read-only main root / sandbox), note it briefly, print the full body in chat (the forced-render arm, sub-step 1), and continue without showing a path.

3. Render the audit summary line and disclosures — ask nothing here. Every pre-creation question belongs to 3a's combined decision question, the confirm/edit one included. **Every confirmation message has the same layout and does not contain the draft body**: the one-line Step 3.6 audit summary, then (when recorded) the per-finding disclosure block, then the investigation record, then the draft-save-location note (the absolute `<bound-root>/.prflow/tmp/spec/<slug>/issue-draft-<slug>.md` path from sub-step 2), and only then 3a's combined question. On a forced-render arm (sub-step 1) the full rendered body is printed above that layout, since there is no saved-file path to read instead.

   Per-finding disclosure block. A run that opened no audit round graded nothing and skips this block entirely — `query-adjudication-records` requires a `--round`, and there is none. On a run that opened a round, read `query-adjudication-records "<slug>" --nonce "<nonce>" --round "<round>"`; when it returns records rather than `records=none`, render each advisory and invalid finding's `summary`, `rationale`, `impact_class` tag, and the auditor's own `auditor_block` beside the grader's restatement, then report that rendering exactly as the calibration paragraph of `references/step-3-6-audit-adjudication.md` states. The audit summary line's own class counts stay unchanged.

   The summary line is one of the root's non-degradable invariants: it renders on every arm and every round count. Do not assemble its fields from recollection. The last state-owner call this sub-step makes — `query-final-byte` below — prints a `summary-block` line carrying the compact fixed `query-summary` subset the line renders: findings count, revisions applied, verdict, rounds run, whether a consumer `## Audit dimensions` section was appended, `degraded`/`user_declined`/`cap_reached`, any embed markers, `adjudicated_verdict` with the per-actionability-class counts (`must_revise`/`advisory`/`invalid`), `unresolved_must_revise`, `effective_unresolved`, `convergence_basis`, the `steering`/`steering_reason` pair, and the trailing `attestation=<match|mismatch|attestation-unavailable|none>` (`none` = before any creation attempt). The block also carries the structural `state` and `scoped_round` fields the summary line does not render — the tool's `--help` enumerates the block's full field set. Read the line's fields from that block rather than a standalone `query-summary` — its recovery instrument, should the block be lost to a context compaction (`query-summary "<slug>" --nonce "<nonce>" --draft-file "<…>"`).

`query-final-byte` also prints the final-byte fields the line names — `final_byte_reason` among them, which the summary block does not carry — so it is both the source of that block and the one gate read this sub-step makes, ahead of sub-step 3a's:

```bash
python3 "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/issue-audit-state.py query-final-byte "<slug>" --nonce "<nonce>" --draft-file "<absolute issue-draft-<slug>.md path>"
```

3a re-reads it there for its own offer decision.

#### Markers the summary line must carry

Steering. When `steering` is anything but `established`, the line carries a dedicated skill-composed marker naming it — `audit independence unestablished (<steering_reason>)` — rendered alongside whatever other skill-composed markers this line carries and distinct from the reserved `degraded` token. It never blocks filing. An `established` round is never described as provably steering-free.

Coverage and adjudication counts. The line reports the bundle's coverage (`axes evidenced, axes marked N/A, axes unestablished`), the post-adjudication counts by actionability class, labelled with the whole-draft round they describe (`counts_round`), the unresolved must-revise findings attributable to an axis on the effective list as frozen at that round's close, and — distinctly, never collapsed onto it — the run-wide effective unresolved count after every post-close resolution, reopen, invalidation and supersession. A round whose actionability or axis attribution could not be established renders `unestablished` rather than a number.

Final-byte coverage. The line carries the final-byte coverage value on every dispatch arm and every round count — the degraded inline arm included — as `final bytes audited` on `covered`, `final bytes NOT audited (<final_byte_reason>)` on `uncovered`, and `final-byte coverage unestablished (<final_byte_reason>)` on `unestablished`; when `final_byte_exhausted=yes`, append `— final-byte passes exhausted`. Read `<final_byte_reason>` from this sub-step's own `query-final-byte` line. A recorded `attestation=match` never stands in for that phrase.

Convergence basis. When `convergence_basis` names a resolution basis, the line additionally carries the phrase `converged via self-verified resolution` — on the stale variant `converged via self-verified resolution (stale — later revisions unverified)`.

Criterion count. The line also carries the criterion count as a skill-composed marker — `<n> acceptance criteria`. It is the length of the `acceptance_criteria` array returned by the `python3 … scripts/parse-acs.py --format json` invocation the run already performs at the run bootstrap's canonical write (which runs regardless of whether an audit round is elected); perform no second parse, and compose the marker in the skill rather than reading it from `query-summary`. It is reported, never enforced.

The number renders only when this run holds an established `acceptance_criteria` array from its own gate invocation; its absence — however it arose — renders a token instead, and a hand count is never substituted. Render `acceptance criteria count unavailable (unreadable item shape)` when the invocation reported `acceptance_criteria_unreadable`, and `acceptance criteria count unavailable` on every other absence. A `state-owner unavailable` fallback entered *after* the run bootstrap's canonical write still carries the parsed array and renders the number normally; only one entered *before* it never reached the gate site. Never count the checkbox rows by eye.

For an exhausted Acceptance Criteria rewrite disclosure, see `references/fallback-step4-exhausted-ac-election.md` per `references/degradation-routing.md`.

The count is as of the bytes that gate invocation read; later revisions are not re-counted. The gate is single-site by design, so a draft that changes across audit rounds or a Step 4 overwrite still renders the first landed canonical draft's count. Carry that residual — `<n> acceptance criteria (as of the first landed canonical draft; later revisions not re-counted)` — whenever any revision landed after that invocation.

#### Criterion-disposition confirmation (report-only, every run)

Before approval is asked, confirm the omit/merge/add disposition record (`references/issue-template.md`'s Acceptance Criteria contract) against the criteria the draft actually carries. Drive the check from the criteria set the rendered draft carries, not a fixed slice of the artifact, so every criterion the draft carries is checked however long the run; for each, look for its disposition line in the `## Criterion disposition record` section of `.prflow/tmp/spec/<slug>/issue-derivation-<slug>.md`. Name, as a skill-composed disclosure beside the criterion-count marker, any added criterion the draft carries whose disposition line the record does not show, marking it **undischarged** — a disposition line the read does not reach is reported undischarged, never silently passed — and when the record cannot be read at all — unreadable, absent, or, on the read-only arm, only an inline stand-in block posted per `references/fallback-read-only-sandbox.md` — read that inline block where one exists, else report the record **unestablished** rather than clean; render nothing when every added criterion the draft carries shows a disposition line. This confirmation sits on the presentation path because a run can add a criterion where a Step 3.6-sited reader would miss it: a run that elects no audit round never enters Step 3.6, and a criterion added while an audit round is adjudicated is added after that step's entry gate has run — the presentation write is the step both those cases still pass through. Naming is all it does — it blocks neither presentation nor creation, and it re-runs on every re-presentation (a sub-step 4 revision returns here).

#### Rendering the line and the draft-path note

Render them as one line (e.g. *"Fresh-context audit: 2 findings, 1 revision applied, VERDICT: FILE, 2 rounds (no consumer audit dimensions), 14 acceptance criteria; bundle: 5 axes evidenced, 2 N/A, 0 unestablished; adjudication (round 1, whole draft): 1 must-revise, 1 advisory, 0 invalid, 1 unresolved at close, 0 effective; body's final bytes audited; converged via self-verified resolution."*), carrying each flag the query reports: the word "degraded" when it reports degraded, the phrase `user declined further audit` when it reports a decline, the ceiling when it reports the cap, and the embed marker when it names one. On the `state-owner unavailable` fallback — where the query itself is what failed — the line carries that marker instead and is composed in-chat; it still renders. Label the class counts with the whole-draft round they describe, read from the summary block's `counts_round`: render them as `adjudication (round <counts_round>, whole draft): <must_revise> must-revise, <advisory> advisory, <invalid> invalid, <unresolved_must_revise> unresolved at close, <effective_unresolved> effective`. When `scoped_round` is not `none`, add the clause `targeted round <scoped_round> ran after it and is not counted in those class counts` when `scoped_round` is greater than `counts_round`, and the clause `targeted round <scoped_round> ran before it and is not counted in those class counts` otherwise. When `counts_round` is `none` — no whole-draft round has completed, so the class counts are all `none` — render `adjudication (no whole-draft round yet): <must_revise> must-revise, <advisory> advisory, <invalid> invalid, <unresolved_must_revise> unresolved at close, <effective_unresolved> effective` and omit the targeted-round comparison clause, which has no whole-draft round to compare `scoped_round` against.

Display the absolute path built from the bound root (`<bound-root>/.prflow/tmp/spec/<slug>/issue-draft-<slug>.md`, `<bound-root>` read back from `query-draft-binding`'s `bound=` field), never `$MAIN_ROOT` from context recall and never a bare relative `.prflow/tmp/…` string. Render the note as its own line — e.g. *"Draft also saved to `<bound-root>/.prflow/tmp/spec/<slug>/issue-draft-<slug>.md` for review."* — after the audit summary and disclosures, after which sub-step 3a's combined decision question resolves the pre-approval gates and asks for approval. If the sub-step 2 write failed, omit the note entirely rather than showing a path to a nonexistent file (and print the full body per the forced-render arm, sub-step 1).

For a `bound=none` unbound run's draft-path note, see `references/fallback-step4-bound-none-display.md` per `references/degradation-routing.md`.

Display the investigation record alongside the brief — on EVERY arm, including the withheld one. After the audit summary line, render the investigation-record bucket (the content `references/issue-template.md`'s routing rule sorted out of the brief) as its own clearly-labeled inline block in chat. It renders even when `spec.investigation_record_enabled` is `false`. This is display, not attestation: `emit-body`'s digest covers only the bound draft file. When the bucket is empty, say so plainly rather than rendering an empty block.

Scope the summary line's final-byte phrase to the body (e.g. *"body's final bytes audited"*), and state beside it that the investigation record is not audited.

   Exactly one of *Create it as-is* / *File anyway* is present, so filing is never blocked on any arm. Neither is keyed on `query-eligibility`: a run that completed no round answers `no-verdict-round` until the offered round's decline is recorded (the override ground), and sub-step 5 re-queries after that record. A draft-only request never reaches this path.

   **Offer grounds, in precedence order, each with its channel.** Offer at most one round per question: the first ground that holds names the option; the others that hold are disclosed in the question text, not re-asked. No ground names the audit-round option while the boundary read's `offer` component is `offer_withheld=yes` (the option-row gate above): the last REVISE round's findings must be revised first.
   1. Final-byte (`final_byte_trigger=hold`) — accept and decline both go through `record-final-byte-offer "<slug>" --nonce "<nonce>" --draft-file "<…>"`, `--accepted` on accept; never a `user-decline` override. Both arms spend the dedicated slot (outside the user-round cap, so offerable at the cap and under `cap-reached`) for these exact bytes; a recorded revision that changes the digest re-arms it, bounded by the per-run cap. A run that completed no round has coverage `unestablished`, on which this ground never holds.
   2. Steering (`query-eligibility` answers `reason=steering-unestablished`) — an unsteered re-dispatch: `record-offer` (`--accepted` on accept); decline `record-override --kind user-decline --surface t1t2-boundary`.
   3. Boundary (`query-boundary` reports `t1=`, `t2=`, `coverage=` or `calibration=` at `hold`, or an `unledgered_revise` round) — conducted as `references/fallback-audit-boundary-offer.md` states, on the same channels as 2.
   4. Post-revision (this presentation follows a sub-step 4 revision) — `record-offer` (`--accepted` on accept); decline `record-override --kind user-decline --surface step4-offer` (`--draft-file`-bound on a file-arm epoch), which is what lets `query-eligibility --mode approve` answer `eligible=yes` for still-unaudited bytes.
   5. Discovery (no round elected yet, user-round cap unspent) — the same channels as 4. This is what funds the first round: the state owner opens no round the user did not elect, and a user satisfied with what they read pays no audit rounds.

   **The question text tells the user how the audit stands.** Read it from sub-step 3's `summary-block`, never recollection. Before the first round: that the draft is unaudited. After a completed round: the latest whole-draft round's verdict, its findings by class (`must_revise`/`advisory`/`invalid`), the unresolved must-revise count, and the revisions applied since — plus, on grounds 1–2, one sentence saying why another round is offered (the current bytes were never audited; the latest completed round's steering was not established).

   **A reply outside the options** is routed by what it asks for: a change request → *Change something first*; an unambiguous approval of the draft as shown → *Create it as-is*, or *File anyway* when that is the option present and the reply names the refusal; a decline of the offered round with nothing else → record the decline on its channel and re-ask. Anything else, and a silent non-response, is not an answer: re-ask this question in the final chat message and stop (Step 2's silent-non-response rule) — never dispatch, create, or proceed on silence.

   **A non-interactive run self-answers this question:** it declines any offered round on that ground's decline channel, re-queries `query-eligibility --mode approve`, and elects *Create it as-is* on `eligible=yes`. When that re-query instead answers `eligible=no reason=unaudited-revision` — and only when no file-anyway ground holds, so *Create it as-is* is the option present — it records the same filing election the *Create it as-is* cell describes, `record-override --kind user-decline --surface step4-offer --draft-file <canonical>`, as its own election, re-queries, and elects *Create it as-is* on the resulting `eligible=yes`. Every other refusal, and any refusal on a run where a file-anyway ground holds, still stops the run paused reporting the refusal ground with no override recorded, since only a user can elect *File anyway*.

   For an accepted final-byte pass return, see `references/fallback-step4-final-byte-carveout.md` per `references/degradation-routing.md`.

4. **Iterate on feedback.** If the user requests any change, revise the draft, re-run the no-options gate (Step 3), then run **Revision-delta verification**, then **run Step 3.5 again against the complete post-verification draft before overwriting or offering approval**. Step 3.5 is deliberately last among the draft-mutating checks: it reruns the Desired-Behavior projection and replaces the structured Steelman projection state for the bytes that reach the overwrite; a newly added Desired Behavior obligation with no representing AC prevents the overwrite/approval path. Overwrite the canonical draft through the *Staged canonical-draft write* shared procedure in `references/step-3-6-audit-shared.md`, which names this site as one of its three: a revision write records the revision from the staged bytes, so `record-revision` takes `--stdin-digest` piped through the helper's `emit` mode there, and the state owner requires it whenever the latest recorded round dispatched on the file arm. Then run **Ledger maintenance after a revision** — record the revision with `record-revision --after-round <round>` in that staged form; when the per-finding verification confirmed at least one finding fixed, `record-resolution` naming those ids against the printed revision ordinal (cross-round when the fix clears an earlier round's entries), and when it confirmed none, record no resolution. A later-discovered regression uses `record-reopen`; a finding discovered misclassified uses `record-invalidate`, never `record-resolution`. Decide each against the `query-findings` read-back, never context recall. Ledger maintenance records state only; it must not edit the draft between this final projection and the overwrite.
