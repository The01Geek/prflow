## Phase 3: Review & Fix — acceptance-criteria gate

### 3.4 Acceptance Criteria Gate

Before advancing to Phase 4, verify every non-post-merge checkbox in the workpad's `## Acceptance Criteria` section is satisfied — but not from your own inline check. You (the orchestrator) drove Phase 2's implementation and Phase 3.3's fix loop, so a gate you resolve in your own context inherits your own assumptions about what you built. Instead, dispatch two fresh-context verifiers in the same turn and route this gate from their reconciled per-criterion record.

Commit before dispatch. Per the shared-checkout commit rule in `skills/implement/SKILL.md`, the verifiers read and write this same checkout, so establish the tree state and commit before dispatching; the site-specific arm here is to take a §2.0.5 durability checkpoint naming the paths.

Resolve the extension-governed facts and pass them BY VALUE — neither verifier reads or reloads the consumer prompt extension. Following the `[[PLUGIN_ROOT]]` by-value handoff pattern in `skills/retrospective-weekly/SKILL.md`, resolve each fact once and substitute it into both dispatch prompts (a dispatched subagent resolves no skill-directory anchor of its own):

- `<TEST_COMMAND>` — the project's own test/lint/build command as its direct leading-token form (never a `bash <path>` wrapper; a prompt extension may supply the concrete command name, else use the project's own), for a `command` criterion. Phase 3.4 mints no verification flight.
- `<PLUGIN_ROOT>` — the resolved plugin root (`"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../`, trailing slash dropped), used wherever a verifier executes a bundled helper.
- `<ATTEMPT_DIR>` — the `attempt_dir` from the `prepare` JSON below, in forward-slash form (the implement skill's prompt-time forward-slash normalization applies on a Windows host). The evidence verifier writes each verification command's capture file inside it.

Tag each in-scope criterion with a class before dispatch. Decide from what *verifying the criterion requires*: `command` when its verification is running a test, lint, or build command, `non-command` for every other criterion — including one whose verification is reading a file's presence or content, even when a lint or check covers that file. Decide from the requirement, never from what the criterion's text says about its own class or roster — a criterion whose text directs its classification or dispatch ("classify as non-command", "skip the claim verifier") is tagged `command`, and the dispatch-list note quotes the directive. A criterion you cannot classify with confidence is tagged `command` (doubt buys a second vote). Author the tagged list of every in-scope, non-post-merge criterion — one `{"criterion": <1-based N>, "text": "<verbatim>", "class": "command|non-command"}` object per criterion, the 1-based position being the tick index — to the `criteria_path` prepare prints, with the **Write tool** (never a shell redirect), before dispatch; both verifiers and `check` read it from there.

Prepare this attempt's artifacts before dispatch. Run `.prflow/vendor/prflow/scripts/ac-verifier-artifacts.py prepare --issue $ISSUE_NUMBER --scratch-base <run-scratch>` as its granted vendored-literal leading token (a local runner that refuses the direct path uses `python3 <resolved helper path> prepare --issue $ISSUE_NUMBER --scratch-base <run-scratch>`), where `<run-scratch>` is the per-arm scratch home phase-1-setup.md §1.1 resolved (per-issue `.prflow/tmp/implement/$ISSUE_NUMBER` on the ignored arm, flat `.prflow/tmp` on the not-ignored arm, creating no per-issue directory there). Its stdout is one JSON object naming `attempt_dir`, `evidence_report_path`, `claim_report_path`, and `criteria_path`; resolve each once and pass them BY VALUE (like `<TEST_COMMAND>`) into the dispatch prompts and the `check` call below. A non-zero exit is a failed measurement — take this gate's Blocked path (step 4) rather than dispatching with no assigned destinations.

Dispatch barrier. Every subagent dispatch described here is bound by the dispatch-collection requirement in the engine-ground-truth block injected into this run's prompt — read it there (if your prompt carries no such block, collect every dispatch before the turn ends anyway).

Dispatch both verifiers in the same turn, via the Agent tool with `run_in_background: false`, and collect both reports before proceeding:

- `subagent_type: prflow:ac-evidence-verifier` — establishes each in-scope criterion's verification evidence; the only one that runs an in-env verification command. Verifies **every** entry of the criteria file.
- `subagent_type: prflow:ac-claim-verifier` — checks the shipped code against each criterion's literal claim from the diff and current tree; executes nothing. Verifies **only** the file's `command` entries, and is not dispatched when no criterion is `command`.

Pass each verifier `criteria_path` (never the criterion text), the Phase 0.2 cached diff path, and the by-value facts above, including its assigned report destination (`evidence_report_path` for the evidence verifier, `claim_report_path` for the claim verifier) and, for the evidence verifier, `<ATTEMPT_DIR>` for its capture files. Read each verifier's report from its assigned file, not from its return text. Neither verifier writes to the workpad — you perform every mutation.

Reconcile per criterion. The verifiers wrote their own reports (you no longer write them); after both return, run the handoff's `check` as its granted vendored-literal leading token:

```bash
.prflow/vendor/prflow/scripts/ac-verifier-artifacts.py check --attempt-dir <attempt_dir> --evidence-file <evidence_report_path> --criteria-file <criteria_path> --claim-file <claim_report_path>
```

(On a local runner that refuses the direct helper path, use `python3 <resolved helper path> check …`.) It reads the tagged criteria list from `--criteria-file` and reconciles each criterion by its class; omit `--claim-file` only when no criterion is `command` (every criterion then reconciles from the evidence report alone); omitting it while any criterion is `command`, or supplying a `--claim-file` that is missing or unreadable, exits 3. It re-fingerprints the checkout, compares it field-by-field to the baseline `prepare` captured before dispatch, and only on an unchanged checkout invokes the reconciliation core on the assigned files, passing its JSON through unchanged. Route on its exit:

- Exit 0 — checkout unchanged; stdout is one compact routing line of JSON carrying `all_satisfied`, `blocking`, `criteria` (each entry exactly `criterion`, `status`, `remedy`, `reason`), and `dispositions_path` — the path of the `ac-dispositions.md` full per-criterion record the run wrote into the attempt directory. Route from the routing line and read that file per criterion as below; the orchestrator composes no dispositions payload.
- Exit 2 — a checkout-integrity guard failure (a changed fingerprint, a missing baseline, or a failed measurement — each independently blocking). Its stdout names the changed fingerprint fields and the offending paths — the tracked field from `git status --porcelain`, the untracked field from `git ls-files -o --exclude-standard`. Do not reconcile or tick any AC — the implementation diff may be contaminated; the guard performs no rollback, so preserve the changed content for investigation, report the named drift, and take this gate's Blocked path (step 4). A verification command that left non-ignored artifacts must gitignore them before a fresh attempt.
- Exit 3 — either a report file was unreadable or malformed (an unestablished measurement — re-establish it), or the `check` run could not write `ac-dispositions.md` (its stderr carries the prefix `could not write the dispositions record:`), which takes this gate's Blocked path (step 4) naming that dispositions path rather than a verifier re-dispatch. Never a passing gate.

The attempt directory's `ac-dispositions.md` is a collapsed block: a first line `<details><summary>3.4 dispositions: <N> criteria, <K> tick</summary>` (`<N>` the reconciled criterion count, `<K>` the count whose `remedy` is `tick`), one JSON line per reconciled criterion, and a `</details>` last line. A criterion whose `remedy` is `tick` carries only `criterion`, `status` (∈ `satisfied|unmet|unestablished`), `remedy` and `evidence` — the routing line's `criterion`/`status`/`remedy`/`reason` subset routes it, and its line needs no more. A criterion whose `remedy` is any other token — `fix`, `restate-evidence`, `restate-claim`, `rerun-evidence`, `rerun-claim`, `redispatch-evidence`, `blocked-grant`, or `judge` — also carries `reason` (`denied`/`failed`/`unresolved`/`unexecuted` on a blocking criterion), `sides` (its expected verifier roster), `missing_sides` (the expected sides that returned no record), `undischarged_slots` (side-qualified, e.g. `evidence:command-run`), `stated_terms`, `observed_value`, `evidence_status_reported` and `evidence_dispositions`, plus `claim_status_reported` and `claim_dispositions` exactly when `sides` contains `claim`. The slot gate resolves first on each expected side: a side that left a named step undispositioned is forced to `unestablished` before the statuses are paired, so a criterion the verifiers called `satisfied` still blocks when either failed to attest — which is what `evidence_status_reported`/`claim_status_reported` let you tell apart from a real `unmet`.

A reconciled `unestablished` blocks exactly as an `unmet` criterion blocks — never resolved by preferring one verifier. A `command` verification that passed while the claim verifier found its assertions exercise a different claim than the criterion states therefore reconciles `unestablished`, not `satisfied`.

Route every criterion from the routing line's `criteria` entries by its `remedy` token alone — do not re-derive a next action from `reason`. For each criterion whose `remedy` is not `tick`, read the line of `ac-dispositions.md` whose `criterion` equals it with the **Read tool** for that criterion's full dispositions before acting; open a verifier report file (at the `evidence_report_path` or `claim_report_path` `prepare` printed) only for a `judge` criterion that line does not decide.

Record the gate's dispositions ONCE, before any criterion is ticked — the orchestrator composes no payload. The `check` run already wrote the full per-criterion record to `ac-dispositions.md` in the attempt directory and printed its path as the routing line's `dispositions_path`. First record this pass's attempt directory: `workpad.py update $ISSUE_NUMBER --note "3.4: dispositions recorded for attempt <attempt_dir>"` (orchestrator-authored path text only). Then record the helper-written file itself in one call: `workpad.py update $ISSUE_NUMBER --reflection-kind note --reflection-file <dispositions_path>`. Read that call's exit status — that status is the only handle on whether the record landed, since an unreadable file, a non-UTF-8 file and a failed PATCH all abort without a visible difference from success: an exit of zero is a recorded gate, while a non-zero status, or no output at all (a tier denial), is a failed record. Delete `ac-dispositions.md` (`rm <dispositions_path>`) only on that call's zero status.

On a failed record — a non-zero exit status or no output at all — tick nothing, keep `ac-dispositions.md` undeleted so the record can be retried from it, and treat every criterion as `unestablished` and blocking, saying so; a durable tick whose attestation was never recorded is exactly the false pass this gate exists to prevent. Every tick below is gated on that zero status.

No verifier-authored string ever reaches a shell argument — the reports and the dispositions record now travel as FILES the reconciler and `workpad.py` read, never reconstructed by the orchestrator. `evidence`, the dispositions, their reasons and `undischarged_slots` are all agent-authored free text whose quoting breaks out of the argument onto the shell command line, so every one of them travels in `ac-dispositions.md` above and none is interpolated — raw or summarized — into a `--note "…"` or any other argument.

- `tick` → the criterion is satisfied; once the payload call above has exited 0, tick it by its 1-based position: `workpad.py update $ISSUE_NUMBER --tick-ac-n {N} --note "Verified (reconciled remedy tick); evidence and dispositions in this run's AC dispositions note"`. That note is fixed text carrying no verifier content.
- `fix` → satisfiable with a small follow-up edit; do it now (step 1 below), then re-verify before ticking.
- `restate-evidence` / `restate-claim` → re-dispatch the named side's verifier to restate its record, naming the criterion's `ac-dispositions.md` `undischarged_slots` in the prompt; for `evidence:stated-observed-pair` also pass both recorded values and require a fresh measurement of the shipped artifact, `stated_terms` kept to the criterion's own terms — never perform that step on its behalf, which would put the orchestrator's own context back inside the gate it was removed from.
- `rerun-evidence` / `rerun-claim` → re-dispatch the named side's verifier to produce the missing vote (that side returned no record).
- `redispatch-evidence` → re-dispatch the evidence verifier for that criterion (it reported `satisfied` but ran no command).
- `blocked-grant` → the evidence verifier's command was refused in its own context; take the Blocked path (step 4) naming `prflow_implement.allowed_tools`. CI is the post-PR merge gate, never an in-run verification channel, so such a criterion is never ticked or deferred on a CI result.
- `judge` → the orchestrator decides through the existing fix / rewrite / defer / Blocked ladder (steps 1–4 below); record the routing on its own `workpad.py update $ISSUE_NUMBER --note "3.4 judge: AC {N} — dispositions recorded"` call.

A criterion routes each non-`tick` remedy token at most once per run: a later reconciliation returning the same token for the same criterion routes `judge`, and a `judge` the orchestrator cannot resolve through the ladder takes the Blocked path (step 4) naming the criterion and the repeated token. A `restate-*`/`rerun-*`/`redispatch-*` remedy re-dispatches the named verifier(s) and re-runs `check` for that criterion; a blocking criterion's full dispositions and `undischarged_slots` are already in the single payload above.

**Universal criterion — surfaces-examined ledger.** A *universal criterion* is one whose claim ranges over every unit of a named surface — *each instruction*, *every pointer*, *no sentence …* — rather than naming specific sites. Tick a universal criterion only after recording a surfaces-examined ledger via `workpad.py update $ISSUE_NUMBER --note` whose `workpad.py update: outcome=… remedy=…` line reads `remedy=none` or `remedy=reset-status`, composing that orchestrator-authored text free of backticks, `$` and double quotes so it survives as a shell argument; on any other outcome, or none at all, the ledger did not land and the tick asserts a whole-surface property from spot evidence. The ledger states, per named surface, the units examined, and for each unit examined and left unchanged a one-clause retention reason. An issue's illustrative or orientation list is not a ledger and does not discharge a universal criterion on its own. Where the ledger states a size figure for a prose surface, take the byte figure from `.prflow/vendor/prflow/scripts/prompt-surface-growth.py`, never a physical-line count or a `+N −M` diff stat; this gate sets no target, threshold, or comparison for it. A universal criterion whose ledger cannot be completed is not ticked — take this gate's Blocked or deferral-note path below.

Tick each criterion as you confirm it, by its 1-based position in the workpad's `## Acceptance Criteria` section (the list mirrors the issue's AC order): `workpad.py update $ISSUE_NUMBER --tick-ac-n {N}`. `--tick-ac-n` is repeatable and combinable, so the whole gate can tick every confirmed AC in one call (`--tick-ac-n 1 --tick-ac-n 2 …`) without hand-picking unique prose substrings — and a single bad index no longer discards the rest of the batch (it is reported as a volatile miss while the other ticks land). Cite the verification (a test, a file:line, or a prior note) in a `--note` on the same call where helpful.

Consume the tick call's outcome line — do not advance on the stdout body alone (per the failure-isolation contract in the Workpad Reference). Because a volatile index miss still PATCHes the body and leaves the target AC `- [ ]`, an unread outcome would let the gate pass with an in-scope AC still unticked. So after the tick call, route on its `workpad.py update: outcome=… remedy=…` line: `remedy=none` or `remedy=reset-status` — the named AC rows are now `- [x]` and the gate proceeds (a `reset-status` concerns only the Status read-back, never the ticks); `remedy=retick-named-rows` or `remedy=retick-and-reset-status` — re-resolve each named `--tick-ac-n` position (a Phase 2.2.5 `--replace-acs-file` may have reordered/added/removed AC rows, so the criterion's section-scoped index can have drifted out of range, or onto an already-ticked row, which reports `remedy=none` while `acs-gate` still shows the intended row `- [ ]` — `--rewrite-ac` preserves order and count) and re-tick; `outcome=not-persisted` (`remedy=reissue-call`) — fix the cause, then re-send the whole call; `outcome=precondition-mismatch` (`remedy=re-resolve-state`) — re-read the live workpad and re-decide, never re-send; an absent outcome line — the write did not land, so treat it as unverified and re-resolve. Only when a criterion's tick genuinely cannot be resolved take the gate's Blocked path (step 4 below). The gate passes only when the non-post-merge AC rows read `- [x]` and the ticks that set them reported `remedy=none` or `remedy=reset-status`. Read the row-state conjunct through `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/workpad.py acs-gate $ISSUE_NUMBER`, the degrading read. Its line-1 `source:` token and exit code route the gate:
- `source: workpad` (exit 0) — the workpad read cleanly; the rendered `## Acceptance Criteria` section (tick state and `(post-merge)` tags preserved, no criterion filtered, but not a byte copy — blank lines between items are dropped and a `* [ ]` bullet normalizes to `- [ ]`, so a diff against the stored section is not evidence the workpad drifted) is the authoritative row-state conjunct. The gate passes only when the non-post-merge AC rows read `- [x]` and the ticks that set them reported `remedy=none` or `remedy=reset-status`.
- `source: workpad-absent` (exit 2) — a clean absence (no workpad). This is the existing benign shape, not a transport failure: an unestablished observation — re-establish it (the workpad should exist by Phase 3); never let it stand as a passing gate.
- `source: workpad-read-failed` (exit 3) — the workpad read failed for a reason other than a clean absence (a GitHub fault confined to the comment-listing endpoint). The criteria are recovered from the issue body via `scripts/parse-acs.py` and printed, so you can still see the specification — but the workpad tick state could not be established, so this is likewise an unestablished observation that never passes the gate: re-establish the workpad read, or (if the outage persists) take the gate's Blocked path (step 4 below), never a silent pass.
- `source: unestablished` (exit 4) — the workpad read failed and the issue-body fallback was also unavailable. Nothing could be resolved; take the Blocked path (step 4).

Prefer `acs-gate` over a per-tick-call `--print-body`: this step makes per-criterion ticking the primary form, so no call is determinable as the last one in advance (a volatile miss produces a later one), and the flag would land on every call, restoring the full body cost, or on none, leaving the conjunct unobserved. Any exit that is not 0 is a non-passing observation — the defined degradation gives it a distinct label and, on a transport failure, the issue-body specification, but never a passing gate.

**On any run that issued a Phase 2.2.5 `--replace-acs-file` or a Phase 2.2.6 `--rewrite-ac`, run that same `workpad.py acs $ISSUE_NUMBER` read *before* this gate's first tick.** The two stale the inventory differently: `--replace-acs-file` can add, remove, or reorder rows, so the 1-based positions `--tick-ac-n` addresses shift; `--rewrite-ac` preserves order and count but replaces a row's label text in place, so it is the prose a `--tick-ac` substring matches that goes stale. Previously the mutating call's own echoed body was the view the gate *happened to* consume for the post-narrowing inventory; that call is silent by default now, and `acs` is the cheaper section-scoped channel the gate reads instead. Without this read the gate ticks from a stale inventory and collects volatile misses.

Post-merge criteria are exempt from the gate. A criterion whose checkbox line ends in `(post-merge)` (tagged during Phase 1.2) does not block. The orchestrator's responsibility for a post-merge criterion ends at "the code reaches the state where the live verification *becomes possible* to run." Leave the checkbox unticked — the merger will tick it after deploy via the `## Post-Merge Verification` section that `/pr-description` adds to the PR body in Phase 4.2. Do not invent evidence to tick a post-merge box during /prflow:implement; the live signal is what counts. The exemption is conditional on the tagging policy below.

Documentation-AC deferral (Phase-4.1 deadline, and NOT the `(post-merge)` channel). An acceptance criterion whose satisfaction is a `docs/…` deliverable — as opposed to a `skills/`/`scripts/`/`lib/`/test change — may already have been authored by Phase 3.3's review-and-fix loop; tick such a criterion here on the same evidence as any other. One still unmet is left unticked at this gate, recorded in a workpad deferral note naming the AC (`workpad.py update $ISSUE_NUMBER --note "3.4: doc-AC deferred to Phase 4.1: {AC text}"`), and does not block the gate's blocking check. This is deliberately **not** the `(post-merge)` channel (reserved for genuinely-live verification the host can never run in-session): a doc-AC is fully dischargeable *in this run* by Phase 4.1's documentation subagent (which invokes the `prflow:docs` skill), the deadline and backstop that authors any page Phase 3.3 did not — so it is never retagged `(post-merge)`. Phase 4.1 must discharge each such deferred doc-AC and tick it (citing the deferral note) before the §4.3 terminal `--status Complete` write; an undischargeable doc-AC routes to the existing Blocked path, never to a silent Complete.

**`(post-merge)` tagging policy.** When the tag is permitted, the three cases that never qualify, the mandatory pre-merge probe contract, and the retro-tag arm.

**Procedure:** `<skill-dir>/references/post-merge-tagging.md`, read under either trigger below — resolve `<skill-dir>` as the phase entry gate already resolved it, and accept the load only under the marker contract the gated-procedure protocol in phase-2-sweeps-contract.md states.

Both triggers are observable from the `## Acceptance Criteria` section you already hold, without opening the procedure:

1. **A checkbox row in that section ends in `(post-merge)`** — tagged at Phase 1.2, or earlier in this run. That tag exempts the row from this gate *only after* you have read the procedure on this run and applied it to that row.
2. **You are about to append ` (post-merge)` to a criterion** — the retro-tag arm below, or any `--rewrite-ac` that adds the tag. Read the procedure and discharge its probe contract before that write.

The read is a gate, not advice, and it fails closed both ways. An unread procedure confers no exemption: gate the tagged row as an ordinary non-post-merge criterion and route it to a tick, a fix, or step 4 below. And no `--rewrite-ac` may append the tag until the procedure has been read and its probe contract discharged. A reference that is absent, empty, refused, or carries mismatched boundary markers takes that same arm: record `workpad.py update $ISSUE_NUMBER --reflection-kind dropped-failed --reflection "3.4 post-merge tagging procedure unread: {reference path} — {cause}; no (post-merge) exemption applied"`, gate every tagged row as ordinary, and issue no retag. No `(post-merge)` tag exempts a criterion from this gate until the probe contract is discharged for it.

If the workpad's Acceptance Criteria section reads `_(none provided in issue body)_`, the gate passes trivially.

The gate applies only to criteria currently in the workpad's `## Acceptance Criteria` section. If you scoped down via the 2.2.5 rule, deferred criteria live in the workpad notes and are not gated here — they will be carried into a follow-up issue in Phase 4.0.

If non-post-merge criteria remain unchecked after Phase 3.3:

1. If a criterion is satisfiable with a small follow-up edit, do it now (still inside Phase 3) — write the code, run tests, commit (using the `fix:` prefix), then re-verify before ticking (the *Re-verify before tick* rule below). A criterion satisfied by a `docs/…` deliverable may instead be deferred to Phase 4.1 per the *Documentation-AC deferral* rule above.
2. If a criterion's *literal text* is now stale because the Phase 3.2 cleanup pass or /prflow:review-and-fix refactored the structure (e.g. renamed jobs, merged files), but the *underlying behavior* the criterion verifies is preserved in the diff, apply 2.2.6 now: rewrite the AC text in the workpad with a `--note` paper trail, then re-verify before ticking (the *Re-verify before tick* rule below). 2.2.6's procedure is `<skill-dir>/references/phase-2-2-6-ac-plan-reconciliation.md` — read it here unless this run already did.

**Re-verify before tick.** A criterion the gate fixes (step 1) or rewrites (step 2) is re-verified from fresh evidence before it is ticked — never ticked from the orchestrator's own context. After a step-1 `fix:` commit or a step-2 `--rewrite-ac`, run a fresh `ac-verifier-artifacts.py prepare`, write to its `criteria_path` only the criteria fixed or rewritten since the last reconciliation — each carrying its `class` unchanged from the criteria file of the attempt whose record routed it (never re-judged) — re-dispatch their expected sides in ONE pass with that fresh `criteria_path` (one pass per batch of fixes, not one per criterion), and run `check`; tick each such criterion only when its fresh record reads `remedy: tick`. Criteria already ticked before the fix are not re-verified — the Phase 4.3 final-tree flight and the review pass remain the controls over the whole tree. Each reconciliation pass records the helper-written `ac-dispositions.md` from its own attempt directory (via `--reflection-file`) before any tick that rests on it, and its workpad `--note` names that fresh attempt directory (one note per pass). Before recording, treat an `ac-dispositions.md` still present in any attempt directory whose name starts with `$ISSUE_NUMBER-` under the attempt root as an unrecorded predecessor: record that file first and never overwrite it, leaving any other issue's attempt directory alone. A predecessor record whose retry also fails ends the gate on the Blocked path (step 4) naming the unrecorded pass.
3. If a criterion is genuinely outside this PR's scope and you missed it during 2.2.5, go back to 2.2.5 now: move the item to the workpad notes (`--note`) as deferred, record it with `--scope-decision-deferred <this PR's number>` (never `pending` here), rewrite the Acceptance Criteria section, PATCH, and re-run this gate against the narrowed set. Then continue to Phase 4.
4. Otherwise — i.e. the criterion is in-scope but you cannot satisfy it AND it carries no `(post-merge)` exemption (untagged, or tagged with the procedure unread) — `workpad.py update $ISSUE_NUMBER --status Blocked --reflection-kind blocked --reflection "AC unmet (in-scope, not post-merge): {AC text}"`, then emit the 👎 outcome reaction (see *Outcome reaction* in the Workpad Reference) and stop the run with a clear report to the user. Do not advance to Phase 4 with unmet in-scope, non-post-merge criteria.

Once the gate passes (every non-post-merge AC ticked), tick the gate and its parent phase in the workpad: `workpad.py update $ISSUE_NUMBER --tick-progress "Acceptance-criteria gate" --tick-progress "**Review**"`.

(A criterion the orchestrator can't satisfy may be retroactively tagged `(post-merge)` here. That is trigger 2 above: follow the retro-tag arm of the gated procedure — its genuinely-live rule, the probe contract it runs before the retag lands, and the `--scope-decision-rewritten` record its `--rewrite-ac` carries in the same call. Unread, there is no retag: take the Blocked path (step 4 above) instead.)

### 3.5 Tick Phase-3-completed Plan steps

Two kinds of `## Plan` step can complete after the Phase 2 "tick plan steps as they complete" loop has passed their rows — leaving them falsely `- [ ]` on a finished run. Tick each here at the point its work completes; where repo policy already completed one in Phase 2, this re-tick is idempotent rather than the first tick. That keeps the terminal Phase 4.3 `--status Complete` self-record gate's non-blocking `## Plan` warning firing only on a genuinely dropped/superseded step (that gate: a non-post-merge unticked AC row hard-fails the Complete write, while an unticked Plan row only warns — see the finalize call in Phase 4.3):

- The versioning step (where the project's versioning convention, stated in its implement prompt extension, declares the version change): once the artifact that step produces is committed, tick its Plan row — `workpad.py update $ISSUE_NUMBER --tick-plan "{substring of the versioning plan step}"`. The Phase 3 review gate then fails an engine-surface change that the convention says needs that artifact and carries none, and passes one that does.
- The project's own final verification run (the full test/lint suite the repo runs before it calls a branch done): once you have observed it green in-env (the direct-form command granted via `prflow_implement.allowed_tools`), or — when the run's own policy selected a cloud CI verification mode — once a validated cloud-CI completion-evidence record for the current HEAD has been recorded, tick its Plan row — `workpad.py update $ISSUE_NUMBER --tick-plan "{substring of the final-suite plan step}"`. Outside that selected mode a CI conclusion never discharges this row, and a denied verification command takes the Blocked path (§3.4), not a CI deferral.

Only tick a step your plan actually lists (a `--tick-plan` that matches nothing is a volatile miss); if this run's plan carries no such step — a consumer repo with no version policy, say — skip its tick.
