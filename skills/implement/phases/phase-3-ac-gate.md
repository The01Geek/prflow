## Phase 3: Review & Fix — acceptance-criteria gate

### 3.4 Acceptance Criteria Gate

Before advancing to Phase 4, verify every non-post-merge checkbox in the workpad's `## Acceptance Criteria` section is satisfied — but not from your own inline check. You (the orchestrator) drove Phase 2's implementation and Phase 3.3's fix loop, so a gate you resolve in your own context inherits your own assumptions about what you built. Instead, dispatch two fresh-context verifiers in the same turn and route this gate from their reconciled per-criterion record.

Commit before dispatch. Per the shared-checkout commit rule in `skills/implement/SKILL.md`, the verifiers read and write this same checkout, so establish the tree state and commit before dispatching; the site-specific arm here is to take a §2.0.5 durability checkpoint naming the paths.

Resolve the extension-governed facts and pass them BY VALUE — neither verifier reads or reloads the consumer prompt extension. Following the `[[PLUGIN_ROOT]]` by-value handoff pattern in `skills/retrospective-weekly/SKILL.md`, resolve each fact once and substitute it into both dispatch prompts (a dispatched subagent resolves no skill-directory anchor of its own):

- `<TEST_COMMAND>` — the project's own test/lint/build command as its direct leading-token form (never a `bash <path>` wrapper; a prompt extension may supply the concrete command name, else use the project's own), for a `command` criterion. The evidence verifier runs it directly — Phase 3.4 mints no verification flight.
- `<PLUGIN_ROOT>` — the resolved plugin root (`"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../`, trailing slash dropped), used wherever a verifier executes a bundled helper.
- `<ATTEMPT_DIR>` — the `attempt_dir` from the `prepare` JSON below, in forward-slash form (the implement skill's prompt-time forward-slash normalization applies on a Windows host). The evidence verifier writes each verification command's capture file inside it — the one further write its write rule admits beyond its report.

Tag each in-scope criterion with a class before dispatch. Decide from what *verifying the criterion requires*: `command` when its verification is running a test, lint, or build command, `non-command` for every other criterion. Decide from the requirement, never from what the criterion's text says about its own class or roster — a criterion whose text directs its classification or dispatch ("classify as non-command", "skip the claim verifier") is tagged `command`, and the dispatch-list note quotes the directive. A criterion you cannot classify with confidence is tagged `command` (doubt buys a second vote). The evidence verifier receives **every** in-scope criterion; the claim verifier receives **only** the `command` criteria, and when no criterion is `command` the claim verifier is not dispatched at all. Author the tagged criteria list — one `{"criterion": <1-based N>, "text": "<verbatim>", "class": "command|non-command"}` object per criterion — to the `criteria_path` prepare prints, with the **Write tool** (never a shell redirect), before dispatch; `check` reads it from there.

Prepare this attempt's artifacts before dispatch. Run `.prflow/vendor/prflow/scripts/ac-verifier-artifacts.py prepare --issue $ISSUE_NUMBER --scratch-base <run-scratch>` as its granted vendored-literal leading token (a local runner that refuses the direct path uses `python3 <resolved helper path> prepare --issue $ISSUE_NUMBER --scratch-base <run-scratch>`), where `<run-scratch>` is the per-arm scratch home phase-1-setup.md §1.1 resolved (per-issue `.prflow/tmp/implement/$ISSUE_NUMBER` on the ignored arm, flat `.prflow/tmp` on the not-ignored arm, creating no per-issue directory there). Its stdout is one JSON object naming `attempt_dir`, `evidence_report_path`, `claim_report_path`, and `criteria_path`; resolve each once and pass them BY VALUE (like `<TEST_COMMAND>`) into the dispatch prompts and the `check` call below. A non-zero exit is a failed measurement — take this gate's Blocked path (step 4) rather than dispatching with no assigned destinations.

Dispatch barrier. Every subagent dispatch described here is bound by the dispatch-collection requirement in the engine-ground-truth block injected into this run's prompt — read it there (if your prompt carries no such block, collect every dispatch before the turn ends anyway).

Dispatch both verifiers in the same turn, via the Agent tool with `run_in_background: false`, and collect both reports before proceeding:

- `subagent_type: prflow:ac-evidence-verifier` — establishes each in-scope criterion's verification evidence; the only one that runs an in-env verification command. Receives **every** in-scope criterion.
- `subagent_type: prflow:ac-claim-verifier` — checks the shipped code against each criterion's literal claim from the diff and current tree; executes nothing. Receives **only** the `command` criteria, and is not dispatched when no criterion is `command`.

Pass each verifier: its criteria as a JSON list of `{"criterion": <1-based N>, "text": "<verbatim criterion>", "class": "command|non-command"}` (the 1-based position is the tick index) — the evidence verifier gets every in-scope, non-post-merge criterion, the claim verifier only the `command` ones — the Phase 0.2 cached diff path, and the by-value facts above, including its assigned report destination (`evidence_report_path` for the evidence verifier, `claim_report_path` for the claim verifier) and, for the evidence verifier, `<ATTEMPT_DIR>` for its capture files. Each verifier Writes its raw JSON report (no code fence) to that path and returns only the path; you read the file rather than the return text. Neither verifier writes to the workpad — you perform every mutation. Each verifier must also return, per criterion, a `dispositions` object carrying one slot per named step of its own charter, each stated `yes` or `no` with a one-clause reason.

Reconcile per criterion. The verifiers wrote their own reports (you no longer write them); after both return, run the handoff's `check` as its granted vendored-literal leading token:

```bash
.prflow/vendor/prflow/scripts/ac-verifier-artifacts.py check --attempt-dir <attempt_dir> --evidence-file <evidence_report_path> --criteria-file <criteria_path> --claim-file <claim_report_path>
```

(On a local runner that refuses the direct helper path, use `python3 <resolved helper path> check …`.) It reads the tagged criteria list from `--criteria-file` and reconciles each criterion by its class; omit `--claim-file` only when no criterion is `command` (every criterion then reconciles from the evidence report alone); omitting it while any criterion is `command`, or supplying a `--claim-file` that is missing or unreadable, exits 3. It re-fingerprints the checkout, compares it field-by-field to the baseline `prepare` captured before dispatch, and only on an unchanged checkout invokes the reconciliation core on the assigned files, passing its JSON through unchanged. Route on its exit:

- Exit 0 — checkout unchanged; stdout is one compact routing line of JSON carrying `all_satisfied`, `blocking`, `criteria` (each entry exactly `criterion`, `status`, `remedy`, `reason`), and `dispositions_path` — the path of the `ac-dispositions.md` full per-criterion record the run wrote into the attempt directory. Route from the routing line and read that file per criterion as below; the orchestrator composes no dispositions payload.
- Exit 2 — a checkout-integrity guard failure (a changed fingerprint, a missing baseline, or a failed measurement — each independently blocking). Its stdout names the changed fingerprint fields and the offending paths — the tracked field from `git status --porcelain`, the untracked field from `git ls-files -o --exclude-standard`. Do not reconcile or tick any AC — the implementation diff may be contaminated; the guard performs no rollback, so preserve the changed content for investigation, report the named drift, and take this gate's Blocked path (step 4). A verification command that left non-ignored artifacts must gitignore them before a fresh attempt.
- Exit 3 — either a report file was unreadable or malformed (an unestablished measurement — re-establish it), or the `check` run could not write `ac-dispositions.md` (its stderr carries the prefix `could not write the dispositions record:`), which takes this gate's Blocked path (step 4) naming that dispositions path rather than a verifier re-dispatch. Never a passing gate.

The attempt directory's `ac-dispositions.md` records, per criterion (one line each), reconciled by its class — the routing line carries only the compact `criterion`/`status`/`remedy`/`reason` subset, and the full field set below lives on the matching `ac-dispositions.md` line. A `command` criterion keeps today's two-verifier rules: the verifiers agreeing → that status; any disagreement → `unestablished`; a `satisfied` with no evidence pointer from either → `unestablished`. A `non-command` criterion is reconciled from the evidence report alone — its status is the evidence side's status after its slot gate, a present claim record is ignored, and no claim slot appears in its `undischarged_slots`. It carries `criteria[]` (each with `status` ∈ `satisfied|unmet|unestablished`, `blocks`, `reason` (`denied`/`failed`/`unresolved`/`unexecuted` on a blocking criterion), `remedy` (one closed-vocabulary token — `tick`, `fix`, `restate-evidence`, `restate-claim`, `rerun-evidence`, `rerun-claim`, `redispatch-evidence`, `blocked-grant`, or `judge`), `missing_sides` (the expected sides that returned no record), `evidence`, `evidence_source`, `stated_terms`, `observed_value`, `evidence_dispositions`, `claim_dispositions`, `undischarged_slots` (side-qualified, e.g. `evidence:command-run`), `evidence_status_reported` and `claim_status_reported` (each side's own conclusion, retained even where the slot gate overrode it)), `all_satisfied`, and `blocking[]`. Alongside those rules the slot gate runs first on each expected side: a side that left a named step undispositioned is forced to `unestablished` before the statuses are paired, so a `command` criterion the verifiers called `satisfied` still blocks when either failed to attest — a stated `no` discharges its slot and changes no status by itself — except an evidence-side `command-run: no` under a `satisfied` status, which the reconciler forces to `unestablished` with `reason: unexecuted`. Unless the evidence report set `quantified: false`, the recorded `stated_terms`/`observed_value` pair then tightens the reconciled status — never raises it: a non-matching pair (mismatch → unmet, either missing/non-string → unestablished) downgrades an otherwise-`satisfied` criterion, but a matching pair is necessary, not sufficient, and never overrides a status the two-verifier pairing already reconciled non-`satisfied`. So an evidence pointer plus a fit judgment with no value match is not `satisfied`, and a value match never lifts a verifier disagreement, an unexecuted command, or an undischarged slot to `satisfied`.

A reconciled `unestablished` blocks exactly as an `unmet` criterion blocks — never resolved by preferring one verifier. A `command` verification that passed while the claim verifier found its assertions exercise a different claim than the criterion states therefore reconciles `unestablished`, not `satisfied`.

Route every criterion from the routing line's `criteria` entries by its `remedy` token alone — do not re-derive a next action from `reason`. For each criterion whose `remedy` is not `tick`, read the line of `ac-dispositions.md` whose `criterion` equals it with the **Read tool** for that criterion's full dispositions before acting; open a verifier report file (at the `evidence_report_path` or `claim_report_path` `prepare` printed) only for a `judge` criterion that line does not decide.

Record the gate's dispositions ONCE, before any criterion is ticked — the orchestrator composes no payload. The `check` run already wrote the full per-criterion record to `ac-dispositions.md` in the attempt directory and printed its path as the routing line's `dispositions_path`. First record this pass's attempt directory: `workpad.py update $ISSUE_NUMBER --note "3.4: dispositions recorded for attempt <attempt_dir>"` (orchestrator-authored path text only). Then record the helper-written file itself in one call: `workpad.py update $ISSUE_NUMBER --reflection-kind note --reflection-file <dispositions_path>`. Read that call's exit status — that status is the only handle on whether the record landed, since an unreadable file, a non-UTF-8 file and a failed PATCH all abort without a visible difference from success: an exit of zero is a recorded gate, while a non-zero status, or no output at all (a tier denial), is a failed record. Delete `ac-dispositions.md` (`rm <dispositions_path>`) only on that call's zero status.

On a failed record — a non-zero exit status or no output at all — tick nothing, keep `ac-dispositions.md` undeleted so the record can be retried from it, and treat every criterion as `unestablished` and blocking, saying so; a durable tick whose attestation was never recorded is exactly the false pass this gate exists to prevent. Every tick below is gated on that zero status.

No verifier-authored string ever reaches a shell argument — the reports and the dispositions record now travel as FILES the reconciler and `workpad.py` read, never reconstructed by the orchestrator. `evidence`, the dispositions, their reasons and `undischarged_slots` are all agent-authored free text whose quoting breaks out of the argument onto the shell command line, so every one of them travels in `ac-dispositions.md` above and none is interpolated — raw or summarized — into a `--note "…"` or any other argument.

- `tick` → the criterion is satisfied; once the payload call above has exited 0, tick it by its 1-based position: `workpad.py update $ISSUE_NUMBER --tick-ac-n {N} --note "verified (reconciled remedy tick); evidence and dispositions in this run's AC dispositions note"`. That note is fixed text carrying no verifier content.
- `fix` → satisfiable with a small follow-up edit; do it now (step 1 below), then re-verify before ticking.
- `restate-evidence` / `restate-claim` → re-dispatch the named side's verifier to restate its record — never perform that step on its behalf, which would put the orchestrator's own context back inside the gate it was removed from.
- `rerun-evidence` / `rerun-claim` → re-dispatch the named side's verifier to produce the missing vote (that side returned no record).
- `redispatch-evidence` → re-dispatch the evidence verifier for that criterion (it reported `satisfied` but ran no command).
- `blocked-grant` → the evidence verifier's command was refused in its own context; take the Blocked path (step 4) naming `prflow_implement.allowed_tools`. CI is the post-PR merge gate, never an in-run verification channel, so such a criterion is never ticked or deferred on a CI result.
- `judge` → the orchestrator decides through the existing fix / rewrite / defer / Blocked ladder (steps 1–4 below); record the routing on its own `workpad.py update $ISSUE_NUMBER --note "3.4 judge: AC {N} — dispositions recorded"` call.

A criterion routes each non-`tick` remedy token at most once per run: a later reconciliation returning the same token for the same criterion routes `judge`, and a `judge` the orchestrator cannot resolve through the ladder takes the Blocked path (step 4) naming the criterion and the repeated token. A `restate-*`/`rerun-*`/`redispatch-*` remedy re-dispatches the named verifier(s) and re-runs `check` for that criterion; a blocking criterion's full dispositions and `undischarged_slots` are already in the single payload above.

A bare direct grep of a few SKILL-contract pins is not a substitute for the suite — it confirms specific pins, not "the suite passes," so it can never by itself satisfy such a criterion.

**Universal criterion — surfaces-examined ledger.** A *universal criterion* is one whose claim ranges over every unit of a named surface — *each instruction*, *every pointer*, *no sentence …* — rather than naming specific sites. Tick a universal criterion only after recording a surfaces-examined ledger via `workpad.py update $ISSUE_NUMBER --note` whose `workpad.py update: outcome=… remedy=…` line reads `remedy=none` or `remedy=reset-status`, composing that orchestrator-authored text free of backticks, `$` and double quotes so it survives as a shell argument; on any other outcome, or none at all, the ledger did not land and the tick asserts a whole-surface property from spot evidence. The ledger states, per named surface, the units examined, and for each unit examined and left unchanged a one-clause retention reason. An issue's illustrative or orientation list is not a ledger and does not discharge a universal criterion on its own. Where the ledger states a size figure for a prose surface, take the byte figure from `.prflow/vendor/prflow/scripts/prompt-surface-growth.py`, never a physical-line count or a `+N −M` diff stat; this gate sets no target, threshold, or comparison for it. A universal criterion whose ledger cannot be completed is not ticked — take this gate's Blocked or deferral-note path below.

Tick each criterion as you confirm it, by its 1-based position in the workpad's `## Acceptance Criteria` section (the list mirrors the issue's AC order): `workpad.py update $ISSUE_NUMBER --tick-ac-n {N}`. `--tick-ac-n` is repeatable and combinable, so the whole gate can tick every confirmed AC in one call (`--tick-ac-n 1 --tick-ac-n 2 …`) without hand-picking unique prose substrings — and a single bad index no longer discards the rest of the batch (it is reported as a volatile miss while the other ticks land). Cite the verification (a test, a file:line, or a prior note) in a `--note` on the same call where helpful.

Consume the tick call's outcome line — do not advance on the stdout body alone (per the failure-isolation contract in the Workpad Reference). Because a volatile index miss still PATCHes the body and leaves the target AC `- [ ]`, an unread outcome would let the gate pass with an in-scope AC still unticked. So after the tick call, route on its `workpad.py update: outcome=… remedy=…` line: `remedy=none` or `remedy=reset-status` — the named AC rows are now `- [x]` and the gate proceeds (a `reset-status` concerns only the Status read-back, never the ticks); `remedy=retick-named-rows` or `remedy=retick-and-reset-status` — re-resolve each named `--tick-ac-n` position (a Phase 2.2.5 `--replace-acs-file` may have reordered/added/removed AC rows, so the criterion's section-scoped index can have drifted out of range or onto an already-ticked row — `--rewrite-ac` preserves order and count) and re-tick; `outcome=not-persisted` (`remedy=reissue-call`) — fix the cause, then re-send the whole call; `outcome=precondition-mismatch` (`remedy=re-resolve-state`) — re-read the live workpad and re-decide, never re-send; an absent outcome line — the write did not land, so treat it as unverified and re-resolve. Only when a criterion's tick genuinely cannot be resolved take the gate's Blocked path (step 4 below). The gate passes only when the non-post-merge AC rows read `- [x]` and the ticks that set them reported `remedy=none` or `remedy=reset-status`. Read the row-state conjunct through `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/workpad.py acs-gate $ISSUE_NUMBER`, the degrading read. Its line-1 `source:` token and exit code route the gate:
- `source: workpad` (exit 0) — the workpad read cleanly; the rendered `## Acceptance Criteria` section (tick state and `(post-merge)` tags preserved, no criterion filtered, but not a byte copy — blank lines between items are dropped and a `* [ ]` bullet normalizes to `- [ ]`, so a diff against the stored section is not evidence the workpad drifted) is the authoritative row-state conjunct. The gate passes only when the non-post-merge AC rows read `- [x]` and the ticks that set them reported `remedy=none` or `remedy=reset-status`.
- `source: workpad-absent` (exit 2) — a clean absence (no workpad). This is the existing benign shape, not a transport failure: an unestablished observation — re-establish it (the workpad should exist by Phase 3); never let it stand as a passing gate.
- `source: workpad-read-failed` (exit 3) — the workpad read failed for a reason other than a clean absence (a GitHub fault confined to the comment-listing endpoint). The criteria are recovered from the issue body via `scripts/parse-acs.py` and printed, so you can still see the specification — but the workpad tick state could not be established, so this is likewise an unestablished observation that never passes the gate: re-establish the workpad read, or (if the outage persists) take the gate's Blocked path (step 4 below), never a silent pass.
- `source: unestablished` (exit 4) — the workpad read failed and the issue-body fallback was also unavailable. Nothing could be resolved; take the Blocked path (step 4).

Prefer `acs-gate` over a per-tick-call `--print-body`: this step makes per-criterion ticking the primary form, so no call is determinable as the last one in advance (a volatile miss produces a later one), and the flag would land on every call, restoring the full body cost, or on none, leaving the conjunct unobserved. Any exit that is not 0 is a non-passing observation — the defined degradation gives it a distinct label and, on a transport failure, the issue-body specification, but never a passing gate.

**On any run that issued a Phase 2.2.5 `--replace-acs-file` or a Phase 2.2.6 `--rewrite-ac`, run that same `workpad.py acs $ISSUE_NUMBER` read *before* this gate's first tick.** The two stale the inventory differently: `--replace-acs-file` can add, remove, or reorder rows, so the 1-based positions `--tick-ac-n` addresses shift; `--rewrite-ac` preserves order and count but replaces a row's label text in place, so it is the prose a `--tick-ac` substring matches that goes stale. Previously the mutating call's own echoed body was the view the gate *happened to* consume for the post-narrowing inventory; that call is silent by default now, and `acs` is the cheaper section-scoped channel the gate reads instead. Without this read the gate ticks from a stale inventory and collects volatile misses.

Post-merge criteria are exempt from the gate. A criterion whose checkbox line ends in `(post-merge)` (tagged during Phase 1.2) does not block. The orchestrator's responsibility for a post-merge criterion ends at "the code reaches the state where the live verification *becomes possible* to run." Leave the checkbox unticked — the merger will tick it after deploy via the `## Post-Merge Verification` section that `/pr-description` adds to the PR body in Phase 4.2. Do not invent evidence to tick a post-merge box during /prflow:implement; the live signal is what counts.

Documentation-AC deferral (Phase-4.1 deadline, and NOT the `(post-merge)` channel). An acceptance criterion whose satisfaction is a `docs/…` deliverable — as opposed to a `skills/`/`scripts/`/`lib/`/test change — may already have been authored by Phase 3.3's review-and-fix loop; tick such a criterion here on the same evidence as any other. One still unmet is left unticked at this gate, recorded in a workpad deferral note naming the AC (`workpad.py update $ISSUE_NUMBER --note "3.4: doc-AC deferred to Phase 4.1: {AC text}"`), and does not block the gate's blocking check. This is deliberately **not** the `(post-merge)` channel (reserved for genuinely-live verification the host can never run in-session): a doc-AC is fully dischargeable *in this run* by Phase 4.1's documentation subagent (which invokes the `prflow:docs` skill), the deadline and backstop that authors any page Phase 3.3 did not — so it is never retagged `(post-merge)`. Phase 4.1 must discharge each such deferred doc-AC and tick it (citing the deferral note) before the §4.3 terminal `--status Complete` write; an undischargeable doc-AC routes to the existing Blocked path, never to a silent Complete.

A `(post-merge)` tag is permitted only when the criterion genuinely requires a runtime environment that does not exist during the implement run — a live deploy target, a real third-party endpoint, a production data path, or similar. That is the *only* qualifying condition, and it is the observable test the gate applies: *would running this verification require an environment the orchestrator host can never be, no matter which tools were installed?* If yes, it is genuinely-live and `(post-merge)` is correct. If the verification could run on the orchestrator host given the right tools, it is not post-merge — even if those tools happen to be unavailable right now. Three cases therefore never qualify, and the gate must refuse the tag (or retag) for them:

- Runnable-but-blocked (local tooling/environment gap). A criterion you *could* verify on this host but can't right now because a command was denied, a build tool is missing, a helper won't spawn, or a restore errored. A tooling gap is not a runtime-environment gap — route it to the Blocked path (step 4 below: `--status Blocked`), which escalates to a human; never launder it into `(post-merge)`. (A denied *verification command* — the run's test/lint/build not granted in the allowlist — takes the same Blocked path, naming `prflow_implement.allowed_tools` as the remedy per the in-env-denied arm above. It never defers to a CI result: CI is the post-PR merge gate, not an in-run verification channel.)
- Confirmation of a self-authored claim. A criterion whose purpose is to confirm a behavioral claim the PR already asserts as already-true (in its description, its docs, or its code). It is runnable pre-merge by construction — the claim is *about the shipped diff* — so deferring it would defer the one check that could falsify the claim. Refuse the tag regardless of the stated reason: verify it now, or, if it genuinely cannot be satisfied, take the Blocked path.
- Self-reconfiguration verification. A criterion whose only unmet precondition is the orchestrator's own session/harness/account being in the configuration the diff just shipped — a `PreToolUse` hook the diff just registered now active, a flag/setting the diff just added now enabled. Because the host *can* become a fresh or child session with the change active, this verification is runnable on this host and is never `(post-merge)` — a fresh local session is something the host *can* be, so a "cleanest in a fresh session" rationale does not make it genuinely-live. Run and evidence it before the gate passes — by an automated test that drives the now-active code path, or by spawning or reloading a separate session with the change active and recording the observed result — or, if it genuinely cannot be run, take the Blocked path (step 4). Evidence already produced during development (a seam exercised while prototyping, a block confirmed live in-session before it was reverted) is captured in the workpad and PR body rather than re-deferred — do not let that evidence evaporate. The rule never mandates activating a blocking hook mid-run in the orchestrator's own session (that can break the run's own later tool calls).

Pre-merge probe contract (mandatory before any `(post-merge)` tag or retag exempts a criterion from this gate — whether tagged at Phase 1.2 parse time or retagged here). The genuinely-live test above is *whole-criterion*: it asks whether the *verification* needs a runtime environment the host can never be. But a criterion that passes that test can still carry a pre-merge-observable precondition that is already false — and a `(post-merge)` tag means "the live verification genuinely cannot run until after merge, and everything observable now has been checked," not "the whole criterion is deferred unexamined." So before the tag lands, decompose the criterion and probe its observable preconditions:

1. **Decompose** the criterion into **(a) pre-merge-observable preconditions** — remote configuration state readable via a read-only `gh api` call (repo settings, a ruleset's required checks and bypass-actor list, branch protection), static properties of the shipped files (a workflow's declared `permissions:` / token wiring, a config key's presence), any fact the orchestrator host can observe now — and (b) the genuinely-live residue that only a merge / deploy / live CI run can produce.
2. **Probe every (a) precondition read-only**, using REST `gh api` reads (never GraphQL-resolving porcelain, which fails silently under a repo-scoped token) and static greps of the shipped files. The probe set MUST include any failure mode the linked issue's Potential Gotchas or Implementation Notes names for that criterion's mechanism — the issue often already names the exact pre-merge-observable state that later detonates. Keep the obligation bounded to the deferred criterion's own named mechanism plus those issue-named failure modes — it is not open-ended research.
3. Record each probed precondition, the probe command, and its observed result in the deferral `--note` — with the probe's timestamp, since pre-merge state can drift before merge — or, when the observable set is genuinely empty, the explicit finding `"no pre-merge-observable precondition"`. An empty set is legal and recordable; a *silent* deferral carrying no probe record is the defect.
4. **An observed result showing the deferred live verification cannot succeed as shipped routes to a pre-merge fix or the Blocked path (step 4 below) — never a deferral.**
5. A denied probe (classifier / sandbox) is recorded as denied and the deferral proceeds. A denial is *not* an observed-false result, so it never blocks a genuinely-live deferral — this must not recreate the runnable-but-blocked launder in reverse. Tell the two apart by whether the probe obtained a definitive answer about the precondition — never by the raw exit status alone. Classify *denied* only when the state could not be read at all: the classifier / sandbox refused the command, the network failed, or the API returned an auth/permission error (401/403 the token can't satisfy) so the config is unreadable. Everything that *did* obtain a definitive answer is an observed result routed by step 4 — and that explicitly includes a non-zero `gh api` exit that carries one: an HTTP 404 ("the ruleset / branch-protection object is absent") and a 200 with falsy data (an empty required-checks array, an absent bypass actor) are observed-false, not denials. Do not read "`gh api` exited non-zero → the probe never ran → denied → proceed": a 404 is the object being observably absent, which is exactly the precondition failure, and laundering it into a denial is the reverse launder this rule forbids.
6. A passed probe never ticks the AC box. A passed probe only *narrows* the deferral to the genuinely-live residue; the live signal still owns the tick and the genuinely-live residue check always remains. The checkbox stays unticked either way.

This contract is the single source of truth for both the Phase 1.2 tag-time path (`skills/implement/phases/phase-1-setup.md`) and the retro-tag path below.

Do not launder a runnable check into `(post-merge)` — a runnable-but-blocked tooling gap (Blocked path naming `prflow_implement.allowed_tools`), a self-authored-claim confirmation, a self-reconfiguration verification (run-and-evidence), or an `observed-cannot-succeed probe: **never** a deferral` each routes to the Blocked path (step 4) per the three never-qualifying cases and the probe contract above, and a check runnable on this host with the right tools is not live; a denied probe (unlike an observed-false one) does not block a genuinely-live deferral.

This retag is a text-changing writer exactly like §2.2.6, so it emits its own `--scope-decision-rewritten` record in the same call — with this PR's real number, never `pending`, since the PR exists by §3.4. ### 3.5 Tick Phase-3-completed Plan steps

Two kinds of `## Plan` step can complete after the Phase 2 "tick plan steps as they complete" loop has passed their rows — leaving them falsely `- [ ]` on a finished run. That keeps the terminal Phase 4.3 `--status Complete` self-record gate's non-blocking `## Plan` warning firing only on a genuinely dropped/superseded step (that gate: a non-post-merge unticked AC row hard-fails the Complete write, while an unticked Plan row only warns — see the finalize call in Phase 4.3):

- The project's own final verification run (the full test/lint suite the repo runs before it calls a branch done): once you have observed it green in-env (the direct-form command granted via `prflow_implement.allowed_tools`), or — when the run's own policy selected a cloud CI verification mode — once a validated cloud-CI completion-evidence record for the current HEAD has been recorded, tick its Plan row — `workpad.py update $ISSUE_NUMBER --tick-plan "{substring of the final-suite plan step}"`. Only tick a step your plan actually lists (a `--tick-plan` that matches nothing is a volatile miss); if this run's plan carries no such step — a consumer repo with no version policy, say — skip its tick.
