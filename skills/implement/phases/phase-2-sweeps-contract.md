## Phase 2: Implement — contract sweeps

### 2.3 Implement

`workpad.py update $ISSUE_NUMBER --status Implementing`.

Now implement the feature yourself. You have full context:
- The explorer's system understanding
- The architect's blueprint (if complex) or your own inline plan (if simple)
- The original issue requirements

**On a §2.0 gate-fire resume, the committed `## Plan` is the working context in place of the ephemeral explorer/architect output** — both dispatches were skipped, so neither the explorer's system understanding nor the architect's blueprint is in your context; the committed Plan (paired with the §2.0 fresh-tree re-verification of what is already implemented and what remains) is what you build on — under §2.0's unchanged freshness obligation, never a stale Plan trusted blindly.

**Criterion-lifecycle accounting (mandatory, before any implementation code).** The resolved workpad `## Acceptance Criteria` rows are the sole formal specification (phase-2-implement.md §2.1), and this gate — not the create-issue Testing Strategy — owns the exhaustive criterion-by-criterion verification accounting. Before you write implementation code, read every resolved criterion row back from the live workpad (`workpad.py id $ISSUE_NUMBER`, then `workpad.py body <id>` — never from memory) and assign each row exactly one verification-lifecycle route, recording the mapping through the existing test-first `--note` channel so a criterion with no recorded route is visible before implementation begins. The four routes, each an *existing* lifecycle this gate references rather than a new mechanism:

- **Testable → a named automated assertion (test-first, RED/GREEN).** The criterion exercises behavior an automated test can drive — a return value, a CLI/API contract, an exit code, a parser's handling of an input shape, a state transition, a raised error, an end-to-end path. Name the assertion that will prove it; the *Test-first gate* below governs how it is written and seen to fail for the right reason. **One assertion may cover several criteria** — record every criterion it discharges, and never let grouping hide a criterion the assertion does not actually prove.
- **Genuinely untestable Phase 2 deliverable → the Phase 2.4 trace.** The deliverable is prose, templates, config, an embedded DSL, or agent-executed prompt prose with no automated boundary (the *When no automated test applies* case below). It maps to the existing Phase 2.4 adversarial dry-trace / prompt RED-GREEN micro-test discipline, never a fabricated assertion. **This route carries a per-criterion forcing function** — the `--note` states, for each criterion routed here, the one-line reason no automated boundary exists — so a genuinely-testable criterion cannot be silently laundered onto a dry-trace: an unjustified "untestable" claim on a criterion that plainly added a return value, an exit code, or a drivable path is then a visible error, exactly as the change-level *Test-first gate* below treats its own no-automated-test note. The change-level gate decides testability for the change as a whole; this route records it per criterion, which the change-level note does not.
- **Documentation criterion owned by the documentation pass → Phase 3.4 deferral, then Phase 4.1 discharge.** A criterion satisfied by an internal- or external-docs edit is not authored here: it is deferred at the Phase 3.4 gate and discharged by the Phase 4.1 documentation subagent (phase-3-ac-gate.md's *Documentation-AC deferral*; phase-4-documentation.md §4.1). It never routes to Phase 2.4.
- **Genuinely-live → the existing `(post-merge)` disposition.** A criterion verifiable only in a live PR / deploy / CI environment maps to the `(post-merge)` tag and its pre-merge probe contract (phase-1-setup.md §1.2; phase-3-ac-gate.md §3.4), never a fabricated pre-merge assertion. The Phase 3.4-forbidden `(post-merge)` cases — a runnable-but-blocked tooling gap, a self-authored-claim confirmation, a self-reconfiguration verification — are **not** this route.

This ledger neither replaces nor duplicates the Acceptance Criteria: it references the exact resolved rows and adds only each row's lifecycle disposition, and it never infers a new criterion from narrative prose — the resolved workpad rows are the only operand. A resolved criterion left with no recorded route is the defect this accounting exists to surface: record it before implementation rather than coding around it. This accounting runs on every implement run; the change-level *Test-first gate* below still governs the testable-route assertions it names.

**Test-first gate (mandatory when the change is testable).** Before you write implementation code, decide whether the change adds or alters behavior an automated test (unit or integration) can exercise — a function's return value, an API or CLI contract, an exit code, a parser's handling of an input shape, a state transition, a raised error, or an end-to-end path an integration test drives. If it does, write the test **first**, run it, and confirm it **fails for the right reason** (the behavior doesn't exist yet), then implement until it passes. §2.1.5's reproduction signal is **any one of** a failing test, a quoted error log, *or* a recorded shell command: only when that signal **was a failing test** does it already satisfy this gate (don't write a second one). If 2.1.5 reproduced the bug with a non-test signal (a log or a shell command) there is no failing test yet, so this gate **still applies** — write the failing test now, before implementing the fix. A test added *after* the code, never seen to fail, encodes whatever the code happens to do rather than what the issue requires.

**Stub-blindness rule (when a test stubs an external boundary).** A stub matches on *some* properties of the request and ignores the rest — and everything the stub cannot see becomes a behavior your test can never exercise, so bugs in it surface one at a time as review findings across later iterations instead of being caught on day one. When a test stubs a boundary (a `gh`/HTTP stub, a mocked client, a fake filesystem), **enumerate the request/shape properties the stub ignores** — URL paths and query parameters, the *order* of compare operands, the *direction* of a default/fallback, headers, method — and close each material blind spot by extending the stub or adding a behavioral test at the executable boundary. Prefer an assertion over the request the executable actually emits or the state transition it produces; do not substitute a static source-wording or comment-presence pin. A static presence pin is available only for one of the typed machine/executable boundary categories defined below. **Record the enumeration and behavioral coverage in the existing test-first `--note`.** Relatedly, a **declared-but-unused stub failure knob** — a failure-injection env var / flag the stub defines (`DRP_STATUS_FAIL`-style) that no test actually drives — is a pre-commit **smell**: it is mechanically detectable (grep the knob name; if it appears only in the stub definition, never in a test that sets it, it is dead) and must be resolved before commit (wire a test to it, or remove it), not left to a downstream reviewer.

**When the test you write IS a guard** (a drift/sync assertion, a coverage check, a regression test that pins a literal or contract), a green suite is necessary but **not sufficient** — a *vacuous* guard passes too. **Mutation-check any test guard you add here:** break what it pins (delete the line/block it asserts, flip the condition) **on a copy of the file — never edit the working-tree file in place** — and confirm the guard goes **RED** against that copy, then discard the copy. A copy-based mutation-check is never destructive: an interrupted or crashing check can never leave the real working-tree file broken, whereas an in-place "break then restore" can. In particular, never restore with `git checkout -- <file>`: it cannot restore an untracked file and silently appears to succeed, leaving every mutation in place. This is the same discipline as the mutation-check rule in `skills/review-and-fix/references/fixing.md` (Step 3), re-scoped to **any added or edited test guard in the diff** — so a guard authored as primary implementation work is covered here, not only a fix-loop deliverable. **Then confirm the guard registered:** a green suite is not evidence that a guard *ran*. After adding any guard, confirm its named assertion actually appears in the run as a PASS **and** that the suite's assertion count rose by what you added — green alone is necessary, not sufficient. A guard that silently no-ops (an assertion helper invoked before it is defined → command-not-found, a test file the runner never sources, a setup probe that returns success on failure) asserts nothing while the suite stays green, so a guard you never saw register as PASS may be protecting nothing.

**When the guard protects a named behavioral regression, test the behavior directly.**
Exercise the executable interface, emitted state, parser result, routing decision, or
other machine-observable contract and prove the test goes RED when that behavior is
broken. Do not encode the regression as a prose-presence pin. Record the executable
RED/GREEN evidence in the workpad note.

**Pin-corpus authoring boundary.** A wording-only pin is a test whose protected literal can
change without changing executable behavior and without breaking a machine-consumed contract.
Do not add wording-only, secondary-prose, documentation-presence, advisory-heading, or
comment-presence pins, including raw `grep`/text-presence assertions. An operative prompt
regression takes the behavioral route above: exercise the rendered or consumed prompt
through an ordinary executable test.

A new non-mutation presence pin is permitted only for this closed set of executable-boundary
categories: `helper-contract`, `schema-config-vocabulary`, `security-credential-boundary`,
`machine-sentinel-provenance`, `routing-dispatch-contract`,
`lifecycle-state-transition`, `generated-artifact-identity`, and
`cross-file-phase-contract`. Put the format-strict declaration
`# structural-pin-ok: <category> -- <rationale>` on the logical assertion line, choosing one
category from that set and supplying a nonempty rationale for the machine-consumed or
executable boundary. The declaration never exempts prose presence.

**Reuse a disposable verification rig across iterations — but only while it still fits.** When RED/GREEN iteration leads you to build a throwaway rig to exercise code in isolation — such as a scratch repo to drive a git-consuming helper, a fixture config to drive a config reader, or an interpreter/CLI wrapper that calls a helper with crafted argv (an illustrative floor, not a closed list — any other disposable rig counts) — keep it under an already-ignored scratch path (`.prflow/tmp/…`, which is gitignored and which no explicitly-scoped checkpoint or §2.5 commit ever names, so it is never staged; a nested `git init` rig placed elsewhere would land as a gitlink), record its location in a workpad `--note`, and on the next iteration reuse it instead of rebuilding it — but only after confirming it still exercises the current code shape. Rebuild it when the surface it exercises has changed: a rig keyed to a superseded shape drives paths that no longer exist and yields a false GREEN. This is the throwaway-scaffold twin of the focused-module iteration default and the 2.2.4 production-code Reuse gate — narrower than either, and it invokes neither's mechanism.

**When no automated test applies**, there is nothing to assert against: a change whose deliverable is prose, templates, config, or an embedded DSL (jq or shell inside Markdown, a `SKILL.md` procedure), or one with no observable behavior boundary. A change whose behavior emerges only from an end-to-end round trip is **not** this case — an integration test can drive it, so it takes the gate above. **Workflow inline shell that selects a branch or composes a user-facing message is also carved OUT of this no-automated-test class** — it is a drivable selector, not un-testable prose: extract it into a `scripts/*.sh` helper so the suite can drive each branch (and its arm-order), then write the test-first gate against that helper. A grep-pin on a message literal is not coverage of the selection that chooses it (`scripts/describe-denial-count.sh` is the reference extraction — see `CLAUDE.md`'s inline-shell-extraction convention). Skip the test and rely on the Phase 2.4 adversarial input-shape dry-trace instead **only** for the genuinely un-drivable deliverables above — do **not** invent a parallel mechanism.

Record the call either way: `workpad.py update $ISSUE_NUMBER --note "test-first: {test path, fails→passes} | {no automated test: <reason>; dry-trace at 2.4}"`. This is an auditable commitment: a "no automated test" note on a change that plainly added a pure function, a new exit code, or a drivable end-to-end path is a visible error a reviewer or the weekly retrospective can catch, where a silent skip is not.

Write the code. Follow the patterns and conventions described in `CLAUDE.md`. As plan steps complete, tick them off: `workpad.py update $ISSUE_NUMBER --tick-plan "{substring of completed step}"`.

**Comment discipline (authoring rule).** A comment the change adds or modifies survives inline only if a competent agent would otherwise make a specific, nameable wrong change — at this line, or at a specific coupled site the clause names by file or symbol. Write it as the prohibition and its consequence, and route everything else — a derivation, a worked example, the provenance of a decision, design narrative — to the project's internal-documentation location or delete it. The forcing function: an author who cannot name the wrong change a clause prevents has established there is no wrong change, and the comment goes. The coupled arm is deliberate — a producer-side comment whose whole value is stopping a wrong edit in a consumer file is the class the coupled-invariant discipline depends on, and it survives only when the clause names that site, which widens what survives without weakening what must be named. This rule binds exactly four populations and nothing else, complete by construction: inline comments in library and script source; test files; module docstrings and contract headers; and workflow and YAML files. Every other commented surface — skill and agent prose bodies among them at minimum — is outside the bound set and is governed as before.

The cap is three physical source lines, including any pointer line. Count a line-marker comment run as each consecutive line whose first non-whitespace token is the comment marker, with blank comment lines included; count a delimited block comment as every line from its opening delimiter's line through its closing delimiter's line inclusive; and count the inline pointer to relocated rationale — pointing somewhere is never free. A docstring's specification statement is not a comment block under this cap.

Three carve-outs are absolute, complete by construction. A comment a tool, a licence, or a policy requires to be present — including one a required coupled mirror or a suite pin requires at a specific site — is not prose under this rule and is never removed by it; that covers both a machine-read declaration or suppression marker a tool parses and a licence, SPDX, or vendored-attribution header no tool parses. A contract-header docstring's specification statement stays while the derivation, precedent and provenance around it move, because a stated specification is what makes the code comparable against it. And where the author cannot decide whether a comment is load-bearing, it stays. A mirror-fact claim authored anyway — a comment restating a fact the code beside it already carries, the distinct rule the 2.3.4a self-authored-claim reconciliation sweep still owns — is reconciled there, along with any prevention-failing comment this authoring rule missed.

**Sweep selection (run first).** The 2.3.x sweeps below are **not a flat checklist** — classify the diff and run the sweeps its shape warrants (**when in doubt, run them all**). Each sweep's heading states its own authoritative trigger; this list only tells you which to *consider*:

- **Deletes** code (a call site, branch, method, file, route, page, or asset) → run **2.3.1**, and **2.3.2** if it deletes a method/file/route/page.
- **Changes a contract** (a signature, a renamed/moved symbol, a tightened validator, a routing/branch predicate, **or a relocated prose literal, heading, section, or file path**) → run **2.3.0**.
- **Adds a rule that has peers** (a clause, guard, validator, or invariant that must hold at two or more co-equal sites — **or at every path through one unit of code** — for the rule to actually hold) → run **2.3.0a**.
- **Adds a value to an enumerated set** (a new enum/string-union member, status, kind, or verdict value — *or a member of a doc-enumerated configuration set: a workflow trigger list (the `on:` event set), a config-key set, a permissions list*) → run **2.3.0b**.
- **Removes a value from an enumerated set** (an enum/string-union member, status, kind, or verdict value — *or a member of a doc-enumerated configuration set: a workflow trigger list, a config-key set, a permissions list*) → run **2.3.0d** (describing-prose reconciliation sweep). **A rename is not this arm** — it is an addition and a removal at once, and §2.3.0d's precedence assigns it to **2.3.0b alone**.
- **Weakens a universal it previously asserted** — softens it ("always"/"every"/"never" becomes "usually"/"most"/"rarely"), scopes it (an unqualified claim gains a qualifier), or removes it outright → run **2.3.0d**.
- **Adds a guard, predicate, validator, or coverage invariant** (in code), **or** the deliverable is **policy-stating agent-executed prose** (a `SKILL.md` / `phases/*.md` command block) → run **2.3.0c** (operand-trace sweep).
- **Adds a collection output with ordering, dedup, or aggregation logic** (a sorted list, a deduped set, a grouped or counted tally, a tie-broken ranking) → run **2.3.7** (collection-cardinality sweep).
- **Always**, whatever the diff's shape → run **2.3.3** (convention), **2.3.4** (boundary-assumption), **2.3.4a** (self-authored-claim reconciliation), **2.3.4b** (coverage-claim enumeration), **2.3.5** (simplification & efficiency), **2.3.6** (error-handling & silent-failure).

This narrows *ceremony*, never *coverage*, and is **fail-safe**: each sweep's heading is authoritative, so if its trigger fires you run it even when this list didn't call it out — if the index ever drifts from a heading, the heading wins (drift can only add a sweep, never skip a warranted one). **The trigger shapes above are substrate-agnostic** — a contract, a peer-replicated rule, or an enumerated-set membership can live in prose / `SKILL.md` / doc / config just as much as in code (this repo's own coupled-invariant rule spans code mirror sites — a constant, a config-key name, a `SKILL.md` contract pin a `run.sh` grep asserts — as well as prose ones), so **classify by what the change replicates across sites, not by whether it is code**. An add-only diff that replicates nothing across sites typically runs just the always-on sweeps — **but** an add-only prose/doc/config diff that adds a peer-replicated rule, a value to an enumerated set, or a contract literal mirrored elsewhere still trips the contract-completeness sweeps (**2.3.0** / **2.3.0a** / **2.3.0b**), not just the always-on set. **Record the diff shape you classified and the sweeps you are running in a workpad `--note`** — the selection is then an auditable commitment a reviewer or the weekly retrospective can check, not a silent skip; a note reading "add-only" on a diff that in fact deleted a file is a visible error, where an unrecorded mental skip is not.

**The §2.3 sweep operand (defined once here — every diff-consuming sweep below reads THIS, never its own `git diff`).** The operand every §2.3.x sweep grades is the delta **from the merge base with the configured base branch to the current working tree** — the whole branch delta, committed and uncommitted work alike. It is defined in this one place; no individual §2.3.x sweep restates it. It is deliberately **not** `git diff HEAD` / `git diff --staged` / `git diff -U0`: the durability checkpoint below commits each sweep boundary's work, so an uncommitted-only operand is near-empty by the time a sweep reads it and the sweep grades almost nothing while still recording a clean pass. Grading the whole branch delta makes a checkpoint remove nothing from any sweep's operand — the checkpoint rule and the sweeps then explain each other rather than conflicting.

Resolve the operand substitution-free (the worktree tier refuses `$(…)`, backticks, `$?`, and a variable bound and read within one fence). First read the base branch — defaulting to `main`, never hardcoded — in its **own** fence, and read the printed value from the tool result:

```bash
.prflow/vendor/prflow/scripts/config-get.sh .base_branch main
```

The ref is the **fetched remote-tracking** `origin/<base>` — substitute the printed base as a literal; a cloud checkout creates only remote-tracking refs and has no local base branch, so a bare name resolves nothing. Then take the branch delta with `git diff --merge-base`, which diffs the merge base against the working tree in one read (see `git diff --help`; needs git ≥ 2.30):

```bash
git diff --merge-base origin/<base> -U0
```

Pipe it to whatever the sweep consumes, exactly as it consumed its former `git diff` (a search sweep greps it; §2.3.4b pipes it to `stale-prose-lint.py --worktree`). Two sweeps need a different **projection** of this same operand, not a different operand: §2.3.0 reads rename records with `git diff --merge-base origin/<base> --name-status`, and §2.3.4b's untracked-file leg still names each new file explicitly (a merge-base diff, like `git diff HEAD`, lists no untracked file).

**Degraded arm — record degraded, never a clean pass.** The branch delta cannot always be computed. When the `origin/<base>` ref is **unfetched or absent** (a shallow or partial clone, no `origin` remote), when `git diff --merge-base` is **unavailable** (git < 2.30), when there is **no reachable merge base**, or when the case is an **ambiguous multi-merge-base**, the operand is degraded. On git < 2.30 where `git merge-base origin/<base> HEAD` itself still resolves, read the merge-base SHA in its **own** fence and substitute it as a literal into `git diff <sha> -U0` — the same operand without `--merge-base`. When none of those recovers the operand, record the sweep **degraded** via `--note`, naming the condition that fired (unfetched/absent base ref, `--merge-base` unavailable, no reachable merge base, or ambiguous merge base), and do **not** record its clean match-count evidence — a degraded operand is a degraded sweep, never a silent clean one.

**Ground-once ledger — bounded work across boundaries.** Because the operand is the whole branch delta, without bounding, every §2.3.x boundary of a long Phase 2 would re-grade the same content. Each boundary handles **only what earlier boundaries did not already record**, and writes a `--note` stating what it **examined** (the operand range it read), what it **newly handled**, and what an earlier boundary **already recorded**. Read the earlier boundaries' notes back in two fences — `workpad.py id $ISSUE_NUMBER`, then `workpad.py body <id>` with the printed id substituted as a literal — and skip anything a prior `§2.3 operand ledger:` note already recorded. A ledger note that **cannot be read back** leaves the earlier boundary's coverage unestablished: redo that work and record this boundary **degraded**, never trusting an unreadable ledger as a discharge. (Any note prefix is accepted except the reserved `prflow:checkpoint …` family; use `§2.3 operand ledger:`.)

**Run each selected sweep after implementing and before running tests (Phase 2.4)** — that timing is the same for every sweep. **Durability checkpoint (§2.0.5):** because §2.3 routinely outlasts the ~10-minute loss window, take a durability checkpoint at each §2.3.x sweep boundary you cross — naming the files produced since the previous checkpoint — so mid-sweep work is durable on the remote before §2.4/§2.5. Because the §2.3 operand above is the whole **branch delta** (merge base → working tree), committing a boundary's work at this checkpoint removes nothing from any later sweep's operand — the checkpoint and the sweeps no longer conflict. **A non-zero exit here takes §2.0.5's resolve-before-continuing rule: do not start the next sweep on an unlanded checkpoint.**

For the search-based sweeps (**2.3.0**, **2.3.0a**, **2.3.0b**, **2.3.0d**, **2.3.2**), don't merely attest you searched: run the actual search the sweep describes, in a **granted** command form, and record a **concise** result via `--note` (the match count plus "all intended", or the specific offending sites) — evidence, not a claim. **2.3.0a's traced arm** records that arm's own note instead of a match count. The granted forms, in order: the **Grep tool** first (ignore-aware, always present in the runner), `rg` when it resolves on the host, and **`grep -rnE` last, and only with an explicit obligation to exclude VCS, dependency, and build directories**. For a quantitative **match count**, preserve the tracked-file operand explicitly — enumerate it with `git ls-files -z` and pipe that NUL-delimited list through `xargs -0` into `rg` or, when `rg` is unavailable, `grep -nE`. **Never `git grep -n`**, which `lib/capability-profiles.json` grants in no profile, so it is silently refused on both cloud tiers.

**Before recording a zero-match result as clean, confirm the search actually ran — this binds every search-based sweep above, not only the one whose body restates it, and the same arm equally admits one non-search cause — a call edge 2.3.0a's trace can neither resolve nor place in a declared reach class.** `rg` and `tr` are *granted* but **not** preflight-guaranteed (that set is git, gh, jq, python3 + PyYAML), and a missing stage empties a pipeline's output instead of failing it, so a search that never ran is byte-identical to one that ran and found nothing. The operand "did the search run?" therefore has to be *produced*, not assumed: **probe each non-preflight tool the form you chose depends on** — `type rg`, `type tr` (`type` and `which` are granted heads; **`command` is granted in no profile**, so `command -v` is silently refused and produces no operand at all) — **before** searching, and treat a search the runner refuses, or a search tool that exits **greater than 1**, as **unrunnable**. A **`grep`/`rg` exit of exactly 1 is zero matches, not a failure** — never route an honest empty result to this arm, or the arm stops discriminating a degraded host from a clean one and re-opens the laundering it exists to close. A missing tool routes to the unrunnable arm **only when every rung of the granted-form ladder above is unavailable or refused** — the Grep tool is the first rung and is always present in the runner, so an absent `rg` alone is a fallback, not a degradation. On that arm record `<sweep>: unrunnable (<which search, which cause>)` via `--note`, **naming the covering backstop** — the Phase 3 review pass, and, when the sweep runs inside the fix loop, the Step 3.5 fix-delta gate plus the convergence shadow — and do **not** record the sweep's clean match-count evidence.

#### 2.3.0 Changed-contract sweep (mandatory whenever the change modifies a signature, renames/moves a symbol, tightens a validator, changes a routing/branch predicate, or relocates a prose literal, heading, section, or file path)

A modified contract slips past `git diff` review because every dependent site still compiles — the call resolves, the fixture parses, the assertion runs — and is only *semantically* stale. After any change that modifies a signature, renames or moves a symbol, tightens a validator, or alters a predicate that classifies input, before running tests, grep the whole repo for every dependent site and bring each into line:

1. **All variants of a changed predicate.** If you changed a predicate that classifies input (e.g. a check for one specific status, type, or keyword), enumerate every value the predicate must now accept or reject and confirm every runner/branch routes them identically. A predicate fixed at one site but not its siblings is a defect in *this* PR, not a follow-up.
2. **Sibling call sites of a shared dependency.** If you wrapped or extended a shared object (e.g. added a per-request guard or a new error branch), grep for every caller that consumes that object and confirm each one plumbs the new inputs and handles the new branch — not just the site that motivated the change.
3. **Fixtures and assertions matching the old contract.** If you tightened a validator or moved output between streams (e.g. stdout↔stderr), grep tests for every fixture value and assertion that encoded the old contract — both in the files you touched *and* in shared `conftest.py` / helper modules — and update them. A fixture under a newly-stricter validator, or an assertion on a stream you rerouted, is a CI failure waiting for the next merge.

A modify / rename / reroute is not done until grepping for the old symbol, predicate value, stream, or contract returns only the intended sites.

**Relocation is a contract change too — of prose or a path, not only a code symbol.** Moving a **prose literal, heading, section, or file path** to a new location, while an **existing citation of its OLD location** survives (a test-suite pin, a docs cross-reference, a budget cell, a config-key list, a failure-map arm), is the same stale-dependent defect this sweep exists to catch: the citation still parses and only *semantically* dangles at the vanished source, so it ships clean and is found reactively instead of enumerated here. A relocation arms this sweep exactly as a moved code symbol does. At this sweep's point, recover what moved and reconcile every old-location citation:

1. **Recover what moved from the §2.3 sweep operand** (defined in the §2.3 preamble above — the merge base → working-tree branch delta). A **content** relocation (a literal, heading, or section) is reconstructed from the operand's **deletion hunks** (the removed lines). A **file-path** relocation's old path is read from the operand's `--name-status` projection (`git diff --merge-base origin/<base> --name-status`): it is the **source** of a rename record (`R### old new`) or the path of a **deletion** entry (`D old`) — recovered whichever way the move was made.
2. **Enumerate the old-location citations in BOTH forms, whitespace-normalized and rendered-surface.** A line-based `grep` misses a citation whose phrase is assembled from wrapped adjacent string literals — it lives on no single line (the blind spot) — so enumerate the citations that **quote the recovered content** with a **whitespace-normalized** search (`grep -rnE` across the repo plus a `tr -s '[:space:]' ' '` normalization — never `git grep`, which the implement profile does not grant) **and** a **rendered-surface** check for a multi-literal `help=`/template concatenation; and separately enumerate the citations that **name the vacated location** (the old path, anchor, or heading — e.g. a docs "see `<old file>`"), which a content search never sees. This ports the authoring-tier discipline in `.prflow/prompt-extensions/create-issue.md`'s Interaction-surface map down to the implement tier.
3. **Reconcile each citation against the destination** — repoint the pin/reference/list to where the content now lives, or restore it. The project's own relocation check is the deterministic desk-time net where one exists (its concrete command for this repository lives in the implement prompt extension): it turns a bare `ABSENT` pin into `relocated to <file>` (fail-closed on a genuine deletion or an unresolvable search set). A relocation is not done until both enumerations return only citations pointing at the new location.

**Re-run this sweep after any merge or rebase of the base branch** (the configured `base_branch`, not a hard-coded `main`)**.** A clean *textual* merge is not a clean *semantic* merge: the base branch may have added a fixture, call site, or assertion that your new contract now rejects, and git merges it cleanly without ever surfacing the conflict. After any `git merge` / `git pull --rebase` of the base branch the run performs (including the Error Handling conflict-recovery path), re-run steps 1–3 against the newly-arrived sites and treat any new site that violates the change's contract as a defect in *this* PR.

#### 2.3.0a Peer-checkpoint completeness sweep (mandatory whenever the change adds a rule/clause/guard/invariant that has co-equal peer sites, or peer paths through one unit of code)

This sweep catches 2.3.0's additive twin: you **add** a rule — a guard, a validator clause, a read-only precondition, a classification tripwire, a fallback — and state it at only *some* of the co-equal sites that must all carry it for the rule to actually hold. Each site reads correct in `git diff` and the happy path works, so the asymmetry ships clean. A **peer set** is two or more sites that must each enforce the *same* rule independently (the gate checkpoints of a skill step, the object/scalar/array branches of a config-leaf handler, the selection predicate *and* the parallel derivation that must agree on the same fallback), **or the paths through one unit of code that must each carry the rule**. After adding any such rule, before running tests:

0. **Classify the rule you added — this classification is the arm-selecting operand, and this step produces it.** Decide whether the added rule is a **control-flow property** (an invariant quantified over the paths through a unit of code rather than over textually similar sites) or a rule whose **peers are textually co-locatable**, and record the classification via `--note`. Route every outcome: co-locatable peers → step 1's **search arm** alone, discharged on the evidence that arm already requires, with **no new obligation** from the trace arm; a control-flow property → step 1's **trace arm**; **both** → both arms; **cannot classify** → **both arms**, the trace **bounded to one hop on every edge kind step 1 names** — the swept unit's direct call edges, and one hop on the caller-direction, handler-installation and scope-exit edges — rather than the full traversal, and that narrowing named in the traced-arm note so a bounded trace is not readable as a full one — an undecided classification leaves the co-locatable case live, and the trace arm alone discharges it vacuously. An unrouted classification is a rule this sweep silently skips.
1. **Enumerate the peer set — by search for co-locatable peers, by trace for a control-flow property.**
   - **Search arm.** Pick the shared marker the peers have in common (the clause's keyword, the guarded variable, the predicate name, the step heading) and search for it across the repo — in a granted form per the grep-evidence rule above (Grep tool, then `rg`, then `grep -rnE`; `git ls-files -z | xargs -0` for a count), **never `git grep -n`** — to list every site the rule must hold at. Working from memory is exactly how a peer gets missed.
   - **Trace arm.** For a control-flow property a shared-marker search does **not** establish the peer set: a path that terminates inside a helper the swept unit calls is spelled nowhere in that unit's own text. Establish the set instead by reading the swept unit's source and **following its call edges**, **following dispatch into pre-existing code the diff calls but did not modify**. **Where the swept unit is not code, read the same edges in its own substrate:** a procedure's step-to-step transfers, its gated reference reads, and its terminal, blocked and degraded arms are its call edges, and the enclosing procedure file is the unit — so a substrate with no code has a trace arm to run rather than a fallback to the search arm's match count. Such a rule takes, **at minimum**, the shapes of a terminating path, an early return, and an error exit; and a terminating path is reached other than by a direct call — **at minimum** through a raised error handled by a caller, a shutdown or signal handler, or a scope-exit construct — so read those edges too. **Bound, stated per direction:** a **callee** edge is followed until the reading reaches a construct that terminates or leaves **the unit being read**, or reaches a unit **already visited** on this traversal, recording an already-visited unit rather than walking it again; a **caller-direction** edge — a raised error the caller handles — is followed to the first enclosing handler and no further; a **handler-installation** edge — a shutdown or signal handler, an at-exit registration — is followed to the handler body and no further; a **scope-exit construct** is read as a terminating path of the unit enclosing it and is not traversed past that unit. That makes a cycle and a **mutually recursive** pair terminate, and it is not a traversal of the whole program's call graph. **Two routes for an edge you cannot resolve:** an edge whose callee is unresolvable but whose *kind* is exactly one of **dynamic dispatch, a registry or decorator table, a callback passed in, or an inherited override** is disclosed in the reach note below and does **not** fire the arm; an edge of any other kind — named below or not — takes the §2.3 preamble's **unrunnable arm** — record `2.3.0a: unrunnable (call-edge trace, <the unresolved edge>)` naming that arm's covering backstop, record the reach disclosure and the single-enforcement answer beside it, and withhold only the **closure** claim that the peer set is complete, which a degraded trace has not earned. **That routing is scoped to the traced arm alone** — a search arm that ran on this same rule still records its own match-count evidence, exactly as §2.3.0d routes one half of a two-half search while the other half records its own.
2. **Apply the rule at every member — or record the exemption.** Add the clause/guard/branch at each enumerated site. If a peer is *deliberately* exempt, that is allowed, but the asymmetry must be recorded with a `--note` (which peer, why) — a *silent* one-sided rule is the defect; a *documented* one is a decision.
3. **Reconcile prose that overclaims the rule's breadth.** Grep the diff's own prose, CHANGELOG, and docs for any statement that describes the rule as universal ("every checkpoint", "all branches", "always"). Either make it true at every peer or narrow the prose to match reality — an overclaiming sentence on a half-applied rule is itself a defect.

**After the trace establishes the peer set, ask once** whether a **single enforcement point** would hold the invariant for every path the trace found, transitively reached ones included, and record the answer via `--note`; a **negative answer** discharges the question fully, and a **positive answer** is discharged by installing that enforcement point and recording in the same note which paths it covers — those paths satisfy step 2 and this sweep's closing obligation through that point, and need no per-path exemption note. Asking it later, per path, is how a rule ends up restated at every path that could have carried it once. This answer and the traced-arm reach below are one `--note`, not two, and step 0's classification either joins that note or stands alone — both discharge it, while leaving it unrecorded does not.

**Traced-arm evidence.** The traced arm's `--note` records the unit the enumeration ranged over and the **reach of the technique**: which kinds of call edge the reading established, and which kinds it **cannot** enumerate — a callee reached through dynamic dispatch, a registry or decorator table, a callback passed in, or an inherited override, **at minimum**; and, whenever the trace was bounded rather than fully resolved, **the narrowing that bounded it** — the one-hop bound step 0 imposes on a `cannot classify` rule among them. That is what covers the edge a reader never sees rather than recognises as unresolvable, and it keeps a traced note from reading as a **closed set**. A well-formed traced note therefore carries fields a searched-arm note never does, so the search arm gains no field and the two stay distinguishable; a traced note missing any of them — the bound-narrowing field included — is an incomplete traced note, not a searched-arm one.

**Precedence — what this sweep does NOT cover, and which sweep owns each.** A **changed** contract's dependent call sites are **§2.3.0's**, never this sweep's. Traversal for an **added** control-flow rule's peer paths is **this sweep's**, never §2.3.0's — callee-direction, the caller-direction reading of the handler a raised path reaches, the body of a handler a shutdown/signal or at-exit registration installs, and the scope-exit constructs those paths run through.

The rule is not done until every member the enumeration **did** reach carries it (or an explicit `--note` for each exemption). **Only a fully resolved traversal earns the closure claim that the set is complete.** The other three outcomes each withhold it and instead record what the reading did reach: a trace whose unresolvable edge fell in a declared reach class, a trace bounded to one hop, and the unrunnable arm. None of the three relaxes the obligation to apply the rule at the members already enumerated — and for a control-flow rule a shared-marker search result never supplies that closure on its own.

#### 2.3.0b Enum-enumeration reconciliation sweep (mandatory whenever the change adds a value to an enumerated value set — a code enum/string-union *or* a doc-enumerated configuration set)

**The "enumerated value set" is not only code-shaped.** A **doc-enumerated configuration set** counts too: a workflow's `on:` **trigger list** (adding a `check_suite` / `workflow_run` / `push` trigger), a **config-key set**, or a **permissions list** is an enumerated set that one or more docs also enumerate — so adding a member pulls the doc-mirror reconciliation below into Phase 2, not a later shadow pass. Reading this sweep as code-enum-only classifies such a change n/a and leaves the contradicting doc mirrors to survive to a later shadow pass.


The defect: you **add a value to an enumerated value set** — a new enum/string-union member, a status, a kind, a verdict, a `fix_decision` — update the code call-sites that branch on it, and leave a *doc/comment enumeration* of the value set, or a *fall-through consumer* (an `else` / `default` / `// null` arm that silently absorbs the new value), stale. The runtime can even be *correct* — the new value rides an intended fall-through — while a prose enumeration of the set and a `case`-less consumer go quietly out of date. "Consistent behavior" is not "reconciled enumeration." The 2.3.0 (changed-contract) sweep greps *code* call-sites and 2.3.0a (peer-checkpoint) reaches them by search or by call-edge trace; this one explicitly adds the **doc/comment enumerations and fall-through consumers** they miss. After adding any value to an enumerated set, before running tests:

1. **Enumerate every site that names a member of the set, by search — not from memory.** Search the repo for the *existing* member literals of the value set (not just the new one) — in a granted form per the grep-evidence rule above (Grep tool, then `rg`, then `grep -rnE`; `git ls-files -z | xargs -0` for a count), **never `git grep -n`** — running each known value across code call-sites, jq/py/sh consumers, **doc/comment enumerations** (a prose list of the values, a docstring taxonomy, an inline `// one of: …` comment), **and fall-through consumers** (an `else` / `default` / `// null` arm whose behavior now depends on whether the new value should reach it). Working from the new value alone misses exactly the sites that enumerate the *old* set.
2. **Reconcile each site, or record an explicit exemption.** Add the new value to every enumeration meant to be exhaustive, and confirm every fall-through consumer treats the new value the way the design intends — verify the *intended* arm; do not assume the `else` is correct just because the suite is green. A site deliberately left out (a fall-through that *should* absorb the value) is allowed, but the exemption must be recorded with a `--note` (which site, why) — a *silent* stale enumeration is the defect; a *documented* one is a decision.
3. **Record the grep result as evidence.** Per the "Sweep selection" grep-evidence rule, record the match count plus "all reconciled" (or the specific stale sites you fixed) via `--note` — evidence, not a claim.

The addition is not done until grepping each member literal of the value set returns every enumerating site reconciled (or an explicit `--note` for each exemption).

#### 2.3.0c Operand-trace sweep (mandatory whenever the diff adds a guard, predicate, validator, or coverage invariant in code, or ships agent-executed imperative prose stating a policy)

2.3.0a/2.3.0b catch a rule or an enumerated value replicated across too few sites; 2.3.4 verifies a boundary the diff *reads* but explicitly carves out the diff's *own* code. This sweep closes the gap between them, and it has **two authoritative triggers** — run it when either fires:

- **(a) Code trigger — the diff adds a guard, predicate, validator, or coverage invariant.** A guard whose comparand comes from the diff's own code is covered by no other sweep: 2.3.4 carves out in-diff code, and 2.3.0a/2.3.0b watch peer sites and enumerated sets, not the operand a single guard reads.
- **(b) Prose-policy trigger — the diff's deliverable is a policy-stating command block.** When the deliverable is a `SKILL.md` or `phases/*.md` command block that states a policy the agent must execute, the policy's operand is a value the *agent* has to observe at run time — and a policy stated against an operand no step produces is inert.

Both triggers are the same defect at bottom: a check written against an operand nobody traced back to what actually produces it, so the check passes — or is inert — exactly on the inputs it was added to catch.

**Trigger (a) — the operand table.** For every comparand the added guard/predicate/validator/coverage invariant reads, commit a table to the workpad via `--note`, **one row per comparand**, with these four columns:

| comparand | producer (file + line) | emitted on every path the guard now selects? | what OTHER inputs produce the same value? |
|---|---|---|---|

The fourth column — the one asking what *else* produces the guard's comparand value — is the **load-bearing** one: it is the column that asks "what else exits 2?", since unrelated causes routinely share an exit code, so a guard reading "exit code 2 ⇒ no workpad" acts on a state it never observed. A comparand whose fourth column names another producer of the same value that the guard does not distinguish is a fail-open guard and a defect in **this** PR.

**Derived comparands enumerate their malformed/empty arms.** When a comparand is *derived* — piped through a helper, a parse step, a subprocess, or any pipeline, rather than read as a plain literal — its row additionally enumerates the malformed/empty arms the producer can emit: producer failure (a non-zero exit or a denial), unparseable output, a wrong-type value, a valid-falsy/empty value, and a missing key or file (the `CLAUDE.md` six-shape adversarial-matrix convention applied to a comparand) — and states the guard's decided behavior on each arm. A derived comparand whose row leaves any such arm unenumerated is an unauthored fail-open accident and a defect in **this** PR: the guard's behavior on the unenumerated arm was never decided, so it fails open on exactly the malformed input the operand-trace exists to surface (a `.get('stats')` on non-object JSON that raises, an empty parse result that passes the guard green).

**Trigger (b) — the stated-policy contract.** For every policy the prose states, name (a) the **observable operand** the agent keys the policy on, (b) the **step that produces it**, and (c) an **explicit route for every outcome** of that operand, **including the failure outcome** (the operand absent, the producing step failing, the value unresolvable). A stated policy whose operand no step produces is an inert guard and a defect in this PR — the promised routing can never fire, so the policy silently no-ops on exactly the input it was written to gate.

**A stated policy places its obligation at the execution point it gates**, carrying at most a cross-reference from any thematic section that also discusses it; prose that describes the hazard only in a thematic section, leaving the execution point it gates with no obligation, does not discharge this trigger — the agent reaches the enforcement point and finds nothing there to execute.

The sweep is not done until every comparand has a completed four-column row — with a derived comparand's malformed/empty arms enumerated and each arm's decided behavior stated (trigger a) — and every stated policy names its observable operand, the step that produces it, a route for each outcome including failure, and places that obligation at the execution point it gates (trigger b).

#### 2.3.0d Describing-prose reconciliation sweep (mandatory whenever the change removes a member from an enumerated value set, or weakens a universal it previously asserted)

2.3.0b catches an *addition* to an enumerated set leaving enumerating sites stale; 2.3.0a catches a newly-added rule stated at too few peers. This sweep catches the two edits neither of them arms on, and it has **two authoritative triggers** — run it when either fires:

- **(a) Membership removal.** The change **removes** a member from an enumerated value set.
- **(b) Weakened universal.** The change **weakens** a universal it previously asserted, by any of these three edits: **softening** it (an "always"/"every"/"never" becomes "usually"/"most"/"rarely"), **scoping** it (an unqualified claim gains a qualifier that narrows the population it ranges over), or **removing** it outright.

Both triggers are the same defect: the change made a claim false **without editing the claim**. The surviving sentence still parses, still reads plausibly, and is only *semantically* false — so it ships clean instead of being reconciled here.

**Precedence — what this sweep does NOT cover, and which sweep owns each.** A membership **addition** is **§2.3.0b's**, never this sweep's. **Adding** a rule that has co-equal peer sites is **§2.3.0a's**, never this sweep's. A **rename** — an addition and a removal at once — is assigned to **§2.3.0b alone**, because §2.3.0b's member-literal enumeration already reaches both the vacated literal and the arriving one; a rename does **not** additionally arm this sweep. (This precedence is about the membership family — §2.3.0b and §2.3.0d — only; a diff that independently arms other sweeps still runs each at the domain its own definition states, as it always has.)

**Scope — the enumerated value set is not only code-shaped**, matching §2.3.0b's own stated scope. A **doc-enumerated configuration set** counts: a workflow's `on:` **trigger list**, a **config-key set**, a **permissions list**. A removal from any of those arms trigger (a) exactly as removing a code enum member does.

After removing a member, or weakening a universal, before running tests:

0. **Probe the tools this sweep's search form depends on, before searching**, per the §2.3 preamble's confirm-the-search-actually-ran rule — `type rg` and `type tr` for whichever the form below uses, never `command -v`. Rung one of that ladder is the Grep tool, which the runner always provides, so an absent `rg` is a fall back to another rung rather than a degradation. **The ladder is per search half, and a rung only substitutes for a capability it actually has** — the Grep tool is line-oriented and cannot perform the `tr`-normalized search the hard-wrapped-copy half of trigger (b) needs, so an absent `tr` with no substitute for that half routes **that half** to the unrunnable arm even while the line-oriented half still runs and records its own evidence. Route a search half to the **unrunnable arm** at the end of this sweep when **every** rung available to *that half* is unavailable or refused, or when its search tool exits greater than 1 — and then do not reach step 3's evidence record.

1. **Enumerate the describing prose by search, not from memory** — two searches, because they find different things:
   - **Describing prose that names no member literal.** This is the case §2.3.0b's member-literal grep structurally cannot reach: a sentence describing *where the set came from*, *how many members it has*, *what its members have in common*, or *what the set is for*, which names no member and so matches no member-literal search. Locate it by searching for the set's **defining symbol, heading, table, or file path** — the constant name, the section title, the doc anchor — and read the surrounding prose, docstring, and block/header comments at every hit, including in files the diff never touched.
   - **Surviving copies of the pre-change claim text** (trigger (b)). Recover the pre-change wording from the **deletion hunks** of the §2.3 sweep operand (defined in the §2.3 preamble above — the merge base → working-tree branch delta) — then search for surviving byte-identical or near-identical copies of that claim elsewhere in the repo. A copy that a *different* file still asserts at full strength is exactly the defect this trigger exists to catch.

   **Search domain and command form.** The domain is **the whole repository**, not the diff: a surviving copy of a weakened universal characteristically lives in a *different directory* from the edit that weakened it, so a delta-bounded search cannot see it. Because a claim hard-wrapped at a different column lives on no single line, use the form **§2.3.0's *Relocation is a contract change too* step 2 already mandates in this file** rather than inventing a second technique for the identical search — `grep -rnE` across the repo plus a `tr -s '[:space:]' ' '` normalization (excluding VCS, dependency, and build directories) — with the **Grep tool** or `rg` for the line-oriented half, per the grep-evidence rule above. **Never `git grep`**, which the implement profile does not grant.

2. **Reconcile each site, or record an explicit exemption.** Rewrite every surviving statement so it describes the post-change set, or the post-change *strength* of the claim. A site deliberately left as-is is allowed, but the asymmetry must be recorded with a `--note` (which site, why) — a *silent* falsified claim is the defect; a *documented* one is a decision.

3. **Record the search result as evidence — only if step 0 passed and the searches ran.** Per the grep-evidence rule above, record the match count plus "all reconciled" (or the specific stale sites you fixed) via `--note` — evidence, not a claim. If step 0 routed to the unrunnable arm, record *that* instead: this step's clean evidence note is never written over a search that did not run.

**Unrunnable arm — an absent tool never yields silence**, per the §2.3 preamble's confirm-the-search-actually-ran rule. When this sweep's enumeration **cannot be run** — a required tool is absent on the host, and equally when the search is **denied** by the runner's permission matcher — do **not** report a clean pass. Record `2.3.0d: unrunnable (<which search, which cause>)` via `--note`, **naming the covering backstop** — the Phase 3 review pass, and, when this sweep runs inside the fix loop, the Step 3.5 fix-delta gate plus the convergence shadow — then continue. A degraded environment yields a visible degradation record, never an indistinguishable clean pass.

**Termination is per fired trigger, never both unconditionally.** The two searches serve different triggers — the defining-symbol search serves trigger (a), the deletion-hunk claim-text search serves trigger (b) — so a diff that fired only one trigger runs only that trigger's search, and is not done until *that* enumeration returns only prose consistent with the post-change set, or with the post-change strength of the claim (or an explicit `--note` for each exemption), or the unrunnable arm above has been recorded. A diff that fired both triggers owes both. Demanding the trigger-(b) search on a removal-only diff would mean recording evidence for a search with no input.
