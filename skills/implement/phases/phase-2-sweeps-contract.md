**Verification policy.** Before implementation, identify how the changed behavior and resolved acceptance criteria will be verified. Use the smallest reliable combination of existing coverage, focused automated tests, and direct checks. One check may cover several criteria; retain the documentation and genuinely-live criterion routes in phase-3-ac-gate.md and post-merge-tagging.md. Honor explicit repository testing requirements and agreed criteria; a cheaper check that does not establish the required outcome is insufficient.

Add or extend permanent tests when they protect consequential behavior that existing coverage does not adequately protect. Choose cases by observable outcomes and materially distinct failure modes, not by function, branch or criterion counts. Prefer extending an existing test at the real executable boundary. Include success and failure cases where either alone could conceal a wrong decision; a check of sorting or deduplication needs inputs that exercise that operation. Fixtures must preserve relevant properties and distinguish success from the claimed failure: a preservation check needs original state different from the value an erroneous overwrite would produce.

For a reproducible bug, prefer a failing regression test before fixing it. Reuse an existing failing test. A test written later can establish regression detection by failing against the unfixed artifact for the intended reason and passing against the fix. Exercise the shipped implementation, never a re-typed copy. A log or direct reproduction can establish the original failure without automatically becoming a permanent test.

Existing behavioral coverage can suffice for a refactor or deletion. Add a helper, fixture system or framework when its continuing value justifies its maintenance, not solely to force a test-first sequence or a unit-test boundary. Apply the same judgment to workflow inline shell: verify the actual selector or integration, extracting it only when that improves the design or provides worthwhile reusable coverage.

**Test effectiveness.** Confirm that a new test is collected and checks the intended outcome. Use a targeted mutation when there is a concrete reason the test could pass with its claimed protection broken, especially preservation or fail-open checks; an observed regression RED already establishing that sensitivity needs no second proof. For a negative test, distinguish the intended rejection from unrelated failures. Reuse existing valid controls where they establish that distinction.

When mutating, prefer a disposable copy the test can read. For an in-place check, wait for other tests using the file to finish, save a byte-identical copy under `.prflow/tmp/in-place/<repo-relative path>`, and record the path and `git hash-object --no-filters <file>` ID in an immediate workpad note before changing it. Confirm the copy has that ID; if the comparison fails, delete the new copy and report `unrunnable: no byte-identical copy`, without mutating. Break the behavior, run the focused check, revert the exact mutation, and confirm the original ID before another edit or deleting the copy. On an immediate mismatch restore the verified copy and re-check; if it still differs, stop Blocked naming the file and both IDs. For a leftover copy, compare the file's ID first: delete the copy only on a match with the recorded original ID; otherwise stop Blocked without changing either file, naming the file and both IDs (or the unavailable ID). Commit nothing while an unsettled copy remains; never use `git stash` or `git checkout -- <file>` over unrelated edits.

**Test boundaries.** Test executable behavior and machine-consumed contracts. Keep reusable scratch verification rigs under an ignored path and out of commits; reuse them only while they still exercise the current implementation. A one-off check need not become a permanent harness.

Phase 2.4 owns direct and prompt verification. Record a denied, unavailable or inconclusive check as unverified. Otherwise obtain sufficient evidence now or stop Blocked. A quiet review is not substitute evidence. Repository suite and completion gates still apply. Comment discipline (authoring rule). A comment the change adds or modifies survives inline only if a competent agent would otherwise make a specific, nameable wrong change — at this line, or at a coupled site the clause names by file or symbol; that coupled arm is what the coupled-invariant discipline depends on, so it survives only when the clause names the site. Write it as the prohibition and its consequence, keep it no longer than naming that wrong change and its consequence takes, and delete or relocate the surplus — a derivation, a worked example, provenance, design narrative — through a `relocate to docs:` workpad note (§2.3.4a) for Phase 4.1 to place. Length alone is never the finding: an author who cannot name the wrong change a comment prevents has established there is none, and it goes. This rule binds exactly four populations and nothing else, complete by construction: inline comments in library and script source; test files; module docstrings and contract headers; and workflow and YAML files. Every other commented surface — skill and agent prose bodies among them — is outside the bound set.

Three carve-outs are absolute, complete by construction. A comment a tool, a licence, or a policy requires to be present — including one a required coupled mirror or a suite pin requires at a specific site — is not prose under this rule and is never removed by it; that covers both a machine-read declaration or suppression marker a tool parses and a licence, SPDX, or vendored-attribution header no tool parses. A contract-header docstring's specification statement stays while the derivation, precedent and provenance around it move, because a stated specification is what makes the code comparable against it. And where the author cannot decide whether a comment is load-bearing, it stays. A mirror-fact claim authored anyway — a comment restating a fact the code beside it already carries, the distinct rule the 2.3.4a self-authored-claim reconciliation sweep still owns — is reconciled there, along with any prevention-failing comment this authoring rule missed.

**Sweep selection.** The 2.3.x sweeps below are **not a flat checklist** — classify the diff and run the sweeps its shape warrants (**when in doubt, run them all**). Each sweep's heading states its own authoritative trigger; this list only tells you which to *consider*:

- Deletes code (a call site, branch, method, file, route, page, or asset) → run 2.3.1, and 2.3.2 if it deletes a method/file/route/page.
- Changes a contract (a signature, a renamed/moved symbol, a tightened validator, a routing/branch predicate, which inputs reach an output value, or a relocated prose literal, heading, section, or file path) → run 2.3.0.
- Adds a rule that has peers (a clause, guard, validator, or invariant that must hold at two or more co-equal sites — or at every path through one unit of code — for the rule to actually hold) → run 2.3.0a.
- Adds a value to an enumerated set (a new enum/string-union member, status, kind, or verdict value — *or a member of a doc-enumerated configuration set: a workflow trigger list (the `on:` event set), a config-key set, a permissions list*) → run 2.3.0b.
- Removes a value from an enumerated set (an enum/string-union member, status, kind, or verdict value — *or a member of a doc-enumerated configuration set: a workflow trigger list, a config-key set, a permissions list*) → run 2.3.0d (describing-prose reconciliation sweep). A rename is not this arm — it is an addition and a removal at once, and §2.3.0d's precedence assigns it to 2.3.0b alone.
- Changes what an already-stated rule, call sequence or claim means — weakening a universal (softening, scoping or removing it) is one such change; so are strengthening it, changing a condition or outcome, reordering a sequence, and an added sentence or member that changes when, whether or in what order it applies → run 2.3.0d.
- Adds or hardens a guard, predicate, validator, or coverage invariant (in code), or ships agent-executed prose stating a policy → run 2.3.0c (operand-trace sweep).
- Adds a collection output with ordering, dedup, or aggregation logic (a sorted list, a deduped set, a grouped or counted tally, a tie-broken ranking) → run 2.3.7 (collection-cardinality sweep).
- Always, whatever the diff's shape → run 2.3.3 (convention), 2.3.4 (boundary-assumption), 2.3.4a (self-authored-claim reconciliation), 2.3.4b (coverage-claim enumeration), 2.3.5 (simplification & efficiency), 2.3.6 (error-handling & silent-failure).

This narrows *ceremony*, never *coverage*, and is fail-safe: each sweep's heading is authoritative, so if its trigger fires you run it even when this list didn't call it out — if the index ever drifts from a heading, the heading wins. The trigger shapes above are substrate-agnostic — a contract, a peer-replicated rule, or an enumerated-set membership can live in prose / `SKILL.md` / doc / config just as much as in code (a repository's own coupled-invariant rule spans code mirror sites — a constant, a config-key name, a `SKILL.md` contract pin a `run.sh` grep asserts — as well as prose ones), so classify by what the change replicates across sites, not by whether it is code. An add-only diff that replicates nothing across sites typically runs just the always-on sweeps — but an add-only prose/doc/config diff that adds a peer-replicated rule, a value to an enumerated set, or a contract literal mirrored elsewhere still trips the contract-completeness sweeps (2.3.0 / 2.3.0a / 2.3.0b), not just the always-on set. Record the diff shape you classified and the sweeps you are running in a workpad `--note` — the selection is then an auditable commitment a reviewer or the weekly retrospective can check, not a silent skip; a note reading "add-only" on a diff that in fact deleted a file is a visible error, where an unrecorded mental skip is not.

The §2.3 sweep operand (defined once here — every diff-consuming sweep below reads THIS, never its own `git diff`). The operand every §2.3.x sweep grades is the delta from the merge base with the configured base branch to the current working tree — the whole branch delta, committed and uncommitted work alike. It is defined in this one place; no individual §2.3.x sweep restates it. It is deliberately **not** `git diff HEAD` / `git diff --staged` / `git diff -U0`: the durability checkpoint below commits each sweep boundary's work, so an uncommitted-only operand is near-empty by the time a sweep reads it and the sweep grades almost nothing while still recording a clean pass.

Resolve the operand substitution-free (the worktree tier refuses `$(…)`, backticks, `$?`, and a variable bound and read within one fence). First read the base branch — defaulting to `main`, never hardcoded — in its own fence, and read the printed value from the tool result:

```bash
.prflow/vendor/prflow/scripts/config-get.sh .base_branch main
```

The ref is the fetched remote-tracking `origin/<base>` — substitute the printed base as a literal; a cloud checkout creates only remote-tracking refs and has no local base branch, so a bare name resolves nothing. Then take the branch delta with `git diff --merge-base`, which diffs the merge base against the working tree in one read (see `git diff --help`; needs git ≥ 2.30):

```bash
git diff --merge-base origin/<base> -U0
```

Pipe it to whatever the sweep consumes, exactly as it consumed its former `git diff` (a search sweep greps it). Two sweeps need a different projection of this same operand, not a different operand: §2.3.0 reads rename records with `git diff --merge-base origin/<base> --name-status`, and §2.3.4b still names each new file explicitly (a merge-base diff, like `git diff HEAD`, lists no untracked file).

Degraded arm — record degraded, never a clean pass. The branch delta cannot always be computed. When the `origin/<base>` ref is unfetched or absent (a shallow or partial clone, no `origin` remote), when `git diff --merge-base` is **unavailable** (git < 2.30), when there is no reachable merge base, or when the case is an ambiguous multi-merge-base, the operand is degraded. On git < 2.30 where `git merge-base origin/<base> HEAD` itself still resolves, read the merge-base SHA in its own fence and substitute it as a literal into `git diff <sha> -U0` — the same operand without `--merge-base`. When none of those recovers the operand, record the sweep degraded via `--note`, naming the condition that fired (unfetched/absent base ref, `--merge-base` unavailable, no reachable merge base, or ambiguous merge base), and do not record its clean match-count evidence — a degraded operand is a degraded sweep, never a silent clean one.

Ground-once ledger — bounded work across boundaries. Each boundary handles only what earlier boundaries did not already record. Keep the machine-consumed ledger at `<run-scratch>/phase2-operand-ledger-$ISSUE_NUMBER.md`: after each boundary, append one compact `§2.3 operand ledger:` entry stating the operand range examined, newly handled work, and earlier coverage; the ledger is never copied to the workpad. Later boundaries Read only this compact artifact and skip what it records. If it is missing, unreadable, or malformed, redo the earlier covered work and recreate the artifact while recording this boundary degraded in each affected sweep's result note. Write the artifact with the Write tool, not shell redirection.

One result, one note. Each run of a selected sweep writes its result — a count and verdict, the offending sites, or its degraded or unrunnable record — once (per search half in 2.3.0d, per arm in 2.3.0a), and a re-run whose result is unchanged writes none. It goes in its own `--note`, or in the sweep-selection note (*Sweep selection* above) only when the result is already known as that note is written and the note still fits the per-note byte budget; the selection note is never held back for a result. The verification notes are the record of the chosen checks and evidence: a later note cites them, never recaps them.

Run each selected sweep after implementing and before running tests (Phase 2.4) — that timing is the same for every sweep. Durability checkpoint (§2.0.5): because §2.3 routinely outlasts the ~10-minute loss window, take a durability checkpoint at each §2.3.x sweep boundary you cross — naming the files produced since the previous checkpoint — so mid-sweep work is durable on the remote before §2.4/§2.5. Because the §2.3 operand above is the whole branch delta (merge base → working tree), committing a boundary's work at this checkpoint removes nothing from any later sweep's operand — the checkpoint and the sweeps no longer conflict. A non-zero exit here takes §2.0.5's resolve-before-continuing rule: do not start the next sweep on an unlanded checkpoint.

Sweep-evidence record (observational; never changes the selection), once, on the last selected sweep's boundary. Run `.prflow/vendor/prflow/scripts/compose-run-key.sh` (ladder as for `workpad.py`); its printed line is `run_identity` (`local-<timestamp>-1` off the cloud tier) — if it prints nothing, note that and skip the record. Write `<run-scratch>/sweep-evidence-$ISSUE_NUMBER.json` as `{"schema_version":1,"kind":"sweep-evidence","run_identity":…,"diff_shape":…,"selected_sweeps":[…],"results":[{"sweep_id":…,"outcome":"completed|degraded|unrunnable"}],"catches":[{"catch_id":…,"discovered_by":…,"evidence":[…]}]}` — one result per selected sweep; one catch per distinct correction, owned by the earliest sweep that found it — a confirmed claims-angle catch by the 2.3.4a or 2.3.4b sweep that reconciled it, its evidence naming the cleanup reviewer. Add `--record-sweep-evidence <that file>` to that boundary's `workpad.py update`; a refused record aborts the call, so rerun it without the flag and note the refusal. Then `rm` the file.

For the search-based sweeps (2.3.0, 2.3.0a, 2.3.0b, 2.3.0d, 2.3.2), don't merely attest you searched: run the actual search the sweep describes, in a granted command form, and record a concise result via `--note` (the match count plus "all intended", or the specific offending sites) — evidence, not a claim. 2.3.0a's traced arm records its traced-arm evidence instead of a match count. The granted line-oriented forms, in order: the Grep tool, else `git grep --untracked -nP -e '<pattern>' -- :/`. For a quantitative match count over tracked files, use `git grep -c -P -e '<pattern>' -- :/`. Escape a searched literal's regex metacharacters in each form.

Before recording a zero-match result as clean, confirm the search actually ran — this binds every search-based sweep above, not only the one whose body restates it, and the same arm equally admits one non-search cause — a call edge 2.3.0a's trace can neither resolve nor place in a declared reach class. Treat a search the runner refuses, or a search tool that exits greater than 1, as unrunnable. A `git grep` exit of exactly 1 is zero matches, not a failure — never route an honest empty result to this arm. A missing tool routes to the unrunnable arm only when every rung available to that search is unavailable or refused — for a line-oriented search, `git` is preflight-guaranteed, so an absent Grep tool alone is a fallback, not a degradation. On that arm record `<sweep>: unrunnable (<search type, pattern and scope>, <cause>)` via `--note` (the search type is the kind of match and file set, never the program that ran it), or for the call-edge cause the `2.3.0a: unrunnable (call-edge trace, <the unresolved edge>)` record its reference gives, naming the covering backstop — the Phase 3 review pass — and do not record the sweep's clean match-count evidence.

A search that ran is not yet a search that delivered. A clean result requires the *relevant output* to have been inspected in full — covering the query's term alternatives and its repository domain. Incomplete delivery — at minimum a preview, a saved-output notice, a continuation, or a cut-off result — establishes no such coverage, even when the search exited 0. Recover the full coverage first: complete reads of the retained output, and partitioned searches that between them preserve every original term and the whole domain (each partition names its counting operand and no match is counted under two partitions). Recovered coverage supports a clean result exactly as an uninterrupted one does. When the relevant output stays incomplete after recovery, record the sweep `degraded` via `--note` — the reach inspected, the reach still missing, the cause, and the same covering backstop the unrunnable arm names — leave the offending sites you already identified in the record, and do not record clean match-count evidence for that search. These three states are distinct and never conflated: an established *complete no-match* is clean; an *incomplete delivery* is `degraded`; an *unavailable, denied, or failed* search is `unrunnable`.

Each conditional sweep below — 2.3.0, 2.3.0a, 2.3.0b, 2.3.0c, 2.3.0d here, and 2.3.1, 2.3.2, 2.3.7 in phase-2-sweeps-quality.md — keeps its trigger and a resident predicate statement in its phase file, and carries its procedure in its own reference under `<skill-dir>/references/`. Marker contract. Accept the load only when the file's first line is its `start` boundary marker and its last line the matching `end` marker, each naming that file's own path — compared against the plugin-relative form starting `skills/implement/references/`, with any vendored (`.prflow/vendor/prflow/`) or absolute prefix stripped from the resolved read path first. Degraded arm — degrade, never halt. #### 2.3.0 Changed-contract sweep (mandatory whenever the change modifies a signature, renames/moves a symbol, tightens a validator, changes a routing/branch predicate or which inputs reach an output value, or relocates a prose literal, heading, section, or file path)

Predicate. #### 2.3.0a Peer-checkpoint completeness sweep (mandatory whenever the change adds a rule/clause/guard/invariant that has co-equal peer sites, or peer paths through one unit of code)

Predicate. Fires when the change adds a rule — a guard, a validator clause, a read-only precondition, a classification tripwire, a fallback — that has co-equal peer sites, or that must hold on every path through one unit of code. A peer set is two or more sites that must each enforce the same rule independently, or the paths through one unit of code that must each carry it. A changed contract's dependent call sites are §2.3.0's, never this sweep's.

**Procedure:** `<skill-dir>/references/sweep-2-3-0a-peer-checkpoint.md`, read under the gated-procedure protocol above.

#### 2.3.0b Enum-enumeration reconciliation sweep (mandatory whenever the change adds a value to an enumerated value set — a code enum/string-union *or* a doc-enumerated configuration set)

Predicate. Fires when the change adds a value to an enumerated value set. The set is not only code-shaped: a set enumerated in documentation — a workflow's `on:` trigger list, a config-key set, a permissions list — is in scope as well. A rename is an addition and a removal at once and is assigned to this sweep alone, not additionally to §2.3.0d.

#### 2.3.0d Describing-prose reconciliation sweep (mandatory whenever the change removes a member from an enumerated value set, or changes what an already-stated rule, call sequence or claim means)

Predicate. Two authoritative triggers — run it when either fires. (a) Membership removal: the change removes a member from an enumerated value set, doc-enumerated configuration sets included. (b) Changed meaning: the change edits text stating a rule, call sequence or claim so that its meaning changes — weakening a universal (softening an "always"/"every"/"never", scoping it with a narrowing qualifier, or removing it) is one such change; strengthening it, changing a condition or outcome, reordering a sequence, or adding a sentence or member that changes when, whether or in what order it applies are others. A membership addition is §2.3.0b's, and fires (b) too when it also changes such a rule's meaning; a rename is §2.3.0b's alone. When unclear, (b) fires.
