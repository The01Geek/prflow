#### 2.0 Resume-idempotency gate — procedure

You reached this because `phase2_resume.resume_kind` is `in-flight` or `terminal-re-trigger`, before §2.0's compact-state checks ran. Follow it only once they pass; a failed check discards it for full discovery. Conjunct (c) reads the Phase 1 audit reader's printed output, which carries exact actionable prior decisions/corrections plus the worker's superseding assumptions, external-fact results, and wrongly excluded surfaces. When Phase 1.6's reuse gate fired there is no such output: the adopted audit supplies an **empty actionable set** in its place (a clean audit is the only one reuse adopts), and every audit-output site below reads that empty set.

Fire the gate when, and only when, all three conjuncts hold:

- (a) `phase2_resume.resume_kind` equals the bare token `in-flight`, or equals `terminal-re-trigger` and `workpad.py reuse-check $ISSUE_NUMBER plan` exits 0. Compare the JSON value exactly, never by containment. Null or any other value does not fire. Intake does not reset the Plan on resume, so a terminal attempt's Plan is built on only when its recorded plan inputs still match the live issue body; exit 1 or 2, or no output, does not fire.
- (b) `phase2_resume.plan_rows` contains at least one real Plan checkbox row and is not exactly the seed placeholder `- [ ] _(planning in progress)_`. Preserve both checked and unchecked rows: `--tick-plan` changes their state as implementation proceeds.
- (c) Every actionable item in the audit handoff's prior-decision/correction and audit-result arrays is already represented by the committed Plan. Compare the instruction/outcome, source, authority, and evidence fields, not keywords. A new or unrepresented correction, superseding assumption, external-fact result, or wrongly excluded surface makes the gate not fire so discovery and planning incorporate it; an empty array satisfies this conjunct.

Conjunct (a) remains a workpad-derived classification, never observable repository state. Branch adoption feeds nothing into it. A run whose branch pre-check adopted a prior attempt still presents the intake decision; missing classification/Plan state therefore fails toward full discovery.

On a gate fire, skip the Phase 2.1 `code-explorer` discovery dispatch and the Phase 2.2 `code-architect` dispatch plus re-planning (§2.2's Path A / Path B planning through §2.2.4's Reuse & Altitude gate — the range ends at the §2.2.4 plan write), and build on the committed `## Plan` and the §1.4-adopted branch state instead of re-discovering the system from scratch. Record the decision — `workpad.py update $ISSUE_NUMBER --note "Phase 2 §2.0 resume gate: fired (resume-kind <kind> + committed Plan present); skipping code-explorer/code-architect re-dispatch and building on the committed Plan"`. Then:

- The skip is scoped to the two DISPATCHES, never to a Blocked-capable gate that sits between them. §2.1.5 (the Reproduce-First gate) lives inside the §2.1–§2.2 range but is not skipped: it re-runs idempotently against the committed workpad (a populated `## Reproduction` section makes it a no-op; an absent one still Blocks on a bug-report classification). Skipping it would bypass a stop condition whose designed outcome is `Blocked`, letting a resumed run that cannot reproduce proceed to implementation and PR.
- Still run §2.2.5 (Scope-Adjustment) and §2.2.6 (AC-Plan reconciliation) idempotently before §2.3. The gate's skip is scoped to *re-derivation*, never to the post-plan-write mandatory steps: the Plan is written by §2.2.4 before §2.2.5/§2.2.6, so "Plan present" cannot prove those two ran. §2.2.5 on a cloud `GITHUB_TOKEN`-fallback run narrows capability-blocked ACs and can take the empty-pushable-subset Blocked path, so skipping it would push a resumed run into implementation and PR creation for work that should have Blocked or been deferred. Both read the committed workpad ACs, so re-executing them is idempotent.
- Still re-verify against a fresh tree. The gate builds on the Plan and re-verifies what is already implemented and what remains against a freshly-read tree — the fresh-tree read-target and cross-pass-coherence rules stated in §2.1 remain in force; the gate never substitutes blind trust in a stale Plan for those freshness rules (a resumed run's tree can have advanced since the first attempt).
- Onward routing — and the second thing an all-ticked Plan cannot prove. When every `plan_rows` item is checked and fresh-tree re-verification confirms nothing remains, do not re-run §2.3 implementation or §2.5's commit of already-shipped work. Plan rows do not prove §2.4 or the mandatory sweeps ran, so use the handoff's exact `code_sweeps_complete` boolean: when false, run §2.4 and the §2.3.x sweeps before leaving Phase 2, then tick the Implement row. Exit linearly to Phase 3; an existing PR never authorizes skipping review. When unchecked Plan rows remain, re-verify each against the fresh tree first, tick work already present with an evidence note, and implement only what remains.

This gate covers the Phase 2 subagent dispatches only; Phase 3 §3.1 decides review reuse.

Criterion re-derivation on this path. Phase 1.3's resume-path `--replace-acs-file` mirror re-mirrors the issue's `## Acceptance Criteria` wholesale while a prior run's §2.2.5 scope-decision records still sit in `## Progress`. The *set* stays safe (a superset of the issue body — nothing dropped), but those surviving records describe deferrals the live set no longer reflects. So re-derive your acceptance criteria from the issue and re-apply any narrowing that still holds through §2.2.5 — never treat a stale record as a live description of the current set.
