- `<dispatch>` — `not-applicable` on the no-shadow-owed arms; `attempted` only when this run positively knows the Step 2.6 fan-out was launched, including on the `CLEAN-NOT-VERIFIED` lost-write arm, where the fact is the `shadow fan-out dispatched: …` clause the loop renders on its missing-`shadow`-block arm (`loop-exit.md`), read from the loop's own record and never inferred from the missing block; `never` when this run positively knows a shadow the run owed was not launched; `unestablished` on any other arm, where the loop renders no dispatch fact at all.
- `<roster>` — `not-applicable` on the no-shadow-owed arms, where no roster was measured; on every arm where a shadow was owed (including `CLEAN-FULL`), read the fix loop's `iter-<N>.json` `shadow` block and derive the axis from its actual `reviewers_dispatched`-vs-`expected_reviewers` join — `all` (the alias `scripts/workpad.py` normalizes to the stored `complete`) only when every expected member is joined, `short` otherwise — never from the marker's summary token alone; where no such block was read, `unestablished`.
- `<checklist>` — `not-applicable` on those same arms; otherwise read from that same block's checklist state: `all` (normalized to the stored `complete`), `skipped-intentional` (`checklist_skipped` reading `"intentional"` — the shadow reference's `small_diff`+`config_only` skip, which is not a shortfall), `skipped` for any other skip; where no such block was read, `unestablished`.

Reusable review (rides the stamp call above). On a `CLEAN-FULL <result>` exit whose record reads `full attempted all` with checklist `all` or `skipped-intentional`, add `--record-reusable-review <result>` so a later resume can reuse this review while the head, merge-base and issue body still match. Omit it on every other arm.

In-loop roster reflection (rides the stamp call above). Read `phase3_failed_agents` from the highest-numbered `iter-<N>.json` the `review-and-fix` invocation whose exit this stamp records wrote — on the cloud tier both invocations share one `<slug>/<run-id>` directory and iteration numbering restarts, so when the stamped invocation's final iteration file cannot be told apart from an earlier invocation's, the outcome is unestablished. When that array names one or more reviewers, add `--reflection-kind dropped-failed` and one `--reflection` to the same stamp call, naming that iteration number and each lost reviewer identifier verbatim, so a reviewer that has no per-agent efficiency-trace entry still has this durable record. On any of these unestablished conditions, complete by construction — that shared-directory ambiguity, the file cannot be read or parsed, `phase3_failed_agents` is absent, it is not an array, or it holds a non-string element — record instead one `dropped-failed` reflection stating the final iteration's in-loop reviewer outcome is unestablished with its reason, except where this run's `<slug>`/`<run-id>` were not held, when the not-held reflection above already discharges it and no second reflection is written. On a present-and-empty array record no reflection. Keep the reflection text interpolation-safe — no backtick, dollar sign, or double quote — so it needs no `--reflection-file` recipe. The terminal Complete gate and the coverage record are unchanged.

`<roster>` and `<checklist>` are this loop's own comparison results — the loop still derives each axis value itself — but the per-member `--record-roster-member` enumeration is now what makes a `complete` roster auditable, so the gate cross-checks a `complete` claim against the always-on roster rather than trusting the summary alone. On any arm where a shadow was owed, guessing a clean value in place of a block that was not read fails open; `unestablished` is the honest record there, and `not-applicable` is available only on the no-shadow-owed arms.

Tick the three Review extension rows on every Phase 3 exit — this clean-completion path, the `APPROVE WITH UNRESOLVED SHADOW FINDINGS` and `REJECT` branches, the severity-aware soft-proceed and the Blocked path alike, because those three extensions loaded on all of them and an unticked row would assert the run never established their state — except on the second-refusal arm, where the `review-and-fix` Skill call was refused twice and the loop never loaded, when those rows stay unticked with the state-not-established note. First Read `<skill-dir>/references/extension-row-ticks.md` and validate its shared-reference markers under the root contract; apply that rule to the review engine, the fix loop, and the code-review reception extensions without reloading Phase 1:
```bash
"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/workpad.py update $ISSUE_NUMBER \
    --tick-progress "extension resolved: review.md" \
    --tick-progress "extension resolved: review-and-fix.md" \
    --tick-progress "extension resolved: fix.md" \
    --note "<how this run established the review engine's extension state>"
```
One moment, one call: the `--record-review-coverage` stamp above stays its own call, carrying the in-loop roster reflection above in that same call when one is owed. The `--note` states how this run established the review engine's extension state: its ladder runs inside the fix loop's own turn sequence and is reached by a file read rather than a Skill-tool call, so there is no separate return to observe. Where that state cannot be established here, leave that row unticked and say so in the note — never tick it from recall.

If the skill returns `APPROVE WITH UNRESOLVED SHADOW FINDINGS` (the iteration-cap shadow pass surfaced new Important — never Critical — findings the loop could not address; see that skill's Step 2.6 outcome 2): this is not a clean approve. The findings came from a *full-coverage* shadow pass and are real, but they reach you only in chat + the report's `## Unresolved Shadow Findings` section (they do not flow through the Step-3 deferrals manifest, so Phase 4.0.5 will not file them). You may not silently hand-fix them and ship — any fix you apply to resolve them is itself unreviewed spec/code that no independent pass has seen, and shipping it is the unreviewed-final-edit gap the skill's caller contract forbids. Carry them into the handoff's `unresolved_findings` array so the parent surfaces them. Pick one:
1. Fix + re-review (bounded once). Apply fixes for the unresolved findings, commit (`fix:` prefix). The bounded re-review below is a second, separate inline `review-and-fix` invocation whose own Loop Exit can be dropped exactly like the first invocation's, so its telemetry needs its own post-return backstop (there is no pre-loop snapshot to take — the persist backstop is addressed per-run by identity). Re-invoke `review-and-fix` exactly one more time (Skill tool, same argument shape as the initial-review site in 3.3 above — the draft PR number as a bare leading numeric token ahead of `--push-each-iteration --issue $ISSUE_NUMBER`, taking the same omit-the-token arm when the dispatch supplied the empty-brackets or absent disposition, and record on the workpad which arm you took) so the fix delta gets an independent shadow/review pass — the loop's *Clean-iteration-1 exit* does not apply to this invocation, which runs its shadow — and immediately after it returns, re-run the same post-return persist backstop from 3.3 above (the targeted persist fence and the `persist-outcome:` routing; the self-check ran once after the first invocation and is not repeated), addressed to the run directory that invocation held — this second invocation's telemetry is protected exactly like the first invocation's, not left unguarded at this seam. On the cloud tier both invocations share one `<slug>/<run-id>` directory (the run key is a function of the runner environment), so an `ok already-persisted` outcome after the second invocation is a recorded limitation — its per-iteration workpads were re-copied to the telemetry branch under the shared key while no second effectiveness record was derived — not a loss. A clean approve-family verdict (`APPROVE` / `APPROVE WITH CAVEAT` / `APPROVE WITH ADVISORY NOTES`) on a full-coverage shadow clears the re-review — read the re-review's own loop-verdict marker first exactly as above (a `CLEAN-FULL` token clears it; the `shadow agreed, full coverage` headline token is the older-loop fallback, same surface as the gate note above) — treat it exactly as a clean completion above (flush residual fixes and issue that path's own `--tick-progress "Review-and-fix loop"` call). Then continue. A clean verdict whose shadow was `not verified` does not clear it: the re-review exists precisely to give the hand-fix delta an *independent, full-coverage* pass. Any other outcome routes through the severity-aware exit below — it does NOT automatically Block (e.g. `APPROVE WITH UNRESOLVED SHADOW FINDINGS` again, `REJECT`, or a not-verified re-review). Do not loop a third time: trigger at most one orchestrator-initiated re-review. (The bounded re-review is an ordinary `review-and-fix` run, so if *it* defers a finding through the Step-3 deferrals manifest, that is the normal Phase 4.0.5 follow-up-issue channel and proceeds as usual — the "AWUSF findings do not flow through the deferrals manifest" rule above is about the *first* run's unresolved shadow findings, not the re-review's own deferrals.)
2. Do not fix — route directly through the severity-aware exit below (treat the unresolved findings as "unresolved after the cap").

Severity-aware exit (do not fully block on diminishing-returns). Reached when the bounded re-review did not return a clean and full-coverage verdict, or when you chose option 2. Two consecutive non-clean review passes (the capped first run + the bounded re-review) is not, by itself, grounds to abort the whole implement lifecycle — hard-blocking there discards the completed work and the review-ready PR over findings that are often advisory or over-graded. Instead, classify the residual unresolved findings by severity and route. First ensure over-grade calibration has actually run on the residual: the loop's over-grade calibration gate (`/prflow:review-and-fix` Step 2.6) — which *flags* a promote-path over-grade and *requires a recorded `severity-calibrated` technical evaluation*, never auto-demoting — ran on the residual only if a bounded re-review actually ran (option 1). On option 2 (you chose not to re-review) and on a first-run REJECT (which may never have reached the shadow-promotion decision where the gate fires), the gate has *not* run — do not assume a finding was already calibrated; apply the same flag-and-evaluate calibration yourself before classifying, and grade conservatively (default to Critical-treatment on doubt). Then route:

- A genuine unresolved Critical — a real Critical (a data-loss/exploit/correctness break citing a concrete failing input), or an Important the orchestrator judges it cannot responsibly defer → Blocked path below (the human gate genuinely applies). The same applies to a re-review that errors / returns no parseable verdict at all (no findings to classify → fail closed), and to any residual whose severity is missing, ambiguous, or cannot be confidently graded — an ungradeable residual fails closed to the Blocked path, it does **not** fall through to soft-proceed. The same applies to a non-convergence reported as `engine-root: incomplete`: the engine never ran, so there are no graded residuals and the soft-proceed test below would pass vacuously on an unreviewed PR. A criterion-conflict decline never exempts a Critical or ungradeable residual. A confidently graded residual below Critical is exempt from this bullet when one `iter-*.json` in either `review-and-fix` invocation's run directory holds a `fix_decisions` pushback row whose `evidence` begins `criterion conflict:` and quotes the full text of one criterion line (checkbox marker excluded) of that run's `acceptance_criteria` — a fragment, or an absent, unreadable or `""` value, exempts nothing — and whose `parking_evidence.finding_ref`, resolved in that same directory, names a `phase3_findings` record whose `defect_signature` object equals the residual's before handoff serialization (a `null` signature never matches): it soft-proceeds, its reflection quoting the latest such row's `evidence`.
- Otherwise — the residual is only advisory / Suggestion / `severity-calibrated`-down / a deferrable Important, *and every residual was confidently gradeable as non-Critical* → Soft-proceed path: do NOT block. The PR is review-ready, not auto-merged; the residual findings ride into the human's merge decision rather than aborting the run.

Soft-proceed path. Surface the residual findings durably and continue, returning a `proceed` handoff outcome carrying those residuals in `unresolved_findings`:
- One moment, one call: every residual finding and the `review-and-fix` gate tick go in a single `update` — one `--reflection-kind` covers them all, and `--reflection` repeats once per residual: `workpad.py update $ISSUE_NUMBER --reflection-kind dropped-failed --reflection "Unresolved after bounded re-review ({grade}, surfaced for human review): {finding}" --reflection "…{each further residual}" --tick-progress "Review-and-fix loop" --note "Review-and-fix did not reach a clean+full-coverage verdict; soft-proceeded on residual findings (surfaced above) — PR is review-ready, not auto-merged"`, where `{grade}` is `non-Critical`, or an exempt residual's original grade. The reflections land under `### ⚠️ Action required`.
- Carve-out — text needing the file-based recipe still rides in one call. Review-finding prose routinely carries a backtick, a `$` or a double quote, and `SKILL.md`'s interpolation-safe contract mandates `--reflection-file` for it on every tier; that flag now repeats (one payload file per residual) under the call's single `--reflection-kind`, riding with the `--tick-progress "Review-and-fix loop"` tick and the `--note` in one call. A single unreadable, empty, undecodable, or repeated-stdin-`-` payload aborts the whole call with no PATCH, so re-send the call with that payload fixed.
- The parent continues to Phase 3.4 and Phase 4 on your `proceed` handoff. The PR ships per the configured `implement_pr_state` with the residual findings documented in the workpad and (where the re-review wrote a deferrals manifest) carried into the PR body by Phase 4.0.5 / `/pr-description`. The human merger decides. Do not silently hand-fix the residual findings after this point — that is still the unreviewed-final-edit gap; they are *surfaced*, not *resolved*.

Blocked path (genuine unresolved Critical, an `engine-root: incomplete` root, an `evidence-missing` terminal, an excluded-class residual row after the Phase 3.3 flush, or the `review-and-fix` Skill call refused twice). Reached from the severity-aware exit when a genuine unresolved Critical remains (or a verdict cannot be parsed at all — fail closed), from the residual-flush step above when an excluded-class row (untracked / staged-new / rename-copy) is still present in the after-capture, from the second-refusal arm above when the `review-and-fix` Skill call is refused twice, and from the loop-verdict marker resolution above when a `NO-MARKER` reading accompanies a loop that reported the `engine-root: incomplete` or `evidence-missing` terminal: `workpad.py update $ISSUE_NUMBER --status Blocked --reflection-kind blocked --reflection "Review-and-fix unresolved Critical (or unparseable verdict): {summary}"` — on the `engine-root: incomplete` entry substitute `--reflection "engine-root: incomplete — {path}"` naming that `SKILL.md` path for that literal, on the `evidence-missing` entry substitute `--reflection "Review-and-fix evidence-missing terminal — {run root}"` (the loop refused to stamp a verdict because required execution evidence was missing, so the run must not be read as reviewed), on the excluded-class-residual entry substitute `--reflection "Phase 3.3 flush left excluded-class residual rows (untracked / staged-new / rename-copy) — {paths}"`, and on the second-refusal entry substitute `--reflection "Review-and-fix Skill call refused twice — {refusal message}"` — then emit the 👎 outcome reaction (see *Outcome reaction* in the Workpad Reference) and return a `blocked` handoff outcome carrying that cause in `blockers`. A non-Critical residual is not a Blocked exit — it soft-proceeds per the path above.

If the skill returns `REJECT` (it could not converge — whether at the iteration cap or via a pre-cap convergence exit per that skill's Step 4.5, whose verdict is still REJECT): route through the severity-aware exit above — a REJECT whose unresolved triggers are all non-Critical/deferrable soft-proceeds (review-ready, surfaced), while a REJECT with a genuine unresolved Critical takes the Blocked path. Like AWUSF, a REJECT must not be silently hand-fixed and shipped as resolved; soft-proceed surfaces it for the human rather than resolving it.

## Worker handoff (write last, then return)

After the routing above resolves, write your compact handoff so the implement orchestrator can validate and continue without reopening your context. Author `<run-scratch>/rf-worker-handoff-$ISSUE_NUMBER.json` with the **Write tool** (never a shell redirect) as a single JSON object — no prose preamble, no Markdown fence — carrying exactly the fields `scripts/validate-review-fix-handoff.py`'s default `review-fix` schema validates — the reader the parent runs — each with the nullability and enum values that reader accepts:

- `schema_version` `1`; `issue_number` the dispatched integer; `dispatch_id`, `repo_root`, `run_id`, `run_attempt` the exact dispatch operands, echoed back so the parent rejects a stale or duplicate return.
- `outcome`: `proceed` on the clean-completion and soft-proceed paths; `blocked` on the Blocked path, and when a decision the issue does not settle is unresolved (name it in a `blockers[]` entry's `reason` — there is no separate stop-reason field); `error` when you could not run the procedure at all. Outcomes are exactly `proceed`, `blocked`, `error` (complete by construction), and there is no `question` field.
- `final_commit` the 40-hex head you left or `null`; `review_coverage_recorded` a boolean (whether the `--record-review-coverage` stamp landed).
- `pr` `{number, draft_pr_disposition}`: `number` an integer or `null`; `draft_pr_disposition` one of `numbered`/`empty-brackets`/`absent`.
- `branch` `{recorded, final}`: `recorded` a string; `final` a string or `null`.
- `verdict` `{bucket, coverage, dispatch, roster, checklist}` — `bucket` one of `clean-full`/`clean-shadow-skipped`/`clean-not-verified`/`awusf`/`reject`/`unestablished`, the other four strings (the values you stamped via `--record-review-coverage`).
- `persistence` `{class, reason}`: `class` one of `ok`/`lost`/`unestablished`; `reason` a string or `null`.
- `blockers` an array of `{reason, evidence}` (both strings), non-empty exactly on `blocked`/`error`; `unresolved_findings` an array of `{severity, description, defect_signature}` (`[]` when none; `severity`/`description` strings, `defect_signature` a string or `null`); `warnings` an array of strings.
- `loop_run` a required object `{slug, run_id, iter_dir}`: each member a string or `null` (`null` when the run key was never held); a non-null `iter_dir` must be a non-empty path inside the checkout — this run's `.prflow/tmp/review/<slug>/<run-id>` directory.

The handoff indexes evidence at its authoritative scratch paths; it never replaces the workpad records you already wrote. Then make your whole hand-back — your final message and any runner-provided hand-back tool message alike — exactly this short envelope (literal values, no JSON body, no transcript), with nothing added:

```text
REVIEW-FIX HANDOFF
outcome: <proceed|blocked|error>
handoff_path: <absolute handoff path or null>
dispatch_id: <exact dispatched identifier>
```

Only when no handoff could be written, add `blocked_reason: <concise observed failure>` with `handoff_path: null`. The parent validates and routes this result; it does not reopen your execution context to reconstruct missing state.
