#### 2.3.0d Describing-prose reconciliation sweep (mandatory whenever the change removes a member from an enumerated value set, or changes what an already-stated rule, call sequence or claim means)

2.3.0b catches an *addition* to an enumerated set leaving enumerating sites stale; 2.3.0a catches a newly-added rule stated at too few peers. This sweep catches a removed member and a changed meaning, which neither of them arms on, and it has two authoritative triggers — run it when either fires:

- (a) Membership removal. The change removes a member from an enumerated value set.
- (b) Changed meaning. The change edits text stating a rule, call sequence or claim so that its meaning changes. Weakening a universal is one such change — softening it (an "always"/"every"/"never" becomes "usually"/"most"/"rarely"), scoping it (an unqualified claim gains a qualifier that narrows the population it ranges over), or removing it outright; strengthening it, changing a condition or outcome, and reordering a sequence are others.

Both triggers are the same defect: the change made a claim false without editing the claim. The surviving sentence still parses, still reads plausibly, and is only *semantically* false — so it ships clean instead of being reconciled here.

Precedence — what this sweep does NOT cover, and which sweep owns each. A membership addition is §2.3.0b's, never this sweep's. Adding a rule that has co-equal peer sites is §2.3.0a's, never this sweep's — for a rule with no prior statement anywhere in the repository. Either sweep owns only that addition itself: an added member or sentence that changes when, whether or in what order an already-stated rule, call sequence or claim applies also fires trigger (b), as does an addition when it is unclear which it is, and a change arming two sweeps runs both. A rename — an addition and a removal at once — is assigned to §2.3.0b alone, because §2.3.0b's member-literal enumeration already reaches both the vacated literal and the arriving one; a rename does not additionally arm this sweep. A diff that independently arms other sweeps still runs each at the domain its own definition states.

Scope — the enumerated value set is not only code-shaped, matching §2.3.0b's own stated scope. A **doc-enumerated configuration set** counts: a workflow's `on:` trigger list, a config-key set, a permissions list. A removal from any of those arms trigger (a) exactly as removing a code enum member does.

After removing a member, or changing what a rule, call sequence or claim means, before running tests:

0. The ladder is per search half — trigger (b)'s near-identical-copy search and its restatement search are separate halves: route a search half to the unrunnable arm at the end of this sweep when every rung available to *that half* is unavailable or refused, or when its search tool exits greater than 1 — even while another half still runs and records its own evidence — and then do not reach step 3's evidence record for that half.

1. Enumerate the describing prose by search, not from memory — separate searches, because they find different things:
   - Describing prose that names no member literal. This is the case §2.3.0b's member-literal grep structurally cannot reach: a sentence describing *where the set came from*, *how many members it has*, *what its members have in common*, or *what the set is for*, which names no member and so matches no member-literal search. Locate it by searching for the set's defining symbol, heading, table, or file path — the constant name, the section title, the doc anchor — and read the surrounding prose, docstring, and block/header comments at every hit, including in files the diff never touched.
   - Surviving copies of the pre-change claim text, and the changed claim's own surroundings (trigger (b)). Recover the pre-change wording from the **deletion hunks** of the §2.3 sweep operand (defined in the §2.3 preamble in phase-2-sweeps-contract.md — the merge base → working-tree branch delta) — then search for surviving byte-identical or near-identical copies of that claim elsewhere in the repo. A copy that a *different* file still asserts with its pre-change meaning is exactly the defect this trigger exists to catch. Then also read the owning changed symbol or claim's surrounding prose, docstring, and block/header comments — the same contextual read trigger (a) performs at each hit — because a nearby header or comment can restate the changed rule, call sequence or claim with its pre-change meaning on a line the repo-wide claim-text search never returns.
   - Restatements (trigger (b)). Search the repository for each changed rule, call sequence or claim by its own distinctive terms — the identifiers, commands and nouns it is about, not the phrase that changed (for a sequence, its step names together) — taken from the deletion hunks and from the rule as the change leaves it, so a condition added as a new sentence still has a key. A hit that states it goes to step 2; a hit that only shares a term without stating it is neither reconciled nor given an exemption note, only counted in step 3; an unclear hit goes to step 2.

   Search domain and command form. The domain is the whole repository, not the diff: a surviving copy of a changed rule, call sequence or claim characteristically lives in a *different directory* from the edit that changed it, so a delta-bounded search cannot see it. Trigger (b)'s searches skip trees the repository vendors from elsewhere and does not own (for example the PRFlow plugin tree under `.prflow/vendor/`); a tree not clearly vendored is searched. Because a claim hard-wrapped at a different column lives on no single line, use the whitespace-normalized form **§2.3.0's *Relocation is a contract change too* step 2 mandates in `<skill-dir>/references/sweep-2-3-0-changed-contract.md`**, and the grep-evidence rule's ladder in the §2.3 preamble in phase-2-sweeps-contract.md for the line-oriented half.

2. **Reconcile each site, or record an explicit exemption.** Reconcile every surviving statement under §2.3.4a step 3; a rewritten one describes the post-change set, or the post-change meaning of the rule, call sequence or claim. A site deliberately left as-is with a `--note` (which site, why) is allowed despite that step's bans on an unreconciled pair: a *silent* falsified claim is the defect; a *documented* one is a decision. Leaving a doc sentence for Phase 4.1 to fix is not an exemption: reconcile it here.

3. Record the search result as evidence for each search half that ran. Per the grep-evidence rule in the §2.3 preamble in phase-2-sweeps-contract.md, record the match count plus "all reconciled" (or the specific stale sites you fixed) via `--note` — evidence, not a claim. The note names each tree its search skipped as vendored. For a half step 0 routed to the unrunnable arm, or a half recorded `degraded`, record *that* instead: this step's clean evidence note is never written over a search that did not run or did not deliver, and one half's clean result never covers another's — the near-identical-copy search's never covers the restatement search's.

Unrunnable arm — an absent tool never yields silence, per the confirm-the-search-actually-ran rule in the §2.3 preamble in phase-2-sweeps-contract.md. When step 0 routes a search half here, do not report a clean pass. Record `2.3.0d: unrunnable (<which search, which cause>)` via `--note`, naming the covering backstop — the Phase 3 review pass — then continue.

Termination is per fired trigger, never both unconditionally — and each trigger owns the same contextual read. Trigger (a) runs the defining-symbol search with the surrounding-prose read at each hit; trigger (b) runs the deletion-hunk claim-text repo-wide search, the restatement search, *and* the surrounding-prose read of the owning changed symbol or claim. A diff that fired only one trigger runs only that trigger's coverage — the membership-removal-only run does not acquire the pre-change-claim or restatement search, while the changed-meaning-only run still owes the contextual read of its changed claim's surroundings — and is not done until that coverage returns only prose consistent with the post-change set, or with the post-change meaning of the rule, call sequence or claim (with an explicit `--note` for each exemption), or has been recorded `degraded` for incomplete delivery (per the search-evidence rule in the §2.3 preamble in phase-2-sweeps-contract.md) or `unrunnable` per the arm above. A diff that fired both triggers owes both.
