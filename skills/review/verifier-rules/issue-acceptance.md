Grading an issue_acceptance item. An item with no `source_file` names the run's diff in its `verify_hint`: read the diff to find where it meets the criterion, and cite the head-view file there, never the diff.

Read `criteria_file` (a run file; resolve a relative path against the repository root) before any FAIL, and before resting a PASS on sibling behavior or extra coverage. It counts only when every element is a `{criterion, text}` object and one carries this item's criterion N (the N of its `claim_signature` `issue-acceptance-N`, or of the `disclosed` entry reaching it). Otherwise grade the criterion alone — allowing neither exception below, never a PASS on that ground — and say in `evidence` that you graded it alone and why. When it counts, judge the criterion as limited by the other criteria.

Neither of these is a FAIL of the criterion, a counterexample, an incorrect part or a softened FAIL. *Sibling behavior*: what another criterion requires, in the case that criterion names, where the code shows that behavior. A case a sibling merely mentions excuses nothing; a sibling narrows this criterion only on the alternatives its words name, so a departure inside the trigger that no sibling's words name, however close in meaning, is a FAIL; a sibling naming a group of faults excuses only the members its words name. *Extra coverage*: the code applying the check, scan or handling this criterion requires to more files, inputs or cases than it names, that check's per-file, per-input or per-case results included — unless this criterion or another excludes it ("only", "exactly"). A `disclosed` Stricter entry for this criterion naming that coverage lifts the exclusion only when the code shows the coverage and every other case the criterion names gets its required outcome; else grade as without it and say in `evidence` it was not borne out. Any other extra output, data, access or side effect (records or fields the criterion does not name) is graded normally.

A PASS resting on sibling behavior or extra coverage names the sibling criterion and its case, or the extra coverage, in `evidence`, and quotes any `disclosed` entry naming it.

Trigger conditions. Before any PASS on a criterion with a trigger condition, whether or not it rests on sibling behavior, trace every path inside the trigger where the code departs from the claim; a passing test of the conforming path does not establish the claim over its whole scope. Split the code condition yielding an outcome other than the criterion's (never the one yielding its outcome) into its alternatives — each `or`/`||` operand, each negated `&&` operand, each case label, each error fallback feeding it — and grade each as outside the trigger, named by a sibling's words, or a departure.

An alternative is outside the trigger only when (i) it needs no runtime fault to fire and no input meeting every condition the trigger states can fire it (e.g. it fires only if the trigger's facts cannot be established), or (ii) it fires only on a runtime fault the criterion does not name (an I/O, tool or network error) and fails closed, surfacing the error or still yielding the criterion's outcome. An alternative reached only by inputs the criterion's qualifiers leave unnamed, or a fault alternative silently yielding another outcome (even when its fault leaves the trigger's facts unestablished), is inside it. One whose reachability you cannot settle makes the item INCONCLUSIVE, not FAIL.

Every PASS on a criterion with a trigger condition lists in `evidence` the code condition you split, then each alternative → `outside the trigger` with the trigger condition any input firing it breaks (a fault alternative: its fault and how it fails closed), or the number of the sibling whose words name it, those words quoted. `none` stands for the whole list only after naming the code condition read, never beside an alternative. Graded alone, it lists only `outside the trigger` entries.
