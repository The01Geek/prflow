# Reference: Engine Entry (shared by Step 1 and the Step 2.6 shadow)

This is the single home of the review-engine entry procedure — the engine-directory resolution, the completeness (EOF) check, the capability check, and the return-file field set. Both `loop-control.md` Step 1 (the primary entry) and `shadow-review.md` Step 2.6 (the shadow entry) point here; neither restates it. The `prflow:review-engine` agent Reads this reference in its own context and executes it; on the `unavailable` fallback the parent executes the resolution/completeness/execution steps below inline.

Your dispatch prompt supplies the entry's literal operands: the entry kind (`primary` for Step 1, `shadow` for Step 2.6) and this iteration's number `<N>`; the held `run_id` and `phase_range_max = 4.3`; the PR-mode `head_override` and the internal `progress_surface` when the loop passes them; the resolved engine-directory candidates and the captured `<loop-skill-dir>`; and, for an iter N≥2 primary entry, the Step 0.9 carry-forward artifacts (`prior_diff_head`, `prior_checklist`, `prior_phase3_findings`). Root every artifact under this checkout's `.prflow/tmp/review/<slug>/<run-id>/`.

## Capability check (`fanned-out` and `unavailable` are the complete `dispatch_mode` set)

Your first action is a capability check. Holding a delegation tool, you resolve the engine directory (below), Read the engine root, establish completeness under resolution step 3, execute Phases 0 through 4.3, fan out the Phase 3 roster, and write the return-file field set below, then return `dispatch_mode: fanned-out` and the return-file path. Holding none, you write that same return file carrying `dispatch_mode: "unavailable"` and a `tools_held` array (empty when you can name none) and return that. This capability check is unconditional.

## Engine-directory resolution (canonical)

Mandatory and authoritative. Locate the review engine's *directory* by an ordered candidate list anchored on the git repository root, then `Read` its `SKILL.md` in full and execute it only once completeness is established per resolution step 3 — a half-delivered engine reviews a merge-gating PR against phases that never arrived. Resolve the directory once per engine entry and reuse it for the root `Read`, every `phases/<file>` read, and the root-identity `git hash-object` list — a re-evaluated lookup could trip the engine's `identity: root-moved` arm. (The Step 2.6 shadow is a *separate* engine entry and resolves it again.)

Resolution steps:

1. Resolve the repository root once with `git rev-parse --show-toplevel` (falling back to the current directory when that fails), so resolution does not depend on the process working directory — which the local tier does not pin to the repo root.
2. Form the ordered candidate engine-directory list, repo-root-relative:
   - `<repo-root>/.prflow/vendor/prflow/skills/review` — the current vendored-consumer layout.
   - `<repo-root>/.devflow/vendor/devflow/skills/review` — the superseded vendored layout, still accepted.
   - `<loop-skill-dir>/../review` — the running plugin's own engine (the `review` sibling of the loop's skill directory), from the `<loop-skill-dir>` the root captured; a lost value re-reads from `root-identity.json`, and when neither resolves this candidate is recorded unestablished. Appended last, so the two vendored candidates win when present; on a thin-install consumer checkout where neither exists, this is the engine that runs.
3. `Read` `<candidate>/SKILL.md` for each candidate in order, answering two separate questions in this order — did the path **resolve**, and was the body **delivered**. **Selection turns on resolution alone, never on whether content came back.**
   - *Resolution.* A path the reader reports as non-existent is **absent** — advance to the next candidate (on a consumer checkout the earlier ones are expected absent). Any other message that **affirms the path exists** — including a permission denial the reader raised *on that path* — positively resolves it: that is the **selected candidate**, whatever the read returned, and no later candidate is read. A refusal returned before the path was consulted — a harness/sandbox denial of the read itself — affirms nothing about existence, so classify it as unclassifiable below, not a resolution. A message you cannot classify *as to whether the path resolved* leaves resolution **unestablished**: that candidate is not selected and the scan advances. Report which candidate it advanced past and why, and whether the selection is later than the first — in this run's report and a dispatched engine subagent's return; an unrecorded advance hides a present-but-unreadable engine behind a different copy.
   - *Delivery.* Once a candidate is selected, a permission failure, a transient reader error, an oversize error returning no content, and an empty/whitespace-only body are each a present engine that was not delivered: they leave completeness **unestablished** and never fall through to a later candidate. When the selected candidate is a `.prflow/vendor/prflow/skills/review` vendored tree whose `.claude-plugin/plugin.json` version differs from the loaded plugin's (read at `<loop-skill-dir>/../../.claude-plugin/plugin.json`), the selection report names both versions.

   The located engine directory — `<engine-dir>` — is confirmed only once **completeness is established**; a merely-readable body does not suffice. Confirm end-of-file from the reader: after a read that appears whole, issue one more bounded read starting at the line immediately after the last held — a read starting later confirms an end beyond a hole. EOF is established **only** by the reader reporting the file is shorter than the position asked for, or returning literally nothing; that report is attributable to the position requested. Any content returned there means the held read was truncated — append it and re-confirm from the new last line — and **a blank line is content**, since that position exists. A reader that clamps the start position and re-returns the head, or answers a later position than asked, proves nothing. A dispatched engine subagent returns the determination as `root_completeness`.

   These shapes leave completeness **unestablished**: a file-read tool that takes no start position, so no confirming read is possible; a confirming read refused or erroring otherwise than by that end-of-file report; a reply whose content cannot be attributed to the position requested; one not starting at the line immediately after the last held; and a gap in a paged read's sequence. Each takes step 4's `engine-root: incomplete` terminal. The engine root carries no boundary markers, so an absent truncation notice is no evidence of a whole body. Do not substitute a line count from an external counting tool, whose absence would yield an empty value and the wrong outcome.

   A partial-view read with an `offset`/`limit` continuation is paged forward, then put through that same confirming read, which alone terminates the paging — neither "no further continuation is offered" nor "this page added nothing new" does.
4. Route the two failure outcomes separately:
   - No candidate was selected — no path positively resolved: take the fatal arm (see `error-handling.md`), whose message names `/prflow:init` as the remedy, and name any candidate the scan advanced past on an unestablished resolution — including a plugin-sibling candidate recorded unestablished when both `<loop-skill-dir>` and `root-identity.json` were unavailable — so the report does not read as an absent engine.
   - The selected candidate's completeness could not be established: stop at the terminal `engine-root: incomplete`, naming that candidate's `SKILL.md` path. The body is unusable — do not execute or repair it. As a dispatched engine subagent you return this terminal to the parent — naming `engine-root: incomplete` and that path — instead of a `fanned-out` payload, and review nothing further; the parent reads that as not well-formed and takes its dispatch fallback. On the `unavailable` inline arm the parent re-decides the terminal on the entry arm (`loop-control.md` Step 1's *Step 1 entry* stop, or `shadow-review.md` Step 2.6's outcome 3).

Bind the bundle to `<engine-dir>`. Because the engine is read as a file rather than through the `Skill` tool, the engine root treats the located `<engine-dir>` as its `<skill-dir>` — phase references resolve at `<engine-dir>/phases/<file>` and root-identity hashing runs over `<engine-dir>/SKILL.md` and `<engine-dir>/phases/*`. It must not re-resolve the runner's skill-directory anchor here, which on this path names *this* (review-and-fix's) skill directory — one with no `phases/`, so the references would not resolve (stopping at `identity: underived`). Leave the bundled-helper anchor as-is — phase files resolve bundled helpers at `<runner-anchor>/../../scripts/…`.

## Execute the engine

Execute the engine's Phases 0 through 4.3 verbatim — do not improvise the Phase 3 agent prompts, do not skip the Phase 1 >10-file batching, do not substitute your own verdict criteria.

Pass the held `run_id` and `phase_range_max = 4.3` into the engine's Phase 0.2 on every entry (both dispatch modes, including the inline `unavailable` fallback). `run_id` scopes the engine's scratch (`diff.patch`) under the *same* `<run-id>` the loop uses for `iter-*.json` / `deferrals.json`; `phase_range_max = 4.3` keeps the loop the sole writer of `iter-<N>.json`. Pass entry kind `primary` and this iteration's number `<N>` on a primary entry (so its Phase 3.1 obtains the plan via `resolve-review-overrides.py --plan-phase3 --entry-kind primary --iteration <N>`); the shadow entry passes entry kind `shadow` (which excludes nobody). When the loop passes an internal `progress_surface = workpad`, pass that exact value into Phase 0.2 every entry; else pass none. In PR mode pass `head_override = local` into Phase 0.2 so the engine reviews the loop's local fix commits. On an iter N≥2 primary entry, hand the Step 0.9 carry-forward artifacts your prompt supplies (`prior_diff_head`, `prior_checklist`, `prior_phase3_findings`) into the engine's Phase 1/2/3; Phase 1+2 always run. Skip the engine's Phase 4.4 (formal GitHub review posting); Phases 0–4.3 still run verbatim. On a standalone fix-loop run, PR mode seeds and ticks the engine's run-keyed progress comment as usual; on an implement-driven run (`progress_surface = workpad`) the engine ticks no issue-workpad row and creates no second progress comment — the fix loop records the tuple-declared review-boundary rows (Step 1.8 the five phase rows, Loop Exit `Run complete`).

**Run no project test suite.** You run none of the project's test-suite runners or test files under any command head, and a dispatched verifier settles a test claim by reading source. Carry this no-suite rule into, and repeat it verbatim in, **every** prompt you issue, so your verifiers and Phase 3 reviewers inherit it.

## Return-file field set

Write, before returning, this entry's `checklist-iter-<N>.json`, `verification-iter-<N>.json`, and the per-item verifier files under `verdicts/iter-<N>/`, then produce the entry-scoped return file `.prflow/tmp/review/<slug>/<run-id>/engine-return-<entry>-iter-<N>.json` (`<entry>` is `step1` for the primary entry, `shadow` for the Step 2.6 entry). On `fanned-out` it carries `root_completeness`, `phase3_findings`, `phase3_dispatched`, `expected_reviewers`, `plan_eligible`, `plan_exclusions`, `phase3_failed_agents`, `diff_profile`, `cap_drops`, `diff_produced_at_head` (the `git rev-parse HEAD` at which Phase 0.2 produced `diff.patch`), and — whenever Phase 1+2 ran — the exact post-dedup `checklist` array with each item's probe and claim metadata intact (`lite_probe`, `verification_mode`, `claim_provenance`, `source_excerpt`). It also carries the engine `verdict` and, on `fanned-out`, its complete Phase 4.1 `report` inline as a nonempty string — never a path, no standalone Markdown report. A valid `unavailable` return carries no report.

**Type only what you authored.** On `fanned-out`, Write `engine-return-<entry>-iter-<N>.authored.json` holding every field above except `dispatch_mode`, `diff_produced_at_head` and `checklist`, then assemble — vendored literal first, the portable anchor `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/review-dirty-tree.sh engine-return` with the same arguments on a not-found reading (`command not found` / `No such file` / exit 127):

```bash
.prflow/vendor/prflow/scripts/review-dirty-tree.sh engine-return --run-dir .prflow/tmp/review/<slug>/<run-id> --entry <entry> --iteration <N> --head <head-sha> --authored .prflow/tmp/review/<slug>/<run-id>/engine-return-<entry>-iter-<N>.authored.json
```

`<head-sha>` is the commit Phase 0.2 produced `diff.patch` at. The helper splices `dispatch_mode`, `diff_produced_at_head` and `checklist-iter-<N>.json` joined by `id` with `verification-iter-<N>.json`'s verdict fields, validates the field set, writes the return file, and prints one JSON line. Add `--no-checklist` when Phase 1+2 did not run. `status: "ok"` is the validation — run no JSON check of your own (a `verification` other than `joined` or `skipped` merged no verdict: repair `verification-iter-<N>.json` and re-run); on `status: "error"` fix the authored part its `reason` names and re-run. Only when it prints no JSON (refused, or not found on both arms) Write the whole return file yourself.

Return only your `dispatch_mode` and this return file's path, as your last action — no summary, verdict, findings or closing text; they live in the file.
