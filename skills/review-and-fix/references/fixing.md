# Reference: Fixing (Step 3)

### Step 3: Fix Findings

Apply the `prflow:receiving-code-review` principles — including the share-the-contract / parse-don't-validate principle (when a fix adds a guard protecting a downstream consumer, prefer the consumer's own operation as the guard rather than a separate validator that re-derives the contract), which Step 3.5's operand-contract check then verifies on the fix delta. After Step 2.5, the findings reaching Step 3 are: Phase 2 checklist FAILs, corroborated Phase 3 findings, confirmed-by-web findings, and codebase-claim findings. Refuted and inconclusive findings have been demoted to advisory and are not in this list; they stay parked.

Test-first gate at fix-authoring time (before any fix that adds automated-testable behavior is written). A fix authored code-first ships its own delta untested and encodes whatever the code happens to do, not what the finding requires. Before you write a fix that adds or alters behavior an automated test can exercise (a return value, a CLI/API contract, an exit code, a parser's handling of an input shape, a state transition, a raised error, or an end-to-end path an integration test drives), write the test first, run it, and confirm it fails for the right reason (the behavior does not exist yet), then implement until it passes. Record the gate's call durably at gate time — the workpad `--note` when implement-driven (Phase 3.3, `$ISSUE_NUMBER` present); when standalone, use the Write tool to create or re-write `.prflow/tmp/review/<slug>/<run-id>/iter-<N>-gate-evidence.json` as a JSON array of `{decision, command, result, evidence}` entries, preserving any entries already recorded there before adding the new logical entry. Item 6's fused `iter-<N>.json` Write consumes that exact scratch file into `test_first_gate`. This gate carries the same stub-blindness and mutation-check discipline the §2.3 test-first gate and item 4 already state. It also carries §2.3's test-authoring proportionality waiver: when the PR's Test Plan records a waiver, do not re-impose the waived ceremony (collection-cardinality, stub blind-spot enumeration, per-criterion one-assertion accounting) on the surfaces it names — the covering RED-first test and the mutation-check discipline stay binding for them.

- Ungranted-command degraded arm. When the test invocation is permission-denied, the durable record states `gate: unrunnable (command ungranted on this tier)`, and the remedy is, keyed on tier first and driver second: cloud implement tier → grant the command in `prflow_implement.allowed_tools`; cloud command path (`devflow.yml`) → grant it in `prflow.allowed_tools`; local tier, regardless of driver → the operator adds the command to their local agent allowlist settings. The test is still written un-run where feasible, Step 3.5 plus the shadow are named as the backstop, and a denied command is never routed to the no-automated-test arm.
- No-automated-test arm. When no conventional automated test can exercise the fix, preserve Phase 2.4's verification taxonomy. For a logic-bearing artifact or human-facing prose, the fixer executes the Phase-2.4-defined adversarial dry-trace / shape-matrix inline at gate time, scoped to the fix delta, and records the trace in the evidence sink. When the fix changes prose that enters a model's context as instruction — including a `SKILL.md` procedure, an injected prompt block, or an agent brief — run the Phase-2.4 subagent RED/GREEN micro-test, including its no-guidance control, and record those behavioral results in the evidence sink; model-context instructions are never discharged by a dry-trace. If that micro-test is unavailable, unusable, or fails, record the attempted command/dispatch, `result: "unrunnable"` or `result: "fail"`, and the concrete reason in the same evidence sink; the finding remains unresolved and blocks convergence. The blinded Step 3.5 gate is cited only as the independent backstop, never as the discharge — the fixer runs the applicable Phase 2.4 verification itself.

Reuse a disposable verification rig across iterations — but only while it still fits. When fixing leads you to build a throwaway rig to exercise code in isolation — such as a scratch repo to drive a git-consuming helper, a fixture config to drive a config reader, or an interpreter/CLI wrapper that calls a helper with crafted argv — keep it under an already-ignored scratch path (`.prflow/tmp/…`, so a terminal `git add` never stages it; a nested `git init` rig placed elsewhere would land as a gitlink), and record its location on this loop's own channel: the workpad `--note` when implement-driven (`$ISSUE_NUMBER` present), otherwise the run-scoped `.prflow/tmp/review/<slug>/<run-id>/…` local record a standalone run already keeps. Reuse it on the next iteration instead of rebuilding it — but only after confirming it still exercises the current code shape. Rebuild it when the surface it exercises has changed: a rig keyed to a superseded shape drives paths that no longer exist and yields a false GREEN.

#### 1. Reading the findings

1. Read all findings without reacting. Understand the full picture before fixing anything.

#### 2. Technical evaluation

2. Evaluate each finding technically:
   - For verification checklist FAILs: Read the evidence. Verify it yourself by reading the source file cited. If the evidence is correct, fix the code. If the evidence is wrong (the verifier misread the source), skip the fix and document why.
   - For Critical/Important findings from review agents: Read the finding. Check if it's valid for this codebase. If valid, fix it. If not, skip and document why. (Note: external-tool claims that survived Step 2.5 are already either web-confirmed or corroborated by ≥2 agents — be slow to dismiss them as invalid.) Also calibrate its severity, not just its validity — applying the receiving-code-review symmetric-severity-calibration principle, evaluate the finding's emitted `Critical`/`Important` grade against its observable fail-direction and impact (does it fail closed / does the suite catch it RED / is its only impact diagnostic?). Record that technical evaluation as a structured `fix_decisions` entry (`decision: "severity-calibrated"`, with `original_severity` / `calibrated_severity` and the observable fail-direction/impact as `evidence`). This recorded evaluation is the evidence the Over-grade calibration gate (Step 2.6) requires before a promote-path `Critical`/`Important` finding may drive a Decide-outcome-2 promotion; a promote-path finding with no such recorded evaluation blocks at that gate as non-convergence.
   - For Suggestion/Minor findings: Fix only if trivial and clearly correct. Do not spend time on cosmetic issues.
   - For a finding that prescribes changing existing _documented_ behavior (a reclassification, a "should be X not Y", or a contradiction of a documented invariant or taxonomy): treat it as a recorded verify-step before you apply it — read the doc, comment, or spec the prescription cites or would change, and verify the prescription against its cited source of truth before applying it. Record the verification as a structured decision the same way item 5 records a pushback — a prescription that contradicts the source of truth is recorded as a pushback (`skip_category: claim-quality`, `evidence` citing the documented invariant it contradicts) and is not applied; a prescription consistent with the source of truth is applied, with the verifying source cited in the `fix_decisions` entry.

#### 3. Class-wide fixes

3. Fix one issue at a time — then fix its whole class, not just the reported instance. After each fix, verify the surrounding code still makes sense. Then generalize the finding to its `defect_signature.kind` and scan the changed surface (the files/hunks in this PR's diff, plus any file your fix just touched) for other instances of the same class; fix every sibling in this same iteration, applying item 2's severity triage to each. Bound the sweep to the PR's own changed surface — never to pre-existing untouched code (that is what the `out-of-scope` skip and the Loop Exit widens-surface guard are for); a sibling you deliberately choose not to fix is recorded through the same pushback flow as any skip (item 5). The pre-shadow parked-class sweep handles the complementary no-fix convergence shape.

When a defect kind reaches the run's efficiency trace as a recurring kind — it has appeared across three separate iterations — stop extending the enumeration the fix keeps patching and model the artifact the rule is written against instead. Another member added to that list will miss in a new way, and the same kind returns next iteration.

Dispatch barrier. Every subagent dispatch described here is bound by the dispatch-collection requirement in the engine-ground-truth block injected into this run's prompt — read it there (if your prompt carries no such block, collect every dispatch before the turn ends anyway).

##### 3a. Mechanism re-sweep

   **3a. Mechanism-scoped self-authored-claim re-sweep — when a fix changes a *mechanism* (a guard, predicate, exclusion pattern, or helper that existing comments describe — *and equally a job-gating or control-flow change: a changed `if:` condition, a moved conclusion arm, a rerouted step, a relocated where-a-decision-concludes*), re-verify every comment describing that mechanism, located by the mechanism's identifiers across the touched files — not limited to the fix's own diff hunks.** A fix that tightens a guard, narrows an exclusion, renames a predicate, moves a helper's contract, or reroutes control flow / job gating leaves any comment describing the *old* mechanism stale. Run it after item 3's class-sweep, once per fix that changed a mechanism:
   - Identify the mechanism's identifiers — the function / variable / flag / pattern name(s) the fix changed (the renamed predicate, the tightened exclusion's variable, the helper whose contract moved).
   - Locate every comment describing the mechanism by those identifiers across the touched files. Search for the identifier(s) in the files this PR's diff touched — using the granted command forms item 3b's Command forms paragraph names (the Grep tool first, `rg` when it resolves on the host, `grep -rnE` last with the directory-exclusion obligation) — and read the comment at each hit, *plus* any block / header comment in those files that names the mechanism. This search is identifier-located, not hunk-located.
   - Re-dispatch `prflow:comment-analyzer` scoped to those comments — pass it the touched file paths, the mechanism's identifiers, and the instruction to verify each comment describing that mechanism against the *post-fix* behavior. The agent analyzes and reports only — it never edits; the orchestrator applies any resulting correction itself.
   - A comment that still describes the pre-change mechanism is a finding — fold it into this same iteration (fix the comment alongside the mechanism change, as a swept sibling under item 3) or, if deliberately left, record it through the item 5 pushback flow.

##### 3b. Fix-delta authoring-side sweeps

   3b. Fix-delta authoring-side sweeps — on every iteration in which Step 3 applied fixes, run the implement Phase 2.3 authoring-side sweeps against the fix delta. A fix is new code and prose that never received the authoring-side sweeps the original diff did. Scope every sweep to the fix delta — the code and prose *this iteration's* fixes add and change, never pre-existing untouched code: a sweep's trigger is scoped to the fix delta *without exception*, while a triggered sweep's enumeration may exceed the delta only where that sweep's own Phase 2.3 definition states a repo-wide search domain, or an enumeration that follows call edges outside the delta — the set §2.3.0, §2.3.0a, §2.3.0b and §2.3.0d. Every other sweep's enumeration stays bounded to the fix delta. A future sweep whose own §2.3 definition states either ground joins that set by that definition.

   Re-anchor onto the full §2.3 index. Classify the fix delta exactly the way Phase 2.3's Sweep selection (run first) preamble classifies a diff, and run every Phase 2.3 sweep the classification warrants — the trigger-gated sweeps whose triggers the delta matches plus every sweep the §2.3 preamble names as always-on (its Always entries, cited by reference, never re-counted here) — each gated by its own Phase 2.3 trigger condition exactly as that sweep's definition states it, so a sweep whose trigger the delta does not match runs not at all. The §2.3 index in the executing bundle's Phase 2 sibling set (enumerated in the Read protocol below) is the single source, and this item carries no hand-enumerated sweep subset. Record the diff shape you classified and the sweeps you are running in the iteration's evidence sink, exactly as the §2.3 preamble's own selection-note rule requires.

   **Read protocol (durable operand).** Resolve the §2.3 source from this executing skill's portable skill-directory anchor as the ordered sibling set `../implement/phases/phase-2-implement.md`, `../implement/phases/phase-2-sweeps-contract.md`, `../implement/phases/phase-2-sweeps-quality.md` (never resolve it from the consumer repository's current working directory); the selection preamble and the sweep definitions are split across that set. On the run's **first fix-applying iteration**, read every member in that order and **record a `sweep_defs_read` list** — one entry per member: its path, a `read` value of `whole` (that member's Read succeeded through EOF) or `incomplete` (empty, truncated, denied, or unresolved), and the sweep identifiers that member yielded. A member returned only in pages — a partial-view notice with an `offset`/`limit` continuation — is not `incomplete`: page it forward to EOF and record `whole`; only a read you cannot complete, or a message you cannot classify as that notice, records `incomplete`. **A member read `whole` that yields no sweep identifier is recorded `whole` with an empty identifier list — a different state from `incomplete`, and from a member with no entry at all; the three are never merged.** **A conditional sweep's phase-file entry carries only its predicate: when that sweep's trigger is warranted for this delta, read its procedure from the gated reference its own `**Procedure:**` pointer names (under `../implement/references/`) and record that read in `sweep_defs_read` as its own entry — its path, its `whole`/`incomplete` value, and the sweep identifier it yielded — exactly like a phase-file member**, because the phase files alone carry no procedure and a sweep run from a predicate stub is not run at all. The set read is complete **only when all three phase members carry a `whole` entry and every warranted conditional sweep's own gated reference carries a `whole` entry**, and the union of those entries contains the §2.3 sweep-selection preamble and the `### 2.4 Test` boundary; a member or warranted sweep reference absent from the list, one recorded `incomplete`, or a completeness that cannot be established takes the unreadable-source arm below. On each subsequent fix-applying iteration, re-read the preamble and **every sweep heading** across the set, then read the full definition of any warranted sweep absent from the recorded `sweep_defs_read` — from its gated reference where its phase-file entry is predicate-only. The decision is **adjudicated against that durable record, never against recall**: a warranted sweep **absent from that record** forces the full re-read, and **a sweep is never executed from recall alone**. When the set **cannot be read completely** under that check — a partial-copy deployment, an unresolvable skill anchor, a denied or truncated read, or an unestablished one — the loop does **not** stall and does **not** silently skip: record `sweeps: unrunnable (phase-2 source set incomplete: <member path> — not-read | incomplete)` in the iteration's evidence sink, name **Step 3.5 and the shadow** as the covering backstop for this iteration's delta, and continue the loop.

   Preserved invariants. Each triggered sweep honors its own Phase 2.3 evidence obligation exactly as its definition states it, with that evidence directed to the loop's own `iter-<N>.json` iteration records when the loop runs standalone with no issue workpad to write to. A finding any of these sweeps surfaces folds into this same iteration exactly as item 3's class-sweep siblings do — fixed in-iteration, or, if deliberately left, recorded through the item 5 pushback flow.

   Command forms (ignore-aware, in order). `git grep -n` is ungranted in both cloud allowlists. Use the Grep tool first (ignore-aware, always present in the runner), `rg` when it resolves on the host, and `grep -rnE` last, and only with an explicit obligation to exclude VCS, dependency, and build directories, to locate qualitative matches — never `git grep -n`. For quantitative sweep match-count evidence, preserve the original tracked-file operand explicitly: enumerate it with `git ls-files -z` and pipe that NUL-delimited list through granted `xargs -0` into `rg` or, when `rg` is unavailable, `grep -nE`; a recursive-search count that also admits untracked or ignored files does not discharge the obligation.

#### 4. Running tests

4. Run tests after all fixes. Check CLAUDE.md, README, or project configuration for the project's test and lint commands. Run the narrowest covering test before the broadest: when more than one automated test bears on the change, run the test that covers only the changed surface before the whole suite. A suite runner retains its output in a log whose path it names on exit, so when you need more of a run's output than you first captured, re-read that retained log rather than re-executing the suite. If tests fail, fix the test failures before continuing.

   Record the suite run as `verification_evidence` in this iteration's workpad. Capture the suite command you ran, its `result`, and how long it took, and carry them into the `iter-<N>.json` record as a `verification_evidence` object, whose field shapes item 7 specifies (`result` is `skipped` with a `reason` for a no-fix iteration with nothing to re-run and for a cloud run whose suite command is ungranted). This object rides the existing item-6-anchored emit (it is written as part of the same `iter-<N>.json` Write in item 6/7, not a separate write). Consumption: the durable verification record this evidence coordinates (the status handle) is now read at **Loop Exit** by the completion-evidence check (`scripts/check-completion-evidence.py`), which validates the completion claim against it — its `result`, its `skipped_checks`, and its recorded candidate identity.

   **A test suite can *pass while a check inside it self-skipped*, and that is not a clean pass — record it, do not launder it.** When the suite's own output reports one or more skipped checks, the `verification_evidence` object also carries a `skipped_checks` list — one entry per skipped check, each naming the check, its kind (whether it was a real gate that should have run here but could not, versus a check the host cannot express), and the reason the runner gave. This is a different fact from `result: skipped`, which means *the whole suite run was skipped* (a no-fix iteration, or an ungranted suite command); leave the `result` enum unchanged and put the per-check information in `skipped_checks`. Detect skips from the runner's own reported output — the summary tally and the per-check skip lines (or machine-readable report) the runner itself prints — never by inference from the exit code, which a skipped check deliberately does not change. A run whose `skipped_checks` is non-empty is not reported by the loop as a clean pass: name the skipped checks in the loop's summary instead of recording an unqualified pass, because a skipped check may be a gate that never actually ran on this run.

   Establishing a suite result — from what the runner reported, never from an exit status you did not read. A command that prints a result tally is established from that tally's terminal summary line, wherever the runner writes it — a runner that prints its summary to stderr rather than stdout is still on this arm, not the exit-status arm — and a process or wrapper exit status does not substitute for it. A command that ran and printed no summary is established from its own exit status, unchanged. A command that never ran — refused, denied, or otherwise unreached — is established as nothing at all: it takes the existing denied path and is never established from an exit status. And for a command still running: a capture file still being written is incomplete, its absent terminal summary means the run has not finished rather than that it passed, and the result stays unestablished until that line appears — re-read the capture, never claim on it.

   Single-flight verification coordination. Consult the single flight before any suite execution this loop launches — whole-suite, shard, or focused, not only a full-suite relaunch — and reuse a clean result it already holds for the current tree by re-reading the retained log the runner named, whichever runner kept it, rather than re-executing. Resolve the gate — `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/config-get.sh .verification_flight.enabled true` — which defaults `true`; only an explicit `false` disables it, and a resolver failure (rc≠0) warns and takes the default. Off-switch is per-caller. An explicit `false` means *ledger bypass* (a direct launch, as before) for a standalone Review-and-Fix run, but only *reuse bypass* when this pass runs inside `/prflow:implement`: an implement-driven run still executes the `claim`/`mark-running`/`finish` record transitions even under `false`, because the terminal `workpad.py --status Complete` evidence gate requires the machine-readable flight record. Record the candidate identity on the `claim`: obtain the current-checkout candidate identity from the reception preflight — the granted `reception-record.py` prints a stdout JSON object carrying `candidate_identity` — read that value and set it as the declaration's `candidate_identity` field; a record with a null `candidate_identity` fails that gate. When it resolves enabled, coordinate this same-checkout verification launch through the non-executing `verification-flight.py` ledger (invoked by the same `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/` anchor the other helpers use) rather than relaunching unconditionally. `claim` first. The owner token is returned once and never persisted in cleartext, so it must survive between the three calls: `claim`, `mark-running`, the verification command, and `finish` are separate invocations, and a shell variable does not survive from one tool call into a later one — capture the token from `claim`'s printed JSON and carry it in the prompt context (or write it to a run-scoped scratch file) before launching the command. A lost token makes `mark-running`/`finish` fail CAS with `token_mismatch`, which silently degrades this run to an uncoordinated direct launch: treat that rejection as a coordination failure to record, not a no-op to ignore. If it returns role `owner`: `mark-running`, run the existing already-authorized verification command unchanged (same command, same allowlist), then `finish --result passed|failed|timed_out|cancelled` with a summary file carrying `command`/`exit_status`/totals/`failure_text`/`skipped_checks`. If it returns role `attacher`, re-anchor before consuming: produce the current-checkout fingerprint with the vendored leading-token `.prflow/vendor/prflow/scripts/checkout-fingerprint.py` — whose JSON output is also what the `claim` declaration's `checkout` field is set from — and pass it as `--current-checkout-file` to `status` (or a bounded `wait`); consume that terminal evidence as this iteration's `verification_evidence` only when the read reports a `passed` flight for the identical descriptor+checkout and `checkout_verified: true`, because the ledger now enforces the checkout AND itself and a bare `status`/`wait` with no fresh `--current-checkout-file` reports non-pass — otherwise fall back to a direct launch, never a reused pass over a tree this read could not verify. Unknown is not a pass: a missing, partial, timed-out, unreadable, stale, or incomplete handle NEVER counts as a pass — fall back to a direct launch, never a relaunch the ledger authorized on its own. On `wait_expired`: a standalone Review-and-Fix run records `verification_evidence.result: skipped` with reason `flight_wait_expired`, follows its locally-unverified terminal arm, and cannot report a clean pass; an implement-driven run takes the existing Blocked path without relaunch. Persist the flight handle + terminal evidence in this iteration's `iter-<N>.json` (it rides the existing item-6-anchored emit).

   For any added or edited test guard in the diff (a new regression test, a coverage check, a drift/sync assertion — whether it is the fix-loop's own deliverable or primary implementation work the diff introduces), a green suite is necessary but not sufficient — a *vacuous* guard passes too. Mutation-check it: break the thing it is supposed to catch (delete the line/block it pins, flip the condition) on a copy of the file — never edit the working-tree file in place — and confirm the guard goes RED against that copy, then discard the copy. A copy-based mutation-check is never destructive: an interrupted or crashing check can never leave the real working-tree file broken, whereas an in-place "break then restore" can. In particular, never restore with `git checkout -- <file>`: it cannot restore an untracked file and silently appears to succeed, leaving every mutation in place. Then confirm the guard registered: its named assertion appears in the run as a PASS and the suite's assertion count rose by what you added.

   Pin-corpus boundary. A wording-only pin is a test whose protected literal can change without changing executable behavior and without breaking a machine-consumed contract. Do not add wording-only, secondary-prose, documentation-presence, advisory-heading, or comment-presence pins, including raw `grep`/text-presence assertions. Prefer behavioral tests at executable boundaries for mirror facts and stub blind spots. A new non-mutation presence pin is permitted only for `helper-contract`, `schema-config-vocabulary`, `security-credential-boundary`, `machine-sentinel-provenance`, `routing-dispatch-contract`, `lifecycle-state-transition`, `generated-artifact-identity`, or `cross-file-phase-contract`, and its logical line must carry `# structural-pin-ok: <category> -- <rationale>` with a nonempty rationale.

   When the guard protects a named behavioral regression — including an operative prompt regression — write an ordinary executable test over the rendered interface or machine-observable contract and prove that test goes RED when the behavior is broken. Do not add a prose-presence pin or invoke a retired mutation-taking helper. Record the evidence, not an attestation: the workpad `--note` records the behavior you broke and the executable test you observed go RED. This requirement does not apply to valid typed structural pins, count guards, or absence guards.

#### 5. Tracking pushbacks

5. **Track pushbacks.** For each finding you skipped (whether checklist FAIL or Phase 3 finding), record a structured entry: `{source_file, claim_text, skip_category, evidence}`. **For a Yes-downgrade deferral** (`skip_category` one of `claim-quality` / `out-of-scope` / `already-tracked`) also write the structured `parking_evidence` object `{basis, failing_input, source, finding_ref}` beside the retained one-line `evidence` string, per its authoritative shape (root `### Schema` example; field semantics in `references/loop-control.md` *Schema field semantics*): `basis` is the one-line parking rationale, `source` is the citation the category requires (source span / `git blame` proof / issue reference — a null `source` on one of these categories fails condition (c) at comparison time), and `finding_ref` is the `{iter, index}` join to the finding's parking-time `phase3_findings` record and is **always** written (`references/loop-control.md` *Schema field semantics* owns the null-is-a-writer-omission → fail-closed semantics). The retained `evidence` string is unchanged (the `deferrals.json` `explanation` input); the `uncategorized` and sweep-only `below-threshold` rows are not Yes-downgrade deferrals and gain no `parking_evidence`. **Foreclosure by disclosure (`skip_category: "settled-by-disclosure"`).** A finding whose deliverable is an **already-shipped disclosure** is recorded once, in place of a fix, with `skip_category: "settled-by-disclosure"` — but **only** for a finding that is **below the run's `verdict_severity_threshold` and not a REJECT driver of the current iteration** (the *writing precondition*, deliberately **not** conditioned on `$FIX_THRESHOLD`). The foreclosure row is **rationale-bearing**: like a Yes-downgrade deferral it carries the structured `parking_evidence` object `{basis, failing_input, source, finding_ref}`, with `source` holding the disclosure's repo path **plus** the short verbatim phrase quoted from it (the operand the comparison-time disclosure verification in `references/loop-control.md` re-checks). `skip_category` MUST be one of the values defined in the **`skip_category` enum (authoritative)** block below — the single source of truth for the enum.

   ##### `skip_category` enum (authoritative)

   | Value | Meaning | Required `evidence` | Pre-mapping gate: qualifies for REJECT downgrade? |
   | --- | --- | --- | --- |
   | `claim-quality` | Verifier evidence is correct in form but the underlying code is fine (e.g. the verifier oversimplified a branch the code handles correctly). | Cite the source span proving the code is correct. | **Yes** |
   | `out-of-scope` | The flagged lines are pre-existing code unmodified by this PR's diff, or belong to a separate concern from what this PR is doing. | Cite `git blame` / `git log -S` or the diff to prove the lines are not in this PR. | **Yes** |
   | `already-tracked` | A separate issue or PR addresses the underlying defect. | Cite the issue/PR number. | **Yes** |
   | `uncategorized` | None of the above fit cleanly. Use for "polish," "defer," "minor," "low priority," or any real-but-unfixed defect. | Free text describing why it wasn't fixed in-loop. | **No** — keeps the REJECT. |
   | `advisory-parked` | Written by Step 2.5 at demotion time (not by this step). Marks a finding that web-verification refuted or could not confirm. | Demotion reason (e.g. `refuted by {url}`, `inconclusive after web verification`, `over verification budget`). | **N/A** — advisory findings are not REJECT triggers; they cannot reach the gate as triggers in the first place. |
   | `below-threshold-parked` | Written by Step 2's below-threshold parking arm. Marks a finding recorded solely as a parked-class-sweep input. | Exact marker `parked-origin: below-threshold`. | **N/A** — sweep-only producer rows are not REJECT triggers and are excluded from existing advisory verdict/report operands. |
   | `settled-by-disclosure` | Written by this step (fixer-routed foreclosure) or by Step 2's per-finding foreclosure arm (parked foreclosure). Marks a non-blocking finding whose deliverable is an **already-shipped disclosure**: it is answered by that disclosure and must **not** be re-attempted. | Name the disclosure's repo path plus a short verbatim phrase quoted from it — both held in `parking_evidence.source` (and carried downstream as the manifest/payload `disclosure: {path, phrase}` object). | **N/A** — recorded only for a finding below the run's `verdict_severity_threshold` and **not** a REJECT driver of the current iteration (the writing precondition in item 5 below), so a foreclosure-eligible row is excluded from REJECT triggers by construction and cannot reach the gate as one. |

   Drift rule. If a future edit adds another value, add a row above AND verify the Pre-mapping gate's reference to this table still makes sense — the gate uses the "qualifies for downgrade?" column verbatim and assumes nothing else.

   A skip recorded with `skip_category` set to a value not in this enum (typo, missing field, etc.) is treated as missing-category and the gate keeps the REJECT.

   If the same `(source_file, claim_text)` pair was also skipped in the previous iteration, escalate to the user: "Finding persists after pushback: {claim}. Manual review needed." and stop the loop. Foreclosure carve-out: a repeat skip of a `(source_file, claim_text)` pair whose **prior-iteration row is `settled-by-disclosure`** does **not** trip this "Finding persists after pushback" escalation. This carve-out keys on the prior row's `skip_category`, never on severity, so a foreclosed row is the only suppressor. It does not apply when the finding is a REJECT trigger of the current iteration: a foreclosed row on a live REJECT trigger escalates exactly as today.

#### 6. Committing fixes

6. Commit fixes before re-running the review. Stage only the specific files this iteration's fix touched, by explicit path — `git add <file1> <file2> …`, listing every file the fix changed (one or many; run `git status --porcelain` first to enumerate them, including any new untracked files a plain `git diff` would miss). The fix-commit-fused Write below then records exactly this committed set as `fix_files` via `git diff --name-only HEAD~1 HEAD` (its full record shape is specified in item 7) — so enumerate from the working tree, not from `fix_files`. Never use `git add -A` or `git add .` at the fix-commit step: an unscoped stage sweeps unrelated working-tree state onto the feature branch, where the blinded shadow then flags it as a Critical that costs an extra fix iteration to revert.
   ```bash
   git add <file1> <file2> …   # the specific files this fix touched — never `git add -A` / `git add .`
   git commit -m "fix: address review findings (iteration {N})"
   ```
   Capture the fix commit's SHA, then Write `iter-<N>.json`, as one step — the workpad emit is fused to this fix-commit moment. Run `git rev-parse HEAD` to capture `fix_commit_sha`, and immediately Write `iter-<N>.json` (with the Write tool, never a shell `>`/heredoc redirect) carrying the full record shape specified in item 7 below — do not defer this Write to a later "persist" step. (`fix_commit_sha` is read by Step 0.9 of iter-(N+1).)

   If `--push-each-iteration` is set, bring the branch up to date with the base and push in one step via the shared checkpoint helper (base-branch update Checkpoint 3) — run it immediately before the push, so the helper's own push carries this iteration's fix and the base merge together. Invoke the helper alone in its fence, and gate the push on the token it prints (below) — never chain a bare `git push` after it in the same fence, which would push on *every* token, including the two that prescribe a stop:
   ```bash
   "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/update-branch-checkpoint.sh
   ```
   Handle the helper's printed token by the context split: inside a `/prflow:implement`-driven loop (Phase 3.3, where the orchestrator holds `$ISSUE_NUMBER`) record outcomes on the issue workpad and take the Blocked hard stop on `MERGE_IN_PROGRESS` / a failed conflict resolution, exactly per phase-1-setup.md §1.4.1; in a standalone run there is no issue workpad, so record the outcome in this iteration's `iter-<N>.json` and, on `MERGE_IN_PROGRESS` or a failed conflict resolution, take the loop's native "stop and report" (report in chat and end the loop) instead of a workpad flip. **In *both* contexts also write the `base_checkpoint` field to this iteration's `iter-<N>.json`** — it is the *named, durable operand* the Loop-exit suite rule in `references/loop-exit.md` reads, so it is never context-conditional (see item 7, which enumerates the field).

   Split the token when you write it — do not store the helper's printed line verbatim. The helper prints `UPDATED <behind>` (e.g. `UPDATED 3`) as a *single* stdout line, so a record that stores that line whole gives `base_checkpoint.token == "UPDATED 3"`, and the Loop-exit rule's `token == "UPDATED"` test is then false for every real merge. Write `token` as the bare token word (`UPDATED`, never `UPDATED 3`) and carry the count in `behind_by` (an integer for `UPDATED`, `null` for every other token): `{"token": "UPDATED", "behind_by": 3}`.

   Write the record AFTER this step, not before it — and after item 6a. Execution order within this item is: fix commit → item 6a's stale-prose pre-check → this checkpoint + its push-gating → re-Write `iter-<N>.json` with BOTH `base_checkpoint` and `stale_prose_check` included. (Item 6a is *printed* below this block but runs at this point in that order; the re-Write is Step 3's last Write — Step 3.5 appends the conditional `reference_reads.fix_delta` after it, per item 7.) An orchestrator that writes the record once, before the checkpoint, and never re-writes it emits a record with no `base_checkpoint` at all — which is exactly the absent-comparand shape the Loop-exit suite rule in `references/loop-exit.md` must fail closed on.

   Push shape (governs every push in this step, whichever token reaches it) — never a bare `git push` on an unverified checkout. Under `push.default=simple` a bare `git push` refuses both when the branch has no upstream *and* when its upstream's remote ref is named differently from the local branch (`fatal: The upstream branch of your current branch does not match the name of your current branch`). Push to an explicit destination ref instead (`git push origin HEAD:refs/heads/<the PR's head ref>`), exactly as `update-branch-checkpoint.sh`'s own `_do_push` resolves it.

   **Push gating — only these tokens push, and the fence above never pushes on its own:**
   - `UPDATED` — the helper already pushed (fix + base merge together). Do not push again.
   - `UP_TO_DATE` / `DISABLED` — the helper did not push, and the tree is in a good state: push now to propagate the fix commit.
   - `UNVERIFIED` — nothing was merged and the tree is untouched, so the fix commit still needs propagating: record the breadcrumb, push, and continue.
   - `PUSH_REJECTED` — the helper already attempted the push twice and restored the branch; do not push again (a third attempt fails identically). Record and continue — unless the helper's stderr carries the failed-restore `WARNING` (see the `PUSH_REJECTED` caveat in phase-1-setup.md §1.4.1), in which case the tree may still carry an unpushed base-merge commit and the run hard-stops per its context rather than continuing.
   - `CONFLICT` — do not push the unresolved tree. Resolve the conflicts. When the conflict is in a checked-in generated or derived artifact, do not hand-merge its bytes — regenerate the artifact or reconcile its source of truth per your repo's guidance; if you cannot establish whether the conflicted file is generated, stop and mark it needs-human-reconciliation rather than hand-merging. Run the project test suite, `git add`+`git commit`+`git push`, record the conflicted files, and re-run the changed-contract sweep before continuing the iteration; a resolution the suite fails is aborted (`git merge --abort`) and the run hard-stops per its context. This suite launch is coordinated by the same single-flight helper (see the Single-flight verification coordination note in Step 3's test-run step).
   - `MERGE_IN_PROGRESS` — nothing was touched and the run hard-stops per its context. Do not push.

   Track that an `UPDATED` merge landed this iteration by that `base_checkpoint` field (for the Loop-exit suite rule in `references/loop-exit.md`). When the flag is absent (the default), skip both the checkpoint and the push entirely.
   If the push fails (no upstream, rejected non-fast-forward, blocked by policy), do not abort the loop — report the failure in chat and continue. A failed push never breaks convergence: Step 1's head-override is what makes the next iteration see the fixes.

   Do not assume a pushed head is automatically re-reviewed. Whether the push's `synchronize` event triggers a fresh review is conditional on the repository's own triggers, so a run that needs the pushed head re-reviewed arranges it rather than waiting.

##### 6a. Stale-prose pre-check

   6a. Stale counted-prose pre-check (the same helper the engine runs in Phase 0.6). Immediately after capturing `fix_commit_sha`, run the *same* `stale-prose-lint.py` the shared review engine runs in its Phase 0.6 — here as a fast local pre-check that recomputes the full branch diff at the just-committed (post-fix) `HEAD` against the exact base operand the engine's Phase 0.2 resolved this iteration. In PR mode carry the held `$HEAD_OVERRIDE_BASE`: normally the fetched tip of `origin/$PR_BASE_BRANCH`, or the retained `$PR_BASE_SHA` only after Phase 0.2 authoritatively confirmed the named base was deleted. In current-branch mode `$PR_BASE_BRANCH` is unset, so resolve `$BASE` via the guarded `config-get.sh .base_branch main` capture (defaulting to `main` on an empty or failed read — the same guarded-capture shape Phase 0.2's current-branch fence uses). The fence keys on `$HEAD_OVERRIDE_BASE`'s presence; `$PR_BASE_BRANCH` only distinguishes a PR-mode iteration whose operand was not carried (fail closed, `exit 65`) from a genuine current-branch run. Hold that selected operand as `$REVIEW_DIFF_BASE`; never independently reconstruct a PR ref after Phase 0.2 has selected its deleted-base fallback, and never substitute the stale run-start SHA on a live base. Recompute at the post-fix `HEAD` and never read the pre-fix `diff.patch` Phase 0.2 cached before this iteration's fix commit, which leaves a stale claim this iteration's fix just introduced out of scope. The helper reads the diff on stdin and resolves referents at `--rev HEAD`; it never derives the diff range itself — the fence supplies the range:
   ```bash
   # BEGIN CURRENT_BRANCH_BASE_CAPTURE
   if test -n "${HEAD_OVERRIDE_BASE:-}"; then
     # Key on the OPERAND's presence, never on the PR_BASE_BRANCH mode-signal: keying on
     # the signal drops a carried operand PR_BASE_BRANCH was not threaded beside, falling
     # to the current-branch base and silently re-scoping the diff.
     REVIEW_DIFF_BASE=$HEAD_OVERRIDE_BASE
   elif test -n "${PR_BASE_BRANCH:-}"; then
     # PR-mode intent is signaled (PR_BASE_BRANCH present) but Phase 0.2's operand was NOT
     # carried: fail closed rather than silently fall back to the current-branch base.
     echo "::error::devflow review-and-fix: Phase 0.2 did not carry its resolved PR base operand; stale-prose pre-check cannot run" >&2
     exit 65
   else
     if ! BASE=$("${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/config-get.sh .base_branch main); then
       echo "::warning::devflow review-and-fix: could not read .base_branch (config-get.sh rc≠0); falling back to 'main'" >&2
       BASE=main
     fi
     if test -z "$BASE"; then
       echo "::warning::devflow review-and-fix: .base_branch resolved empty; falling back to 'main'" >&2
       BASE=main
     fi
     REVIEW_DIFF_BASE=origin/$BASE
   fi
   # END CURRENT_BRANCH_BASE_CAPTURE
   set -o pipefail
   git diff "$REVIEW_DIFF_BASE...HEAD" | "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/stale-prose-lint.py --rev HEAD
   ```
   With `pipefail` set the pipeline's exit code routes exactly as Phase 0.6 routes on the helper's own: `0` (no STALE), `1` (a STALE row present), and `2` (helper internal error) are the helper's arms. Any other non-zero code is a producer-or-helper failure — a `git diff` that could not resolve the base (`git diff` exits `128` on an unresolved base ref / detached-HEAD edge, piping empty stdout into the helper), or the helper itself failing to launch (`127`, or a signal death — the harness-refused / helper-absent arms Phase 0.6 defines). Record it as a degradation note carrying the observed exit code (`stale-prose pre-check: producer/helper failed (rc=<code>)`) and route per Phase 0.6's arms; do not read the empty output as a clean pass or hard-assert `git diff` as the culprit when the code is not `128`. Record the invocation outcome (the TSV rows, the producer/helper-failure note, or the helper's degradation arm) in this iteration's `iter-<N>.json` under a `stale_prose_check` entry. Reconcile any `STALE` row in this same iteration (fix the counted claim). A STALE row you judge a false positive is recorded through the existing `fix_decisions` pushback shape (`skip_category` plus evidence). A STALE row that survives unresolved to the `$MAX_ITERS` cap follows the existing `APPROVE WITH UNRESOLVED SHADOW FINDINGS` path. `UNRESOLVABLE` rows are informational and never gate. The rule classes, the config gate, and the degradation arms are defined once in the engine's Phase 0.6 and the helper's own header.

#### 7. Iteration record shape

7. The `iter-<N>.json` record shape (authoritative specification). The Write itself is anchored to item 6's fix-commit moment (see item 6 — capture `fix_commit_sha`, then Write, as one step); this item specifies exactly what that record carries. The write is a non-optional emit on every iteration — including a degraded or hand-run path where the review engine was dispatched directly via `Agent` instead of this Skill — and it is done using the Write tool, not a shell `>` redirect (which the cloud sandbox denies into `.prflow/tmp`); a permission/sandbox denial elsewhere in the run is never license to skip it. The `lib/efficiency-trace.sh --persist` synthesis backstop is a floor, not license to skip this emit: when the emit is dropped entirely, `--persist` reconstructs a *minimal* record (the `ITER_SYNTH_EXPECTED_FIELDS` set in `lib/efficiency-trace.sh`) from the fix commits, carrying none of the checklist / findings / per-phase cost detail this full record does. Write `iter-<N>.json` with: fix_commit_sha, fix_files (`git diff --name-only HEAD~1 HEAD`), `loop_role` (the iteration role from the schema: fix for a normal fix iteration, promoted for a Decide-outcome-2 shadow-promoted iter; `efficiency-trace.jq` derives it as a backstop, but persist it on every iteration as the source of truth), `sweep_defs_read` (one entry per Phase 2 source member, per item 3b), `sweep_evidence` (the item 3b sweep outcomes, including any `sweeps: unrunnable` degradation record), the iter-N `checklist` array — mandatory whenever Phase 1+2 ran this iteration (i.e. `checklist_skipped` is `null`): one entry per checklist item carrying its `verification_mode` (`lite` or `agent`, per /prflow:review's Phase 2 lite/agent partition), `verdict`, `claim_signature`, and `reused_from_iter_prev: true|false` (whether Phase 2.0.5's narrow-reuse path was taken). Persisting `checklist[]` is what lets `efficiency-trace.jq` derive the real lite/agent split and a `verification_posture` other than `none-recorded`; omitting it on a run where Phase 1+2 ran is a telemetry regression. (When Phase 1+2 were genuinely skipped — `checklist_skipped` is `"intentional"` or `"failure"` — `checklist` is `[]` and the posture reflects the skip.) Continue with `phase3_dispatched` (the array of Phase-3 agent identifiers actually launched this iteration after Phase 0.5 gating — see the workpad schema note in `references/loop-control.md`), `expected_reviewers` (the engine's own recorded Phase 3.1 gate decisions for this iteration — the roster its gates selected, same identifier strings as `phase3_dispatched`; see that schema note), `phase3_failed_agents` (the array of Phase-3 agent identifiers dispatched but that did not return a usable result — evidence-empty / failed / lost; same identifier strings as `phase3_dispatched`, written on every iteration (`[]` when none), the sink the efficiency trace reads to mark a `failed` per-agent disposition), `dispatched_effort` (the per-dispatch-phase effort observability entries captured per the schema note in `references/loop-control.md` — one entry per dispatched agent per phase 1/1.5/2/3 from `resolve-review-overrides.py --effort-json`), `diff_profile` (the engine's Phase 0.5 flags + `checklist_skipped` for this iteration — see the schema note), Phase 3 findings (each with `defect_signature`, `step25_classification`, and the matching `fix_decision` so iter-(N+1)'s Phase 3 handoff has the full record), `fix_decisions` (one entry per finding using the shape shown in the workpad schema example: `applied` entries carry `{finding_id, decision, commit}`; `pushed_back` / `deferred` entries carry the structured pushback fields `{source_file, claim_text, skip_category, evidence}` from Step 3's item 5 where `skip_category` is one of the values in the `skip_category` enum (authoritative) table; `advisory` entries — written by Step 2.5 at demotion time, not here — carry `skip_category: "advisory-parked"` plus the demotion `evidence`; `below-threshold` entries — written by Step 2's below-threshold parking arm as a sweep-only producer row — carry `{finding_id, decision: "below-threshold", source_file, claim_text, skip_category: "below-threshold-parked", evidence: "parked-origin: below-threshold"}`; `settled-by-disclosure` entries — written by this step (a fixer-routed foreclosure) or by Step 2's per-finding foreclosure arm (a parked foreclosure) — carry `{finding_id, decision: "settled-by-disclosure", source_file, claim_text, skip_category: "settled-by-disclosure", evidence, parking_evidence, disclosure: {path, phrase}}` (rationale-bearing, so `parking_evidence` is present and its `source` names the disclosure). On any loop shape exactly one `fix_decisions` row is written per foreclosed finding — foreclosure dominates, so a finding foreclosed off the below-threshold path carries the `settled-by-disclosure` row **instead of** (never in addition to) a `below-threshold` row; `severity-calibrated` entries — written by the Over-grade calibration gate / Step 3's item 2 as its recorded technical evaluation — carry `{finding_id, decision: "severity-calibrated", source_file, claim_text, original_severity, calibrated_severity, evidence}` with no `skip_category` (it is a calibration record, not a skip)), convergence_inputs, `cap_drops` (from /prflow:review's Phase 1.1.5 output — see that skill for the shape), and the `telemetry` block — mandatory: populate per-phase `calls` / `tokens` / `wall_clock_s` for the phases that ran this iteration (capture rules in Loop Exit's "Run telemetry summary"). Per-phase `tokens` is best-effort *per source* — a missing `<usage>` block for one agent is skipped, but the `telemetry` key as a whole must still be written; when no phase figures were established, write `"telemetry": "unavailable"` — never omit the key or write JSON `null`. Also write `base_checkpoint` (from item 6, **whenever the Checkpoint-3 helper ran this iteration — in *either* context, implement-driven or standalone**) — an object `{token, behind_by}` where `token` is the bare outcome word (`UP_TO_DATE` / `UPDATED` / `DISABLED` / `CONFLICT` / `UNVERIFIED` / `PUSH_REJECTED` / `MERGE_IN_PROGRESS`) and `behind_by` is the count the helper printed alongside `UPDATED` (an integer for `UPDATED`, `null` for every other token). Never store the helper's printed line verbatim (see item 6). This field is added by the re-Write item 6 mandates once the checkpoint and its push-gating have completed. It is not optional bookkeeping: it is the *named, durable operand* the Loop-exit suite rule reads to decide whether a Checkpoint-3 merge landed after the loop's last suite run, so an iteration that omits it leaves that rule with an absent comparand and it fails open. An iteration in which the helper did not run (the flag is absent, or a no-fix iteration) simply carries no `base_checkpoint` — which the Loop-exit rule reads as "no merge landed". Also write `stale_prose_check` (from item 6a) — the invocation outcome of the stale-prose pre-check (its TSV rows, or the producer/helper-failure note). Also write `verification_evidence` (from item 4) — an object `{command, result, duration_s, skipped_checks, focused_selection}` recording the iteration's test-suite run: `result` is `pass` / `fail` / `skipped` (a `skipped` value additionally carries a `reason`, e.g. a no-fix iteration or a cloud run whose suite command is ungranted). `skipped_checks` is a list — one entry `{check, kind, reason}` per check the suite reported skipped *inside* a run that otherwise executed (distinct from `result: "skipped"`, which means the whole suite run was skipped); it is omitted or `[]` when nothing skipped, and a non-empty `skipped_checks` means the iteration is not a clean pass (item 4). `focused_selection` is the focused-first selection record — the named record `scripts/focused_selection.py`'s `build_record` produces, stored verbatim here as the standalone fix loop's sink: per touched surface it names either the coverage-map entry consulted and the target selected (a discharging focused result) or which exemption ground applied, plus a `single_flight_consulted` field recording whether `scripts/verification-flight.py`'s durable status handle was read before a full-suite relaunch. It is omitted when no focused selection was recorded this iteration (a reader treats its absence as "no focused-selection record"), distinct from a present record whose `surfaces` list is empty. The field is optional; a reader treats its absence as "no evidence recorded" / "no skips recorded". The `shadow` block, if any, is appended later by Step 2.6 and is not populated here.

   Conditional gate/sweep fields (part of the authoritative item-7 shape). Also write `test_first_gate`: the JSON array consumed from `.prflow/tmp/review/<slug>/<run-id>/iter-<N>-gate-evidence.json` in standalone mode, or the equivalent structured entries derived from the implement workpad notes. Preserve every applicable automated-test RED/GREEN result, no-automated-test dry-trace, and model-context RED/GREEN/no-guidance micro-test outcome (including `unrunnable` / `fail` records); use `[]` only when none of those three verification routes applied this iteration. On a fix-applying iteration, `sweep_defs_read` and `sweep_evidence` carry the item-3b values specified above; `sweep_evidence.status` is `"run"` on an iteration whose sweeps executed, so the defined statuses are `"run"`, `"not-run"`, and the `"unrecoverable"` value the synthesis floor stamps (with `sweeps: unrunnable` recording a degraded source read). On a no-fix iteration, write `sweep_defs_read: []` and `sweep_evidence: {"status":"not-run","reason":"no fixes applied"}` — never fabricate a sweep run and never omit the authoritative fields. `reference_reads` is a *conditional* top-level field (like `shadow`), appended by Step 3.5's fix-delta gate: it is absent on an iteration where that gate did not run, and its absence is not a defect. It is a registry keyed by the producing reference — `fix_delta` (from `fix-delta-gate.md`) is its only member today; a future reference recording its own read adds a sibling key, never nests under `fix_delta`. Shape: `{"fix_delta": {"status": ..., "outcome": ..., "reason": ...}}` — `status` is `"verified"` when the gate ran and produced a usable result and `"not_verified"` when it could not verify (the gate-subagent double-failure arm, the deterministic delta-computation failure arm, or the added-assertion check's unestablished arm — an added assertion whose target could not be read); `outcome` records what a `verified` gate concluded (`"clean"`, `"refixed"`, or `"promoted"`) and is `null` on `not_verified`; `reason` is `null` on `verified` and otherwise carries that arm's specific breadcrumb text, naming *which* arm fired (a failed re-dispatch vs an unresolved `<iter_fix_base>` vs an unreadable assertion target), matching the distinct-breadcrumb rule `references/fix-delta-gate.md` already states. A `not_verified` fix_delta prohibits a clean APPROVE-family verdict for the run. When the `--persist` synthesis floor reconstructs a record, these evidence fields instead carry `{"status":"unrecoverable","reason":…}` (for `reference_reads`, inside `fix_delta`), so a consumer must branch on `status` before any shape-specific operation (a synthesized `sweep_defs_read` is an object where a real one is an array).

For item 7's record shape, `promotion_provenance` is conditional beside `loop_role`: every record with `loop_role: "promoted"` persists exactly one of `"shadow"`, `"park-calibration-post-shadow"`, or `"park-calibration-pre-shadow"`, read by item 6's fused Write from Step 0.9's staged value. A normal `loop_role: "fix"` iteration carries no provenance field.
