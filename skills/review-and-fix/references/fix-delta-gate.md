# Reference: Fix-delta Verification Gate (Step 3.5)

### Step 3.5: Fix-delta verification gate (before Step 4 / the convergence check)

Step 1's review and Step 2.6's shadow both audit the *whole* diff; neither re-audits the fix itself, with independent eyes, in the iteration that produced it. A fix is new code, and it can introduce a fresh instance of a bug class — most often the `unverified-assumption` class, where a guard's accepted-input set is wider than its downstream consumer's contract. This gate catches such a fix-introduced regression in the same iteration that produced it, rather than at the end-of-loop Step 2.6 shadow, which would promote a costly extra iteration. It is review-and-fix-only by construction (it runs only inside this fix loop); it leaves `/prflow:review`'s verdict computation untouched.

Fires after Step 3 commits the iteration's fixes and captures `fix_commit_sha`, and before Step 4 / the Step 4.5 convergence check — on every iteration unconditionally, not gated on the verdict. The gate, and its inner re-fix → re-gate attempts, are not counted toward the `$MAX_ITERS` cap — they verify the current iteration rather than starting a new fix iteration (the same accounting the Step 2.6 shadow uses).

Dispatch barrier. Every subagent dispatch described here is bound by the dispatch-collection requirement in the engine-ground-truth block injected into this run's prompt — read it there (if your prompt carries no such block, collect every dispatch before the turn ends anyway); it is deliberately not restated here.

No-fix iteration → no delta → no-op. The gate is not gated on the verdict, and it does not manufacture a delta where none exists. Key the skip on the direct signal — *Step 3 applied no fixes this iteration* (every finding pushed back / deferred, so Step 3 item 6 produced no new fix commit) — not on a derived SHA comparison: when no fix commit was made this iteration there is no `<iter_fix_base>..HEAD` span to review, so skip the gate for that iteration and proceed to Step 4.

Dispatch a blinded subagent (a `general-purpose` Task that does not itself fan out — like a single shadow reviewer) that re-reviews only the cumulative fix delta of this iteration — `git diff <iter_fix_base>..HEAD`, where `<iter_fix_base>` is the parent of the iteration's first fix commit (capture it once, before Step 3's first commit this iteration) — plus the relevant consumer code the delta calls into, treating it as brand-new code. For the added-assertion check below, the dispatch scope additionally admits a bounded read of each added assertion's own target — the file whose content that assertion reads — which, for an assertion guarding text the delta did not touch, is by construction outside the delta. That widening is bounded to the targets the delta's own added assertions name and not already present in the delta, and is granted for that check alone; it does not widen the other checks' scope. Span the iteration's *first*-fix parent through `HEAD` rather than a single `<fix_commit_sha>~1..<fix_commit_sha>` commit: an inner re-fix attempt below adds a further commit, so a single-commit span would re-gate only the re-fix and leave the original fix commit's surface unreviewed, letting a cross-commit contract mismatch read clean. The cumulative span keeps the whole iteration's current fix set in scope on every gate run, including re-gates. Blinding is the point — the context that wrote the fix is the one that cannot see its flaw. So withhold the loop's prior findings, fix decisions, and fixer reasoning from the subagent's prompt: do NOT pass `prior_phase3_findings` / `prior_checklist` / `fix_files`, and do NOT include any `fix_decisions` rows or the fixer's rationale. This is the inverse of Step 0.9's iter-N handoff, mirroring exactly how Step 2.6 blinds its shadow reviewers ("Blind every shadow reviewer prompt").

The gate's checks explicitly include:
- the operand-contract check — any guard or predicate the fix adds must have an accepted-input set that is a *subset* of its downstream consumer's contract. Prefer sharing the consumer's own operation as the guard (the share-the-contract / parse-don't-validate principle in `prflow:receiving-code-review`) over a separate validator that re-derives the contract; and
- the adversarial input-shape matrix for hand-corruptible inputs — sweep the `{object, array, scalar, valid-falsy (explicit false / 0 / empty string), missing, wrong-type}` shapes — the adversarial matrix any parser over hand-corruptible config JSON owes — asserting the fix fails closed (a specific breadcrumb), not open, on each. The valid-falsy shape is the one an `// true` / `// default`-style extraction silently coerces (a real `false`/`0`/`""` read as its truthy default) — and inline jq inside a workflow file is a parser this matrix applies to, not only a standalone `.sh`/`.py`/jq consumer. The same matrix discipline widens to a parser over agent- or human-mutable markdown and a reader of a new external structured format — each governed by the malformed-shape matrix appropriate to its input type (mutable markdown: missing/duplicate sections and markers, non-canonical layout, empty/truncated input; an external format: that format's own boundary rows), the six-shape set staying the config-JSON matrix; and
- the added-assertion attribution check — for each assertion the fix delta adds, identify the regression that assertion's own name and description claim it catches, then ask whether the assertion as reported would single that regression out. Three outcomes are reportable, and each is reported against the specific assertion: (i) the assertion would not change state under the named regression — the regression occurs and the assertion still reports the same result, so it guards nothing it claims to; (ii) the assertion would change state under a cause other than the named regression — it flips for an unrelated reason (most often because the change it depends on destroys the anchor it keys on rather than the behavior it names), so its signal does not mean what its name says; (iii) the assertion's reported identity does not distinguish it from a sibling arm — two or more arms report under the same name or description, so a result is not attributable to one of them. When an added assertion's target cannot be read, report that assertion **unestablished** — never clean, since an unread target is an unestablished measurement. Route an unestablished assertion as an added-assertion attribution finding under the third routing arm below (its correction is making the target readable, or making the assertion self-contained), and because the check was not discharged for that assertion the iteration's record takes the existing `{"status":"not_verified","outcome":null,"reason":"<which assertion, and why its target was unreadable>"}` shape rather than the clean outcome. When the iteration applied fixes but added no assertions, the check's input is empty by construction rather than undefined: report that arm explicitly and record it in the `reference_reads.fix_delta` record below. This check names no command to run, no test framework, no test-runner invocation, and no repository-specific helper identifier — it is discharged by reading the assertion and its target, so a consumer repository in any language discharges it with no framework-specific affordance. It inherits the no-fix skip arm above: an iteration in which Step 3 applied no fixes has no delta, so it runs no added-assertion check.

Routing of a gate finding: the two severity-graded arms below apply to the operand-contract check and the adversarial input-shape matrix — the two checks that predate the added-assertion check. The added-assertion attribution check carries its own disposition, stated in the third arm, so every input has exactly one applicable disposition.
- A new Critical/Important gate finding first passes through the Over-grade calibration gate (in `references/shadow-review.md`, Step 2.6): per that gate a suspected over-grade is flagged and requires a recorded `severity-calibrated` technical evaluation — it is never auto-demoted, and the recorded evaluation then decides the finding's fate. A finding the evaluation calibrates down does not trigger a re-fix; one re-affirmed at Critical/Important routes back into the same-iteration Step 3 (re-fix → re-gate), capped at 2 inner attempts. After the 2 inner attempts are exhausted the finding is promoted to a normal iteration (a Step 1 re-review), which does count toward `$MAX_ITERS` — so a fix the gate cannot settle in-iteration still terminates under the cap. If iter N is *already* the cap iteration (the promotion cannot start a further iteration), the unresolved finding is not dropped: it is carried into the end-of-loop Step 2.6 shadow's whole-diff audit, where a genuine fix-introduced regression re-surfaces (and routes through the shadow's own cap handling — `APPROVE WITH UNRESOLVED SHADOW FINDINGS`, or `REJECT` if Critical). Because the shadow re-derives findings independently over the whole diff (it is not handed the gate's specific finding — Step 2.6 is unchanged), also record the unresolved at-cap finding in a `## Devflow Reflection` bullet so it is durably surfaced for the human reviewer even in the corner case where the shadow's whole-diff pass does not independently re-raise a delta-isolation-only regression.
  An exhausted two-attempt fix-delta finding starts a normal re-review iteration that persists `loop_role: "fix"`; it is not a Decide-outcome-2 promotion.
- A Suggestion/Minor gate finding from either of those two checks is recorded as advisory and does not trigger a re-fix (mirrors the loop's existing severity routing).
- An added-assertion attribution finding is not routed by severity at all: the assertion it reports on is corrected in the same iteration, exactly as a swept sibling under Step 3 item 3, and one deliberately left is recorded through the item 5 pushback flow. This disposition inherits this gate's existing termination machinery: a correction routes back into the same-iteration Step 3 under the same 2-inner-attempt cap, an exhausted pair of attempts is promoted exactly as the Critical/Important arm's is — into a cap-counting Step 1 re-review — and at the cap the unresolved item is carried into the end-of-loop Step 2.6 shadow's whole-diff audit and recorded in a `## Devflow Reflection` bullet.

Gate-subagent failure — the subagent errors, cannot run, or returns an unusable result — triggers exactly one bounded re-dispatch (same blinded prompt). If that re-dispatch also fails, record `fix-delta not verified` in a `## Devflow Reflection` bullet and proceed to Step 4. This is the same single-bounded-re-dispatch-then-record-and-proceed shape the Step 2.6 shadow uses for a transiently-failed reviewer, and the one re-dispatch applies to every *subagent* failure kind. Distinguish a deterministic input failure, though: if the delta itself cannot be computed — `<iter_fix_base>` was not captured, or `git diff <iter_fix_base>..HEAD` returns an error/empty on an iteration that *did* commit a fix — that is an orchestrator ref-computation defect, not a flaky subagent, so retrying the same prompt against the same broken ref is pointless. Skip the re-dispatch in that case and record a distinct, specific breadcrumb (`fix-delta gate could not compute the delta (iter_fix_base unresolved) — gate disabled this run, shadow is the backstop`) so a structurally-broken gate is not laundered into a breadcrumb that reads identically to a transient subagent hiccup. A gate that fails for the whole run (structurally broken subagent dispatch, an unresolvable `<iter_fix_base>`) records its breadcrumb each iteration and degrades to the Step 2.6 shadow as the safety net, rather than blocking convergence.

The Step 2.6 shadow pass and the Loop Exit post-shadow edit gate are unchanged; this gate complements them by front-loading delta-regression detection. Record one `## Devflow Reflection` bullet with the gate's per-iteration result — `fix-delta gate clean`, which finding was re-fixed or promoted, or `fix-delta not verified`. A consumer repo sharpens the generic input-shape checks with local instances via `.prflow/prompt-extensions/review-and-fix.md`; the extension sharpens but does not supplant this gate.

Also persist that result durably into the active iteration's `iter-<N>.json` under the conditional top-level `reference_reads.fix_delta` field, in the shape `fixing.md` item 7 specifies: the clean path → `{"status":"verified","outcome":"clean","reason":null}`; a finding re-fixed or promoted → `{"status":"verified","outcome":"refixed","reason":null}` or `{"status":"verified","outcome":"promoted","reason":null}`; any failure arm → `{"status":"not_verified","outcome":null,"reason":"<that arm's breadcrumb>"}`. Every arm that yields this shape keeps its distinct breadcrumb in `reason` — the bounded-re-dispatch-also-failed arm, the unresolved-`<iter_fix_base>` arm above, and the unestablished-assertion arm the added-assertion check routes here each carry their own text, and `reason` must preserve that distinction rather than collapsing them onto one string. A fix iteration that applied fixes but added no assertions records that arm explicitly as the clean path's `{"status":"verified","outcome":"clean","reason":null}` object, naming `no assertions added` in the same iteration's reflection bullet. The reflection bullet remains; the field is the durable record.
