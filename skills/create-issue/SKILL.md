## Forward to spec

`/prflow:create-issue` is a thin forwarding alias for `/prflow:spec`. Open `skills/spec/SKILL.md` with your file-read tool and follow it exactly, as if `/prflow:spec` had been invoked — but before you resolve any reference file spec names, read and apply the reference-base redirect below, because it governs where those references resolve and skipping it silently degrades the run. The spec root you open performs the one prompt-extension load for both command names — it reads the `spec.md` extension file — and the create-issue alias loads none of its own.

Reference-base redirect (load-bearing). The runner leaves the skill base directory (`${CLAUDE_SKILL_DIR}`) pointing at this shim's own directory even after you open spec as a plain file, so spec's own reference paths would otherwise resolve to a nonexistent `references/` directory beside this shim and silently degrade onto its reference-load-failure arms. Resolve spec's reference files from `skills/spec/references/`, and resolve any path spec derives from its own skill directory against `skills/spec/` — never the invoked shim directory. Helpers reached through the `../../scripts/` suffix, and prompt extensions named by a literal skill name, are unaffected.

Resolve those spec targets portably, not as bare working-directory-relative paths — in an installed consumer checkout the working directory is the consumer's own project (which has no `skills/` tree), while the plugin's skills live beside `${CLAUDE_SKILL_DIR}`. Because `${CLAUDE_SKILL_DIR}` is this shim's own directory, its sibling spec directory is `${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}/../spec/`; resolve spec's `SKILL.md` and every reference path under it relative to that sibling directory (when `${CLAUDE_SKILL_DIR}` is empty, take the spec sibling of the skill base directory the runner reports in context — never that base directory itself, which is the invoked shim directory) so both the initial open of spec's skill file and its reference loads resolve in a consumer checkout and not only in PRFlow's own dev tree.

## Runner setup

**Portable helper anchor (single-statement).** The bundled-helper commands in this skill spell the skill directory as `${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}`. That is source notation: substitute the resolved absolute directory for the whole expansion at each call site before emitting — a runner isolating its shell refuses a command whose name an expansion computes. Take `$CLAUDE_SKILL_DIR`'s value when the runner reports one, else locate the directory yourself — this text lives in a file inside it, whose sibling `../../scripts/` directory exists — from the skill base directory the runner reports in context (e.g. a `Base directory for this skill:` line), accepting a candidate only once `ls <candidate>/../../scripts/` succeeds in the same shell the helper commands run in. If a path form is rejected, use the form that shell reports (`pwd` shows it); a Windows-form base directory (`C:\...`) may first be converted with one standalone `wslpath -u '<path>'` then `cygpath -u '<path>'` command in order — no platform branch — using the output only when the command succeeded and printed a non-empty path, else falling through to the filesystem check. Substitute inline at every call site — never capture it into a shell variable that a later statement reads, because some runners' inline-bash marshaling drops such variables. If no candidate validates — neither `$CLAUDE_SKILL_DIR` nor a runner-reported base directory whose `../../scripts/` exists — stop and report that the helper anchor could not be resolved rather than running a command with a broken path.
