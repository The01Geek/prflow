### Step 4: Review with the user, then create

Sub-steps: 1 show the draft · 2 write the draft file · 3 render the audit summary line and disclosures · 3a the single audit-round offer · 3b the single file-anyway election · 3c the combined approve-and-assign question · 4 iterate on feedback · 5 create (5a label, 5b dependencies, 5c investigation record) · 6 gated implement offer.

Every question this step puts to the user sits in 3a–3c, in that order, and each is asked at most once per pause — one audit-round offer whatever its ground, one file-anyway election whatever its ground, then approval and assignment together. Nothing is asked before the rendered draft is on screen, and no question that gates creation is asked after `record-creation-epoch` binds it — sub-step 6's implement offer, which runs only once the issue exists, is the one later question this step puts.

**The issue is never created until the user has seen the full rendered draft and explicitly approved it.** This gate is **unconditional** — no matter how thoroughly Step 2 resolved every decision, and no matter what the user said earlier. A rough user story is not approval of the assembled ticket.

**Presentation gate (before the draft is shown).** Clear these four in order. Each blocks presentation only; none blocks creation.

- **Consume the clean Steelman projection.** Re-read the latest Steelman pass and `.prflow/tmp/steelman-projection-<slug>.json`, require matching pass numbers, then run `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/run-jq.sh -e -f "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../lib/projection-gate.jq ".prflow/tmp/steelman-projection-<slug>.json"`. It restates `references/step-3-5-steelman.md`'s entry-confirmation contract (item 9) deliberately: a Step 4 entry need not hold that reference. Missing, stale, wrong-typed, inconsistent, or unmatched state stops presentation and returns to Step 3.5's revise-and-re-gate path, **at most once per presentation attempt**: a second failure is reported in chat and presentation proceeds with the projection state named unestablished. The read-only degraded arm is eligible only when its current-turn inline state is `represented` with an empty unmatched array. Nonempty ACs or a clean Step 3.6 verdict never substitute for this check.
- **Confirm the run bootstrap ran.** This run holds a minted nonce and a bound draft root (`query-draft-binding` answers a real absolute root). If neither exists, stop and run the bootstrap now before presenting. This gate re-enters the run bootstrap and never an audit round, and the Step 4 working-file listing reports the audit path's class but re-enters no step for it.
- **Read what the bootstrap's two Step 3.5 gates left, rather than asserting they ran.** The verified-premise check and the acceptance-criteria parseability gate execute at the bootstrap canonical write (`references/step-3-6-audit-dispatch.md`), and what this run carries from them is the only evidence available here: an established `acceptance_criteria` array, or the in-chat breadcrumb naming the failure kind. Carrying neither, the count marker renders its unavailable token (sub-step 3) — never a claim that the gates ran.
- **Confirm the audit artifact only when a round was opened.** A run that has elected no audit round has no audit artifact, and the gate admits it — it never re-enters Step 3.6 to dispatch a round the user has not been asked about. Only when this run has elected and opened a round is `.prflow/tmp/issue-audit-<slug>.md` expected — then confirm it is present and holds this run's audit (the Step 3.6 write deletes any same-slug leftover first). If any `.prflow/tmp/` write or delete was refused earlier in this run, the on-disk artifact can only be a stale leftover: distrust it and rely solely on the visible inline-in-chat audit block re-posted this turn, per `references/fallback-read-only-sandbox.md` — the run-state condition, not a local write failure, is what selects that fallback here.

1. **Show the complete rendered issue in chat.** Post the exact title and the full body — every section, verbatim, as Markdown — directly in your message. Do not summarize, abridge, or describe it. Do not use the runner's user-question tool (`AskUserQuestion` or its equivalent) to stand in for showing the body — such tools truncate. Render the body first, then use that tool for the confirm/edit prompt if you wish.
2. Also write the draft to a file for easy review — at the MAIN repo root. Reuse the run's kebab-case `<slug>`: Step 1 binds it, and this is the only site that derives one instead. Read it from turn-one context, else from the pointer `.prflow/tmp/issue-run-slug` Step 1 wrote, judging that pointer **unestablished** on the grounds the skill root's Step 1 states. Only then derive one from the issue title here (e.g. "Add CSV export for survey results" → `add-csv-export-for-survey-results`).

   Resolve the main working-tree root with the bundled `resolve-main-root.sh` (same portable anchor recipe as above), then create its `.prflow/tmp` and write there:
   ```bash
   MAIN_ROOT="$("${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/resolve-main-root.sh)"
   mkdir -p "$MAIN_ROOT/.prflow/tmp"
   ```
   Capturing the resolver's output into `MAIN_ROOT` is fine — both statements sit in this one fence. Step 3.6's binding fence re-resolves inline instead because it is a separate fence, where this variable expands empty.

   Write the rendered title + body to the absolute path `$MAIN_ROOT/.prflow/tmp/issue-draft-<slug>.md`, with the title as a top `# ` heading. Perform this write through the *Staged canonical-draft write* shared procedure in `references/step-3-6-audit-shared.md` — load that file per the *Reference routing* rules when this entry does not already hold it; on a failed load, stage nothing, write the bytes straight to the canonical path, report the unstaged write in chat, and report `--write-landed no` to `query-arm`. The procedure records no revision, so it runs the stage → apply → verify steps, and its landed re-check compares the canonical file against this write's own in-turn `--expect-digest`. Use the main root, not the cwd.

   Bind the draft root once, then reuse it — bind if not already bound. The binding is recorded by the first landed canonical-draft write of the run, normally Step 3.6's pre-dispatch write. Do not assume what that site did — detect the case here: read `query-draft-binding "<slug>" --nonce "<nonce>"` and branch as Step 3.6's binding procedure specifies — already-bound (skip, take the `bound=` root); `bound=none` with no `reason=` (run Step 3.6's `record-draft-binding … --tier main-root` fence here; it is query-first and idempotent, so `binding-already-recorded` is the benign expected outcome); `reason=foreign-nonce` (the foreign-nonce arm of `references/fallback-draft-write-recovery.md`, loaded per `references/degradation-routing.md` — surface the drift, never the quiet unbound arm, and never compose a path); and a query that returns no answer at all (state owner unavailable, or the invocation refused) — attempt no bind, and treat the run as legitimately unbound. An unbound run is legal and must stay safe: `none` is a decided token, not a path, so never compose a path from it — fall back to the `MAIN_ROOT=` root for this write and follow the `bound=none` display arm in sub-step 3.

   Every later write site (a Step 3.6 re-dispatch write, the sub-step 4 overwrite, and the sub-step 5c record write) runs in a later turn, so it takes the bound root from `query-draft-binding "<slug>" --nonce "<nonce>"`'s `bound=` field — never context recall, never a second `resolve-main-root.sh` resolution while a binding exists; `<bound-root>` in the sub-step 3 display note is that same root. The presentation write above is the exception: same turn, root already in hand. **When the binding read reported a bare `bound=none` (no `reason=`), the run is legitimately unbound: re-resolve the main root for *this* turn with the sub-step 2 `resolve-main-root.sh` recipe and write under that root** — never compose a relative `none/…` path from the token, and never reach for a `MAIN_ROOT` bound in an earlier turn. Take the `bound=none` display arm in sub-step 3 alongside it. On the file arm, forward the exact absolute canonical path to `record-dispatch --write-path <that path>`, which the state owner refuses with `write-path-mismatch` on divergence.

   Keep this one `<slug>` throughout, reusing that exact absolute path from then on. This copy never replaces showing the body in chat. On an embed/inline-arm epoch it is not the source the issue is created from; on a file-arm epoch this canonical file *is* the posting source — but only through the gated `emit-body` emitter (sub-step 5), never by passing the path to `--body-file <path>` directly. If the write fails (read-only main root / sandbox), note it briefly and continue without showing a path.

3. Render the audit summary line and disclosures — ask nothing here. Every question belongs to 3a–3c, the confirm/edit one to 3c. **The draft-save-location note (the absolute `<bound-root>/.prflow/tmp/issue-draft-<slug>.md` path from sub-step 2) always renders *below* the rendered issue preview — never above it**, so every confirmation message has the same layout: the full rendered body first, then the one-line Step 3.6 audit summary, then (when recorded) the per-finding disclosure block, then the draft-path note, and only then 3a–3c's questions.

   Per-finding disclosure block. A run that opened no audit round graded nothing and skips this block entirely — `query-adjudication-records` requires a `--round`, and there is none. On a run that opened a round, read `query-adjudication-records "<slug>" --nonce "<nonce>" --round "<round>"`; when it returns records rather than `records=none`, render each advisory and invalid finding's `summary`, `rationale`, `impact_class` tag, and the auditor's own `auditor_block` beside the grader's restatement, then report that rendering exactly as the calibration paragraph of `references/step-3-6-audit-adjudication.md` states. The audit summary line's own class counts stay unchanged.

   The summary line is one of the root's non-degradable invariants: it renders on every arm and every round count. Do not assemble its fields from recollection — read them from `query-summary`:

```bash
python3 "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/issue-audit-state.py query-summary "<slug>" --nonce "<nonce>" --draft-file "<absolute issue-draft-<slug>.md path>"
```

#### The `query-summary` fields this line consumes

The command prints more fields than the line renders; these are the ones it reads. Findings count, revisions applied, verdict, rounds run, whether a consumer `## Audit dimensions` section was appended, the degraded flag, the user-declined and cap-reached flags, any embed-arm markers, the eligibility token, and `attestation=<match|mismatch|attestation-unavailable|none>` (`none` = before any creation attempt). Per latest completed round: `adjudicated_verdict`, the per-actionability-class counts (`must_revise`, `advisory`, `invalid`), `unresolved_must_revise`, and — rendered immediately before the trailing `attestation=` — the pair `steering=<established|not-established|unestablished>` and `steering_reason=<token|none>`. Run-wide, before `bound_root=`: `effective_unresolved`, `convergence_basis`, `final_byte_passes=`, `final_byte_exhausted=`, and `final_byte_coverage=<covered|uncovered|unestablished>` (whether the bytes that would be filed carry a verdict from a round dispatched against those exact bytes).

`query-summary` prints no `final_byte_reason`, so a line that must name one reads it here, from its own `query-final-byte` call — the one gate read this sub-step makes, ahead of sub-step 3a's:

```bash
python3 "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/issue-audit-state.py query-final-byte "<slug>" --nonce "<nonce>" --draft-file "<absolute issue-draft-<slug>.md path>"
```

3a re-reads it there for its own offer decision.

#### Markers the summary line must carry

Steering. When `steering` is anything but `established`, the line carries a dedicated skill-composed marker naming it — `audit independence unestablished (<steering_reason>)` — rendered alongside whatever other skill-composed markers this line carries and distinct from the reserved `degraded` token. It never blocks filing. An `established` round is never described as provably steering-free.

Coverage and adjudication counts. The line reports the bundle's coverage (`axes evidenced, axes marked N/A, axes unestablished`), the post-adjudication counts by actionability class, the unresolved must-revise findings attributable to an axis on the effective list as frozen at that round's close, and — distinctly, never collapsed onto it — the run-wide effective unresolved count after every post-close resolution, reopen, invalidation and supersession. A round whose actionability or axis attribution could not be established renders `unestablished` rather than a number.

Final-byte coverage. The line carries the final-byte coverage value on every dispatch arm and every round count — the degraded inline arm included — as `final bytes audited` on `covered`, `final bytes NOT audited (<final_byte_reason>)` on `uncovered`, and `final-byte coverage unestablished (<final_byte_reason>)` on `unestablished`; when `final_byte_exhausted=yes`, append `— final-byte passes exhausted`. Read `<final_byte_reason>` from this sub-step's own `query-final-byte` line above. A recorded `attestation=match` never stands in for that phrase.

Convergence basis. When `convergence_basis` names a resolution basis, the line additionally carries the phrase `converged via self-verified resolution` — on the stale variant `converged via self-verified resolution (stale — later revisions unverified)`.

Criterion count. The line also carries the criterion count as a skill-composed marker — `<n> acceptance criteria` — rendered alongside the other skill-composed markers this line already carries. It is the length of the `acceptance_criteria` array returned by the `python3 … scripts/parse-acs.py --format json` invocation the run already performs at the run bootstrap's canonical write (which runs regardless of whether an audit round is elected); perform no second parse, and compose the marker in the skill rather than reading it from `query-summary`. It is reported, never enforced.

The number renders only when this run holds an established `acceptance_criteria` array from its own gate invocation; its absence — however it arose — renders a token instead, and a hand count is never substituted. Render `acceptance criteria count unavailable (unreadable item shape)` when the invocation reported `acceptance_criteria_unreadable`, and `acceptance criteria count unavailable` on every other absence. A `state-owner unavailable` fallback entered *after* the run bootstrap's canonical write still carries the parsed array and renders the number normally; only one entered *before* it never reached the gate site. Never count the checkbox rows by eye.

Exhausted Acceptance Criteria rewrite election. This route has two inputs from Step 3.5: three consecutive genuinely-empty rewrites, or a third unreadable-item-shape repair whose re-run remains unreadable. On either input, disclose that implementing runs will not read the drafted criteria, and render the matching unavailable token above. An exhausted Acceptance Criteria rewrite requires an explicit file-anyway election before the ordinary approval gate can authorize creation. That election is sub-step 3b's single file-anyway election, carrying exhaustion as one of its named grounds rather than a second question of its own.

The count is as of the bytes that gate invocation read; later revisions are not re-counted. The gate is single-site by design, so a draft that changes across audit rounds or a Step 4 overwrite still renders the first landed canonical draft's count. Carry that residual — `<n> acceptance criteria (as of the first landed canonical draft; later revisions not re-counted)` — whenever any revision landed after that invocation.

#### Criterion-disposition confirmation (report-only, every run)

Before approval is asked, confirm the omit/merge/add disposition record (`references/issue-template.md`'s Acceptance Criteria contract) against the criteria the draft actually carries. Drive the check from the criteria set the rendered draft carries, not a fixed slice of the artifact, so every criterion the draft carries is checked however long the run; for each, look for its disposition line in the `## Criterion disposition record` section of `.prflow/tmp/issue-derivation-<slug>.md`. Name, as a skill-composed disclosure beside the criterion-count marker below, any added criterion the draft carries whose disposition line the record does not show, marking it **undischarged** — a disposition line the read does not reach is reported undischarged, never silently passed — and when the record cannot be read at all — unreadable, absent, or, on the read-only arm, only an inline stand-in block posted per `references/fallback-read-only-sandbox.md` — read that inline block where one exists, else report the record **unestablished** rather than clean; render nothing when every added criterion the draft carries shows a disposition line. This confirmation sits on the presentation path because a run can add a criterion where a Step 3.6-sited reader would miss it: a run that elects no audit round never enters Step 3.6, and a criterion added while an audit round is adjudicated is added after that step's entry gate has run — the presentation write is the step both those cases still pass through. Naming is all it does — it blocks neither presentation nor creation, and it re-runs on every re-presentation (a sub-step 4 revision returns here).

#### Rendering the line and the draft-path note

Render them as one line (e.g. *"Fresh-context audit: 2 findings, 1 revision applied, VERDICT: FILE, 2 rounds (no consumer audit dimensions), 14 acceptance criteria; bundle: 5 axes evidenced, 2 N/A, 0 unestablished; adjudication: 1 must-revise, 1 advisory, 0 invalid, 1 unresolved at close, 0 effective; body's final bytes audited; converged via self-verified resolution."*), carrying each flag the query reports: the word "degraded" when it reports degraded, the phrase `user declined further audit` when it reports a decline, the ceiling when it reports the cap, and the embed marker when it names one. On the `state-owner unavailable` fallback — where the query itself is what failed — the line carries that marker instead and is composed in-chat; it still renders.

Display the absolute path built from the bound root (`<bound-root>/.prflow/tmp/issue-draft-<slug>.md`, `<bound-root>` read back from `query-draft-binding`'s `bound=` field), never `$MAIN_ROOT` from context recall and never a bare relative `.prflow/tmp/…` string. Keep the note separate from the preview — e.g. after the rendered body, a line such as *"Draft also saved to `<bound-root>/.prflow/tmp/issue-draft-<slug>.md` for review."* — after which sub-steps 3a–3c resolve the pre-approval gates and ask for approval. If the sub-step 2 write failed, omit the note entirely rather than showing a path to a nonexistent file.

`bound=none` arm (no `reason=`): for a legitimately unbound run there is no bound root to display; never substitute the token into the path. Omit the draft-path note entirely, exactly as the write-failure arm does. `reason=foreign-nonce` is a distinct arm, never this one: the run *is* bound and only the nonce drifted, so take the foreign-nonce arm of `references/fallback-draft-write-recovery.md`, loaded per `references/degradation-routing.md` — recover the nonce and re-query, else stop and tell the user the drift.

Display the investigation record alongside the brief — on EVERY arm, including the withheld one. After the rendered body and the audit summary line, render the investigation-record bucket (the content `references/issue-template.md`'s routing rule sorted out of the brief) as its own clearly-labeled inline block in chat. It renders even when `create_issue.investigation_record_enabled` is `false`. This is display, not attestation: `emit-body`'s digest covers only the bound draft file. When the bucket is empty, say so plainly rather than rendering an empty block.

Scope the summary line's final-byte phrase to the body, and report the record's unaudited status beside it. State the body scope (e.g. *"body's final bytes audited"*) and, beside it, that the investigation record is not audited.

3a. Read every gate that decides an offer, then make at most ONE audit-round offer. Every read that *decides* something happens here, with the draft already on screen and before any approval question; sub-step 3's `query-final-byte` call is the one earlier read, made to render a line rather than to decide, and this sub-step re-reads it for its own decision. Read `query-eligibility --mode approve`, `query-final-byte "<slug>" --nonce "<nonce>" --draft-file "<absolute issue-draft-<slug>.md path>"` (its one decided line `final_byte_trigger= final_byte_coverage= final_byte_reason= final_byte_passes= final_byte_exhausted=`), and the `query-boundary` answer Step 3.6 already carried here.

   One offer, stated precedence. A pause offers exactly one more audit round, whichever grounds hold, naming the ground in the question. When several hold, the first of these that applies is the one offered, and the others are disclosed in the same message rather than re-asked:

   - final-byte (`final_byte_trigger=hold`) — funded from its own dedicated slot outside the user-round cap, so it is offerable at the cap and under a `cap-reached` override. Record with `record-final-byte-offer "<slug>" --nonce "<nonce>" --draft-file "<…>"`, `--accepted` on "yes"; never as a `user-decline` override. Both arms spend the slot for these exact bytes; a recorded revision that changes the canonical digest re-arms it, bounded by the per-run cap. This ground subsumes the steering ground below. On a run that completed no audit round the final-byte coverage is `unestablished`, on which this trigger never holds, so such a run is offered no final-byte pass and this pause names no final-byte ground on it.
   - steering (`query-eligibility` answers `reason=steering-unestablished`) — an unsteered re-dispatch, offered here only when the final-byte ground did not fire; it spends the boundary slot through `record-offer`.
   - boundary grounds (`t1=`, `t2=`, `coverage=`, `calibration=` at `hold`, or an `unledgered_revise` round) — conducted exactly as `references/fallback-audit-boundary-offer.md` states, recorded with `record-offer` / `record-override --kind user-decline --surface t1t2-boundary`.
   - post-revision (this pause follows a sub-step 4 revision) — recorded on decline with `record-override --kind user-decline --surface step4-offer` (`--draft-file`-bound on a file-arm epoch), which is what lets `query-eligibility --mode approve` answer `eligible=yes` for still-unaudited bytes.
   - discovery election (the lowest-precedence ground, the one that holds on a run that has elected no audit round yet, while the user-round cap is unspent) — this is the offer that makes every fresh-context audit round user-elected: offer one fresh whole-draft audit round before it opens, recorded through `record-offer` (`--accepted` on "yes"), which is what funds the first round — the state owner opens no round the user did not elect. On decline record `record-override --kind user-decline --surface step4-offer` (`--draft-file`-bound on a file-arm epoch) and file unaudited; a user satisfied with what they read pays no audit rounds. On a non-interactive run, self-answer this offer as a decline, recording the same `user-decline` override, and proceed unaudited.

   Fold a foreseeable file-anyway election into these options — never ask it as a second pause. When the `query-eligibility --mode approve` read above answers `not-eligible`, that refusal is known before this question is asked, so offer three options: run the offered round; file as-is, worded as the election itself — *"the gate refuses these bytes as `<the ground>`; choosing this files them anyway"*; or decline the round without filing, which pauses. The file-as-is option records the decline on its ground's channel and `record-override --kind user-decline --surface step4-approval-after-exhausted-offer`, then re-queries. Never label a decline option as filing unless it carries that election.

   On "yes" first load the dispatch and adjudication members (parts 2 and 3 of the Step 3.6 set, held as a pair per `references/step-3-6-audit.md`) — a run that reaches this pause having elected nothing has not read them, and conducting a round requires their procedure — then run the round through the ordinary machinery — the pre-dispatch canonical-draft write, the generated dispatch instructions, `query-arm` → `record-dispatch` → dispatch → `record-return`, then the return handling sub-step 4 states — and return to 3a on the re-presented bytes. On "no" record the decline on that ground's channel and continue to 3b — except under the three-option shape above, where the two nos are different answers: *file as-is* carries the election and continues to 3b, while *decline the round without filing* records the same decline and then pauses, exactly as that option is worded. A silent non-response pauses and re-asks in the final chat message, per Step 2's silent-non-response rule; never dispatch and never proceed on silence. A run where no ground holds asks nothing here and goes straight to 3b.

   Return-handling carve-out for an accepted final-byte pass. On `VERDICT: REVISE` its findings are adjudicated with a ledger like any round's and disclosed at 3c's approval question; the run then files on the user's explicit election. It does not trigger a mandatory revise-and-re-present cycle. On a verdict-less return the existing no-verdict machinery governs the round unchanged and the slot is refunded. Dispatch it with the generated instruction file exactly as any round, passing `--instructions-file`/`--instructions-draft-path` and quoting the auditor's `--instructions-object-id`/`--extra-dispatch-content` back on the return.

3b. Then make at most ONE file-anyway election, on the grounds 3a could not foresee. Once 3a's offer is resolved, a gate may still refuse the bytes. Every such refusal is put to the user as one election — *"file these bytes anyway?"* — naming each ground that fired, rather than one election per gate. A ground already folded into 3a's options and elected there is resolved and is never re-asked here:

   - Exhausted Acceptance Criteria rewrite (either exhaustion input above): disclose that implementing runs will not read the drafted criteria, and render the matching count-unavailable token.
   - `query-eligibility --mode approve` answers `not-eligible` because the bytes carry an unresolved `VERDICT: REVISE`/`no-verdict`, or `reason=steering-unestablished` — the verdict may be a clean `VERDICT: FILE` whose audit independence could not be established. This ground is reachable only once 3a's offer surface has been exhausted for it. On an explicit election, record it with `record-override --kind user-decline --surface step4-approval-after-exhausted-offer` (`--draft-file`-bound on a file-arm epoch) and re-query. Never narrow this to "unresolved REVISE only".

   An explicit yes permits the run to reach the approval gate and is not itself approval; an explicit no or silence pauses without creating and without soliciting approval. Filing is never blocked on any arm. A run with no ground firing asks nothing here.

3c. Then ask for approval and assignment together — one pause, two answers. Ask *"Want me to create it as-is, or change anything first?"* and *"Assign this issue to you?"* in the same question. A draft-only request never reaches this path.

   - Approval is explicit and about *this* rendered draft ("yes", "create it", "looks good, file it"). Any requested change routes to sub-step 4 instead, and the assignment answer is re-asked with the re-presented draft.
   - Assignment — an explicit yes (`yes`, `assign it to me`) makes `<assignee-args>` the single token pair `--assignee "@me"`; an explicit no (`no`, `leave it unassigned`) makes it empty. Silence or any non-yes/non-no reply — a question-tool timeout, a `No response` return, or any answer that is neither a clear yes nor a clear no — pauses creation and re-asks the assignment question in your final chat message, exactly as Step 2's silent-non-response rule governs a clarification question. Do not guess a default: no `gh issue create` runs until the user gives an explicit yes or no, however clear the approval was.

   Ask this only on bytes `query-eligibility --mode approve` answers `eligible=yes` for, re-querying after any 3b election. Approval and eligibility are two different gates and creation needs both.

4. **Iterate on feedback.** If the user requests any change, revise the draft, re-run the no-options gate (Step 3), then run **Revision-delta verification**, then **run Step 3.5 again against the complete post-verification draft before overwriting or offering approval**. Step 3.5 is deliberately last among the draft-mutating checks: it reruns the Desired-Behavior projection and replaces the structured Steelman projection state for the bytes that reach the overwrite; a newly added Desired Behavior obligation with no representing AC prevents the overwrite/approval path. Overwrite the canonical draft through the *Staged canonical-draft write* shared procedure in `references/step-3-6-audit-shared.md`, which names this site as one of its three: a revision write records the revision from the staged bytes, so `record-revision` takes `--stdin-digest` piped through the helper's `emit` mode there, and the state owner requires it whenever the latest recorded round dispatched on the file arm. Then run **Ledger maintenance after a revision** — record the revision with `record-revision --after-round <round>` in that staged form; when the per-finding verification confirmed at least one finding fixed, `record-resolution` naming those ids against the printed revision ordinal (cross-round when the fix clears an earlier round's entries), and when it confirmed none, record no resolution. A later-discovered regression uses `record-reopen`; a finding discovered misclassified uses `record-invalidate`, never `record-resolution`. Decide each against the `query-findings` read-back, never context recall. Ledger maintenance records state only; it must not edit the draft between this final projection and the overwrite.

   Overwrite the same `<bound-root>/.prflow/tmp/issue-draft-<slug>.md` file — the identical absolute path from the recorded binding, read back via `query-draft-binding`, never re-resolved — keeping the original filename even if the title changes. This overwrite is a revision write, so it runs the full Staged canonical-draft write shared procedure (`references/step-3-6-audit-shared.md`) including step 2's `record-revision --stdin-digest` from the staged bytes and step 4's write-failure recovery; a verified multi-finding revision wave applies as exactly one `apply` and one `record-revision`. Branch the read-back as sub-step 2 does, under the later-write-site rule above, and omit the draft-path note when re-presenting per sub-step 3's `bound=none` arm. Each revision is re-presented in full — never apply edits and create in the same turn without showing the updated draft.

   Re-present, then re-enter 3a — never ask for approval straight off a revision.    - Resolve the gate. Read `create_issue.investigation_record_enabled` (default `true`) through the bundled resolver as the command's **leading token**:
