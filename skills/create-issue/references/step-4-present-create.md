### Step 4: Review with the user, then create

Sub-steps: 1 present the draft (saved-file path by default; body in chat on request) · 2 write the draft file · 3 render the audit summary line and disclosures · 3a the combined decision question · 4 iterate on feedback · 5 create (5a label, 5b dependencies, 5c investigation record) · 6 the single post-creation pause (assignment + gated implement offer).

Every pre-creation question this step asks is 3a's one combined decision question — one question per presentation, re-asked whole only where 3a says so. Nothing is asked before the draft has been presented (its saved-file path at sub-step 3, or the body on a forced-render arm), and nothing that gates creation is asked after `record-creation-epoch` binds it; sub-step 6's post-creation pause gates nothing.

**The issue is never created until the user has seen the draft as presented — its saved-file path, or the body printed on request — and explicitly approved it.** This gate is **unconditional** — no matter how thoroughly Step 2 resolved every decision, and no matter what the user said earlier. A rough user story is not approval of the assembled ticket.

**Presentation gate (before the draft is shown).** Clear its pre-show checks per `references/fallback-step4-gate-discipline.md` (`references/degradation-routing.md`).

**The provenance signature is already in the body — do not append it again here.** The run bootstrap (`references/step-3-6-audit-shared.md`) appended the shared `/prflow:create-issue` provenance line as the body's last line before its first canonical draft write, so it is already inside the bytes shown and written here and posted as the created issue. On a sub-step 4 revision, keep it as the body's last line — re-appending it only if the regenerated body no longer carries it — so exactly one copy survives every re-presentation.

1. **Present the draft — saved-file path by default, body in chat only on request.** The saved draft file (sub-step 2) is the default presentation and its path is shown at sub-step 3; the full body is printed in chat only when the user chooses *print the full draft in chat* at 3a, or on a forced-render arm — a write-failed run, a `bound=none` run, or a non-interactive run — each of which prints the body before 3a's question and offers no print answer. **When you do print it** (on request or on a forced-render arm), show the complete rendered issue in chat: post the exact title and the full body — every section, verbatim, as Markdown — directly in your message. Do not summarize, abridge, or describe it. Do not use the runner's user-question tool (`AskUserQuestion` or its equivalent) to stand in for showing the body — such tools truncate.
2. Also write the draft to a file for easy review — at the MAIN repo root. Reuse the run's kebab-case `<slug>`: Step 1 binds it, and this is the only site that derives one instead. Read it from turn-one context, else from the pointer `.prflow/tmp/create-issue/issue-run-slug` Step 1 wrote, judging that pointer **unestablished** on the grounds the skill root's Step 1 states. Only then derive one from the issue title here (e.g. "Add CSV export for survey results" → `add-csv-export-for-survey-results`).

   Resolve the main working-tree root with the bundled `resolve-main-root.sh` (same portable anchor recipe as above), then create its `.prflow/tmp` and write there:
   ```bash
   MAIN_ROOT="$("${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/resolve-main-root.sh)"
   mkdir -p "$MAIN_ROOT/.prflow/tmp/create-issue/<slug>"
   ```
   Capturing the resolver's output into `MAIN_ROOT` is fine — both statements sit in this one fence. Step 3.6's binding fence re-resolves inline instead because it is a separate fence, where this variable expands empty.

   Write the rendered title + body to the absolute path `$MAIN_ROOT/.prflow/tmp/create-issue/<slug>/issue-draft-<slug>.md`, with the title as a top `# ` heading. Perform this write through the *Staged canonical-draft write* shared procedure in `references/step-3-6-audit-shared.md` — load that file per the *Reference routing* rules when this entry does not already hold it; on a failed load, stage nothing, write the bytes straight to the canonical path, report the unstaged write in chat, and report `--write-landed no` to `query-arm`. The procedure records no revision, so it runs the stage → apply → verify steps, and its landed re-check compares the canonical file against this write's own in-turn `--expect-digest`. Use the main root, not the cwd.

   Bind the draft root once, then reuse it — bind if not already bound. The binding is recorded by the first landed canonical-draft write of the run, normally Step 3.6's pre-dispatch write. Do not assume what that site did — detect the case here: read `query-draft-binding "<slug>" --nonce "<nonce>"` and branch as Step 3.6's binding procedure specifies — already-bound (skip, take the `bound=` root); `bound=none` with no `reason=` (run Step 3.6's `record-draft-binding … --tier main-root` fence here; it is query-first and idempotent, so `binding-already-recorded` is the benign expected outcome); `reason=foreign-nonce` (the foreign-nonce arm of `references/fallback-draft-write-recovery.md`, loaded per `references/degradation-routing.md` — surface the drift, never the quiet unbound arm, and never compose a path); and a query that returns no answer at all (state owner unavailable, or the invocation refused) — attempt no bind, and treat the run as legitimately unbound. An unbound run is legal and must stay safe: `none` is a decided token, not a path, so never compose a path from it — fall back to the `MAIN_ROOT=` root for this write and follow the `bound=none` display arm in sub-step 3.

   Every later write site (a Step 3.6 re-dispatch write, the sub-step 4 overwrite, and the sub-step 5c record write) runs in a later turn, so it takes the bound root from `query-draft-binding "<slug>" --nonce "<nonce>"`'s `bound=` field — never context recall, never a second `resolve-main-root.sh` resolution while a binding exists; `<bound-root>` in the sub-step 3 display note is that same root. The presentation write above is the exception: same turn, root already in hand. **When the binding read reported a bare `bound=none` (no `reason=`), the run is legitimately unbound: re-resolve the main root for *this* turn with the sub-step 2 `resolve-main-root.sh` recipe and write under that root** — never compose a relative `none/…` path from the token, and never reach for a `MAIN_ROOT` bound in an earlier turn. Take the `bound=none` display arm in sub-step 3 alongside it. On the file arm, forward the exact absolute canonical path to `record-dispatch --write-path <that path>`, which the state owner refuses with `write-path-mismatch` on divergence.

   Keep this one `<slug>` throughout, reusing that exact absolute path from then on. This saved file is the default presentation — its path is shown at sub-step 3, and the body is printed in chat only on request (sub-step 1). On an embed/inline-arm epoch it is not the source the issue is created from; on a file-arm epoch this canonical file *is* the posting source — but only through the gated `emit-body` emitter (sub-step 5), never by passing the path to `--body-file <path>` directly. If the write fails (read-only main root / sandbox), note it briefly, print the full body in chat (the forced-render arm, sub-step 1), and continue without showing a path.

3. Render the audit summary line and disclosures — ask nothing here. Every pre-creation question belongs to 3a's combined decision question, the confirm/edit one included. **The first Step 4 message renders the one-line Step 3.6 audit summary, then (when recorded) the per-finding disclosure block, then the investigation record, then the draft-save-location note (the absolute `<bound-root>/.prflow/tmp/create-issue/<slug>/issue-draft-<slug>.md` path from sub-step 2) — and does not contain the draft body**, so every confirmation message has the same layout: the audit summary line, then (when recorded) the per-finding disclosure block, then the investigation record, then the draft-path note, and only then 3a's combined question. On a forced-render arm (sub-step 1) the full rendered body is printed above that layout, since there is no saved-file path to read instead.

   Render the per-finding disclosure, rare summary markers, and criterion-disposition confirmation per `references/fallback-step4-summary-rendering.md` (`references/degradation-routing.md`).

   The summary line is one of the root's non-degradable invariants: it renders on every arm and every round count. Do not assemble its fields from recollection. The last state-owner call this sub-step makes — `query-final-byte` below — prints a `summary-block` line carrying the compact fixed `query-summary` subset the line renders: findings count, revisions applied, verdict, rounds run, whether a consumer `## Audit dimensions` section was appended, `degraded`/`user_declined`/`cap_reached`, any embed markers, `adjudicated_verdict` with the per-actionability-class counts (`must_revise`/`advisory`/`invalid`), `unresolved_must_revise`, `effective_unresolved`, `convergence_basis`, the `steering`/`steering_reason` pair, and the trailing `attestation=<match|mismatch|attestation-unavailable|none>` (`none` = before any creation attempt). The block also carries the structural `state` and `scoped_round` fields the summary line does not render — the tool's `--help` enumerates the block's full field set. Read the line's fields from that block rather than a standalone `query-summary` — its recovery instrument, should the block be lost to a context compaction (`query-summary "<slug>" --nonce "<nonce>" --draft-file "<…>"`).

`query-final-byte` also prints the final-byte fields the line names — `final_byte_reason` among them, which the summary block does not carry — so it is both the source of that block and the one gate read this sub-step makes, ahead of sub-step 3a's:

```bash
python3 "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/issue-audit-state.py query-final-byte "<slug>" --nonce "<nonce>" --draft-file "<absolute issue-draft-<slug>.md path>"
```

3a re-reads it there for its own offer decision.

#### Markers the summary line must carry

Steering. When `steering` is anything but `established`, the line carries a dedicated skill-composed marker naming it — `audit independence unestablished (<steering_reason>)` — rendered alongside whatever other skill-composed markers this line carries and distinct from the reserved `degraded` token. It never blocks filing. An `established` round is never described as provably steering-free.

The rare markers are in `references/fallback-step4-summary-rendering.md`.

For an exhausted Acceptance Criteria rewrite disclosure, see `references/fallback-step4-exhausted-ac-election.md` per `references/degradation-routing.md`.

The count is as of the bytes that gate invocation read; later revisions are not re-counted. The gate is single-site by design, so a draft that changes across audit rounds or a Step 4 overwrite still renders the first landed canonical draft's count. Carry that residual — `<n> acceptance criteria (as of the first landed canonical draft; later revisions not re-counted)` — whenever any revision landed after that invocation.

The criterion-disposition confirmation is in `references/fallback-step4-summary-rendering.md`.

#### Rendering the line and the draft-path note

Render them as one line (e.g. *"Fresh-context audit: 2 findings, 1 revision applied, VERDICT: FILE, 2 rounds (no consumer audit dimensions), 14 acceptance criteria; bundle: 5 axes evidenced, 2 N/A, 0 unestablished; adjudication: 1 must-revise, 1 advisory, 0 invalid, 1 unresolved at close, 0 effective; body's final bytes audited; converged via self-verified resolution."*), carrying each flag the query reports: the word "degraded" when it reports degraded, the phrase `user declined further audit` when it reports a decline, the ceiling when it reports the cap, and the embed marker when it names one. On the `state-owner unavailable` fallback — where the query itself is what failed — the line carries that marker instead and is composed in-chat; it still renders.

Display the absolute path built from the bound root (`<bound-root>/.prflow/tmp/create-issue/<slug>/issue-draft-<slug>.md`, `<bound-root>` read back from `query-draft-binding`'s `bound=` field), never `$MAIN_ROOT` from context recall and never a bare relative `.prflow/tmp/…` string. Render the note as its own line — e.g. *"Draft also saved to `<bound-root>/.prflow/tmp/create-issue/<slug>/issue-draft-<slug>.md` for review."* — after the audit summary and disclosures, after which sub-step 3a's combined decision question resolves the pre-approval gates and asks for approval. If the sub-step 2 write failed, omit the note entirely rather than showing a path to a nonexistent file (and print the full body per the forced-render arm, sub-step 1).

For a `bound=none` unbound run's draft-path note, see `references/fallback-step4-bound-none-display.md` per `references/degradation-routing.md`.

Display the investigation record alongside the brief — on EVERY arm, including the withheld one. After the audit summary line, render the investigation-record bucket (the content `references/issue-template.md`'s routing rule sorted out of the brief) as its own clearly-labeled inline block in chat. It renders even when `create_issue.investigation_record_enabled` is `false`. This is display, not attestation: `emit-body`'s digest covers only the bound draft file. When the bucket is empty, say so plainly rather than rendering an empty block.

Scope the summary line's final-byte phrase to the body, and report the record's unaudited status beside it. State the body scope (e.g. *"body's final bytes audited"*) and, beside it, that the investigation record is not audited.

3a. **Ask ONE combined decision question.** Read the gates first — `query-eligibility --mode approve`; `query-final-byte "<slug>" --nonce "<nonce>" --draft-file "<absolute issue-draft-<slug>.md path>"` (its one decided line `final_byte_trigger= final_byte_coverage= final_byte_reason= final_byte_passes= final_byte_exhausted=`); and the `query-boundary` answer Step 3.6 carried here — then ask one question through the runner's user-question tool (`AskUserQuestion` on Claude Code, or the equivalent your runner exposes, as in Step 2). Its options, in this order, each present only when its condition holds; labels are used verbatim, the audit option and *File anyway* completing their `<…>` slot:

   | Option | Present when | Choosing it |
   |---|---|---|
   | **Run a fresh-context audit round** (first round) / **Run one more fresh-context audit round — `<ground>`** | an offer ground below holds | record the acceptance on that ground's channel; load parts 2 and 3 of the Step 3.6 set (a run that elected nothing has not read them); run the round through the ordinary machinery — the pre-dispatch canonical-draft write, the generated dispatch instructions, `query-arm` → `record-dispatch` → dispatch → `record-return`, then sub-step 4's return handling — and re-present, where this question is asked again |
   | **Print the full draft in chat** | the draft file was written and its path shown at sub-step 3 | post the exact title and full body verbatim as Markdown (sub-step 1's render), then re-ask this question without this option. It elects nothing and records nothing; the saved bytes stay digest-bound to the file |
   | **Create it as-is** | no file-anyway ground below holds | this IS the explicit approval of these exact bytes, printed or not, because on a file-arm epoch they are digest-bound to the saved file. Record any offered round's decline on its ground's channel, then sub-step 5 |
   | **File anyway — `<ground>`** | a file-anyway ground holds, read from the summary block: `effective_unresolved` above zero (unresolved must-revise findings); `steering` not `established` on a completed round (a clean `VERDICT: FILE` counts); or an exhausted Acceptance Criteria rewrite (either exhaustion input above — disclose that implementing runs will not read the drafted criteria). Name every ground that holds | the explicit file-anyway election: record any offered round's decline on its channel plus `record-override --kind user-decline --surface step4-approval-after-exhausted-offer` (`--draft-file`-bound on a file-arm epoch), then sub-step 5 |
   | **Change something first** | always | sub-step 4 |

   Exactly one of *Create it as-is* / *File anyway* is present, so filing is never blocked on any arm. Neither is keyed on `query-eligibility`: a run that completed no round answers `no-verdict-round` until the offered round's decline is recorded (the override ground), and sub-step 5 re-queries after that record. A draft-only request never reaches this path.

   **Offer grounds, in precedence order, each with its channel.** Offer at most one round per question: the first ground that holds names the option; the others that hold are disclosed in the question text, not re-asked.
   1. Final-byte (`final_byte_trigger=hold`) — accept and decline both go through `record-final-byte-offer "<slug>" --nonce "<nonce>" --draft-file "<…>"`, `--accepted` on accept; never a `user-decline` override. Both arms spend the dedicated slot (outside the user-round cap, so offerable at the cap and under `cap-reached`) for these exact bytes; a recorded revision that changes the digest re-arms it, bounded by the per-run cap. A run that completed no round has coverage `unestablished`, on which this ground never holds.
   2. Steering (`query-eligibility` answers `reason=steering-unestablished`) — an unsteered re-dispatch: `record-offer` (`--accepted` on accept); decline `record-override --kind user-decline --surface t1t2-boundary`.
   3. Boundary (`query-boundary` reports `t1=`, `t2=`, `coverage=` or `calibration=` at `hold`, or an `unledgered_revise` round) — conducted as `references/fallback-audit-boundary-offer.md` states, on the same channels as 2.
   4. Post-revision (this presentation follows a sub-step 4 revision) — `record-offer` (`--accepted` on accept); decline `record-override --kind user-decline --surface step4-offer` (`--draft-file`-bound on a file-arm epoch), which is what lets `query-eligibility --mode approve` answer `eligible=yes` for still-unaudited bytes.
   5. Discovery (no round elected yet, user-round cap unspent) — the same channels as 4. This is what funds the first round: the state owner opens no round the user did not elect, and a user satisfied with what they read pays no audit rounds.

   **The question text tells the user how the audit stands, so the election is informed.** Read it from sub-step 3's `summary-block`, never recollection. Before the first round: that the draft is unaudited. After a completed round: the last round's verdict, its findings by class (`must_revise`/`advisory`/`invalid`), the unresolved must-revise count, and the revisions applied since — plus, on grounds 1–2, one sentence saying why another round is offered (the current bytes were never audited; the last round's steering was not established).

   **A reply outside the options** is routed by what it asks for: a change request → *Change something first*; an unambiguous approval of the draft as shown → *Create it as-is*, or *File anyway* when that is the option present and the reply names the refusal; a decline of the offered round with nothing else → record the decline on its channel and re-ask. Anything else, and a silent non-response, is not an answer: re-ask this question in the final chat message and stop (Step 2's silent-non-response rule) — never dispatch, create, or proceed on silence.

   **A non-interactive run self-answers this question:** it declines any offered round on that ground's decline channel, then elects *Create it as-is* when eligibility answered `eligible=yes`; when the gate refuses, it stops paused and reports the refusal ground, since only a user can elect *File anyway*.

   For an accepted final-byte pass return, see `references/fallback-step4-final-byte-carveout.md` per `references/degradation-routing.md`.

4. **Iterate on feedback.** If the user requests any change, revise the draft, re-run the no-options gate (Step 3), then run **Revision-delta verification**, then **run Step 3.5 again against the complete post-verification draft before overwriting or offering approval**. Step 3.5 is deliberately last among the draft-mutating checks: it reruns the Desired-Behavior projection and replaces the structured Steelman projection state for the bytes that reach the overwrite; a newly added Desired Behavior obligation with no representing AC prevents the overwrite/approval path. Overwrite the canonical draft through the *Staged canonical-draft write* shared procedure in `references/step-3-6-audit-shared.md`, which names this site as one of its three: a revision write records the revision from the staged bytes, so `record-revision` takes `--stdin-digest` piped through the helper's `emit` mode there, and the state owner requires it whenever the latest recorded round dispatched on the file arm. Then run **Ledger maintenance after a revision** — record the revision with `record-revision --after-round <round>` in that staged form; when the per-finding verification confirmed at least one finding fixed, `record-resolution` naming those ids against the printed revision ordinal (cross-round when the fix clears an earlier round's entries), and when it confirmed none, record no resolution. A later-discovered regression uses `record-reopen`; a finding discovered misclassified uses `record-invalidate`, never `record-resolution`. Decide each against the `query-findings` read-back, never context recall. Ledger maintenance records state only; it must not edit the draft between this final projection and the overwrite.

   Overwrite the same `<bound-root>/.prflow/tmp/create-issue/<slug>/issue-draft-<slug>.md` file — the identical absolute path from the recorded binding, read back via `query-draft-binding`, never re-resolved — keeping the original filename even if the title changes. This overwrite is a revision write, so it runs the full Staged canonical-draft write shared procedure (`references/step-3-6-audit-shared.md`) including step 2's `record-revision --stdin-digest` from the staged bytes and step 4's write-failure recovery; a verified multi-finding revision wave applies as exactly one `apply` and one `record-revision`. Branch the read-back as sub-step 2 does, under the later-write-site rule above, and omit the draft-path note when re-presenting per sub-step 3's `bound=none` arm. Each revision is re-presented — never apply edits and create in the same turn without re-presenting the updated draft (its draft-path note, and the body on request per 3a's print answer).

   Re-present, then re-ask 3a's question — never treat a revision as approval. A just-revised draft is shown under `query-eligibility --mode iterate` (`iterate=ok ordinal=N`), which authorizes the re-show only. Re-present (the draft-path note; the body only when *Print the full draft in chat* is chosen again), then ask 3a's question on those bytes, where the post-revision ground is an offer ground. Repeat until the user elects *Create it as-is* or *File anyway*.

   For a re-audit on user feedback, see `references/fallback-step4-dispatched-reaudit.md` per `references/degradation-routing.md`.
5. **Create only on explicit approval.** **Creation-time confirmation re-check (path-agnostic — the last of the re-read anchors `references/fallback-no-task-tool.md` enumerates; it runs on every path, tool or fallback, whether or not that reference was ever loaded).** Immediately before running `gh issue create`, re-confirm two things in the current conversation: the user has explicitly approved the rendered draft, and the active tracking mechanism shows item 6 in progress — read it from the task tool (its read-back call, or the conversation record of the last status update where the tool exposes no read-back), or from the checklist state file on the inline-checklist fallback path. On that fallback an absent or unreadable state file is a pipeline-paused signal, not a clear-to-create one: rebuild and rewrite it, and create only on explicit in-conversation approval, never on the guard's silence.

   Complete the post-election creation, posting, and attestation per `references/fallback-step4-attestation.md` (`references/degradation-routing.md`).
5a. Stamp the reserved `PRFlow` provenance label (best-effort). After a successful `gh issue create`, ensure the reserved label exists and apply it to the new issue. `PRFlow` is a hardcoded provenance constant no config key controls (its superseded `DevFlow` spelling stays selectable on already-labelled history; new issues are stamped only `PRFlow`). Apply it *after* creation:
   ```bash
   "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/ensure-label.sh PRFlow
   "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/apply-labels.sh <issue_number> PRFlow
   ```
   Both steps are best-effort and need only the `repo` scope: `ensure-label.sh` and `apply-labels.sh` each always exit 0, logging the label and apply outcomes. Application goes through `apply-labels.sh`'s REST `POST .../issues/{n}/labels`, never `gh issue edit --add-label`. The always-exit-0 contract applies only once a helper actually runs: an invocation that fails because the helper path does not exist (`No such file`, exit 127, or the platform equivalent) is the anchor-resolution failure noted at the top of this skill, not a benign label outcome — fix the anchor and re-run both commands. If the anchor cannot be resolved on this runner at all, report the degradation explicitly in the final outcome — issue created, `PRFlow` provenance label NOT applied. Continue to sub-step 5b regardless of the label outcome.
5b. Register declared prerequisites as GitHub-native blocked-by dependencies (best-effort). After a successful `gh issue create`, register each prerequisite the drafted body declares inside its `## Dependencies` section as a GitHub-native blocked-by dependency on the created issue. `scripts/apply-issue-dependencies.py` mirrors the label-stamp contract: it fetches the created issue's body itself, derives the prerequisites through the same section-scoped recognizer factored out of `scripts/preflight.py` (only the reserved section registers), always exits 0, and leaves a specific `apply-issue-dependencies.py:`-prefixed stderr breadcrumb on every path it can reach. Invoke it as the command's **leading token** with just the created issue's number:
   ```bash
   "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/apply-issue-dependencies.py <issue_number>
   ```
   Read the helper's stderr from the tool result and route on it — the same four-outcome routing `skills/implement/references/deferred-ac-followups.md` states for the same `apply-issue-dependencies.py` dependency registration. A `apply-issue-dependencies.py: linked …` / `… already blocked_by …` / `… declares no prerequisites …` / `… skipped #<n>: … reads as an OUTBOUND relation …` / `… done for #<n>: …` line is a successful registration outcome (the `skipped …` line names a prerequisite dropped because its `## Dependencies` line declares this issue as the prerequisite rather than a blocker — restate it as `blocked by #<n>` on its own line if it must land first). A `… could not link … (API refused …)` or `… every declared prerequisite's registration was refused …` line is an API failure. A `… missing or non-numeric issue-number argument …` line is a caller arg-slip — re-emit the call once with the captured number. No output at all means the harness refused the command, not that nothing needed doing. Name any number the helper could not resolve or link in the run's final outcome, exactly as 5a names an unapplied `PRFlow` label; the remaining numbers are still linked. If the anchor cannot be resolved at all, report the degradation (issue created, prerequisites NOT registered). Continue to sub-step 6 regardless of the outcome.
5c. Publish the investigation record as the first comment (gated, best-effort, before the implement offer). The draft was composed into two buckets by `references/issue-template.md`'s Brief / investigation-record routing rule — the brief (the created issue body) and the investigation record. Publish that record bucket as the issue's first comment, *after* creation (5) and *before* the implement-offer comment (6). Sorting always ran; publication is what this gate controls. Before the record-bucket empty-check below, fold in any passed-over-candidate trace line by reading it back from its durable store: read the run's cwd/worktree-anchored `.prflow/tmp/create-issue/<slug>/issue-derivation-<slug>.md` derivation artifact — where the line was parked at the implementation-approach ask precisely so a later-compacted run recovers it (see `references/step-2-clarify.md`) — and if it holds a `Considered-and-rejected: <n> heavier candidate(s) — <one clause>` line, append that line to this record bucket, so the empty/non-empty determination below is made on the post-fold bucket. That line rides the derivation artifact, not the brief, so the routing rule never sorts it in on its own, yet it belongs in the record and never the issue body. A readable artifact carrying no such line is simply no line; an unreadable artifact, or a read-only sandbox that wrote none, is unestablished — publish the record without the line and name that unestablished fold in the run's final reported outcome rather than dropping it silently.

   - Fold the run's decision record into the bucket, so the reasoning behind each criterion survives the closing cleanup (5d), which deletes the whole run directory. Extend the same derivation-artifact read the passed-over-candidate fold above already performs — do not add a second read — reading `.prflow/tmp/create-issue/<slug>/issue-derivation-<slug>.md` in bounded pieces, never whole, because a long run's artifact outgrows the runner's read cap. Copy exactly three blocks into the record bucket, each under its own clear heading: the `## Criterion disposition record`, the `## Steelman record`, and the `## Evidence bundle`. These are the blocks a later reader needs to check why a criterion exists. The raw derivation prose, the `## Revision-delta record`, and the run's verified-claims ledger are deliberately not folded — the closing cleanup (5d) deletes them and reports that it did. A block the artifact does not carry is simply absent from the fold; when the derivation artifact is unreadable or was never written to disk (the read-only sandbox), fold no block and record in the run's final reported outcome that no blocks were available to preserve. Folded content is neutralized against the workflow-trigger tokens exactly as the rest of the record body is, because it is written into the same file and passes through the same mechanical grep below before the comment is posted.

   - Resolve the gate. Read `create_issue.investigation_record_enabled` (default `true`) through the bundled resolver as the command's **leading token**:
     ```bash
     "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/config-get.sh .create_issue.investigation_record_enabled true
     ```

     Withhold publication when, and only when, the resolved value is exactly the literal `false` — compare with bash builtins only (`case "$V" in false) … ;; esac`, never `tr`/`sed` lowering). Apply exactly one result row: `devflow: posted comment on #<n>` means posted; `devflow: warning: could not post comment on #<n> …` means NOT posted and the final outcome names the failure; a warning containing `missing issue-number argument (caller argument slip` or `missing body-file argument (caller argument slip` means NOT posted, the final outcome names the caller slip, no API request was made, and the run continues to sub-step 6 without retrying or blocking issue creation; no output, multiple contradictory result breadcrumbs, or an unrecognized breadcrumb is a harness refusal, means NOT posted, and is named in the final outcome.
