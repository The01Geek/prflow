### Step 4: Review with the user, then create

Sub-steps: 1 show the draft · 2 write the draft file · 3 confirm, with the audit summary line · 4 iterate on feedback · 5 create (5a label, 5b dependencies, 5c investigation record) · 6 gated implement offer.

**The issue is never created until the user has seen the full rendered draft and explicitly approved it.** This gate is **unconditional** — no matter how thoroughly Step 2 resolved every decision, and no matter what the user said earlier. A rough user story is not approval of the assembled ticket.

**Presentation gate — consume the clean Steelman projection, then confirm *this run's* audit artifact exists before the draft is shown.** Re-read the latest Steelman pass and `.prflow/tmp/steelman-projection-<slug>.json`; require matching pass numbers, then run `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/run-jq.sh -e -f "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../lib/projection-gate.jq ".prflow/tmp/steelman-projection-<slug>.json"`. Missing, stale, wrong-typed, inconsistent, or unmatched state stops presentation and returns to Step 3.5's bounded revise/re-audit path. The read-only degraded arm is eligible only when its current-turn inline state is `represented` with an empty unmatched array. This check is repeated here because Step 4 owns the filing boundary; nonempty ACs or a clean Step 3.6 verdict never substitute for it. After it passes, confirm `.prflow/tmp/issue-audit-<slug>.md` is present **and holds this run's audit** (the Step 3.6 write deletes any same-slug leftover first). If any `.prflow/tmp/` write or delete was refused earlier in this run, the on-disk artifact can only be a stale leftover: distrust it and rely solely on the visible inline-in-chat audit block re-posted this turn, per `references/fallback-read-only-sandbox.md` — the run-state condition, not a local write failure, is what selects that fallback here. If neither this run's artifact nor its inline stand-in is present, Step 3.6 was skipped — **stop and run it now before presenting the draft.**

1. **Show the complete rendered issue in chat.** Post the exact title and the full body — every section, verbatim, as Markdown — directly in your message. Do not summarize, abridge, or describe it; the user reviews the literal text that would be filed. Do not use the runner's user-question tool (`AskUserQuestion` or its equivalent) to stand in for showing the body — such tools truncate. Render the body first, then use that tool for the confirm/edit prompt if you wish.
2. **Also write the draft to a file for easy review — at the MAIN repo root, so its displayed path is correct inside a worktree.** Reuse the run's kebab-case `<slug>`: **Step 1 bound it and no later step binds one**, so one issue keeps a single stem across every artifact. Read it from turn-one context, else from the pointer `.prflow/tmp/issue-run-slug` Step 1 wrote. Only when that pointer is **unestablished** — absent, unreadable, empty, whitespace-only, or not a single kebab-case slug on one line — derive one from the issue title here (e.g. "Add CSV export for survey results" → `add-csv-export-for-survey-results`). **Resolve the main working-tree root** with the bundled `resolve-main-root.sh` (same portable anchor recipe as above), then create its `.prflow/tmp` and write there:
   ```bash
   MAIN_ROOT="$("${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/resolve-main-root.sh)"
   mkdir -p "$MAIN_ROOT/.prflow/tmp"
   ```
   Capturing the resolver's **output** into `MAIN_ROOT` is fine — the *anchor* is still expanded inline in that single statement, per the never-capture-the-anchor rule above.

   Write the rendered title + body to the **absolute path** `$MAIN_ROOT/.prflow/tmp/issue-draft-<slug>.md`, with the title as a top `# ` heading — that path is gitignored. Perform this write through the **Staged canonical-draft write** shared procedure (`skills/create-issue/references/step-3-6-audit.md`): it records no revision, so it runs the stage → apply → verify steps, and its landed re-check compares the canonical file against this write's own in-turn `--expect-digest`. Use the **main** root, not the cwd: inside a linked Claude worktree the cwd-relative path resolves to a file the user's editor cannot open.

   **Bind the draft root once, then reuse it — bind if not already bound.** The binding is recorded by the **first landed canonical-draft write** of the run, normally Step 3.6's pre-dispatch write. **Do not assume what that site did — detect the case here:** read `query-draft-binding "<slug>" --nonce "<nonce>"` and branch as Step 3.6's binding procedure specifies — already-bound (skip, take the `bound=` root); `bound=none` with no `reason=` (run Step 3.6's `record-draft-binding … --tier main-root` fence here; it is query-first and idempotent, so `binding-already-recorded` is the benign expected outcome); `reason=foreign-nonce` (the **foreign-nonce arm** of `references/fallback-draft-write-recovery.md`, loaded per `references/degradation-routing.md` — surface the drift, never the quiet unbound arm, and never compose a path); and a query that returns **no answer at all** (state owner unavailable, or the invocation refused) — attempt **no** bind, since `record-draft-binding` cannot bind without a state file either, and treat the run as legitimately unbound. **An unbound run is legal and must stay safe:** `none` is a decided token, not a path, so **never compose a path from it** — fall back to the `MAIN_ROOT=` root for this write and follow the `bound=none` display arm in sub-step 3.

Every **later** write site (a Step 3.6 re-dispatch write, the sub-step 4 overwrite, and the sub-step 5c record write) runs in a later turn, after a possible compaction, so it takes the bound root from `query-draft-binding "<slug>" --nonce "<nonce>"`'s `bound=` field — never context recall, never a second `resolve-main-root.sh` resolution while a binding exists; `<bound-root>` in the sub-step 3 display note is that same root. The presentation write above is the exception: same turn, root already in hand. **When the binding read reported a bare `bound=none` (no `reason=`), the run is legitimately unbound: re-resolve the main root for *this* turn with the sub-step 2 `resolve-main-root.sh` recipe and write under that root** — never compose a relative `none/…` path from the token, and never reach for a `MAIN_ROOT` bound in an earlier turn. Take the `bound=none` display arm in sub-step 3 alongside it. On the **file arm**, forward the exact absolute canonical path to `record-dispatch --write-path <that path>`, which the state owner refuses with `write-path-mismatch` on divergence.

**Keep this one `<slug>` throughout, reusing that exact absolute path from then on** — so revisions overwrite the one file and a later draft gets its own. This is a **convenience copy** for the user's editor; it never replaces showing the body in chat. On an **embed/inline-arm epoch** it is **not** the source the issue is created from; on a **file-arm epoch** this canonical file *is* the posting source — but only **through the gated `emit-body` emitter** (sub-step 5), never by passing the path to `--body-file <path>` directly. If the write fails (read-only main root / sandbox), note it briefly and continue **without showing a path**.

3. **Ask for explicit confirmation or feedback.** Plainly invite the user to approve creation or request changes. **The draft-save-location note (the absolute `<bound-root>/.prflow/tmp/issue-draft-<slug>.md` path from sub-step 2) always renders *below* the rendered issue preview — never above it**, so every confirmation message has the same layout: the full rendered body first, then the **one-line Step 3.6 audit summary**, then (when recorded) the per-finding disclosure block, then the draft-path note, then the confirm/edit question.

   **Per-finding disclosure block.** When the run recorded advisory or invalid grades (`query-adjudication-records "<slug>" --nonce "<nonce>" --round "<round>"` returns records, not `records=none`), render each advisory and invalid finding's `summary`, `rationale`, `impact_class` tag, and the auditor's own `auditor_block` beside the grader's restatement, so the user sees the tag that decides whether the calibration layer fires. Then report that rendering with `record-adjudication-render "<slug>" --nonce "<nonce>" --round "<round>" --landed yes` — the tool cannot observe chat, so an unreported rendering surfaces as `adjudication_render=unreported` on `query-summary`/`query-calibration` and holds the calibration trigger. The **audit summary line's own class counts stay unchanged**.

   The summary line is one of the root's non-degradable invariants: it renders on every arm and every round count. **Do not assemble its fields from recollection — read them from `query-summary`:**

```bash
python3 "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/issue-audit-state.py query-summary "<slug>" --nonce "<nonce>" --draft-file "<absolute issue-draft-<slug>.md path>"
```

#### What `query-summary` reports

Findings count, revisions applied, verdict, rounds run, whether a consumer `## Audit dimensions` section was appended, the degraded flag, the user-declined and cap-reached flags, any embed-arm markers, the eligibility token, and `attestation=<match|mismatch|attestation-unavailable|none>` (`none` = before any creation attempt). Per latest completed round: `adjudicated_verdict`, the per-actionability-class counts (`must_revise`, `advisory`, `invalid`), `unresolved_must_revise`, and — rendered immediately before the trailing `attestation=` — the pair `steering=<established|not-established|unestablished>` and `steering_reason=<token|none>`. Run-wide, before `bound_root=`: `effective_unresolved`, `convergence_basis`, `final_byte_passes=`, `final_byte_exhausted=`, and `final_byte_coverage=<covered|uncovered|unestablished>` (whether the bytes that would be filed carry a verdict from a round dispatched against those exact bytes).

#### Markers the summary line must carry

**Steering.** **When `steering` is anything but `established`, the line carries a dedicated skill-composed marker naming it — `audit independence unestablished (<steering_reason>)` — rendered alongside the other skill-composed markers this line already carries (the state-owner-unavailable arm, the unreadable-template terminal arm, and the unestablished consumer-dimensions arm) and distinct from the reserved `degraded` token.** It means the run could not establish that the auditor's instructions were the canonically-generated ones; it never blocks filing. **An `established` round is never described as provably steering-free** — it proves the instruction *content* was canonical, nothing more.

**Coverage and adjudication counts.** **The line reports the bundle's coverage (`axes evidenced, axes marked N/A, axes unestablished`), the post-adjudication counts by actionability class, the unresolved must-revise findings attributable to an axis on the effective list as frozen at that round's close, and — distinctly, never collapsed onto it — the run-wide effective unresolved count after every post-close resolution, reopen, invalidation and supersession.** A round whose actionability or axis attribution could not be established renders `unestablished` rather than a number — unknown is not zero.

**Final-byte coverage.** **The line carries the final-byte coverage value on every dispatch arm and every round count — the degraded inline arm included** — as `final bytes audited` on `covered`, `final bytes NOT audited (<final_byte_reason>)` on `uncovered`, and `final-byte coverage unestablished (<final_byte_reason>)` on `unestablished`; when `final_byte_exhausted=yes`, append `— final-byte passes exhausted`. **Read `<final_byte_reason>` from the `query-final-byte` line sub-step 5 mandates, not from `query-summary`**, which prints no reason token. A recorded `attestation=match` never stands in for that phrase: it proves the posted bytes are the bytes, not that an auditor read them.

**Convergence basis.** **When `convergence_basis` names a resolution basis, the line additionally carries the phrase `converged via self-verified resolution`** — on the stale variant **`converged via self-verified resolution (stale — later revisions unverified)`** — so a convergence the drafter verified for itself is never rendered indistinguishably from one an auditor's `VERDICT: FILE` vouched for.

**Criterion count.** **The line also carries the criterion count as a skill-composed marker — `<n> acceptance criteria` — rendered alongside the other skill-composed markers this line already carries.** It is the **length of the `acceptance_criteria` array** returned by the `python3 … scripts/parse-acs.py --format json` invocation the run already performs at the Step 3.6 pre-dispatch canonical write; perform no second parse, and compose the marker in the skill rather than reading it from `query-summary`. It exists so the drafter and the approver see the size of the set while splitting is still cheap. **It is reported, never enforced:** it changes no verdict and blocks no filing.

**The number renders only when this run holds an established count; every other state renders a token, and a hand count is never substituted.** The trigger is the **absence of an established `acceptance_criteria` array from this run's own gate invocation** — stated as that absence, not as a list of failure modes, so an unenumerated arm still routes here. Render `acceptance criteria count unavailable` when the invocation could not run, when the bounded rewrite loop exhausted without producing a non-empty array, and **equally when the run never reached the gate site at all** (a `state-owner unavailable` fallback entered *before* the pre-dispatch canonical write; one entered *after* a completed round carries that round's array and renders the number normally). Render `acceptance criteria count unavailable (unreadable item shape)` when the invocation reported `acceptance_criteria_unreadable` — zero parsed items from a section that visibly carries criteria is not a count of zero. Never count the checkbox rows by eye.

**Exhausted Acceptance Criteria rewrite election.** This route has two inputs from Step 3.5: three consecutive genuinely-empty rewrites, or a third unreadable-item-shape repair whose re-run remains unreadable. On either input, disclose that implementing runs will not read the drafted criteria. Render `acceptance criteria count unavailable` for genuinely-empty exhaustion and `acceptance criteria count unavailable (unreadable item shape)` for unreadable-shape exhaustion. An exhausted Acceptance Criteria rewrite requires an explicit file-anyway election before the ordinary approval gate can authorize creation. Ask that election as a separate yes/no question before the ordinary confirm/edit question: an explicit yes permits the run to reach the ordinary approval gate but is not itself approval; an explicit no or silence pauses without creating or soliciting ordinary approval. This narrow election preserves best-effort filing while preventing either exhausted rewrite path from being treated as a clean parse.

**The count is as of the bytes that gate invocation read; later revisions are not re-counted.** The gate is single-site by design, so a draft that changes across audit rounds or a Step 4 overwrite still renders the first landed canonical draft's count. Carry that residual — `<n> acceptance criteria (as of the audited draft; later revisions not re-counted)` — whenever any revision landed after that invocation.

#### Rendering the line and the draft-path note

Render them as one line (e.g. *"Fresh-context audit: 2 findings, 1 revision applied, VERDICT: FILE, 2 rounds (no consumer audit dimensions), 14 acceptance criteria; bundle: 5 axes evidenced, 2 N/A, 0 unestablished; adjudication: 1 must-revise, 1 advisory, 0 invalid, 1 unresolved at close, 0 effective; converged via self-verified resolution."*), carrying each flag the query reports: the word "degraded" when it reports degraded, the phrase `user declined further audit` when it reports a decline, the ceiling when it reports the cap, and the embed marker when it names one. On the `state-owner unavailable` fallback — where the query itself is what failed — the line carries that marker instead and is composed in-chat; it still renders.

Display the **absolute path built from the bound root** (`<bound-root>/.prflow/tmp/issue-draft-<slug>.md`, `<bound-root>` read back from `query-draft-binding`'s `bound=` field), never `$MAIN_ROOT` from context recall and never a bare relative `.prflow/tmp/…` string. Keep the note separate from the preview — e.g. after the rendered body, a line such as *"Draft also saved to `<bound-root>/.prflow/tmp/issue-draft-<slug>.md` for review."* — then ask *"Want me to create it as-is, or change anything first?"* If the sub-step 2 write failed, omit the note entirely rather than showing a path to a nonexistent file.

**`bound=none` arm (no `reason=`):** for a legitimately unbound run there is no bound root to display; **never** substitute the token into the path (that would show a relative `none/.prflow/tmp/issue-draft-<slug>.md` under the cwd). **Omit the draft-path note entirely**, exactly as the write-failure arm does. **`reason=foreign-nonce` is a distinct arm, never this one:** the run *is* bound and only the nonce drifted, so take the **foreign-nonce arm** of `references/fallback-draft-write-recovery.md`, loaded per `references/degradation-routing.md` — recover the nonce and re-query, else stop and tell the user the drift.

   **Display the investigation record alongside the brief — on EVERY arm, including the withheld one.** After the rendered body and the audit summary line, render the **investigation-record bucket** (the content `references/issue-template.md`'s routing rule sorted out of the brief) as its own clearly-labeled inline block in chat, so the user can audit what the sorting removed before approving. It renders even when `create_issue.investigation_record_enabled` is `false`, where this is the *only* surface the user ever sees that content on. This is **display, not attestation**: `emit-body`'s digest covers only the bound draft file. When the bucket is **empty**, say so plainly rather than rendering an empty block.

   **Scope the summary line's final-byte phrase to the body, and report the record's unaudited status beside it.** `final_byte_coverage` is about the bytes filed as the issue **body** only. The investigation record is a second filed artifact the out-of-bounds declarations place beyond the auditor's reach, so an unqualified `final bytes audited` would falsely claim coverage of it. State the body scope (e.g. *"body's final bytes audited"*) and, beside it, that **the investigation record is not audited**.

4. **Iterate on feedback.** If the user requests any change, revise the draft, re-run the no-options gate (Step 3), then run **Revision-delta verification**, then **run Step 3.5 again against the complete post-verification draft before overwriting or offering approval**. Step 3.5 is deliberately last among the draft-mutating checks: it reruns the Desired-Behavior projection and replaces the structured Steelman projection state for the bytes that reach the overwrite; a newly added Desired Behavior obligation with no representing AC prevents the overwrite/approval path. Then run **Ledger maintenance after a revision** — record the revision with `record-revision --after-round <round>`; when the per-finding verification confirmed at least one finding fixed, `record-resolution` naming those ids against the printed revision ordinal (cross-round when the fix clears an earlier round's entries), and when it confirmed none, record no resolution. A later-discovered regression uses `record-reopen`; a finding discovered misclassified uses `record-invalidate`, never `record-resolution`. Decide each against the `query-findings` read-back, never context recall. Ledger maintenance records state only; it must not edit the draft between this final projection and the overwrite.

   **Overwrite the same `<bound-root>/.prflow/tmp/issue-draft-<slug>.md` file** — the identical absolute path from the recorded binding, read back via `query-draft-binding`, never re-resolved — keeping the original filename even if the title changes, so you leave no orphaned drafts. This overwrite is a **revision write**, so it runs the full **Staged canonical-draft write** shared procedure (`skills/create-issue/references/step-3-6-audit.md`) including step 2's `record-revision --stdin-digest` from the staged bytes and step 4's write-failure recovery; a verified multi-finding revision wave applies as exactly one `apply` and one `record-revision`. Branch the read-back as sub-step 2 does: on `reason=foreign-nonce` take the **foreign-nonce arm** of `references/fallback-draft-write-recovery.md`, loaded per `references/degradation-routing.md` rather than treating the run as unbound; on a bare `bound=none` (no `reason=`) the run is unbound, so **overwrite at the main root re-resolved for this turn with the sub-step 2 `resolve-main-root.sh` recipe** — never a path composed from the `none` token, never a `MAIN_ROOT` from an earlier turn — and omit the draft-path note when re-presenting, per sub-step 3's `bound=none` arm. Each revision is re-presented in full — never apply edits and create in the same turn without showing the updated draft.

   **Order matters here — resolve the re-audit offer BEFORE asking for approval.** A just-revised draft is shown in-loop under `query-eligibility --mode iterate` (`iterate=ok ordinal=N`), which authorizes the **re-show only** — never approval and never creation. So: show the revised draft, then **offer a fresh re-audit** via the runner's user-question tool. On **"yes"**, dispatch one. On **"no"**, record the decline with `record-override --kind user-decline --surface step4-offer` (on a **file-arm epoch** additionally pass `--draft-file "<absolute issue-draft-<slug>.md path>"` so the override is digest-bound to the bytes; omit it on embed/inline epochs). That override is what lets `query-eligibility --mode approve` answer `eligible=yes` for the still-unaudited bytes — **without it, a draft the auditor keeps returning `VERDICT: REVISE` on can never clear the sub-step 5 eligibility gate and filing deadlocks.** Only once the offer is resolved do you ask the confirm/edit approval question, and **only on bytes `query-eligibility --mode approve` answers `eligible=yes` for**. Repeat until the user approves.

   This sub-step-4 offer is the **only discovery-offer surface inside Step 4's iterate-on-feedback loop**; the Step 3.6 → Step 4 boundary's T1/T2 offer fires only *before* presentation. The sub-step 5 final-byte trigger is evaluated at the **approval election on every run** and is **suppressed only when this offer opened a round in the same pause**, so exactly one offer fires per pause. A dispatched re-audit runs the pre-dispatch canonical-draft write first, then `query-arm` → `record-dispatch` → dispatch, exactly as Step 3.6 specifies. Its return is handled by the **same loop as Step 3.6** — `record-return`, obey `query-next-action`, verify findings against the code, revise, re-run the no-options gate, then run **Revision-delta verification**, and re-present the full draft — and its report **overwrites the same `.prflow/tmp/issue-audit-<slug>.md` artifact**.
5. **Create only on explicit approval.** **Creation-time confirmation re-check (path-agnostic — the fourth re-read anchor named above; it runs on every path, tool or fallback).** Immediately before running `gh issue create`, re-confirm two things in the current conversation: the user has explicitly approved the rendered draft, and the active tracking mechanism shows item 6 in progress — read it from the task tool (its read-back call, or the conversation record of the last status update where the tool exposes no read-back), or from the checklist state file on the inline-checklist fallback path. On that fallback an absent or unreadable state file is a pipeline-paused signal, not a clear-to-create one: rebuild and rewrite it, and create only on explicit in-conversation approval, never on the guard's silence.

   Once the user clearly says to create it (e.g. "yes", "create it", "looks good, file it"), **first confirm `query-eligibility --mode approve` answers `eligible=yes`** — the user's approval and the tool's eligibility are two different gates, and creation needs both.

   **Filing over a `not-eligible` answer — the sanctioned election.** **If it answers `not-eligible` because the bytes still carry an unresolved `VERDICT: REVISE`/`no-verdict` and the user — after the re-audit offer surface has been exhausted (an accepted re-audit returned `VERDICT: REVISE` and they choose to file the revised bytes without another round) — is explicitly electing to file anyway, record that election with `record-override --kind user-decline --surface step4-approval-after-exhausted-offer` (`--draft-file`-bound on a file-arm epoch) and re-query. `reason=steering-unestablished` takes this same sanctioned path — the verdict may be a clean `VERDICT: FILE` whose audit-independence could not be established, so the user's explicit election is what carries the filing. Before soliciting that election, surface exactly one offer of an unsteered re-dispatch, naming the state — but **when coverage is `uncovered` the final-byte offer below subsumes it and this offer defers to it**; only when that does not fire do you make the Step 3.6 offer here (`query-triggers` holds T2 with `reason=steering-unestablished`). The subsuming offer spends the dedicated slot rather than routing through `record-offer`, so a run already at the user-round cap is still asked once. On decline — or silence, per the pause-and-re-ask rule — proceed to presentation with the state disclosed. Never narrow this to "unresolved REVISE only": that would deadlock a clean-but-unestablished round. Proceed only once `query-eligibility --mode approve` answers `eligible=yes`.**

   **Self-assignment election (mandatory, after approval is established and before `gh issue create`).** Once the user has approved and `query-eligibility --mode approve` answers `eligible=yes`, ask one more question via the runner's user-question tool — *"Assign this issue to you?"* — before any creation command runs. A **draft-only** request never reaches this path. The answer is a required input to the posting recipe:

   - **Explicit yes** (`yes`, `assign it to me`, `yes please`) → the creation command adds `--assignee "@me"` (the account authenticated in GitHub CLI). Hold this as the `<assignee-args>` you substitute into the recipe below: on yes the single token pair `--assignee "@me"`, on no empty.
   - **Explicit no** (`no`, `leave it unassigned`) → no assignee argument; `<assignee-args>` is empty.
   - **Silence or an explicit non-yes/non-no reply** — a question-tool timeout, a `No response` return, or any answer that is neither a clear yes nor a clear no — **pauses creation and re-asks the assignment question in your final chat message**, exactly as Step 2's silent-non-response rule (`references/step-2-clarify.md`) governs a clarification question. Do **not** guess a default and do **not** run any issue-creation command: no `gh issue create` runs until the user gives an explicit yes or no.

   Then bind creation to the audited round with `record-creation-epoch --round <round>` — **on a file-arm epoch additionally pass `--draft-file "<absolute issue-draft-<slug>.md path>"`** (the same canonical file `emit-body` posts from), so the epoch's attestation comparand is the digest of the bytes actually posted and a legitimate override filing attests `match` rather than a false `mismatch`. Omit `--draft-file` on embed/inline epochs, where the audited round body stays the comparand.

   **Final-byte audit coverage — evaluated at the approval election, on every run.** Immediately before the election, when the bytes are final, read the trigger on its own query — `query-final-byte "<slug>" --nonce "<nonce>" --draft-file "<absolute issue-draft-<slug>.md path>"` (it answers one decided line `final_byte_trigger= final_byte_coverage= final_byte_reason= final_byte_passes= final_byte_exhausted=`). Do **not** look for it on `query-triggers`, which is consumed at the pre-presentation pause where the bytes are not yet final. **On `final_byte_trigger=hold`, offer exactly one exact-byte audit round** via the runner's user-question tool, naming the reported `final_byte_reason`. The pass is funded from its **own dedicated slot outside the user-round cap**, so it is offerable at the cap and under a `cap-reached` override. Record the outcome on that dedicated channel — `record-final-byte-offer "<slug>" --nonce "<nonce>" --draft-file "<…>"` with `--accepted` on "yes", without it on "no" — and **never** as a `user-decline` override: declining an optional safety pass is not the narrow election to file bytes the audit never cleared. Both arms spend the slot for these exact bytes; a recorded revision that changes the canonical digest re-arms it, bounded by the per-run cap on honoured passes.

   The trigger fires wherever the reported coverage is `uncovered` and that slot is unspent. A run that converged `basis=resolution` on the drafter's own self-verified fixes reports `uncovered` and is the **common** case. **Filing is never blocked:** the user's explicit election remains the path by which a determined filer files.

   **Return-handling carve-out.** An accepted pass is an **ordinary whole-draft round** dispatched through the existing file-arm machinery (pre-dispatch canonical-draft write → generated dispatch instructions → `query-arm` → `record-dispatch` → dispatch → `record-return`). **Dispatch it with the generated instruction file exactly as any round, passing `--instructions-file`/`--instructions-draft-path` and quoting the auditor's `--instructions-object-id`/`--extra-dispatch-content` back on the return** — without those inputs the pass records `steering_reason=inputs-unrecorded` and the field reports `uncovered` whatever verdict comes back. The pass is nevertheless carved **out** of sub-step 4's return handling: on `VERDICT: REVISE` its findings are adjudicated with a ledger like any round's and **disclosed to the user at this approval election**, and the run files on the user's explicit election — it does **not** trigger a mandatory revise-and-re-present cycle, which would change the canonical digest and re-arm the slot off the mechanism's own return. On a **verdict-less** return the existing no-verdict machinery governs the round unchanged (and the slot is refunded).

   **Source the body from the single presentation source.** On a **file-arm epoch** the body comes from the gated canonical file via `emit-body`, which emits the audited bytes only when eligibility grounds them. **Never pipe `emit-body` straight into `gh`** — without `pipefail` a refused `emit-body` (non-zero exit, **empty stdout**) would create an **empty-bodied issue**. Emit the output to a temp file, **guard it non-empty**, and only then hand that file to `gh issue create --body-file <path>` directly — never re-piped through `cat` into `--body-file -` (`cat` is a non-preflight PATH tool whose absence would feed `gh` empty stdin) — all in one single statement, byte-exact through the file (never a `"$(…)"` capture read by a later statement; see `references/issue-template.md` for the exact recipe). On **embed/inline-arm epochs** there is no trustworthy canonical file, so the in-context heredoc re-emission remains — a disclosed residual. **Pass `<assignee-args>` from the self-assignment election on the `gh issue create` invocation, on both the file-arm and embedded-body posting arms.** **Do not pass `--label` on `gh issue create`.** Report the issue URL that `gh` prints, and capture the new issue's number from the trailing path segment (e.g. `…/issues/42` → `42`) — sub-steps 5a and 6 need it.

   After creation, attest what actually landed: fetch the created issue's body and pipe those bytes into `record-creation-attestation`, **byte-exact through a file, in one single statement** (never a `"$(…)"` capture re-emitted via `printf`, which mutates trailing bytes against the recorded digest):
   ```bash
   if gh api repos/{owner}/{repo}/issues/<issue_number> --jq .body > "<main-root>/.prflow/tmp/issue-fetched-<slug>.md"; then python3 "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/issue-audit-state.py record-creation-attestation "<slug>" --nonce "<nonce>" < "<main-root>/.prflow/tmp/issue-fetched-<slug>.md"; else python3 "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/issue-audit-state.py record-creation-attestation "<slug>" --nonce "<nonce>" --attestation-unavailable; fi
   ```
   The tool tolerates exactly **one** fetch-framing trailing newline (jq's output framing) — reporting `matched modulo the fetch's single trailing newline` on stderr when that tolerance fired — and anything else stays a mismatch.

   **The failed-fetch arm is part of the recipe — that is what the `if`/`else` shape is for.** Written as a bare `&&` chain it would short-circuit, `record-creation-attestation` would never run, and the summary would render `attestation=none` — which above means *before any creation attempt*, i.e. indistinguishable from never attempted. Branch on the **fetch's own** exit status, not a blanket `||` over the whole chain: the `--attestation-unavailable` arm is scoped to a failed fetch, matching the tool's own `fetch-failed` transition, so a *tool* failure after a successful fetch surfaces its own breadcrumb instead of being re-run into an unavailable record. A recorded `match`/`mismatch` is forward-only tamper evidence — the tool refuses to overwrite one.

   **When that then-branch `record-creation-attestation` call itself exits non-zero** (a `git`/read/persist failure *after* a successful fetch, so nothing was recorded and `query-summary` still reports `attestation=none`), **surface it in the summary line as an errored post-fetch attestation** — e.g. append `attestation errored post-fetch: <breadcrumb>` — **not** the bare `attestation=none`, which means *no creation was attempted*.
5a. **Stamp the reserved `PRFlow` provenance label (best-effort).** After a successful `gh issue create`, ensure the reserved label exists and apply it to the new issue. `PRFlow` is a hardcoded provenance constant no config key controls (its superseded `DevFlow` spelling stays selectable on already-labelled history; new issues are stamped only `PRFlow`) — the branch-naming-independent signal the weekly retrospective uses to detect DevFlow-authored work. Apply it *after* creation so a label hiccup can never block the issue from being created:
   ```bash
   "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/ensure-label.sh PRFlow
   "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/apply-labels.sh <issue_number> PRFlow
   ```
   Both steps are best-effort and need only the `repo` scope: `ensure-label.sh` and `apply-labels.sh` each always exit 0, logging the label and apply outcomes. Application goes through `apply-labels.sh`'s REST `POST .../issues/{n}/labels`, never `gh issue edit --add-label`, which resolves the repo via org-scoped GraphQL and fails under a repo-scoped token. The always-exit-0 contract applies only once a helper actually runs: an invocation that fails because the helper path does not exist (`No such file`, exit 127, or the platform equivalent) is the **anchor-resolution** failure noted at the top of this skill, not a benign label outcome — fix the anchor and re-run both commands, since a silently skipped `PRFlow` label drops the issue out of retrospective provenance detection. If the anchor cannot be resolved on this runner at all, report the degradation explicitly in the final outcome — issue created, `PRFlow` provenance label NOT applied. Continue to sub-step 5b regardless of the label outcome.
5b. **Register declared prerequisites as GitHub-native blocked-by dependencies (best-effort).** After a successful `gh issue create`, register each prerequisite the drafted body declares **inside its `## Dependencies` section** as a GitHub-native blocked-by dependency on the created issue, so the blocker shows in GitHub's own issue header, issue list, and project views without anyone reading the body. `scripts/apply-issue-dependencies.py` mirrors the label-stamp contract: it fetches the created issue's body itself (so it takes only the number), derives the prerequisites through the same **section-scoped** recognizer factored out of `scripts/preflight.py` (only the reserved section registers), always exits 0, and leaves a specific `apply-issue-dependencies.py:`-prefixed stderr breadcrumb on every path it can reach. Invoke it as the command's **leading token** with just the created issue's number:
   ```bash
   "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/apply-issue-dependencies.py <issue_number>
   ```
   **Read the helper's stderr from the tool result and route on it — the same four-outcome routing `skills/implement/references/deferred-ac-followups.md` states for its label stamps.** A `apply-issue-dependencies.py: linked …` / `… already blocked_by …` / `… declares no prerequisites …` / `… skipped #<n>: … reads as an OUTBOUND relation …` / `… done for #<n>: …` line is a **successful registration outcome** (the `skipped …` line names a prerequisite dropped because its `## Dependencies` line declares this issue as the prerequisite rather than a blocker — restate it as `blocked by #<n>` on its own line if it must land first). A `… could not link … (API refused …)` or `… every declared prerequisite's registration was refused …` line is an **API failure**. A `… missing or non-numeric issue-number argument …` line is a **caller arg-slip** (the breadcrumb says outright it is *not* a harness denial) — re-emit the call once with the captured number. **No output at all means the harness refused the command**, not that nothing needed doing — the helper breadcrumbs on every path its own code reaches. **Name any number the helper could not resolve or link in the run's final outcome**, exactly as 5a names an unapplied `PRFlow` label; the remaining numbers are still linked. If the anchor cannot be resolved at all, report the degradation (issue created, prerequisites NOT registered). Continue to sub-step 6 regardless of the outcome — a dependency-registration hiccup can never block or reverse the creation.
5c. **Publish the investigation record as the first comment (gated, best-effort, before the implement offer).** The draft was composed into two buckets by `references/issue-template.md`'s **Brief / investigation-record routing** rule — the **brief** (the created issue body) and the **investigation record** (rejected designs, refutation prose, confirmatory evidence, deliberation, lower-severity hazards). Publish that record bucket as the issue's **first comment**, *after* creation (5) and *before* the implement-offer comment (6) so the record precedes any implement trigger. **Sorting always ran; publication is what this gate controls.**

   - **Resolve the gate.** Read `create_issue.investigation_record_enabled` (default `true`) through the bundled resolver as the command's **leading token**:
     ```bash
     "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/config-get.sh .create_issue.investigation_record_enabled true
     ```
     **Withhold publication when, and only when, the resolved value is exactly the literal `false`** — compare with **bash builtins only** (`case "$V" in false) … ;; esac`, never `tr`/`sed` lowering, which fails open when the tool is absent, guard-class 2). So the observed resolver outputs `True`, `0`, and the **empty stdout of an exit-2 resolver failure** each leave publication **enabled** (empty ≠ `false`) — the silent-off-switch inversion an `!= true` spelling would introduce. An absent key, an absent family, an absent file, `null`, and an empty-string value all resolve to the default `true` and publish.

   - **Delete any same-slug record leftover first, on every arm**, so a failed prior-run delete cannot leave a stale record that misleads or gets posted. Resolve the write root the way every later write site does — from `query-draft-binding "<slug>" --nonce "<nonce>"`'s `bound=` field, **never a second `resolve-main-root.sh` resolution while a binding exists** (this sub-step runs in a later turn, after a possible compaction). Branch as sub-step 4 does: on `reason=foreign-nonce` take the **foreign-nonce arm** of `references/fallback-draft-write-recovery.md`, loaded per `references/degradation-routing.md` and compose **no** record path at all; on a bare `bound=none` (no `reason=`) the run is legitimately unbound, so **write under the main root re-resolved for this turn with the sub-step 2 `resolve-main-root.sh` recipe** and never compose a `none/…` path from the token. The record file is `.prflow/tmp/issue-record-<slug>.md` under that root's `.prflow/tmp/` — **never** written into `issue-draft-<slug>.md`, so the canonical draft's `emit-body` digest is unaffected by record edits.

   - **When publication is withheld** (`false`): post **no** comment, write **no** record file at all (never write-then-delete this run's own record — the leftover delete above targets only a *prior run's* stale file), and ensure **no** record-bucket content reached the created body. Report in the run's final outcome that the investigation record was withheld by config.

   - **When publication is enabled and the record bucket is non-empty:** write the record bucket to `.prflow/tmp/issue-record-<slug>.md` with the **Write tool**, its **first line exactly** `<!-- prflow:investigation-record -->`. **Neutralize every workflow-trigger token in the record body before writing the file** — at minimum `/prflow:<command>`, `/devflow:<command>`, and `@claude` — so the literal trigger substring no longer appears verbatim in the posted bytes: rewrite each in prose (a rejected design that *names* `/prflow:implement` becomes "the prflow-implement trigger"), or break the substring with a zero-width space (U+200B) after the leading `/` or `@`. The first two are the tokens `devflow-implement.yml`/`devflow.yml` positively match in a comment body; `@claude` is the trigger surface of a consumer's stock `claude.yml`, which those two workflows **negate** — a record must not dispatch a run against the issue just created.

     **Verify neutralization mechanically before posting — do not trust the hand-rewrite alone.** The record body is arbitrary drafting content an LLM rewrote by hand, so one missed occurrence would survive verbatim and dispatch an unwanted run. After writing the file, run this one status-preserving check; `grep` is inside an `if`, so errexit cannot erase its status:

     ```bash
     if grep -nE '/(pr|dev)flow:|@claude' "<record-file>"; then
       neutralization_grep_status=0
     else
       neutralization_grep_status=$?
     fi
     printf 'neutralization_grep_status=%s\n' "$neutralization_grep_status"
     ```

     Read the final status line together with any match lines. First require exactly one final result line matching `neutralization_grep_status=<decimal integer>` with no extra text. Zero result lines, multiple result lines, a non-decimal value, or trailing text are all `neutralization grep harness refusal`: withhold the post and report that refusal. Only a valid result line reaches status routing. Status `0` plus its match lines means triggers survive: do **not** post, re-neutralize those exact occurrences, and re-run the fence. Status `1` is the only clean no-match result and permits posting. Status `2` or greater is a grep failure: withhold the post and report it. **The line-1 marker `<!-- prflow:investigation-record -->` is safe — it carries no leading `/` and no `@`.** If surviving triggers cannot be made clean, withhold the post and name them in the final outcome.

     Then post the verified file:
     ```bash
     "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/post-issue-comment.sh <issue_number> "<bound-root>/.prflow/tmp/issue-record-<slug>.md"
     ```
     `post-issue-comment.sh` posts via REST `POST …/issues/{n}/comments` (repo-scoped), reads its body **only from a file**, and **always exits 0**, so route on its stderr breadcrumb rather than its exit code. Apply exactly one result row: `devflow: posted comment on #<n>` means posted; `devflow: warning: could not post comment on #<n> …` means **NOT posted** and the final outcome names the failure; a warning containing `missing issue-number argument (caller argument slip` or `missing body-file argument (caller argument slip` means **NOT posted**, the final outcome names the caller slip, no API request was made, and the run continues to sub-step 6 without retrying or blocking issue creation; no output, multiple contradictory result breadcrumbs, or an unrecognized breadcrumb is a harness refusal, means **NOT posted**, and is named in the final outcome. A caller-slip breadcrumb is therefore never success merely because rc is 0, and never a reason to stop the already-created issue's best-effort flow.

   - **When publication is enabled but the record bucket is empty:** post **no** record comment and report in the final outcome that there was **nothing to record**.

   - **A record post that fails never blocks issue creation**, and the failure is **named in the run's reported final outcome** (issue created, record NOT posted, with the helper's stderr breadcrumb). Continue to sub-step 6 regardless of the record outcome.

6. **Gated offer to start implementation.** This sub-step runs **only after `gh issue create` succeeds** (it exits zero and prints an issue URL) and the URL has been reported. If creation failed (non-zero exit, or no URL printed), stop here and surface `gh`'s error output verbatim — do **not** show this prompt. After a successful creation, evaluate a **two-condition gate** and present the yes/no implement prompt **only when both conditions hold** (an unconditional offer would post a comment that fires nothing on a tier-disabled repo, or green-light an implement run whose prerequisites are still open):

   - **(a) The created issue's body has no open prerequisites and no unresolved decisions** — the body you just drafted and posted contains **no `## Dependencies` entries** (the section is absent, or present but with no `Blocked by #N` line) **and no `## 🚫 Blocked` section**. Read this from that body.
   - **(b) The cloud implement tier is enabled** — `workflows.prflow` resolves to **exactly `true`** from `.prflow/config.json` (the same fail-closed semantics `.github/workflows/devflow-implement.yml`'s gate job reads as `.workflows.prflow // false`). Read it first through the bundled resolver as the command's **leading token** via the portable anchor:
     ```bash
     "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/config-get.sh .workflows.prflow false
     ```
     When that invocation is **denied or fails** (the local-tier classifier can deny a script-by-path call; the anchor may be unresolvable), load `references/fallback-implement-offer-tier-read.md` per `references/degradation-routing.md` and follow its fallback read ladder. A resolver that answers cleanly — the normal path — never loads it.

   **When both conditions hold**, present the prompt via the runner's user-question tool (`AskUserQuestion` on Claude Code, as used in Step 2) asking whether to start implementation now by commenting `/prflow:implement <issue_number>` on the newly created issue.
   - **On "yes":** post the comment yourself with `gh issue comment <issue_number> --body "/prflow:implement <issue_number>"`, using the number captured in sub-step 5. Use the bare `/prflow:implement <n>` form with **no** `@claude` mention, so it routes to the repo's `devflow-implement.yml` listener rather than the stock Anthropic one. On success, report that the comment was posted and that it fires the implement run **only when** the repo's devflow workflows are enabled and the commenter is authorized — both enforced by the `gate` job in `.github/workflows/devflow-implement.yml` (authorization via `scripts/resolve-implement-trigger.sh`). Surface that caveat in the reported outcome. If `gh issue comment` fails, surface its error output and report that the issue was created but the implement comment could not be posted.
   - **On "no":** finish without posting any comment.

   **When the gate withholds the prompt, print a one-line reason naming the exact failed condition** — one of: *declared dependencies present*, *blocked decisions present*, *cloud implement tier disabled or unconfigured*, *config unreadable (all read paths failed)*, or *tier state unestablished* (`references/degradation-routing.md`'s degraded cell for `references/fallback-implement-offer-tier-read.md`, taken when that file itself could not be loaded, so no rung established a value). A withheld offer is **never silent**, and the issue-created outcome (the URL and the sub-step 5a `PRFlow`-label result) is still reported **in full**.

   **Selecting between *tier disabled/unconfigured* and *config unreadable* — observe the read, don't guess it.** When the fallback ladder ran, classify its outcome per the arms in the already-loaded `references/fallback-implement-offer-tier-read.md`; a resolver that answered cleanly at exit 0 needs no classification.

**This gate has no exceptions.** Neither Step 2's resolved decision forks, nor an earlier "just create it" / "you decide", nor a disengaged user, nor brevity is a substitute for showing the literal title and body that will be filed and getting an explicit go-ahead on *that draft*. If the user never returns to confirm, leave the pipeline paused at todo 6 — do **not** create the issue to "finish".

**Red flags — STOP, you are about to skip the gate:** you are constructing the `gh issue create` command in the same turn you drafted the body with no approving user message in between; you are creating because Step 2 was "complete"; or you are treating an earlier "just create it" as approval of a draft the user has not seen. All of these mean: show the full rendered issue, ask, and wait for an explicit yes.
