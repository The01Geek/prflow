## Quality group — compatibility and rollout

Trigger (observable before this reference loads): the grounded change does at least one of — changes a supported-version boundary across runtimes, tools, APIs, schemas, configurations, or plugin releases; changes a contract already used by existing data, configuration, or consumers; spans independently upgraded components or artifacts that can therefore run at mixed versions; or introduces rollout behavior such as staged activation, rollback, or old/new coexistence. Merely touching a shipped path does not trigger this group — the change must alter one of those boundaries — and uncertain applicability loads it.

Each obligation appears once, as its checklist row plus the rule text it carries, and the group resolves only the touched decisions. The decisions land in the issue's existing Desired Behavior, Technical Context, Acceptance Criteria, and Testing Strategy sections where they affect implementation — this group adds no compatibility section to the body.

- [ ] **Every touched support boundary states its supported old/new combinations and the behavior of the unsupported ones.** For each version, schema, API, configuration, or release boundary the change moves, the issue names which old/new pairings are supported and what happens on an unsupported pairing (refuse, degrade, or error). An inferable answer is taken from repository policy or verified code and cited; only a remaining load-bearing policy choice reaches the user.
- [ ] **Every changed contract states how existing data, configuration, and consumers cross the change boundary.** When the change alters a contract already in use, the issue states how the already-deployed data, config, and consumers move across it — read-through, migration, or dual-support; an untouched contract imposes nothing.
- [ ] **Independently released components state their valid upgrade order and partial-deployment behavior.** When the change spans components or artifacts that upgrade separately (so they can run at mixed versions), the issue states the valid upgrade order and the behavior while only part of the set has been upgraded.
- [ ] **A rollout that can leave mixed states states its rollback and coexistence behavior.** When the requested rollout uses staged activation, rollback, or old/new coexistence and can leave the system in a mixed state, the issue states how old and new coexist and how a rollback behaves — rollout mechanics are required only when partial deployment is actually possible, not for an atomic change.
- [ ] **The resolved compatibility decisions map to focused acceptance criteria and tests, and the one clarification question (if any) is consolidated.** Each decided combination, transition, mixed-version rule, and rollback behavior that affects implementation appears as a focused acceptance criterion and a test, expressed through the existing sections above; when a load-bearing policy choice survives repository-policy and verified-code inference, it is asked as **one** consolidated clarification question, never a per-decision interrogation.
