   Per-finding disclosure block. A run that opened no audit round graded nothing and skips this block entirely — `query-adjudication-records` requires a `--round`, and there is none. On a run that opened a round, read `query-adjudication-records "<slug>" --nonce "<nonce>" --round "<round>"`; when it returns records rather than `records=none`, render each advisory and invalid finding's `summary`, `rationale`, `impact_class` tag, and the auditor's own `auditor_block` beside the grader's restatement, then report that rendering exactly as the calibration paragraph of `references/step-3-6-audit-adjudication.md` states. The audit summary line's own class counts stay unchanged.

Coverage and adjudication counts. The line reports the bundle's coverage (`axes evidenced, axes marked N/A, axes unestablished`), the post-adjudication counts by actionability class, the unresolved must-revise findings attributable to an axis on the effective list as frozen at that round's close, and — distinctly, never collapsed onto it — the run-wide effective unresolved count after every post-close resolution, reopen, invalidation and supersession. A round whose actionability or axis attribution could not be established renders `unestablished` rather than a number.

Final-byte coverage. The line carries the final-byte coverage value on every dispatch arm and every round count — the degraded inline arm included — as `final bytes audited` on `covered`, `final bytes NOT audited (<final_byte_reason>)` on `uncovered`, and `final-byte coverage unestablished (<final_byte_reason>)` on `unestablished`; when `final_byte_exhausted=yes`, append `— final-byte passes exhausted`. Read `<final_byte_reason>` from this sub-step's own `query-final-byte` line above. A recorded `attestation=match` never stands in for that phrase.

Convergence basis. When `convergence_basis` names a resolution basis, the line additionally carries the phrase `converged via self-verified resolution` — on the stale variant `converged via self-verified resolution (stale — later revisions unverified)`.

Criterion count. The line also carries the criterion count as a skill-composed marker — `<n> acceptance criteria` — rendered alongside the other skill-composed markers this line already carries. It is the length of the `acceptance_criteria` array returned by the `python3 … scripts/parse-acs.py --format json` invocation the run already performs at the run bootstrap's canonical write (which runs regardless of whether an audit round is elected); perform no second parse, and compose the marker in the skill rather than reading it from `query-summary`. It is reported, never enforced.

The number renders only when this run holds an established `acceptance_criteria` array from its own gate invocation; its absence — however it arose — renders a token instead, and a hand count is never substituted. Render `acceptance criteria count unavailable (unreadable item shape)` when the invocation reported `acceptance_criteria_unreadable`, and `acceptance criteria count unavailable` on every other absence. A `state-owner unavailable` fallback entered *after* the run bootstrap's canonical write still carries the parsed array and renders the number normally; only one entered *before* it never reached the gate site. Never count the checkbox rows by eye.

#### Criterion-disposition confirmation (report-only, every run)

Before approval is asked, confirm the omit/merge/add disposition record (`references/issue-template.md`'s Acceptance Criteria contract) against the criteria the draft actually carries. Drive the check from the criteria set the rendered draft carries, not a fixed slice of the artifact, so every criterion the draft carries is checked however long the run; for each, look for its disposition line in the `## Criterion disposition record` section of `.prflow/tmp/create-issue/<slug>/issue-derivation-<slug>.md`. Name, as a skill-composed disclosure beside the criterion-count marker below, any added criterion the draft carries whose disposition line the record does not show, marking it **undischarged** — a disposition line the read does not reach is reported undischarged, never silently passed — and when the record cannot be read at all — unreadable, absent, or, on the read-only arm, only an inline stand-in block posted per `references/fallback-read-only-sandbox.md` — read that inline block where one exists, else report the record **unestablished** rather than clean; render nothing when every added criterion the draft carries shows a disposition line. This confirmation sits on the presentation path because a run can add a criterion where a Step 3.6-sited reader would miss it: a run that elects no audit round never enters Step 3.6, and a criterion added while an audit round is adjudicated is added after that step's entry gate has run — the presentation write is the step both those cases still pass through. Naming is all it does — it blocks neither presentation nor creation, and it re-runs on every re-presentation (a sub-step 4 revision returns here).
