### Step 2: Clarify until the Definition of Ready is met

Clarification is the default, not the exception. Do not assess "is this clear enough to skip" — assess "which Definition-of-Ready facts are still unknown" and ask about those. The only way to skip a question is to already know its answer from the user story or the Step 1 findings.

Definition of Ready — every item below must have a single, decided answer before you draft:

- [ ] **Independent derivation before anchoring (run the pass below FIRST, on every run).** You have re-derived the full Definition of Ready from the problem and the Step 1 findings *before* weighing the user's supplied criteria — challenging supplied acceptance criteria on both **completeness** and **correctness** — **written that derivation to its observable artifact (`.prflow/tmp/create-issue/<slug>/issue-derivation-<slug>.md`) before any clarification round**, and you drive clarification from the **delta plus conflicts**. The gate before the first clarification round (and the per-round re-check) confirm the file — or, in a read-only sandbox, its visible inline-in-chat stand-in — exists. See the independent-derivation pass below.
- [ ] **Problem & beneficiary** — who hits this pain and why it matters. (Not "users want export" — *which* users, doing *what*, blocked *how*.)
- [ ] **Single coherent scope** — the issue is exactly one feature/fix. If the story bundles two or more ("export results *and* notify when ready"), ask the user whether to split; default to one issue per feature.
- [ ] **One decided behavior per fork** — every place the story could mean different things (format, channel, trigger condition, access model, edge-case handling) has *one* chosen answer, with no unresolved fork left in the body — the canonical no-options rule and its vocabulary live in `references/issue-template.md`.
- [ ] **Solution-space expansion before convergence (do this BEFORE the implementation-approach fork below).** The user's proposed mechanism is an *input*, not the menu. Before asking the user to pick an approach, independently generate the full space of mechanisms that could solve the stated problem — and in particular ask: *is there a categorically STRONGER class of mechanism than what the user proposed?* A mechanism's **strength** has two axes: the **guarantee it enforces**, and the **long-term cost it leaves behind** — codebase weight, implementation weight, and how hard it makes later change; weigh both, not shape alone. Ranked by guarantee, a useful ladder runs weakest→strongest: (a) documentation/wording that asks a human or agent to remember; (b) an in-process self-check that *warns* when the thing was skipped; (c) a *deterministic* mechanism that runs regardless of the actor's choices (a harness/hook/wrapper that fires after-the-fact, an enforced gate, an idempotent backstop that re-does the work). If the user proposed only (a) and/or (b), you MUST generate at least one (c)-class candidate and put it on the menu. Name the strongest viable mechanism even if the user did not think of it. If after genuine effort no stronger class exists (or the stronger classes don't apply to this problem — e.g. a harness fires at the wrong point), say so explicitly in the question rationale rather than silently omitting it.
- [ ] **One implementation approach** — present the expanded mechanism menu (including the strongest class found above), and the user has picked one. You surface each option's **guarantee-strength** and trade-offs *in the question*, not in the issue.
- [ ] **Concrete acceptance criteria** — you can state each as a single unconditional, testable assertion. If an AC would need a conditional ("if links are public…"), the underlying fork isn't resolved yet — go ask.
- [ ] **Known prerequisites (cross-issue ordering)** — candidate prerequisite issues (another issue/PR that must land before this work can *start*) are inferred from the story and the Step 1 findings, and **when at least one candidate exists** they are confirmed with the user via the runner's user-question tool. A story with **no** inferable prerequisite gains **no new question** — this item adds a question only when it applies. Confirmed **still-open** prerequisites populate the draft's `## Dependencies` section as `Blocked by #N — <reason>` lines (see `references/issue-template.md`); already-closed ones are recorded as Technical Context provenance instead.
- [ ] **Visual specification (user-visible UI changes only)** — for an issue you infer involves user-visible UI, either a screenshot/mockup is recorded or the visual details are verbally verified with the user. **Skipped entirely for non-UI issues**, which gain no new questions. See the *Visual-specification guidance* below for the dimensions to verify and the screenshot-preferred-not-mandatory rule.
- [ ] **Reproduction facts (defect reports only)** — for a story you read as reporting a defect, the reproduction facts `references/issue-template.md`'s `Current Behavior` requires (triggering steps or input, observed result, expected result, and environment) are each recorded, or recorded `unestablished — <reason>` when a fact cannot be established. **Skipped entirely for non-defect stories**, which gain no new questions. A reproduction fact nobody answers is handled exactly like any other unanswered readiness item — it reaches `## 🚫 Blocked` as a question by the path that already exists, not a new one.

Independent-derivation pass (mandatory, before any clarification round — runs on every run regardless of how complete the story looks).

1. Derive first, read the supplied answers second — and write the derivation to an observable artifact. Before reading the user's acceptance criteria (and any other pre-supplied decisions) *as answers*, independently re-derive the full Definition of Ready above — problem/beneficiary framing, every behavioral fork, edge/error cases, and the acceptance criteria — from the stated problem and the Step 1 codebase findings.

   Write that derivation to `.prflow/tmp/create-issue/<slug>/issue-derivation-<slug>.md` before any clarification round begins — run `mkdir -p .prflow/tmp/create-issue/<slug>` first, then use the run's kebab-case `<slug>`, which Step 1 bound before it dispatched anything — this pass never binds one of its own. Read it from turn-one context when you still hold it, and otherwise from the fixed pointer `.prflow/tmp/create-issue/issue-run-slug` Step 1 wrote; a pointer that is absent, unreadable, empty, whitespace-only, or not a single kebab-case slug on one line is recorded **unestablished** (never guessed), which routes to the title-derived fallback `references/step-4-present-create.md` retains. Reuse that exact path for the rest of this run. As the very first action of this pass — before you derive anything — delete any pre-existing `issue-derivation-<slug>.md`, then write it fresh. Reuse the same `<slug>` as Step 4's `issue-draft-<slug>.md`, under the same gitignored `.prflow/tmp/` convention. This derivation artifact stays cwd/worktree-anchored, whereas Step 4's user-facing *draft* is written under the main repo root (`resolve-main-root.sh`) — same `.prflow/tmp/` subpath and slug, intentionally different root. On a filesystem that refuses the write, follow `references/fallback-read-only-sandbox.md`, loaded per `references/degradation-routing.md`. Clarification and drafting stay inline — this pass dispatches no subagent and adds no new script or dependency.
2. Treat supplied acceptance criteria as suspect on two axes. *Completeness* — which behavioral forks, edge cases, and factors does your independent list have that theirs omits? *Correctness* — is each supplied criterion atomic, testable, and a genuinely resolved decision, or a buried unresolved fork wearing the costume of a decided one? A polished, comprehensive-looking list earns the same scrutiny a terse story gets.
3. Drive the clarification rounds from the delta. Diff your independently-derived list against the story and clarify from the delta plus any conflicts — the forks, edge cases, and factors you derived that the story left unresolved; the supplied criteria that fail the correctness test; and anywhere the two lists disagree. The supplied criteria are one of the two inputs to that diff, never a shortcut past it.

This pass feeds the clarification rounds; the no-options gate (Step 3) still governs the final body. Its output is a working derivation to clarify against — never a place to park options in the issue itself.

Evidence-bundle sub-pass (mandatory, part of the independent-derivation pass — runs on every run, after the Definition-of-Ready derivation and before the first clarification round).

This sub-pass records the mechanism space's evidence up front, so the approach question is asked only once every axis that mechanism touches — producers, values, consumers, execution tiers, lifecycle states, failure paths, migrations, and coupled surfaces — carries a bundle entry, with any axis still `unestablished` at ask time disclosed in the question rather than left silent. It asks the user nothing (it draws nothing from the ~18-question clarification budget) and, mirroring the Step 3 drafting rule, performs no whole-codebase re-exploration — its reads and searches are targeted, seeded from the Step 1 findings (plus the currency re-evidencing below, seeded from clarification answers and from mechanism classes added during solution-space expansion).

- Step 1 evidence is read, not re-derived. This sub-pass seeds from the Step 1 evidence artifact `.prflow/tmp/create-issue/<slug>/issue-step1-<slug>.md` — written on every Step 1 path (shallow return, deep reconciliation, degraded inline verification) — and an escalating deep arm reads the same file, warm-starting rather than re-deriving. **Treat it as a best-effort parser treats agent-mutable markdown.** An **empty or truncated** file, a **missing or duplicated** section marker, or a **non-canonical layout** routes to **re-running the Step 1 pass**, never a partial parse. An absent file where Step 1 already completed is instead recorded `unestablished — Step 1 evidence artifact absent`. Degraded Step 1 evidence carries its degradation into the entries it seeds.
- Axis floor. After writing the derivation, append a `## Evidence bundle` section to the same `.prflow/tmp/create-issue/<slug>/issue-derivation-<slug>.md` artifact (in a read-only sandbox, to the same visible inline-in-chat block that stands in for it). The bundle records, per axis on the effective list, what the mechanism space under discussion touches, covering at minimum these generic axes: authoritative producers and the values they emit; consumers of each touched value or surface; execution environments (tiers, host OSes, degraded arms); persistence paths; lifecycle states and termination paths including retries and backstops; migration and coexistence surfaces (what is already deployed that the change must coexist with — this axis stays evidence collection; the *decisions* about supported combinations, transitions, mixed versions, and rollback are owned by the conditionally-loaded compatibility-and-rollout quality group, `references/quality-group-compatibility.md`, not settled here); and coupled tests and docs. The `at minimum` marker is deliberate — a consumer `## Evidence axes` section extends the list.
- Entry form. Every axis entry takes exactly one of three legal forms — one to three lines in `Verified:` form (the executed command or file reference plus what it established), the single line `N/A — checked <how>` (the axis genuinely does not apply, with the check named), or the single line `unestablished — <why>` (the probe was unavailable or denied, or the entry was superseded by a later clarification answer) — and an axis with no entry is not a legal bundle state. Proportionality clause: on a run whose mechanism space plainly does not touch a set of axes (a one-line docs fix touches no migration surface), those axes may be batch-marked `N/A — checked: scope inference, <one line>` in a single pass.
- Self-describing header. The `## Evidence bundle` section opens with a compact fixed header restating the three entry forms, the three currency triggers, and the effective axis list as computed at pass time. Each gate site cross-checks its freshly recomputed effective list against the header's pass-time list (a difference is a currency trigger).
- Information diet unchanged. Bundle claims the draft relies on land in the issue's `Technical Context` as `Verified:` bullets, where the Step 3.6 auditor re-verifies them through the draft; the `## Evidence bundle` section itself stays inside the derivation artifact and is never carried into the Step 3.6 dispatch prompt.

`## Evidence axes` forwarding. At pass time the skill re-runs `load-prompt-extension.sh create-issue --section '## Evidence axes'` fresh (via the portable anchor recipe above) and appends any section headed exactly `## Evidence axes` to the generic axis floor; an extension without that heading still contributes no consumer section, and that absent heading is now breadcrumbed and reported rather than invisible.

On any loader stderr from this re-load, read the exit status first. A loader exit-2 refusal (a malformed flag or a guard failure) at this site is an **unestablished** load, surfaced per the loader-failure arm's discipline below — never laundered into the designed absent-heading no-op. At exit 0, an absent-heading breadcrumb from a non-empty extension is instead the designed no-op: report the headings the breadcrumb lists — surfacing a near-miss heading (case drift, say) and equally the routine single-hook extension that carries only the other heading — and then proceed treating the selection as no consumer section for that hook: a **report-then-proceed** step, never a stall, a user question, or a degraded-arm claim.

The heading-extraction rule is owned by `scripts/render-audit-prompt.py` — the loader invocation above stays this hook's operative fresh re-load (its stderr absent-heading breadcrumb is what the report-then-proceed step reads), and the renderer exposes the same rule as `render-audit-prompt.py extract --hook evidence-axes`, applying the positional two-marker delivery check — `render-status:` first line, `render-end:` last line. The renderer's four extraction clauses are documented in `skills/create-issue/references/audit-prompt-template.md`; the same extraction rule also serves the Step 3.6 `## Audit dimensions` hook, which consumes it spliced into a dispatch arm as `{CONSUMER_DIMENSIONS}` rather than through a standalone `extract` call.

Loader-failure arm: a denied or failed pass-time re-load is surfaced, never treated as "no extension" — the bundle records the dedicated line `consumer axes: unestablished — loader denied or failed`, the gate evaluates the generic floor with that line present, and the Step 3.5/Step 4 coverage reporting names the effective list as floor-only-degraded.

Bundle-coverage gate. The bundle-coverage gate fires at the same two sites as the derivation gate it extends — before the first clarification question, and unconditionally at the Step 3 drafting precondition on every run. At each site it requires the `## Evidence bundle` section to exist with an entry for every axis on the effective list (the generic floor plus any consumer `## Evidence axes` section), and each gate site recomputes the effective list — re-running `load-prompt-extension.sh create-issue --section '## Evidence axes'` per the fresh re-load recipe.

On any loader stderr from this re-load, read the exit status first. A loader exit-2 refusal (a malformed flag or a guard failure) at this site is an **unestablished** load, surfaced per the Step 2 loader-failure arm's discipline — never laundered into the designed absent-heading no-op. At exit 0, an absent-heading breadcrumb from a non-empty extension is instead the designed no-op: report the headings the breadcrumb lists — surfacing a near-miss heading (case drift, say) and equally the routine single-hook extension that carries only the other heading — and then proceed treating the selection as no consumer section for that hook: a **report-then-proceed** step, never a stall, a user question, or a degraded-arm claim.

The gate reuses the derivation gate's shape: this-run freshness, the read-only-sandbox visible inline stand-in, and on-disk distrust when the filesystem is read-only.

Bundle currency (per-round re-check). The existing per-round Definition-of-Ready re-check additionally re-checks bundle currency against three triggers — a clarification answer that changes the mechanism space; a clarification answer that contradicts an axis entry; and a mechanism class added to the approach menu after the bundle was written (drafter-generated during the mandated solution-space expansion, or user-proposed) — updating the affected entries or re-marking them `unestablished — superseded by <the trigger>` before the approach question is asked. Asking-order rule: the implementation-approach fork question is asked in its own question-tool call, never batched with any question whose answer is a currency trigger, and only after the mechanism-space-shaping answers are in; if an answer arriving in the approach question's own call nevertheless invalidates the cited entry, the approach answer is treated as unconfirmed and the question is re-asked with a refreshed citation. The approach question's background opens with the run's problem framing — the problem, the current behavior, and the desired behavior at outcome level — so the user confirms the framing and picks the mechanism in one pause. A run that passed over at least one heavier candidate writes exactly one line — `Considered-and-rejected: <n> heavier candidate(s) — <one clause>` — to the derivation artifact at ask time; the investigation-record composition carries that line into the investigation-record bucket, never the issue body, and when record publication is disabled by configuration the line is dropped with the record and that outcome is named in the run's final reported outcome.

Visual-specification guidance (user-visible UI changes only — skipped entirely otherwise). When your scope assessment above infers that the issue changes what the user sees, load `references/fallback-visual-specification.md` per `references/degradation-routing.md` and follow it as part of this clarification. An obviously non-UI issue never loads it, so a text-only story carries none of that guidance.

How to ask:

- **Gate — confirm *this run's* derivation artifact exists before the first clarification round.** Before the first clarification question — or, if the story is complete enough that you will ask none, before drafting in Step 3 (the gate must fire on every run, not only ones that clarify — the Step 3 drafting precondition is its unconditional backstop for the zero-question path) — verify `.prflow/tmp/create-issue/<slug>/issue-derivation-<slug>.md` is present and holds the derivation you produced for the current story. Presence alone is not enough: the slug is deterministic from the topic, so a prior run on the same topic can leave a stale file at this exact path. If the file is missing, or you cannot confirm its content is this run's derivation, the independent-derivation pass was skipped — stop, run the pass and write the artifact now, and only then ask anything. Do not begin clarification without it; surface its absence rather than silently continuing. On a filesystem that refuses the write, follow `references/fallback-read-only-sandbox.md`, loaded per `references/degradation-routing.md`. The same gate also confirms this run's `## Evidence bundle` is present and axis-complete (an entry for every axis on the effective list, recomputed here per the *Bundle-coverage gate* above) — a missing section or a missing axis entry means the evidence-bundle sub-pass was skipped, and the same stop-and-run remedy applies.
- Ask via the runner's user-question tool — `AskUserQuestion` (Claude Code, the canonical example), or the equivalent your runner exposes (e.g. `ask_user` on GitHub Copilot CLI). Source the questions from the independent-derivation delta plus conflicts (the pass above). Batching is conditional on the tool: where it supports multi-question batches (as `AskUserQuestion` does), batch 2–4 related questions per call rather than one long interrogation; where it is one-question-per-call, ask them sequentially (as on `ask_user`) — the total budget below is the same either way.
- Every question has three parts, in this order: background, then the question, then the options — all in plain language. The background says what the answer decides and what in the system it touches, written for a reader who has not seen this codebase and reads English as a second language. Choose where it goes by its length: one or two sentences open the `question` text itself; anything longer, or one background covering a whole batch, goes in your chat message immediately before the tool call — the question tool has no background field and truncates long text. Add a short concrete example wherever one makes a choice clearer than a description does — a sample line of output, a filename, a before-and-after pair — in the background or inside an option. The question itself is one sentence. The options follow (next bullet). Use everyday words, spell out any term private to this repository the first time it appears, and prefer a longer plain sentence to a shorter one only a reader who already knows this code could act on. A user who cannot tell what a question is asking picks the wrong fork, and that wrong fork ships as an acceptance criterion.
- For each question, offer concrete multiple-choice options, each a decision — never a deferral ("let the implementer choose", "decide later"): an undecided item is asked here or filed under Blocked, never handed to the implementing run. When one choice is clearly best, list it first, marked `(Recommended)` with a one-line why; a free-text-only question tool gets the same options in the question text.
- **Simplest-reliable selection (one rule, three scopes).** The simplest mechanism that reliably solves the stated problem is a **mandatory menu entry** at the implementation-approach question — where a single candidate may fill the simplest and the strongest role at once, and the question rationale states that coincidence when it does; a **mandatory answer entry** in every other clarification question; and the **selection rule** for the decisions this skill already sanctions a run to settle without asking — an answer already known from the user story or the Step 1 findings, and a choice genuinely inconsequential to scope. It settles no fork the clarification rules and the Blocked rule reserve to the user: an open decision still goes to the user, and on disengagement to `## 🚫 Blocked`, exactly as elsewhere. Before finalizing the options, ask *KISS* — the smallest, most creative change that solves the stated problem (one simple prompt, one existing mechanism reused, one default flipped) — and include it.
- On the implementation-approach fork question specifically, the `(Recommended)` one-line why cites at least one bundle entry by axis name, and the cited entry's named check must have been executed — a `Verified:` row, or a `N/A — checked <how>` row whose named check was run, qualifies, but a row batch-marked by the scope-inference shortcut does not (an `unestablished` entry cannot ground a recommendation). That question's rationale additionally discloses by name every effective-list axis that is `unestablished` at ask time, plus the count of axes batch-marked N/A by scope inference; the question is still asked (this skill is best-effort and never blocks issue creation), with the gap disclosed rather than hidden. `(Recommended)` markings on other clarification questions (behavior forks, formats, channels) keep the existing one-line-why rule and gain no citation or disclosure obligation. No-citation-grade arm: when no citation-grade entry exists at ask time (every entry inference-marked or unestablished), the drafter executes exactly one targeted probe to upgrade the most decision-relevant axis before asking; if that probe too is unavailable or denied, the question is asked with no `(Recommended)` marking and its rationale states that no citation-grade evidence exists — the marking is withheld visibly for evidence reasons, never silently. The marked recommendation goes to the **weakest mechanism class whose single-failure consequence — stated in the rationale — the problem statement tolerates**, and that rationale **prices the strongest passed-over candidate in one clause**. When the problem statement does not establish that it tolerates a class's single-failure consequence, that consequence is not treated as tolerated and that class is not the recommendation — step up to the next stronger class. A consumer prompt extension that states its own recommendation policy overrides this default recommendation. The user's recorded mechanism election is a resolved decision: a later steelman pass and audit pass adjudicate against it rather than reopening it toward a stronger class, except on a verified must-revise defect (correctness, safety, implementability).
- After each round of answers, re-check the Definition of Ready — including that the derivation artifact still exists and still holds this run's derivation (or, in a read-only sandbox where the write failed, re-post the visible inline-in-chat stand-in in this turn), **and re-check bundle currency per the *Bundle currency* rule above** (update or re-mark superseded any axis entry the round's answers changed or contradicted, and any axis a newly-added mechanism class touches). If the file has vanished — or, on a read-only filesystem, you have not re-posted the inline derivation this turn — treat it exactly as the gate above: stop and re-write the file (or re-post the inline derivation) before asking the next batch. If gaps remain, ask another batch. Keep going until the list is fully satisfied — do not draft with items still open.
- Cap clarification at a runner-neutral total-clarifying-question budget of ~18 questions total — a *count of answered questions*, not a count of rounds or of questions merely asked, so a one-question-per-call runner gets the same budget as a batching one. A silent non-response is not an answer: it never counts toward the budget and never trips "treat the remainder as disengagement" — re-ask it instead (see the silent-non-response rule below, which defines what counts as silence). If the budget is exhausted by explicit answers and facts are still missing, treat the remainder as disengagement (below).

Push back once before accepting total disengagement. If the user disengages while the issue is still *unbuildable* — no decided scope, or the single core behavior fork is still open (the ticket would be almost entirely Blocked) — do not silently produce a hollow issue. Say so plainly, once: e.g. *"As-is this issue won't be buildable — every decision is still open. Can you answer just two things: (1) is this one feature or several, and (2) <the single most defining behavior fork>? Otherwise I'll file it with everything flagged as blocked."* Ask those via the runner's user-question tool (one batch where it batches, sequentially where it is one-question-per-call). If the user answers, continue clarifying; if they give an explicit disengagement signal again (silence is not one — see the silent-non-response rule below), proceed below. This push-back happens at most once — do not nag. It does not apply when only peripheral forks remain open (e.g. link expiry) — Block those without comment.

A silent non-response is not disengagement — never proceed on silence. A question-tool timeout, a `No response after 60s` return, or the user simply stepping away is not a disengagement signal. When a question has been asked and no answer has come back, pause and re-ask that question in your final chat message; do not proceed, draft the issue, guess a default, or route the item to the Blocked section on that basis. Only an explicit reply from the user — "just create it", "you decide", or "I don't know" — or an exhausted clarification budget of explicit answers (the budget rule above), engages the disengagement / draft-from-decided / Blocked path below; a silent non-response never does.

When the user disengages — gives one of the explicit signals "just create it", "I don't know", or "you decide" to a Definition-of-Ready question (these three explicit replies are the *only* user-reply disengagement triggers — the sole non-reply entry is an exhausted budget of explicit answers, above; silence is never a trigger — see the rule directly above):

- Stop asking. Draft the issue from what *is* decided.
- Every still-unresolved Definition-of-Ready item goes into the issue's `## 🚫 Blocked — resolve before implementation` section, phrased as a direct question with one line on why it blocks work (see template).
- Do not invent a default and bury it in the body, and do not rephrase the open decision as a resolved-looking one elsewhere — the canonical no-options rule (`references/issue-template.md`) governs this. The Blocked section is the *only* place an unresolved decision may appear.
- "You decide" is not permission to guess silently — it is an unresolved item that belongs in Blocked, unless the choice is genuinely inconsequential to scope (e.g. a variable name).
