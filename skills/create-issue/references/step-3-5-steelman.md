### Step 3.5: Steelman the draft against the code (mandatory, before the user sees it)

*"Steelman this. Did we miss anything?"* — run that challenge against your own draft every run, immediately after the no-options gate passes and before Step 4 presents anything.

This is a **code-grounded verification loop, not a re-read**. Every check below runs against the actual repository content, via tool calls made now — targeted `Read`s and `Grep`s, never a full re-exploration.

1. Re-read the rendered draft end-to-end as an adversarial reviewer whose job is to find what is wrong or missing, not to admire what is right.
2. Verify each load-bearing claim, file reference, and acceptance criterion against the code. Every named file/path exists as named (a `Glob`/`ls` per reference); every "the code currently does X" claim is confirmed by reading the code that does X; every AC is checked to be assertable against the code surface it names. `Relevant Classes/Files` references cite the symbol or section, not a `file:line` anchor. Match the verification method to the claim class, by the clauses below.

   **Third-party behavior.** The **relied-on-third-party-behavior** class: every behavior of an external platform, API, or service the draft **relies on** — load-bearing for the Desired Behavior, an acceptance criterion, **or** the Implementation Notes Approach, not only an AC's mechanism (webhook / event delivery, trigger syntax, token scopes, endpoint behavior, response shapes, rate limits) — is verified against the vendor's **official documentation via `WebFetch`**; when official docs are unreachable, via **`WebSearch`**; when search is unavailable or fails, by **asking the user to provide the documentation** (not memory), and the verified fact + source URL is recorded in the draft's `Technical Context`. An empty or inconclusive result is **unverified, never confirmed** — rewrite such a claim as an explicitly flagged assumption (the template's `— assumption, confirm before implementing` form). Terminal arm, two ways (mirroring the template): a relied-on behavior with **no** documentation and **no** in-repo example proving it becomes a `## 🚫 Blocked` vendor-behavior question; one a working in-repo example proves is written as a flagged `— assumption, confirm before implementing` line citing that example. An **incidental** third-party mention (not load-bearing) stays light and triggers no verification.

   Mechanical claims. A mechanical claim is verified-or-obligation, never a bare prediction: a Testing Strategy assertion of the form "running X reports Y" / "this must fail RED reporting Y" is written either as verified output you actually ran while drafting and are citing, or as an obligation on the implementer ("the pin must cover X") — never a prediction of a specific result you did not execute.

   Value-comparison ACs are checked for observed-output grounding (mirroring the template's Acceptance Criteria rule): an AC or Testing-Strategy assertion comparing a produced value against a literal must state the comparison in the producing surface's observed-output terms, grounded by a probe that exercises the distinguishing boundary fixture (for a type-sensitive comparison, the type-boundary fixture — a JSON string `"true"` vs. a boolean `true`) or by a named implementer obligation stating the decided semantics or the exact fixture-and-observed-output command. Adjective-only ("explicit/exactly X") or probe-silent-on-the-axis comparison language is flagged non-conforming and rewritten to observed-output terms — or, when the axis is a specification *choice* rather than a probeable fact, routed to Step 2's user-question machinery, not an obligation.

   Universal-quantifier sweep (mandatory, same carve-out as the template's Acceptance Criteria universal-claim rule): scan every universal quantifier the assembled draft asserts about the system under change — "never", "always", "each", "every", "all", "cannot" — outside `## 🚫 Blocked`, and confirm each is grounded one of the three decided ways (pinned per-arm/per-element, with an accepted-loss/suppression claim pinned by a fixture in which the suppressed input is present; scoped to the mechanism's supported form; or removed). The only exemptions are mandated-verbatim template boilerplate and rule text the change ships as artifact content; an AC or Desired-Behavior sentence is never exempt however imperative its phrasing. A detector/guard coverage claim additionally requires a planted-defect positive-control obligation on the implementer. Rewrite or ground any ungrounded quantifier now, before the user sees the draft.

   Request-origin sweep (mandatory). A criterion has exactly two admissible origins — the request named the guarantee, or a failure the change introduces requires it. Scan every acceptance criterion and every named Testing-Strategy assertion the assembled draft asserts, and grade each against that pair. The *request* is the words the filer actually supplied — Step 1's captured request and any Step 2 clarifications recorded in this run's derivation artifact — never the drafted issue restating them back. When this run cannot establish the request from that artifact (it is unreadable, absent, or was never written), record that unestablished-request state in the summary rather than silently passing every criterion — an unreadable request is unknown, not "the request named it"; still grade each criterion and named assertion against the second origin and report every one that does not rest on a change-introduced failure. Report each criterion and named assertion whose asserted guarantee the request did not name and which no failure the change introduces requires — the plausible, individually defensible guarantee nobody asked for (a startup-time validation, a byte-identical-output promise, a "no such module exists" negative, a proof-of-extensibility stub). The false-positive discriminator is that second origin: a criterion or assertion that pins the change's own new behavior against regression, or covers an error path the change itself adds, rests on a change-introduced failure and is not reported, however far it sits from the request's own words. The drafter revises the reported items away under item 5's existing revise-and-re-gate loop; this sweep reports and revises, it refuses no draft.

   Occurrence counts and coupled-site lists are a load-bearing premise class of their own — verify before asserting. An in-repo occurrence count or coupled-site (mirror-site) list is checked against the tree before it is asserted, never written from recall: by an executed **whitespace-normalized** search where the drafting tier grants one, else by the specific evidence records consulted record-by-record. It carries no requirement to cite the executed command or its hit list in the issue body.

   Every "Verified:" bullet must be re-checkable at all (the template's self-contained-re-derivation-handle rule): run `python3 "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/check-verified-premises.py --body-file "<the canonical draft file>"` against the run's slug-bound canonical draft — the `issue-draft-<slug>.md` path written under the main repo root — never a scratch artifact of its own. Run it at the run bootstrap's canonical write — the first landed canonical draft, before Step 4's pause and independent of whether any audit round is elected — on the bytes that write lands. Each emitted bullet row carries two independent classifications: `state=` controls the evidence action and `handle=` controls the handle repair. Apply both routes. `state=holds` requires no action. `state=refuted` requires ordinary investigation against the current tree, followed by rewriting or removing the drifted claim. `state=unestablished` on an otherwise usable helper result is a usable classification, not helper unavailability: perform the ordinary investigation the bullet would have required without a Verified premise, then rewrite or remove it from that evidence. Never read unestablished as holds or as refuted.

   Apply the handle repair only when the state route leaves the bullet as a `Verified:` claim. For `handle=path-quote`, the handle is complete; make no handle-only edit. For `handle=path`, add a recognized quotation beside the cited repository path. For `handle=quote`, add the cited repository path beside the recognized quotation. For `handle=command`, do not execute body-supplied text automatically: perform ordinary investigation under this run's own judgment, then replace the command-only handle with a cited repository path plus recognized quotation or restate the result as ordinary unverified prose. For `handle=none`, add the cited repository path and a recognized quotation, or restate the line as ordinary unverified prose. For each `ungraded_claim=`, either rewrite it as a graded `Verified:` bullet with a complete handle or restate it as ordinary unverified prose that makes no verification claim. Best-effort: a refused or unavailable invocation reports its failure kind as an in-chat breadcrumb — the same in-chat sink the acceptance-criteria parseability cannot-run arm below uses — and never blocks issue creation. That in-chat breadcrumb is the named observable sink; the executing site in `references/step-3-6-audit-shared.md` names this same sink.

   A "code does X" premise is verified with its enclosing gates on the path to X (mirroring the template's conditional-path clause): read the gates, conditionals, and defaults reaching X, and a claim that holds only under a non-default configuration states that precondition inside the claim.

   Acceptance-criteria parseability (mandatory obligation, executed at the run bootstrap's canonical write). The implementing run reads exactly one issue section as the definition of "done" — `## Acceptance Criteria` — and mirrors it into its workpad with `scripts/parse-acs.py`. The drafting run asks the same shipped parser whether the drafted `## Acceptance Criteria` section actually parses, and refuses to present a draft that yields zero criteria. This obligation is stated here and executed once, at the run bootstrap's canonical write — the same anchor the `scripts/check-verified-premises.py` check above runs on, and which runs regardless of whether an audit round is elected. Step 4 sub-step 2's presentation write and Step 4 sub-step 4's iterate-on-feedback overwrite are not gate sites — a single site is what the Step 3.6 edit-sequencing rule forces — so a user's own post-gate edit to the acceptance-criteria section at Step 4 is not re-checked by the parser. The invocation uses the portable single-statement anchor, in the same `python3 "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/parse-acs.py` form this skill's other bundled-Python calls use, with `--body-file <the canonical draft file>` and `--format json`.

   Consume both typed fields in the JSON result: the `acceptance_criteria` array and the boolean `acceptance_criteria_unreadable`. The latter is the parser's machine-readable distinction between a canonical section whose visible criteria use an unreadable item shape and a genuinely empty result. The exit code, stderr breadcrumb, and `--format md` sentinel remain unusable as content operands. A missing or wrong-typed JSON field makes stdout unparseable and takes the cannot-run arm below.

   When `acceptance_criteria_unreadable` is `true`, take the independently bounded unreadable-shape path. Keep an `unreadable repairs used` count for this gate, separate from the genuinely-empty rewrite count. When fewer than three unreadable repairs have been used, preserve each visible criterion's substance, rewrite it under the canonical `## Acceptance Criteria` heading as the parser's documented checkbox item shape `- [ ] <criterion>`, increment only the unreadable-repair count, and re-run the JSON gate. Backticks, bold paragraphs, numbered rows, and prose are not substitutes for that checkbox shape. A `true` result never increments or resets the genuinely-empty counter. If the re-run after the third unreadable repair still reports `acceptance_criteria_unreadable=true`, stop repairing and carry `Acceptance Criteria rewrite exhausted (unreadable item shape)` to Step 4; carry no established count. Step 4 owns the disclosure, unavailable-item-shape marker, and explicit file-anyway election.

   When `acceptance_criteria_unreadable` is `false` and `acceptance_criteria` is non-empty, the gate passes. When it is `false` and the array is empty, take the genuinely-empty path: do not dispatch or present yet; restore the missing criteria as canonical `- [ ] <criterion>` rows and re-run the gate on the rewritten bytes. Count only consecutive re-runs that again return `acceptance_criteria_unreadable=false` with an empty array. After the third such rewrite, stop rewriting and carry the exhausted state to Step 4, which must disclose that implementing runs will not read the criteria, render the count unavailable, and obtain the user's explicit file-anyway election before the ordinary approval gate. This is a bounded best-effort filing path, never permission to read the third empty result as clean.

   When the parser cannot run — an unreadable helper, a non-zero exit, a denied invocation, or unparseable stdout — emit an in-chat breadcrumb naming the failure kind and proceed to presentation. It never blocks issue creation.

   The `acceptance_criteria` array length from this gate's last invocation whose array was non-empty is the criterion count Step 4's audit summary line reports (`references/step-4-present-create.md`, which owns the rendering and every unavailable arm). It is read from this one already-mandated invocation — the run performs no second parse for it — and it is reported, never enforced: no count refuses a draft, changes a verdict, or gates anything. A run that carries no established array — the parser could not run, the bounded genuinely-empty rewrite loop exhausted, an unreadable shape could not be repaired, or the run never reached this gate site — carries no count forward, and Step 4 renders its matching unavailable token rather than a number, a zero, or a hand count.
3. Hunt for what the draft omits, specifically:

   Produce the projection disposition first. Desired Behavior is authoritative intent; Acceptance Criteria are its exhaustive, merge-gated projection. Account for every independently verifiable post-change obligation as `represented` (one AC or a jointly sufficient AC set preserves its subject, scope, outcome, and strength), `unmatched`, or `non-obligation` (explanation, motivation, estimate, or current-behavior description). Record the explicit `projection disposition: represented` only when the unmatched set is empty. When it is non-empty, record `projection disposition: unmatched`, revise the draft by adding or correcting the author-owned ACs, and re-audit before the draft is eligible for creation; never treat the generic hunt bullet alone as evidence that projection was checked. Weak topic overlap is unmatched, while multiple ACs may jointly represent one obligation.

   - Missed acceptance criteria — behavior the Desired Behavior implies but no AC pins.
   - Missed edge cases — error paths, empty/absent inputs, concurrent or repeated events.
   - Wrong assumptions — claims step 2 could not confirm.
   - Unstated scope — surfaces the change touches that the draft never mentions; grep the identifiers the draft names for consumers it missed.
   - A missing input-is-data guard — a new LLM/semantic-judgment surface over third-party text without the guard-AC-plus-hostile-case pair.
   - An undeclared enumerated AC list — an enumerated test/case/example list inside an AC that declares neither a floor marker nor a closed-set exhaustiveness statement.
   - A smuggled fork in the gate-exempt `Relevant files` block — a behavior decision, a library choice, or a mechanism fork written inside the Implementation Notes `Relevant files` block. The block admits file and function references only: rewrite it as a decision resolved with the user or, on disengagement, a `## 🚫 Blocked` entry.
   - An unreconciled multi-state contract — when the draft states a multi-state contract (a set of outcome tokens, error/exit codes, a status enum, or a state machine, where each state has one or more trigger causes) in more than one form, e.g. a summary or table form *plus* the detailed per-state acceptance criteria, verify the forms agree: no summary or table form lists fewer causes for a state than the detailed per-state ACs collectively specify. It is scoped only to drafts that actually state such a contract — a draft that states none draws no new hunt, question, or revision here. A disagreement found here is fixed by revising the draft (step 5's revise-and-re-gate loop), not surfaced to the user.

   Then run these three mandatory checks on the `## Acceptance Criteria` section:

   - Criterion shape (mirroring the template's Acceptance Criteria rules). Every criterion states what is true after the change rather than what the diff contains — rewrite a diff-shaped criterion into its post-change outcome, except where its subject is a surface the change must not touch, which is a legitimate post-change fact about the diff's boundary and stays as written. The section's supporting apparatus sits where the template's consequence test puts it: a statement belongs in the grounding block only if deleting it changes no criterion's truth value, so framing read by the drafter and the audit step is stated once in that block while anything narrowing, bounding, quantifying, defining a term used by, or naming a verification route for a criterion stays inside that criterion however much it repeats (the measurement instrument, floor marker, closed-set exhaustiveness statement, obligation command, and depended-on term definition are that floor's commonest members, not its closed set). Confirm the block opens the section. Check the block against Step 3's unresolved-decision gate like any other prose — it is inside that gate's scan and carries no choice, hedge, or deferral language.
   - AC mutual consistency. No acceptance criterion forbids a surface — a path, a file class, a tier — that another AC's discharge must touch; a pair that conflicts is an unresolved scope fork, not two independent criteria.
   - Trust-boundary closure (mirroring the template's Acceptance Criteria rule). When an AC establishes a trust or integrity boundary over executable artifacts (scripts, hooks, anything sourced, exec'd, or imported), confirm the protected set is defined over the transitive source/exec/import closure of its entry points, or that the residual unprotected surface is stated explicitly.
4. Sweep the draft's own unstated mechanism dependencies (mandatory). Beyond the *stated* premises checked in step 2, enumerate the in-repo behaviors the draft's designed mechanism relies on but never asserts as a claim — a helper's exit code, a resolver's output shape, a gate's semantics, and, just as much, an existence-shaped reliance the enumeration must not skip: a renderer mode, a persisted state field, a subcommand or flag, a config key, or an emitted field the mechanism names. A capability the drafter treats as ordinary machinery is enumerated as a dependency too — name it here rather than assume it.

   Determine existence, then route. For each enumerated dependency, first determine whether the depended-on capability is in the tree at drafting time — by the targeted `Read`/`Grep` capability this step's preamble already mandates, applied to *is this here* rather than *what does this do* — and pick the discharge route from that determination. The determination's domain is the tree the drafter is authoring against; a capability the plugin itself provides is outside that domain when the plugin tree is absent, because a thin consumer install leaves the vendored tree untracked and materializes it at runtime. Resolve whether a plugin tree is reachable at all before reading the search — the repository root itself when you are authoring inside the plugin's own repository, else the vendored root (`.prflow/vendor/prflow/`, or its superseded `.devflow/vendor/devflow/` spelling in a consumer that has not run `/prflow:init`): a capability whose producing surface would live in the plugin tree routes to that surface when a plugin tree resolves, and to not established when none does, whatever the hit count. The determination has exactly three outcomes, complete by construction:

   - present — found in the producing surface that owns the capability and read there, not merely matched somewhere in the tree (a mention in a changelog, a doc page, a comment, or a fixture name is not a producing surface and does not promote). Discharged by a cited probe (a "Verified:" bullet citing observed output) or, where that probe is denied or unavailable on the drafting tier, by an implementer-obligation AC naming the behavior to establish — reading a capability's existence in its producing surface never by itself discharges a *behavioral* dependency on it. A capability reachable only under a non-default configuration reads as present and routes to item 2's existing conditional-path clause — no second treatment.
   - absent — the drafter named the producing surface that would own the capability (renderer, state owner, config schema, subcommand dispatch table) and, by reading it, established it is not there. **Promotion to absent requires that named-and-read producing surface *and* an executed search grounding it** — a zero-hit search alone never promotes, and a denied or unavailable search records not established even when the producing surface was read. That search is an executed **whitespace-normalized** search, here required to be repo-wide — a directory-scoped search does not establish an absence — and no citation of the command or its hit list is required in the issue body. Disposition, which the drafter states: inside this issue's scope, an implementer-obligation AC naming adding the capability as new work (stating the build, not implying a confirmation); outside scope, the mechanism is re-derived under item 5's existing revise-and-re-gate loop and the scope question routes through item 5's existing decision-fork route, landing in `## 🚫 Blocked` on disengagement — and a scope question item 5's fork predicate does not admit is still put to the user through that same Step 2 user-question machinery, reaching `## 🚫 Blocked` only on disengagement and phrased there as a direct question with its one-line reason. An absent determination never expands the issue's scope without that expansion being written down.
   - not established — any reading that is neither of the above (a zero-hit search with no producing surface read; a search denied or unsearchable at drafting time; a plugin-provided capability with no plugin tree present; ambiguous evidence). Recorded as itself — why it could not be made — not as a "Verified:" claim, and as neither of the other two. Discharged by an implementer-obligation AC whose first named unit of work is establishing whether the capability exists, naming a termination arm for every way that unit of work can end: proceed on the remaining criteria when it proves present; build it under this issue when it proves absent and in this issue's scope; file the build as deferred work through the existing deferred-follow-up path when it proves absent and out of this issue's scope; and, when the run cannot establish existence either, record the run Blocked on the criteria that depend on it rather than proceeding as though it were present. Write those arms as the obligation's own procedure, never as competing options for the drafter to resolve.

   The obligation-AC dispositions above are governed by the obligation-arm execution-tier constraint stated in `references/quality-group-contracts.md`, which states its own reach over them — pointed at, not restated here. That group is conditionally loaded, so when an obligation arm fires and it is not already loaded, load it per the *Reference routing* rules before minting the obligation AC. A draft whose mechanism enumerates no dependencies performs no existence determination.

   Extend the sweep to stated-but-unbound inputs (mandatory): a mechanism input the draft describes by *role* — "the value the caller already tracks", "the branch diff it already has" — with no named referent is bound to a named variable, artifact, or file with a cited code reference proving it exists at the consuming site; when drafting cannot establish that binding, the draft carries an implementer-obligation AC naming the binding as work, never an unbound role description that expands to nothing at implement time.
5. Revise the draft yourself and re-run the Step 3 no-options gate on the revision. Then run **Revision-delta verification** (the shared procedure below). Fixing a false claim or adding a missed AC is your work, done now — do not present the flaws to the user as questions attached to an unrevised draft. If — and only if — the steelman surfaces a genuinely new unresolved decision fork (competing behaviors only the user can choose between), route it through the existing Step 2 machinery: ask via the runner's user-question tool, and on disengagement it lands in `## 🚫 Blocked` — no new decision-handling path.
6. Self-check the draft against the Step 3.6 audit dimensions. Before summarizing, run the same dimension checklist the auditor will receive — the Step 3.6 generic dimension checklist plus any consumer `## Audit dimensions` section, assembled by running `render-audit-prompt.py checklist` orchestrator-side and consuming its stdout as a tool result (applying the positional two-marker delivery check — `render-status:` first line, `render-end:` last line — and the fallback-to-Read-the-template-file rung when the markers are missing or out of position). Read the delivered `render-status:` line, not a loader exit status — this site re-runs no loader. A rendered `unestablished` status is surfaced per the Step 2 loader-failure arm's discipline — never laundered into the designed absent-heading no-op. A rendered `absent` status is instead the designed no-op: report that no consumer `## Audit dimensions` section was selected, and then proceed treating the selection as no consumer section for that hook: a **report-then-proceed** step, never a stall, a user question, or a degraded-arm claim. Judge the assembled draft against each dimension, fix what the check finds, and re-run the Step 3 no-options gate on any revision. Then run **Revision-delta verification**.
7. Log the outcome either way. Report a one-line summary in your next message — claims/file-refs/ACs checked (count), what was revised, or "steelman: N claims verified against the code, no revisions needed". Every sweep below reports its own result in that summary, and wherever a zero arm is named below the summary states that falsifiable claim rather than a bare zero count:

   - the Desired-Behavior projection disposition (represented obligations, non-obligations, unmatched obligations, and the exact unmatched statements before any revision; the final disposition is eligible only at zero unmatched);
   - the value-comparison type-semantics check (step 2);
   - the unstated-mechanism-dependency hunt (step 4) — its zero arm is the claim "the mechanism invokes no in-repo helpers, resolvers, or gates", checkable against the draft's Implementation Notes;
   - the existence determinations that sweep made, reporting per enumerated dependency the outcome reached (present / absent / not established), and on a run that enumerated none the claim that the sweep enumerated no dependency needing an existence determination;
   - the universal-quantifier sweep — zero arm: "the draft carries no ungrounded universal quantifier";
   - the request-origin sweep — the criteria and named assertions it flagged, or, when the request could not be established from the derivation artifact, the explicit `request unestablished` outcome (never the zero-arm claim, which asserts a tracing the unread request cannot support); zero arm: "every acceptance criterion and named Testing-Strategy assertion traces to the request or to a failure the change introduces";
   - the Step 3.6 dimension self-check (step 6) — its finding and revision counts, zero arm: "no dimension-checklist finding".

   The summary additionally reports the evidence bundle's coverage — `axes evidenced, axes marked N/A, axes unestablished` — as counts the reader can check against the artifact (and names the effective list floor-only-degraded when the loader-failure arm fired).
8. Persist that same summary to the derivation artifact before the step returns. Append it — in addition to reporting it in chat — as a numbered `### pass <n>` entry to a `## Steelman record` section of this run's derivation artifact `.prflow/tmp/issue-derivation-<slug>.md` (the file Step 2 wrote and owns), creating the section on the first pass and appending to it thereafter. This record is what the Step 3.6 entry confirmation (item 9) reads to establish that this step ran.
   Alongside that record, overwrite `.prflow/tmp/steelman-projection-<slug>.json` with this pass's structured state: `{"pass":<n>,"projection_disposition":"represented|unmatched","unmatched_desired_behavior":["<exact unmatched statement>", ...]}`. The unmatched field is always an array, including `[]`; never synthesize an AC or encode `none` as a string.
   - **Leave the artifact's existing `## Evidence bundle` section untouched**.
   - The record is append-only, never a rewrite. `<n>` counts this run's completed Step 3.5 passes: the first writes `### pass 1`, each later pass a fresh incrementing number, and an earlier pass's entry stays in the artifact verbatim after a later pass has appended its own.
   - The entry carries exactly the field set of item 7's summary line, one line per field: the counts of claims, file references and acceptance criteria checked; what was revised; the Desired-Behavior projection counts, exact pre-revision unmatched statements, and final disposition; each of the named sweeps' result recorded exactly as its item-7 entry states (the item-7 list is the authority for that set) — its falsifiable zero-arm claim wherever the sweep found nothing, or the per-outcome result its item-7 entry carries instead, such as the request-origin sweep's `request unestablished` (never the zero-arm claim in that state); the evidence bundle's `axes evidenced, axes marked N/A, axes unestablished` coverage counts; and, when the loader-failure arm fired, the marker naming the effective list floor-only-degraded.
   - It runs on all three arms, complete by construction: the ordinary arm; the arm where this Step 3.5 reference itself failed to load and the step ran reduced (the record obligation is load-independent of the reference that failed — `references/degradation-routing.md`'s Step 3.5 row states it for that arm); and the arm where a bundled helper this step invokes did not run to a result (the reduced summary still names what did run, and is still recorded).
   - On a read-only filesystem the record degrades to a visible inline-in-chat block posted in the current turn with the on-disk copy distrusted, per `skills/create-issue/references/fallback-read-only-sandbox.md`'s per-artifact Steelman-record arm.
9. The Step 3.6 entry-confirmation contract (the reader of item 8's record; stated here where there is headroom, invoked from `references/step-3-6-audit.md`'s Step 3.6 entry). At Step 3.6 entry, before that step dispatches its audit subagent, confirm the Step 3.5 record is present and this run's, then route:
   - Report the outcome as an in-chat breadcrumb before routing. Emit a one-line in-chat breadcrumb distinguishing the three outcomes — confirmed (a fresh this-run `### pass <n>` entry), missing (no record), or stale (a record from a prior run on the same deterministic slug) — before acting on the route below. A missing or stale outcome still blocks only the audit dispatch, never issue creation.
   - Read a bounded tail of `.prflow/tmp/issue-derivation-<slug>.md`, not the whole file — a long run's artifact grows past the runner's read cap, and a whole-file read would return the head and drop the newest `### pass <n>` entry the confirmation must see.
   - Freshness, not presence — the latest `### pass <n>` entry must be *this run's*, in the same freshness sense `references/step-2-clarify.md` defines for the derivation artifact (a prior run on the same deterministic slug can leave a stale `## Steelman record`). A missing record is treated as a skipped Step 3.5.
   - On failure, stop and run Step 3.5, then proceed once both the record and structured projection state are written. A read-only refusal uses the bounded inline-audit fallback, but proceeds only after that audit establishes `represented` with zero unmatched statements and posts the structured state in the current turn.
   - The remedy runs at most once per Step 3.6 entry. If persistence fails again, report it and proceed to audit dispatch only when the inline audit established that clean state. Missing, stale, wrong-typed, inconsistent, or unmatched projection state never becomes filing-eligible.
   - Consume, do not infer. Confirm the JSON `pass` matches the latest Steelman pass, then run `"${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../scripts/run-jq.sh -e -f "${CLAUDE_SKILL_DIR:-<absolute skill base directory this runner reports in context>}"/../../lib/projection-gate.jq ".prflow/tmp/steelman-projection-<slug>.json"`. Only exit zero establishes eligibility; a non-zero result returns through the one-remedy revise/re-audit path and never directly to Step 4.

Only a draft that has survived this step — revised and re-gated if anything was found — proceeds to Step 3.6.
