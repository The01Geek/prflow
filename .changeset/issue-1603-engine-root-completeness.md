- **The review engine root must be established complete before it is executed on the file-read path.** The fix loop reaches `skills/review/SKILL.md` by an ordinary file read on three paths, and the acceptance predicate was that the read returned *something* carrying no truncation notice — but the engine root has no boundary-marker pair, and an over-cap read of a marker-less file returns a fragment with no notice at all, so a half-delivered merge gate was indistinguishable from a whole one and executed with no stop label. The canonical statement in `skills/review-and-fix/references/loop-control.md` Step 1 now establishes completeness by a **positive end-of-file confirmation** taken from the reader itself: after a read that appears whole, one further bounded read starting past the last line already held, whose reply must be **attributable to the position requested**. A reply returning nothing there — the reader's own report that the file is shorter than the position asked for, or nothing beyond a trailing empty line, among them — confirms the end of the file and **establishes** completeness, the ordinary outcome on a whole body; a reader that ignores or clamps the start position and re-returns the head, or answers a position later than asked, proves nothing about the end of the file. Further non-empty content means the earlier read was truncated, so the caller pages forward and re-confirms, each confirming read starting strictly past the one before it and a finite file reporting its end, so the re-confirmation terminates. The paged arm terminates on that same confirmation rather than on "no continuation offered" or "a page added nothing new", neither of which distinguishes the file's end from a reader that stopped short of it. No byte or line count from an external tool is used, since none is guaranteed installed.
- **The confirming read's own failure modes are routed rather than left open.** The shapes that leave completeness *unestablished* name only genuine failures: a runner whose file-read tool takes no start position, so the confirmation cannot be issued at all; a confirming read refused or erroring otherwise than by that end-of-file report; a reply whose content cannot be attributed to the position requested; a confirming read that does not advance past the one before it; and a gap in a paged read's page sequence. Each takes the same terminal — so an intact engine on a non-paging reader stops, which is the specified behaviour: a run that cannot establish completeness must not act on the body.
- **Selection splits the resolution question from the delivery question, so the fail-closed default sits where it is right.** A path the reader reports as non-existent is *absent* and advances the list; a reader message that cannot be classified *as to whether the path resolved* leaves **resolution** unestablished — that candidate is not selected and the scan advances too, naming in the run's own report which candidate it advanced past, since the earlier candidates are expected to be absent on a consumer checkout and hard-stopping there would strand a run whose vendored engine is one candidate later. A path that positively **resolved** is the selected candidate whatever the read returned — any message that affirms the path exists, a permission failure among them, resolves it, so the self-review note is scoped to match: the repo-root candidate resolves the branch's own engine unless its own resolution is left unestablished, which advances the scan to a vendored copy. From there a permission failure, a transient reader error, an oversize error returning no content, and an empty or whitespace-only body are a present-but-undelivered engine that leaves **completeness** unestablished and can no longer fall through to a different engine copy. Step 4 routes the failures apart: no candidate selected keeps the existing absent-engine fatal naming `/prflow:init`, while an unestablished body stops at the terminal `engine-root: incomplete`, which names the file, treats the body as unusable and repairs nothing.
- **That terminal is now scoped by engine entry, and its record has one writer.** On the Step 1 entry the loop reports non-convergence, which is never eligible for a caller's soft-proceed arm; the blocked record is written by a caller that maintains a workpad, and standalone `/prflow:review-and-fix` maintains none, so the record no longer lands twice on the implement path or name an absent surface on the standalone one. On the Step 2.6 shadow entry the same stop is a structural failure taking that pass's outcome 3, which the shadow reference already prescribed — the two sites no longer disagree.
- **An `engine-root: incomplete` non-convergence can no longer be soft-proceeded.** `skills/implement/phases/phase-3-fix-loop.md` routes it to that phase's Blocked path on both reachable paths, whose `engine-root: incomplete` substitution states the real cause instead of the path's unresolved-Critical literal — previously the engine never running satisfied "every residual was gradeable as non-Critical" vacuously and stamped the PR review-ready with no review having happened. Because such a loop never reaches Loop Exit it returns no verdict and no marker, so that phase reads a `NO-MARKER` alongside the reported terminal as the Blocked path directly rather than only through the severity-aware exit. `references/error-handling.md` and `references/shadow-review.md` point at the one canonical statement.
